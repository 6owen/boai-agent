# Agent IM 功能调研

检索日期：2026-09-29。范围是“以聊天组织 Agent 工作”的产品能力，不是普通 IM 功能大全。本次阅读官方说明与仓库，没有注册亲测，没有复现竞品的质量、成本或稳定性。下文“支持”均表示官方文档的声明，不能等同于经过本项目验证的效果。外部比较本身不证明 BoAI 缺少对应能力。

## 结论与定位假设

BoAI 已有较完整的多员工协作底座。下一步最值得做的是让用户顺利完成“交材料、让员工办事、检查成果、提出修改、确认采用”，再降低同时管理多个聊天的负担。

本报告暂按“个人用户在本机指挥多个 Agent 完成知识工作”排序。用户尚未确认首批目标人群，因此这不是已经确定的市场定位。如果优先面向开发者，应把代码仓库、差异审阅、隔离工作区与测试结果提前；如果面向多人团队，则需要重新评估真人身份、共享权限和同步的优先级。

成功标准不是功能数量，而是用户能否用真实材料，在可接受的时间和预算内拿到愿意采用的成果。竞争产品提供可借鉴的设计线索，不构成市场需求或付费意愿的证明；后续仍须用真实用户任务验证。

## 建议的功能优先级

P0 表示下一轮完整工作闭环需要优先解决；P1 表示闭环通过后提升日常使用效率。优先级是产品判断，不是开发工期承诺。

| 优先级 | 建议功能 | 最小范围与验收标准 |
| --- | --- | --- |
| P0 | **完整任务稳定交付，权限显示准确** | 用现有评估器复核一个代表性任务从材料到最终成果的全链路；保留原预算，减少无效判断与重复汇报，不能靠扩大额度掩盖失败。显示真实的工具、权限与运行状态。 |
| P0 | **聊天附件与资料处理** | 先支持拖入/粘贴图片、文本型 PDF、TXT/MD，明确哪些成员可读取；扫描 PDF、表格和 Word 分批扩展。能定位原文件/页码，解析失败可见；附件访问沿用已有授权，不因进入群聊就自动向所有员工或外部后端开放。 |
| P0 | **产物预览、修改与采用** | 先预览 Markdown、图片和 PDF；在特定产物上提出修改、生成关联的新版本并保留旧版，支持“采用这版/要求修改”。用户采用与运行完成、工作声明交付分别保存。初版无需完整在线 Office 编辑器。 |
| P0 | **实际能力接通与检查** | 优先做研究场景所需的网页搜索/读取与来源引用，并补齐“选给哪位员工、缺什么依赖、能否执行”的检查流程。复用现有技能与授权入口；首轮只做少量必要连接。能验证真实调用成功，而不是只显示“已安装”。 |
| P1 | **统一待处理收件箱** | 聚合等我补充、等我批准、失败需处理和待验收结果，回到准确消息/工作/产物；以持久记录消重，处理后可靠消失。通知设置沿用现有策略，不把每条 Agent 发言变成系统提醒。 |
| P1 | **消息/文件搜索与未读定位** | 搜正文、文件名，按员工/群/时间筛选，点击定位原消息；增加持久阅读位置和“返回未读”。先采用确定性文本搜索，有质量证据再考虑语义检索。读取消息不等于批准操作或验收交付。 |
| P1 | **可运行团队模板** | 先做“资料研究→写作→核对”一个完整模板，再做内容生产或表格分析；一并检查模型、工具、资料、权限与输出格式。安装技能保持用户显式选择，不自动扩大员工权限。新用户无需编写系统提示词即可完成样例任务。 |
| P1 | **用量和协作收益可见** | 利用现有账本按任务/员工显示已知 token、未知用量、耗时和请求数；只有可靠价格与用量齐全才显示费用估计。能比较同一任务单员工与多员工的质量、成本和人工介入，决定何时值得协作。 |
| P1 / 按需 | **群目标与长期上下文** | 从置顶目标、已确认结论、关键资料入口做起，复用现有群知识与记忆；用户可检查、纠正和撤销。将多次工作串成可查阅的成果历史，暂不强加另一套项目管理层级。 |

两项会直接影响上述优先级的现有证据：

- **真实交付仍有待补齐的验证。** [评估记录](./spec/6.Cumora协作重构/09-多Agent测试体系与评估集方案.md)记载四角色探路已生成正确分析和草稿，但在审核及最终交付前耗尽原预算，缺少最终报告，因此判为失败；正式留出、人工校准和单人/多人对照尚未完成。这是一个已记录样本，不能据此推断所有任务都失败，也不能用早期 44/45 口径宣称当前全链路已稳定。
- **权限界面有需要校准的具体处。** [输入栏权限菜单](../src/renderer/pages/conversations/-components/composer-toolbar.tsx)中的“完全访问权限”只改变本地预览状态，不保存实际授权，但文案提到沙盒。与[当前执行环境](../src/runtime/modules/workspaces/environment-plan.ts)结合看，应先消除这种能力认知偏差，再扩展权限选项。本次只记录问题，未修改该界面。

## 建议的实施切片

### 第一个切片：只证明一个可用场景

选择“从用户材料生成可核对的研究报告”：上传两份文本型 PDF或文本资料 → 提炼事实与来源 → 写作 → 核对 → 显示最终报告 → 用户要求改一处 → 保留前后版本并确认采用。需要外部资料时再接入第一项只读网页能力；不要等所有连接器到齐。

验收同时覆盖：最终报告真实存在、关键结论能回查材料、审核针对实际交付版本、预算覆盖整条链、无权读取的员工拿不到附件、停止后不继续执行、修改不会重复原本已完成的外部动作。利用现有评估与 BDD 体系，不另建平行测试平台。

先选择一小组目标用户，用其自己的材料重复完成该场景。记录首次产出时间、结果采用率、修改次数、人工介入次数、已知/未知用量和中断原因；门槛在试运行后预先登记，再进行正式比较，不臆造用户需求或成功率。

### 第二个切片：同时管理多项工作

在第一个切片通过后，补统一待处理、全文搜索、未读定位和可运行模板。验收用户离开一段时间后回来，能找到“哪项工作等我处理、最新成果在哪、下一步该做什么”，无需逐个群翻聊天。

### 第三个切片：按实际工作接入外部系统

再根据首批用户任务选择邮箱、日历、知识库、代码仓库等连接；先打通一种高频应用，再推广通用连接管理。涉及发信、提交、发布的操作展示具体对象和内容，并沿用已有明确授权边界。浏览器交互和操作系统级隔离按所承诺的执行能力推进，不能把路径隔离描述成系统沙箱。

暂时后置：复杂多层组织架构、强制“经理”角色、通用可视化工作流搭建器、继续扩展技能市场数量、自动重放中断任务，以及在个人定位未验证前的大规模多人账号/云同步/移动端建设。语音输入可以是后续体验增强，音视频会议不作为当前闭环前置条件。面向外部分发时，签名、公证、安装升级及恢复验收仍是发布准备事项。

独立讨论串可在长群聊确有串题证据时再评估；[已选群聊设计](./spec/3.前端重构与功能/16-群聊界面设计/README.md)采用统一消息流，本报告不建议为补功能而强制重做它。已实现的主题、头像、表情和快捷命令也不应作为下一阶段核心差异化投入。

## 分产品观察与取舍

**Cumora 的关键是聊天与执行相连。** 官方 README 描述了浏览器、文件、邮件、Skills 等工具，以及按模型调用记录的成本账本；群聊使用消息新鲜度检查、工作原子认领与轻量判断减少冲突。[来源](https://github.com/yetone/cumora) 可借鉴的是可操作的工作对象、结果与成本可追踪。不能据此认定其多 Agent 必然更快；也不应仅为形态相似就复制云端 Pod、多人账号与移动端基础设施。本次读的是检索时的仓库内容，与项目既有固定提交研究应分别看待。

**LobeHub 把“团队”延伸到共同成果。** Agent Builder 根据需求配置 Agent；Agent Groups 负责协作，Pages 承载共同写作，白盒记忆允许查看编辑。[来源](https://github.com/lobehub/lobehub) 官网同时介绍 Agent/Skill/MCP 的发现与复用。[官方索引](https://lobehub.com/llms.txt) 值得借鉴的是配置好的团队、能力入口与成果编辑相连。不要把商店条目多当作能力已可用；安装、依赖、授权和实际测试仍应有明确状态。本次部分使用文档无法读取，未据此补写其组内线程、权限或实际运行语义。

**Paperclip 能解释“下一件需要我处理的事”。** 官方定义它为 Agent 管理控制台，而非聊天软件；任务、审批、预算、活动记录属于同一工作体系，还支持组织模板导入导出。[来源](https://github.com/paperclipai/paperclip) 可借鉴任务关联的待处理入口、审批历史与预算视图。BoAI 不必引入 CEO—经理—员工的强制层级；也不能照搬自动恢复，因为恢复外部动作的风险与当前本地产品边界不同。

**Taskade 说明新手入口可以是完整场景。** AI Team Generator 能由一句描述创建团队；聊天上下文可跟随项目，输出能回到任务或知识。[团队指南](https://help.taskade.com/en/articles/9586050-ai-teams) 工具指南还描述了工具启停、把自动化流程封装为 Agent 工具，以及外部动作审批。[工具指南](https://help.taskade.com/en/articles/9314171-tools-for-ai-agents) 可借鉴“团队＋工具＋输入资料＋输出位置”一起配置。不能只提供几个角色提示词，就宣称团队开箱即用；审批频率也应适合动作，而非每句话都要求确认。

**Claude 提供统一入口的有力参考。** 官方已宣布逐步合并 Cowork 与 chat，用户可以在同一对话中从提问转向多步执行，无需先判断工作类型。[官方公告](https://claude.com/blog/cowork-is-now-claude) 入门指南明确结果可预览下载、Markdown 草稿可局部修改；插件将技能、连接器与子 Agent 打包，并说明多步任务消耗更多用量。[入门指南](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork) 可借鉴统一聊天入口与成果操作；不能把其云端执行、持久在线和权限机制直接视作本地 Electron 已具备的条件。

## 外部比较支持的产品判断

这些参考更支持把现有协作做成完整闭环：**材料进入 → 能力确实可用 → 员工执行 → 用户检查成品 → 成果可找回和复用。** 群聊只是这一过程的入口。无需为了比较对象的功能列表而重新设计所有聊天结构。

1. **输入与成果优先。** 附件、多格式资料、来源引用，以及成品预览和定向修改，可以直接减少用户复制、下载、切应用的次数。验收应看能否完成一项真实办公任务。
2. **待处理入口优先于更多提醒。** 跨会话聚合“等我补充、等我批准、等我验收、执行失败”，每项可回到准确上下文；这样用户不必逐群寻找阻塞。
3. **能力状态必须真实。** 对外部连接、Skills 和模型，区分已配置、依赖缺失、待授权、已测试、运行失败。权限文案必须对应实际执行边界。
4. **卖场景而非角色数量。** 先准备少量能运行的团队方案，例如研究报告、内容生产、资料分析；一起提供输入示例、依赖检查、交付格式和大致预算。
5. **质量和成本以本地证据决定。** 比较一人和多人完成同一任务的验收率、用户介入次数、总用量与时间；成功运行、宣称完成、用户接受成果应分别记录。更多 Agent 或更长对话不自动代表更高价值。

上文每个产品事实均已链接第一方来源；未发现某项能力不等于竞品没有该能力。本文优先级已结合当前源码与既有评估，但尚未经过首批用户访谈或付费验证。Memmy 历史检索本次不可用，未将推测的历史偏好作为依据；定位假设以开头说明为准。
