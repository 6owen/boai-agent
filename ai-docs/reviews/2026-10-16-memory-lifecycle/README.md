# 内存泄漏与关闭卡死专项

## Standards：资源所有权与清理

| 优先级 | 复现/依据 | 修复 |
| --- | --- | --- |
| P2 PDF资源滞留 | 原查看器卸载只调用`cleanup()`，真实pdfjs有效PDF循环3次后，ResizeObserver和document copy监听器分别累积到3个；`loadingTask.destroy()`不会解除viewer级全局监听器。 | 传现有AbortSignal，卸载/换源调用`setDocument(null)`并断开linkService，销毁l10n观察器，保留加载任务销毁与原异步失败回报。 |
| P2 浏览器网络Map滞留 | 同一Manager循环建立/关闭30个页面后，网络计数及活动时间Map仍留30条；迟到网络完成/错误事件可重新插入已退出页面。 | 实际实例销毁/弹窗注销时删除记录；网络事件只跟踪仍有所属实例的页面，已销毁页面迟到loading事件不再更新。 |

PDF回归使用真实pdfjs查看器、真实有效PDF与解析路径；jsdom观察监听器/observer是否释放。它不测实际Electron画布性能或长期RSS。底层源码/许可证保持，依赖.d.ts遗漏的可空reset签名在一个局部类型位置说明，未替换pdfjs实现。

## Spec：常驻内存与明确关闭

| 优先级 | 复现/依据 | 修复 |
| --- | --- | --- |
| P1 明确关闭的等待环 | Main close/shutdown先等待scope队列/CDP/load结束，Manager之后才销毁页面；无响应页面上的请求可能只有页面销毁才拒绝。原生X又被宿主拦截，导致关闭或退出一直等。Runtime close另有先drain再通知Main的同源前置等待。 | 用户明确close/应用shutdown先封禁新动作并发起真实页面销毁，再核对destroyed及原操作settle。关闭过程中旧认领/迟到ready成功或失败不能复活原窗口；独立review复现的closed被迟到catch覆为idle也已修复。Runtime将明确close/clear送到Main后等待原session；清除登录资料仍须原明确操作且等实际退出后清理，普通任务drain不强关页面，不能超时冒充退出或重放未知副作用。 |
| P2 聊天保留全部历史正文 | AppShell长寿命incoming/messageRevisions两张Map接受全部会话实时消息，只在清空/删除聊天时释放；即使消息已离开有界阅读页，完整正文仍在内存。 | `LiveMessageBuffer`只暂存当前读取期间的同会话增量，读取结束/替换/切页/清理就清空。请求token和原80条阅读窗口保持，迟到旧读取不能清掉新缓冲。 |
| P2 后台更新作废或淘汰显式分页 | 真实Electron延迟较新页响应，原API流在等待期发布正文；changed事件触发refreshDetail递增同一请求token，用户页结果被丢弃，仍停在旧窗口。 | 分页期间仅记录待补读标记，先合并当前页和实时消息，再按当前已加载窗口补读员工状态；查询中心与可见阅读锚点分开，避免刷新淘汰新页。切页/清理清标记，旧finally不能清新请求，卸载后不再发补读。 |
| P2 已关闭文件的编辑store滞留 | `useFileEdits`全局stores没有释放路径；打开不同文件会永久保留各文件的修改要求/选文和状态，即使全部预览关闭。 | 稳定订阅、最后视图关闭且没有在途提交时释放store；同commit重订阅延至微任务核对。持久原请求保留，进行中提交跨关闭/重开仍共享同身份，迟到回执完成后才释放。 |

Standards两项最高P2；Spec四项最高P1。没有将一般缓存、隐藏窗口保留草稿或单次RSS上涨直接判为泄漏；上表列出的是无消费方继续持有资源/正文或可复现等待环。
