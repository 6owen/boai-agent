# BOAI 代码审查 · 2026-11-20

**整体判断：包边界清楚，单个模块的校验和回执设计较扎实；优先改进跨模块失败时的数据一致性和恢复能力。** 例如，应用已经为备份建立了保存屏障、为员工删除建立了持久化清理记录，但当协作的另一端超时或连续失败，这些局部保证仍可能让备份失败或令整个运行时无法启动。

基线为 `main@05909997`。审查覆盖 3 个应用、13 个包、运行时的 25 个业务域，以及构建、测试、资源和发布工程。按模块阅读代表入口、追踪调用方，并用现有用例或受控实验核对部分判断。共列出 **30 项发现，其中 P1 有 3 项、P2 有 20 项、P3 有 7 项**。其中一项是旧测试断言与现行会话合同冲突。严重度按潜在影响和恢复成本评定，证据强度在每条单独注明。[审查范围与检查记录](09-coverage-and-checks.md)

## 优先处理的三项问题

| 优先项 | 触发条件和用户影响 | 修复后的关键验收 |
| --- | --- | --- |
| [RT-01 单个员工清理失败阻断启动](02-runtime-flows.md#rt-01) | 员工删除已提交，但工作区或画板持续无法清理。重启时第一条失败记录中断服务初始化，其他员工也无法工作。 | 保留原文件和失败记录；健康员工能继续使用，随后可重试清理。 |
| [DESK-01 慢备份仍在写入就被清理](03-desktop.md#desk-01) | 导出超过默认 120 秒，桌面端清除等待项并删除本次备份目录，worker 可能仍在写。风险涉及导出的副本。 | 故意延迟 worker，让备份跨过时限；只有明确完成或停止后才能提交或清理目录。 |
| [ENG-01 保存失败却已变更凭据](05-engine.md#eng-01) | 编辑模型连接时，凭据先写入，配置后提交。若后一步失败，旧端点与新凭据可能组合使用。 | 分别在两次写入之间和重启时注入故障，验证配置始终对应同一版本的凭据。 |

三项 P1 均有当前源码调用链；本次未在个人环境触发破坏性故障。已有邻近用例通过的范围列在分册里。

## 已验证的表现

- 群聊详情在 40 轮和 80 轮的受控输入下，三组记录的访问次数从 4,920 增至 19,440。对历史较多的用户，按轮次建立查找索引值得优先做。数字是记录访问量，实际启动耗时需要单独测。[群聊调度](05-engine.md#eng-02)
- 员工 A 的知识资料首屏读取期间，员工 B 的会话连续变化 5 次，实际 Hook 在 jsdom 中启动了 6 次读取，前 5 次均未展示数据。事件停止后页面才完成加载。[知识列表刷新](04-interface.md#view-01)
- 工程边界、TypeScript 和 UI lint 通过。定向 Vitest 共 379 项，其中 377 项通过、1 项失败、1 项条件跳过。唯一失败是在固定主聊天上仍期待附件名作为标题；这个用例在验证原件与幂等性之前就停止了。角色子模块另有 1,095 项测试通过。[检查明细](09-coverage-and-checks.md)
