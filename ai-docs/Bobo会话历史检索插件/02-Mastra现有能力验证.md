# Mastra 现有能力验证

日期：2026-11-02。结论：当前 Mastra 已有无向量的原始会话浏览工具，Bobo 普通对话已经接入；优先复用现有能力，无需先开发独立归档或检索插件。

## 1. 实际执行结果

使用项目锁定的 `@mastra/core 1.71.0`、`@mastra/memory 1.32.1`、`@mastra/libsql 1.23.3`。

直接调用安装包提供的 `recall` 工具，在临时 SQLite 中完成 8 项检查：跨会话列举、在 B 读取 A 的原文、向后续页、围绕消息向前翻页、按返回游标读取精确内容片段、拒绝另一个员工的会话、无向量时不提供语义搜索模式、关闭并重新打开数据库后继续读取。8 项最终均通过。

再用真实 `MastraEngine.run` 和 `EmployeeConversationMemory`，接入本地受控模型响应：

1. 当前会话为 B，已授权的历史会话 A 保存一个精确原文标记。
2. 发给模型的工具声明实际包含 `recall`。
3. 受控响应请求读取 A；原引擎允许普通聊天执行该工具。
4. 下一次模型请求实际收到 A 的原始消息 ID 和原文标记。
5. 引擎继续生成包含该标记的回复；工具事件为 `completed`。

该链路最终通过，共两次本地受控请求，零外部模型调用、无向量。受控模型主动选择了工具，证明工具往返可用，不证明用户当前使用的真实模型会主动选择同样的调用。

现有 `bobo-conversation-memory.test.ts` 与 `mastra-memory-service.test.ts` 合计 17 项通过，覆盖持久化、跨身份隔离、来源撤回、遗忘、记忆管理及 API/native 归属。

工具协议细节：围绕游标使用 `detail: high` 时，可能只返回一个内容片段，并指示下一条消息或 `partIndex`；应沿返回的游标继续读取。初次验证脚本错误假设会一次返回多个片段，随后按安装包实际协议修正，最终通过；未修改产品代码或包源码。

## 5. 2026-11-03 跨会话体检追问实际失败

用户在原 Bobo 会话说明体检安排，又在新的 Bobo 会话询问“你知道我什么时候体检吗”。新会话在 `2026-11-03T02:48:19.041Z` 开始的 execution Run 已完成，回复表示没记着，但没有先查询历史。

只读核对结果：

- 原会话包含用户“周三去体检”的消息。按当前接线的稳定消息 ID 算法核对，Mastra SQL 中确有对应原消息。

- 本次真实请求包含 `recall`，但 `toolEvents` 为空；模型没有发起查询。
- 新 thread 的自动 `memory: recall` 没有加载旧 thread 的原文。自动加载当前会话历史，不代表其他 thread 原文会整批进入本轮上下文。

诊断：原文存储和跨 thread 访问能力已有，当前失败发生在“回答前主动查询”这一步。OM 达到阈值后可能提供跨会话摘要，但原文查询不需要等 OM 触发；降低 OM 阈值不能替代这一步。

后续应优先为 Bobo 明确“遇到过去的交流、用户曾告知的信息，先用现有 recall 列举/读取获准历史，再回答；不能仅因当前上下文没有就断言用户没说过”的指引，并沿此次原始场景复验。此为待实施方向，本轮未改产品代码或启动实现。原隔离工具验证通过与本次真实体验失败分别保留。
