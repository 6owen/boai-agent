# Bobo 主动回忆指引修复与验证

日期：2026-11-03。按用户授权修改现有 Mastra 接入，保持 OM 观察阈值 **6000 message tokens**、反思阈值 **12000 observation tokens**。不合并 Bobo 会话，不新建历史库、向量检索或 supervisor。

## 1. 最终实现

- 在官方 `observationalMemory.retrieval.instructions` 配置中文补充指引。模型主动判断历史对当前回答是否有帮助：当前信息足够就直接回答；可能依赖既往交流且信息不足时，优先用 recall 查证；小范围发现会话、按需读取原文并停止扩展。不使用关键词触发器、每轮强制工具或固定调用频率。
- 适用当前 Bobo 的 API 私聊。既有普通回复路径和 Bobo 私聊的 `ask` 路径均能提供 recall；组织执行、交接等原隔离路径保持。其他员工和原生 Agent 的行为不由这次补充改动。
- 锁定的 `@mastra/memory@1.32.1` 在 readOnly 模式、没有 OM record 时跳过 retrieval 指引。冷启动使用官方 `Agent.stream({ system })` 补入同一段自定义指引；有 record 时交给原 OM processor，避免重复。
- 不为注入指引创建空 OM record，不提前生成观察摘要，也不把其他会话原文直接拼入冷启动上下文。既有来源同步、授权、遗忘及历史加载保持。
- `tool_choice` 仍为 auto。后台不强行调用 recall，是否查询以及查询多少次由模型选择。

代码入口：[conversation-memory.ts](../../packages/runtime/src/adapters/mastra/conversation-memory.ts)、[engine.ts](../../packages/runtime/src/adapters/mastra/engine.ts)。

官方接口说明：[OM 配置](https://mastra.ai/reference/memory/observational-memory)、[stream 的 system 参数](https://mastra.ai/blog/migration-guide-streaming)。实际兼容依据为锁定安装包的 embedded docs、公开类型及实现；`core@1.71.0 / memory@1.32.1 / libsql@1.23.3`。

## 2. 真实模型对照

使用 Bobo 当前保存的 `deepseek-flash` 连接，真实 AppService → MastraEngine → DeepSeek API。每题独立产品库和 Mastra 库，凭据仅经既有只读 Electron 桥在内存传递，不写个人聊天或配置。

合成旧会话原文为“周三去体检，周一晚上熬夜到3点，准备周二早点休息。”，标题为“日常交流”。随后新建 Bobo 会话分别问：

- 历史问题：“你知道我什么时候体检吗？”
- 自包含对照：“17乘以6是多少？”

请求数包括正常的判断请求及回答请求，recall 次数为完成的工具调用数。耗时从提交新会话到运行收尾，包含同步、判断、工具和网络；不是纯工具 SQL 耗时。

| 版本与问题 | 回答/来源结果 | recall 次数 | 模型请求数 | 耗时 |
| --- | --- | ---: | ---: | ---: |
| 原实现，体检追问 1 | 否认存在记录，失败 | 0 | 2 | 3.716 秒 |
| 原实现，体检追问 2 | 称没说过，失败 | 0 | 2 | 4.318 秒 |
| 原实现，算术 1 | 102 | 0 | 2 | 2.079 秒 |
| 原实现，算术 2 | 102 | 0 | 2 | 2.055 秒 |
| 最终候选，体检追问 | 从旧会话查到周三，原文核对通过 | 3 | 5 | 7.476 秒 |
| 最终候选，算术 | 102 | 0 | 2 | 1.582 秒 |

最终候选的体检查询依次为：列出 threads → 读取旧 thread 的低细节消息 → 按 cursor 展开原始用户消息。低细节结果出现截断提示后，模型自主展开了原文。检索前的真实 HTTP 请求中没有体检原文；检索后的 tool 消息中才出现原文。算术对照的请求始终没有这条原文，也没有工具调用。

体检最终答复为：“你之前说过周三去体检，而且周一熬到3点、周二想早点睡。怎么了，明天就是周三？别又熬到后半夜啊。” 其中“周三”及作息来自原文；完整语气、健康建议质量没有独立评审。本次仅检查已知事实、真实查询来源、次数和延迟。

**结论边界：** 原实现两次失败，最终候选一组通过，证明这条实际执行路径能自主查询并回答，不能证明所有跨会话问题都会触发，也不能估算稳定成功率。检索增加了三个模型工具步骤，本例端到端约多 3.2–3.8 秒；普通问答没有增加请求数。网络波动和样本量使本次耗时不能作为性能基准。

## 3. 未采用方案与原失败

前两版候选曾尝试初始化空 OM record，让官方 processor 自动注入完整指引。真实请求检查发现，这也会让官方 `getContext` 按 resource 加载未观察的其他会话原文。因此“答对周三但零 recall”不算检索成功，最终已撤回该方案。

第一版候选还出现 `ask` 路径没有 recall，以及评估程序把合法 `waiting_user` 状态等到 180 秒期限的问题。第一批候选实际 7 次请求；其中一例答对但无 recall，一例普通问答通过，另一历史例等待超时。补齐 ask 和评估等待后，第二版候选 9 次请求、两次历史回答虽正确，但因提前带入原文、零 recall，仍未通过来源检索判定。

最终改为只补指引后，再在剩余预算中验证一组。四部分实际请求为 **基线 8 + 第一版 7 + 第二版 9 + 最终版 7 = 31**，累计输入 **397605 tokens**、输出 **3058 tokens**；原上限 32 请求/16000 输出 tokens 未扩大。没有额外 judge 请求，费用未另行估算，Codex 分析用量不计入这份 BOAI API 账本。保留全部失败及未执行的第二组最终候选，不挑最好的一次冒充重复通过。

## 4. 工程与复现

- `bobo-recall-guidance.test.ts` 加入真实安装的 Mastra/LibSQL 和受控 HTTP 供应商回归：冷启动没有 OM record、不加载其他会话原文；已有 record 使用官方指引；原阈值和 readOnly 保持；普通员工/组织隔离；reply/ask 可读原会话；自包含问答自主零工具。
- 与 `bobo-conversation-memory.test.ts`、`mastra-memory-service.test.ts` 合计 **3 文件/22 项通过**；`pnpm typecheck` 通过。受控协议回归与上面的真实模型成绩分开。
- 手动入口为 `node scripts/evaluate-bobo-recall.mjs`，冻结当时 HEAD 的记忆桥作为基线，与未提交候选比较；默认每类两次。`--continue-from <目录>` 只在原累计预算内保留前批结果并继续候选，`--repetitions 1` 可收窄采样；不是自动反复重跑取最好值。
- 本次基线为 `16c9c6ed`。原件目录 ID 依次是 `1793676403630`、`1793676836024`、`1793677000602`；包含源码 hash、模型身份、实际工具输入/输出、用量与请求标记，凭据不保存。收尾时将专用证据迁出任务 worktree，防止回收丢失。
