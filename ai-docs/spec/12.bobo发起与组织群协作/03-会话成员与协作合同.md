# 会话成员与协作合同

本文件描述当前接入的组织合同。实际技术、桌面、真实模型与人工验收只在 [05](./05-实施步骤与验收清单.md) 登记；字段以 `src/shared/domain/bobo-collaboration.ts` 和 `work.ts` 为准。

## 1. 身份、会话与工作是三个对象

| 对象 | 固定边界 | 不能推导出的权限或生命周期 |
| --- | --- | --- |
| 员工 `DigitalAgent` | 长期 ID、配置、能力、自己的 workspace 和获准记忆 | 加入群不复制员工；离群/解散群不删除员工 |
| 原 bobo Conversation | 用户与固定核心身份 bobo 的聊天讨论 | 不自动转群、删除、归档或搬迁历史；不会被新群替代 |
| 独立协作群 Conversation | 同一次组织操作发布的普通 `group`，含 bobo 和所选员工 | 群不是员工的所有者；群存在不等于已经开工或交付 |
| 具体 Work | 一次明确工作目标、负责人、预算、状态与结果证据 | 子工作仅描述本次分工，不能创建第二个员工身份 |

首批新群使用 `kind=group`、普通会话用途，`agentIds` 保存 bobo 与员工的唯一 ID；用户仍以 `senderType=user && senderId=user` 发言，不加入 `agentIds`。
当前普通会话输入的 `conversationSchema.agentIds` 明确使用 `.max(12)`（[service.ts](../../../src/runtime/service.ts#L103)），不只是团队方案生成限制。首批沿该上限计入 bobo，因此最多安排 11 名其他员工；更大团队须另行调整容量和验收。
bobo 在群里以自己的名字和头像发言；其他员工也以自己的身份发言。成员可以独立回应、提问、说明限制或配合他人，不由 bobo 替他们生成署名回复。

**当前准入**：普通手动新建群仍不能加入 bobo。组织模块按真实核心身份发布新协作群，后续保存仅允许该已发布群保留原 bobo；核心 Conversation 仍是独立 direct，不能改绑成员。
“A2A”在本组描述群中独立 Agent 交流；首批不要求正式 A2A 协议、远程 Agent 服务或 Agent Controller。

## 2. 找人只读取获准能力摘要

已接入有界通讯录查询，宿主先排除已删除、清理中、停用和不支持群聊的 ACP 员工，再按稳定游标返回候选。
候选只包含员工 ID、当前姓名/角色、配置版本，以及浏览器、命令、已绑定技能和知识等能力配置摘要；无有效模型配置的员工先被过滤。摘要不包含独立的依赖验证状态或被排除对象的失败原因，不证明模型调用或工具已经执行成功。
不返回连接密钥、完整指令、员工私聊、长期记忆正文、文件目录或整个 workspace；姓名/标签不是权限证明。
按名称或角色筛选仅用于发现。模型比较候选适合程度，宿主确定成员是否存在、当前是否支持群协作、数量上限和配置有效性。
找人期间保存查询条件和通讯录 revision；冻结所选员工时逐个核对 `configVersion`，最终发布前再核对。迟到候选不能覆盖用户已改变的需求。
缺员时生成最小补齐配置，沿现有员工初始化和资源绑定规则准备；不能把扫描到的技能自动安装/授权，也不能承诺未验证的工具可执行。
新员工的身份与初始化目录由宿主冻结，不能按名字判断重复员工。已有员工不改名、不改人格、不重建 workspace。

## 2.1 只创建员工的受控支路

用户明确“只创建一个编辑，先不要拉群”时，原 core 会话保留，创建交付是该次原 Work 的明确目标。
`BoboCollaborationOperation.mode=employee_creation` 明确区分此支路；复用同一组织账本，不制造任何群字段/开场/启动意图。
宿主沿原用户请求/Work 保存稳定 `requestId/payloadHash`、原 `budgetId`、固定员工 ID、冻结配置/hash 和所见版本。
缺失原预算或授权时阻塞，不另建一份业务预算；分析/配置生成/创建调用累计沿原额度与期限。
受管目录准备可复用组织模块的新员工暂存、所有权/hash 日志及初始化清单，不复制其他员工 workspace。
文件准备结束后核对配置、目录和取消门禁，同一 SQLite 事务发布新员工与创建成功回执。
**此支路不创建群、群目标消息、群业务根或群启动意图，也不自动让新员工开始处理其他任务。**
不能调用旧 `create_team` 创建默认群后再隐藏/删除群；新员工创建必须具有真实独立受理/发布路径。
成功回执返回真实员工身份，原 bobo 回复提供员工详情/开始聊天入口；处理事情由用户直接找员工。
同 key 同载荷返回原结果，异载荷拒绝；未知回执保留原 key/hash，只读核对，不自动重新初始化。
发布前取消等待文件/模型实际退出，再清理本次 hash 匹配文件；发布后员工保留，删除沿通讯录原合同。
重启核对与备份恢复不自动创建/执行，外改文件保留并显性显示清理问题；不影响其他员工或现有群。

## 3. 当前权威记录与 API

产品 SQLite 是唯一权威。组织工具输入 `BoboCollaborationPlan` 严格接收 `{existingMembers:[{agentId,configVersion}],newEmployees:[{name,role,instructions,color?}],groupTitle?,announcement?}`。人数合计 1–11，新员工规则每人最多 2000 字、合计最多 16000 字，公告最多 4000 字。未知 mode、预算、核心身份、材料 ID 或本机路径字段均拒绝。

模式/目标/稳定请求由宿主在 claim 前写入 `Work.organization={requestId,mode,goal}`；`requestId=bobo-collaboration:<真实原用户messageId>`。工具不能改变阶段或自报授权。操作 ID 由该 request 稳定计算，`payloadHash` 绑定严格校验后的模式、目标和完整方案；同 key 同载荷核对原操作，异载荷拒绝。

| 真实集合/类型 | 保存内容 |
| --- | --- |
| `boboCollaborations` / `BoboCollaborationOperation` | schemaVersion/version、request/hash、原 core Conversation/Message/hash、organizationWorkId/budgetId、mode/goal、真实 holder authority、通讯录 revision、既有员工 ID/配置及连接指纹、仅本次新员工、群/真实公告、文件归属/hash/取消门禁 |
| `workItems` / `Work.organization` | claim 前冻结原组织范围；组织 Work 与群根各有自己的会话、来源和责任，不跨会话搬迁 |
| `collaborationStarts` / `CollaborationStartIntent` | 唯一原请求、群、公告 ID/hash、群根、原预算、rootWorkVersion、状态/实际 turn 受理回执 |
| `messages` / `Message.collaborationSource` | 原 operation/sourceRun/modelCall/toolCall 身份；开场为 agent/bobo，**不设置 core runId，也不伪造群 run/用户消息** |
| `boboCandidateClock` | 员工/连接/资源/通讯录/删除变更与源事务一同推进；发现游标绑定配置代际和查询条件 |

组织状态为 `accepted/preparing/ready_to_commit/interrupted/needs_attention/committed/cancelled`；启动意图状态为 `pending/consumed/interrupted/blocked/cancelled`。两者分开：`committed` 证明组织对象发布，不证明群已开工或已交付。业务结果继续从真实 Work/成果证据读取。

| 当前接口 | 输入与边界 |
| --- | --- |
| 模型 `find_employees` | `{search?,cursor?,limit?}`，每页最多20，返回员工 ID/姓名/职责/配置版本和已配置 browser/commands/绑定资源名称；无私人规则、密钥、路径或聊天正文 |
| 模型 `organize_collaboration` | 严格方案，不接收 mode/goal/budgetId；真实当前工具调用身份由 SDK/宿主填入，沿原 Work effect 回执 |
| `listBoboCollaborationOperations` | `{conversationId}`，只读原 core 的有界公共回执 |
| `getBoboCollaborationOperation` | `{operationId}`，只读真实回执及当前 startStatus，不执行文件/模型 |
| `resumeBoboCollaboration` / `abandonBoboCollaboration` | `{operationId,expectedVersion}`，固定所见版本；继续先核对实际文件，认领原 Work 新 holder 后复用原计划，放弃只清理本次未发布 hash-owned 文件 |
| `resumeBoboCollaborationStart` | `{operationId,expectedVersion}`，仅核对已发布群并消费原启动意图，不重新建群/发公告/分配预算 |

`BoboCollaborationReceipt` 只包含真实对象 ID、员工摘要、群名、组织/启动状态及有界错误；不含内部新员工规则、文件清单、任意路径或凭据。内部 `auditOperation` 返回冻结操作供宿主恢复事务核对，**不通过 IPC 暴露**。

## 4. 首批跨会话开工方案：一个请求、一个预算、两个阶段

**选择这一条方案，首批不同时实现跨会话后台委派或把原 Work 移到新群。**

1. 原 bobo 会话接受用户真实请求；普通讨论只有 Message，不制造 Work。
2. 用户明确要求组织时，宿主冻结原 `Work.organization`。组织阶段工作只承担分析/找人/补齐/组群，原业务目标另存于请求。
3. `organize_only` 发布员工/群和 bobo 的目标说明，不创建业务根工作、启动意图或自动执行员工任务。
4. `organize_and_execute` 同次授权发布群内唯一业务根工作和一次启动意图；不要求用户为已授权“组织大家完成”再确认一次。
5. 组织工作完成只证明组织成功；群业务工作独立承担完成用户目标，工作自己的 `conversationId/sourceMessageId` 固定在群内。
6. 两个阶段绑定同一个原始预算 `budgetId`，组织消耗、群判断、执行、修复、记忆及分工累计计入，不分别新领默认额度。

组织 Work 和群业务根 Work 范围不同，不是两个重复业务根；不设跨会话 `parentWorkId`，不拿源 Work 作为群成员的执行权。
新组织能力必须在工作认领之前明确阶段：源 Work 的 scope/deliverable 固定为组织交付，不得先在源会话认领整个业务 `main` 再改写范围。
如果既有源 Work 已在执行完整业务，不能通过后续建群工具暗改其责任；首批拒绝这种隐式转换，要求明确新组织请求，保留旧工作的可见状态。
唯一群业务根负责人首批为 bobo；bobo 在群说明目标/分工，其他员工拥有各自明确工作和结果，仍然是独立成员。
群内分工沿已有 WorkRepository 父子工作/结果依赖，子工作继承该群业务根及同一预算。独立于本次请求的其他工作不取得该预算。

预算绑定由 [work-collaboration.ts](../../../src/runtime/modules/collaboration/work-collaboration.ts) 和 WorkRepository 的同事务 helper 负责：核对原 holder、真实用户源/公告、已写入本事务的员工/群，执行模式才登记唯一群根/启动意图。普通工具或 renderer 不能指定任意预算。

组织判断的已知前置调用按真实 decision run/call 回执计入，受理后的组织、群判断/执行/记忆及子任务继续用唯一调用预留/结算账本。未知用量保持未知，不伪造 automation origin。共享绝对期限、累计限额和取消树继续有效；切会话、等待、重启或恢复不刷新期限。

新的 `organize_and_execute` 请求在首次认领事务中确定 **48 次总模型调用**，覆盖找人、组织、群成员判断、实际分工、成员执行和群汇总。`organize_only`、`employee_creation`、普通任务与自动化仍使用原 **24 次**。所有成员共用一个预算；**16,000 输出 tokens、原始 5 分钟绝对期限及其余限制不变**，不是每名员工各领 48 次。模型不能在方案中指定或扩大额度。已受理的旧预算保留实际保存值，重启、恢复、重认领和群/子工作不升级旧 24 次，也不把已失败请求自动续行。

重新汇报先将实际新读原文纳入原召回快照并核验来源，仍最多两次且不重放执行；它沿原 Work 的累计预算与绝对期限，不被独立 30 秒报告计时器提前取消。相关来源失效、原期限到达或原额度耗尽仍阻止发布。判断和记忆维护的各自时限保留。新规则的技术及真实供应商结果另在 05 登记，不回写旧冻结失败成绩。

## 5. 群内首条目标必须是 bobo 真实发言

目标说明由本次实际 bobo 模型输出产生，宿主严格校验并冻结正文/hash。可包含用户获准目的、验收预期、成员和初始分工建议。
发布时使用 `senderType=agent && senderId=bobo`，保留真实输出来源；不把这段文字伪造成用户在群里再次提出的新请求。
Message 明确关联源协作请求，但新群不能通过该关联读取整个 core 历史。
若只授权建群，“先讨论需求/介绍职责”等应为普通交流；群设置 `teamSetup` 仍只是背景，不能制造开工权限。
若授权执行，首条消息与固定群根、原预算绑定和启动意图同事务受理；群首个执行事件核对实际用户授权，不能只凭一条 Agent 消息扩权。

已接入 `prepareCollaborationStart` 内部调度入口，不能直接把现有 `prepare` 的 `user_message` 套在 bobo 的 Agent 消息上。
第一轮需保留真实 bobo 消息身份，启动事件携带固定请求与群根，员工判断使用当前成员和获准上下文。
同一请求只有一个群业务根；员工不得把目标说明各自认领成多个“整个请求”根工作。
bobo 认领组织协调工作并使用群内已有 `delegate_work/wait_for_work` 形成具体分工，这是内部执行机制，不是后台子 Agent 产品关系。
员工可以普通回应、提出限制，或承担具体已授权分工；分工目标不能超出整体授权，不能通过同伴消息取得额外命令权限。
后续普通用户聊天保持 chat；明确补充按实际问题/工作回执接续原工作和预算，新的独立要求建立新请求，不按文本相似度去重。

## 6. 组织受理与整套发布的事务边界

| 阶段 | SQLite 同事务保存 | 事务外操作/门禁 |
| --- | --- | --- |
| 受理 | 原授权 Message 身份、唯一请求/载荷 hash、组织 Work/原预算关联、冻结对象 ID 和取消门禁 | 尚不公开新员工/群，不调用员工执行 |
| 准备 | 每一步受管文件所有权/hash/checkpoint | 初始化新员工暂存文件；已有员工目录不复制、不覆盖 |
| 发布 | 全部新员工、独立群/成员版本、bobo 目标消息、组织成功回执；执行授权时同时保存群根/原预算绑定和启动意图 | 复核员工/连接/材料/配置/完整目录及取消门禁后一次发布 |
| 启动领取 | 条件领取启动意图、绑定 Turn/Event/Delivery 与固定群根 | 提交后才调度；事务失败不调用模型/工具 |
| 消费核对 | 原意图与真实轮次受理回执同事务 | 不按 UI 卡片显示或群存在推断已启动 |

事务内不做模型、网络、文件搬运或等执行器退出；文件准备参照团队创建的受管暂存/hash 日志，最终发布进入宿主临界区。
已有员工和新员工的混合选人是本组已接入的新合同，不能用既有“全新团队创建”替换而重复建立同名员工。
发布失败可靠回滚后才清理本次独占文件；状态未知或文件外改时保留，显示核对/清理待修复，不宣称全部回滚。
已提交但内存未安装完整对象时要求只读重新载入/重启核对，不能返回不可用群 ID 或再次创建。

## 7. 稳定请求、未知回执与重启

组织工具/typed IPC 统一复用 `requestId + payloadHash`。同 key 同载荷返回原结果，同 key 不同载荷拒绝。
稳定 request 由原受理身份保存，不按模型工具调用次数、成员姓名或重试次数生成；未知提交保留原 key/载荷跨关闭和重启。
只读核对返回实际组织状态；内部 lookup 确认无记录才返回 null。sourceCleared/cancelled 保留原 hash 去重并拒绝重放。查询失败不是不存在，响应未知保留原 operation/key/version，不自动重试。
`not_found` 必须是权威事务已完成核对的结果，不能把查询失败、超时或未载入记录当作不存在。
启动意图只有一次事务领取/消费，旧持有者不释放新运行的执行权；群根与已执行/结果不明的工具不得自动重放。
重启只核对已提交员工、群、消息、文件和回执，把未完成执行标为中断；未消费启动意图也不自动调度模型。
继续组织或继续群工作需要明确恢复动作，仍引用原请求/群/账本并核对待查副作用；不再创建员工、群或默认预算。
群对象已成功发布而启动失败，应保留可进入群和明确“尚未开始/已中断”，不能把群回滚删除当作恢复手段。

## 8. workspace、材料和记忆的归属

每个成员执行沿 `agents/<agentId>/workspace/sessions/<groupConversationId>/...`；员工根空间保持独立，当前 run 仍有自己的目录。
群共享目录只放明确登记共享的文件，不能作为成员合并 workspace；bobo 不获得其他员工根目录的任意读写权限。
员工使用自己的连接、配置、绑定技能/知识及当前群授权；bobo 不能把自己的资源绑定当作全群工具许可。
记忆沿现有员工统一召回，先核对实际获知、来源、范围、事项、有效期和忘记屏障，再按相关性和预算选择。
bobo 加入群不等于其全部私人记忆授权给别人，也不保证可凭提示词硬防泄漏；严格私人内容应限定原 core 会话。
默认仅向群发布本次获准目的摘要，不整段复制 bobo 私聊，不把其私人文件/材料自动搬进群。
群成员记住的是自己获准见到的群内容；不因为知道员工 ID 或协作请求关联就取得源会话权限。

后续若扩展共享源会话材料，须有明确材料 ID/版号/hash、目标群、明确成员与用户共享授权，并先增加跨会话材料受理合同。
当前材料校验要求本会话，不可把源 MaterialReadRef 直接塞给新群。首批在 core 当前模型输入带 materialRefs 时拒绝组织，并提示在新群明确提供/授权；只发布获准摘要，不自动复制原件。
受理共享材料时，目标群登记自己的受管原件/授权回执并保留派生来源链，不重读外部路径；外改、删除或撤权立即失效旧正文。
新加入成员不自动获得旧材料许可；每次模型开始、工具读取、回复/成果发布和记忆维护都检查当前授权与来源版本。
目的摘要的独立群发布和带原文材料的派生来源不同：源聊天删除不解散群，但须传播其实际材料/记忆来源失效，不保留被清理私文。

## 9. 交付、并发与结果回流

群内继续按成员独立判断和流式回复，不用模型决定唯一发言者；同伴普通发言不作废他人对原始用户需求的独立判断。
同一协作中已有明确工作的成员收到真实任务结果广播时，宿主在任何模型计数前以单事务核对全部合并事件、公开消息、实际任务Run和Work结果登记，以及成员当前ready/running/依赖waiting的原工作。纯状态广播仅保留上下文并登记跳过原因，沿原工作及定向唤醒接续；来源或目标公开问题/待核对、明确收件人/提及、用户/首轮/wake/交接、普通聊天和未分工成员仍沿正常判断。跳过不删除消息、创建判断运行或改变原额度。
既有同连接最多六项模型调用、独立工作区最多六项执行及同员工会话文件互斥保留；允许宿主命令的工作沿既有全局互斥。
群分工提交、认领、预算预留、结果证据、依赖版本和唤醒都经过 WorkRepository SQLite 条件事务。
停止/撤权/成员变更与公开提交共用宿主临界区；旧配置快照不得在新成员/权限版本下继续启动或发布。
执行器退出不等于已交付，工具成功不等于成果可用。群根完成须引用实际公开回答或获准、可核对 hash/版本的成果。
bobo 汇总只引用实际参与本次工作的消息/成果，不把成员计划、失败日志或群创建回执写成完成证据。
原 bobo 会话读取组织回执、明确群/员工ID和启动状态，并提供进入群入口；工作状态、具体问题、消息与成果证据在该群核对。不产生第二套工作状态，不把群成果全文自动复制到私人历史。
群工作等待用户时保留明确问题和原预算，用户去群补充或通过明确关联补充入口回答；普通 core 聊天不自动解除群等待。

## 10. 取消、删除与解散

| 用户操作 | 本组必须保证的行为 |
| --- | --- |
| 发布前取消组织 | 先保存取消门禁，禁止整套发布；等待文件/模型实际退出后清理本次 hash 匹配文件并释放容量 |
| 发布后取消组织步骤 | 保留已创建员工/群；不自动停止正在执行的群工作。若要停止整个协作，操作明确指出目标群/本次工作 |
| 停止本次群工作 | 定向停止该群业务根及其子工作，等待真实退出；不取消无父子归属的独立工作/共享依赖 |
| 删除或清空原 core 会话 | 清理原正文/组织来源，保留最小去重回执；已发布群和员工保持存在，不自动继续任何工作 |
| 解散协作群 | 沿群清理合同停止该群执行/关联计划并清理群配置/历史/受管会话目录；所有员工及其其他会话保留 |
| 删除某个普通员工 | 沿通讯录合同清理该员工 workspace/记忆/专属资源，移除各群成员关系；其他员工仍保留，受影响工作可见阻塞/停止 |

源会话清理不能按原 budget 的来源会话一并删掉仍被已发布群引用的账本；BC4 需核对跨阶段引用计数/清理归属，保留最小运行核对事实。
清理不能从保留的群反向恢复源私聊，也不能凭 tombstone 重新建群。群删除后旧入口只显示已不存在，不猜同名新群。
取消资源在执行适配器实际退出前保持占用；旧超时/取消回调不得取消新认领或追加额度后的运行。
受管文件只删除本次所有权与 hash 匹配内容；外部修改保留并显性记录，不能为了清理成功覆盖用户修改。
未结束文件组织操作与备份互斥；恢复备份核对员工/群/消息/共享预算及来源，不自动重建群、续行或重发旧启动意图。

## 11. 后续已有群复用边界

BC5 才处理复用群。用户需明确选择具体群 ID，宿主冻结所见配置版本/成员/授权并判断是否满足本次目标。
不按群名、标签、团队创建来源或“之前合作过”自动选群；不能擅自把原群成员移出或给新增成员授权全部旧历史材料。
复用是新的稳定协作请求和真实群说明，不改写原群目标/历史，不接续已交付旧业务根，不重新创建现有员工。
与群内已有工作共存的预算和停止范围必须分开；只有当前请求的子工作使用当前预算，独立旧工作继续自己的身份。

## 13. 当前明确恢复的实际步骤

继续未发布组织：`auditOperation` 对原 manifest 实际核对归属/hash/已记录写入前缀；宿主同事务认领原组织 Work 新执行权，保留原预算/期限和待查 effect。模块再次核对原 holder/用户源/通讯录/配置/连接/原模型输入来源，复用原 ready 文件，只补齐原日志未完成项。提交后按真实组织证据确认 effect，不调用模型重新规划，不伪造员工或群回复。

恢复 holder 与原公告生成来源分开：公告继续引用最初真实 model/sourceRun/toolCall，新恢复 run 只承载文件准备和发布。原模型来源失效、忘记或到期阻止旧计划发布。停止恢复同样传递取消信号并等待文件执行实际退出；外改文件保留并显示 needs_attention。

已发布群的启动恢复走独立 start API。重启仅保存 interrupted/只读核对，不自动认领任何模型或文件任务。core 清理保留已提交群公告的独立来源证明与仍被群引用的累计预算，清除原私人摘要；不能从群反向恢复已清 core。
