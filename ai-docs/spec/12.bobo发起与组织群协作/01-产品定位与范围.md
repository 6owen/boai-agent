# 产品定位与范围

日期：2026-10-02。状态：待实施设计。唯一实施进度见 [05](./05-实施步骤与验收清单.md)。

## 1. 用户已经确定的产品模型

员工 Agent 是独立的一等公民，含义与 IM 中的联系人一致。每位员工有稳定身份、自己的配置、workspace、能力和获准记忆，可以长期使用，也可以按既有删除规则删除。

员工的身份与交流形式没有关系。私聊、群聊、接受分工、参与讨论都只是这个员工参与事情的方式；群聊只组织参与者，不拥有成员的身份或 workspace。

bobo 是项目中的关键 Agent，用户可以配置它，并长期与它交流。它更熟悉用户，也可以帮助用户分析需求、找到合适员工、补齐缺少的员工，再发起和组织群协作。这些深度组织能力是本组规划，不能写成当前已经实现。

用户处理事情的三个入口始终并存：

| 入口 | 用户可以做什么 | bobo 的关系 |
| --- | --- | --- |
| 直接找员工 | 私聊某个已有员工，交代事情、讨论和查看成果 | 不要求先经过 bobo |
| 直接进入群聊 | 与群成员交流，让成员各自判断、分工和配合 | 不要求群中存在 bobo |
| 先与 bobo 讨论 | 分析需求，找员工或创建缺少的员工，再组织群协作 | bobo 以自己的身份帮助发起和组织 |

不能把所有员工的使用入口收进 bobo，也不能要求所有群聊都由 bobo 主持。

## 2. 本组确认的流程

> 你找 bobo 讨论需求 → bobo 分析需要哪些员工 → 找到已有员工或创建缺员 → 拉群 → 在群里说明目标、安排分工 → 员工之间交流、配合和交付。

首批落地使用独立的新群承载这次群协作。原 bobo Conversation 保留原身份、标题、消息、草稿和历史；不自动关闭、消失、转换成群，也不把原记录迁移或合并进新群。

新群包括用户、bobo 和选中的员工；用户身份不加入 `agentIds`，bobo 与员工使用各自真实 Agent 身份。bobo 在群里说明本次目标与分工，员工以自己的署名交流和工作。允许 bobo 参与这种群是待实施规则变更，当前规则仍禁止它加入员工群。

创建后，在原 bobo 回复中提供真实群入口与参与员工入口。是否打开由用户决定，不自动切走正在阅读的会话。用户随后可以继续与 bobo 讨论，也可以去群里参与，或直接私聊其中某个员工。

## 3. 对象职责

| 对象 | 长期保存什么 | 不承担什么 |
| --- | --- | --- |
| 员工 | 稳定 ID、模型和能力配置、workspace、本人获准记忆 | 不因某次群协作产生一个副本身份 |
| bobo Conversation | 用户与 bobo 的讨论、组织请求、实际回执与入口 | 不自动变成群，不作为所有群的母会话 |
| 普通协作群 | 成员、群名、背景、群消息、本群真实工作和成果 | 不取得成员私有 workspace 的所有权 |
| 群内工作 | 明确目标、承担员工、依赖、预算、状态、交付证据 | 不用全体成员名单冒充已经成立的分工 |
| 创建/组织回执 | 原请求身份、已提交对象和当前核对状态 | 不凭模型文字声明创建成功或任务完成 |

同一员工可以同时出现在多个群，并保留自己的私聊。每次执行沿现有员工和会话空间隔离，不能把多个群的私有上下文装进一份共享提示词。

“群内分工”是成员在本次交流中明确承担工作。产品不增加一套隐藏的后台 subagent 人员体系；框架内部的执行实例也不能替代通讯录员工身份。

## 4. bobo 首批新增能力

### 4.1 分析需求

bobo 分析用户想完成的目标、必要能力、现有约束和预期交付。它可以在原 Conversation 中继续讨论；纯问答、比较和建议不创建员工、群或 Work。

缺少决定执行方式的必要信息时才询问。已有明确目标和组织授权时直接按合理默认值执行，不额外引入固定的审批弹窗、模板向导或必填配置页面。

### 4.2 找到已有员工

先从实际可用员工中找人，再考虑补齐缺员。匹配依据是获准读取的配置、职责和已绑定能力，不是员工姓名的关键词命中，更不能靠读取私聊全文判断员工是否合适。

查找必须有界；结果固定真实员工 ID 和配置版本。停用、删除、能力不足、连接不可用分别说明，不能把“绑定过技能”说成“依赖已验证且执行成功”。

### 4.3 补齐缺少的员工

只创建现有员工无法覆盖的必要角色。创建出的对象就是通讯录中的普通独立员工，有自己的身份和受管 workspace；不是本次群运行结束后自动消失的临时角色。

员工配置沿既有创建规则和模型连接范围，不凭群需求授予宿主命令、技能、知识或私人材料权限。模型负责提出角色和配置，宿主负责身份、校验、文件准备和提交。

首批把缺员、新群和 bobo 模型实际生成并冻结的群内首条说明作为同一次组织操作原子发布；细节见 [03](./03-会话成员与协作合同.md)。不先暴露一半员工，再靠后续界面保存拼出群。

用户明确只要求创建员工时，走 [03 的独立员工创建支路](./03-会话成员与协作合同.md#21-只创建员工的受控支路)，仅发布员工和真实入口，不创建群或自动执行业务。该支路与补齐缺员共用初始化/发布底座，但保持自己的请求和交付范围。

### 4.4 发起群协作

组织准备阶段，bobo 以自己身份生成群内实际目标、约束、建议分工和需要用户回答的问题；首条说明随群一同发布。目标不是欢迎词，分工必须能追溯到原用户需求和当前有效成员。

员工继续沿现有自然群聊机制独立判断、回应、承担工作、等待或提出接续请求。宿主检查确定性规则，不由 bobo 冒充其他员工发言。

### 4.5 汇报真实状态

原 bobo 会话提供“已创建群/员工”“目标已说明”“某工作等待输入/已交付”等有证据的状态。对象已创建、消息已公开、工作已执行、成果已交付是不同事实。

bobo 只能依据明确关联的本次组织和群内工作回执汇报，不自动读取任意群历史、员工私聊或整个 workspace。

## 5. 首批范围与后续扩展

| 范围 | 首批决定 |
| --- | --- |
| bobo 原会话 | 完整保留，不改变为群，不自动结束 |
| 找人 | 有界查找已有员工，冻结明确身份和配置版本 |
| 缺员 | 按需要补齐，沿既有员工创建/文件底座 |
| 群 | 新建一个独立普通协作群，包含 bobo 和选中员工 |
| 入群背景 | 仅本次明确目标、必要摘要与获准材料 |
| 群内交流 | 各员工独立署名，复用自然群聊、工作和成果机制 |
| 原会话入口 | 真实群 ID、员工 ID，不抢导航 |
| 已有群复用 | BC5 条件扩展；仅用户明确指向已有群，不按文本相似度选择 |

首批不加入个人事项平台、自动长期计划、全员记忆共享、统一大工作区、外部通信协议、新的模型运行框架或工具插件系统。这些不能成为本组闭环的前置依赖。

既有群复用尚未实施时，首批界面不显示一个只能演示的“自动复用群”选项。用户明确要求在某个已有群继续时，说明当前支持范围，不静默创建一个冒充原群的新对象。

## 6. 与当前实现的关系

当前 [第 9 组 15](../9.团队创建助手/15-bobo核心助手与会话式团队创建.md) 已有稳定 bobo 身份、核心 Conversation、统一员工记忆和真实 `create_team` 工具。

其 `create_team` 创建一组新员工和默认群，沿冻结方案、原子发布、文件 hash、回执与显式恢复。它还不支持本组的“找已有员工 + 只补缺员 + bobo 入群组织实际工作”。

本组优先复用员工创建、群配置、自然群聊、Work、材料、成果和回执底座。不要把旧工具换个名称后，宣称深度组织能力已经完成。

当前“核心会话只含 bobo、bobo 不进入员工群”的规则需要定向扩展；只允许真实 bobo 在新组织群里参与交流。它在群中的身份不使普通群任务获得核心创建工具，其他成员也不能取得核心身份。

## 7. 生命周期与授权

群与员工各自按现有边界管理。解散群清理这个群的配置、记录与受管会话空间，保留员工与员工其他会话；删除员工沿既有完整清理流程，不因此重建一个替代员工。

删除或清空原 bobo Conversation 不级联删除已发布的新员工或群。未提交组织操作先停止并等待实际执行退出，再按原操作归属清理；已提交对象仍保留真实身份。

新群不自动获得 bobo 旧会话全文、全部用户偏好或员工私有材料。背景摘要和材料的来源、范围、成员授权需逐项核对；创建群和加入成员不等于获得所有旧来源权限。

## 8. 首批成功标准

1. 用户可以在原 bobo 会话讨论多轮；没有明确组织请求时不生成员工、群或工作。
2. 明确组织请求优先选择已有员工，只创建确实缺少的角色。
3. 原会话保留；新群和参与员工入口来自已提交真实对象，打开后身份一致。
4. bobo 能在新群说明实际目标，员工各自交流、配合并发布可检查成果。
5. 用户可以从群成员入口继续私聊同一个员工，员工也能参与其他群。
6. 响应未知、取消、重启和清理不会重复创建对象、重发目标或重放已执行工作。
7. 创建成功、公开回复与业务交付分别验证，不把模型宣称或运行结束记为通过。
