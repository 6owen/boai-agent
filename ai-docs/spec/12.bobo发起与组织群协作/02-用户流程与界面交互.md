# 用户流程与界面交互

日期：2026-10-02。状态：待实施设计。首批范围见 [01](./01-产品定位与范围.md)，流程图见 [06](./06-界面线框与流程图.md)。

## 1. 延续当前会话界面

bobo 讨论继续显示在现有 bobo 会话分组下。原 Conversation 的身份和历史完整保留，新群不嵌套成它的子会话，也不替换原列表行。

新群以普通群聊显示在现有会话列表，并在通讯录沿用普通群入口。群名、成员头像、时间和消息预览使用真实数据；不新增“子 Agent 会话”分类或特殊后台人员列表。

本组不改 bobo 历史行的纯标题、紧凑缩进、标题编辑与独立设置/新会话图标合同，也不把用户当前截图中的测试标题设为新默认标题。

## 2. 从讨论到组织

### 2.1 讨论阶段

用户可以继续问“这件事怎么做”“我现有员工够不够”“需要什么角色”。bobo 给出建议或提出必要问题，原消息按普通会话保存。

这时不创建员工、群或 Work，不凭用户提到“团队”“写作”等词触发副作用。推荐角色也不是已创建员工，建议名字不能提供假联系人入口。

### 2.2 明确组织请求

以下是用户表达的例子，不是用关键词实现的固定模板：

| 用户表达 | bobo 应做的事 |
| --- | --- |
| “先讨论，不用建群” | 只继续讨论，不执行组织 |
| “用现有研究员和写作员，拉个群完成这篇文章” | 找到真实员工并组织群协作 |
| “帮我找合适的人，不够的就创建，然后拉群处理” | 先复用，补齐必要缺员，再创建群 |
| “只创建一个编辑员工，先不要拉群” | 按明确创建范围处理，不擅自发起群协作 |
| “让某位员工单独帮我做” | 保留直接找员工的路径，不强制建群 |

首批群协作入口仍是用户在 bobo 会话里发消息。授权已明确时，不增加一个必须逐项确认成员和方案的弹窗；缺少必要授权或关键目标时才在原会话询问。

### 2.3 有界找人

bobo 可以在正常回复中说明“准备找现有研究员和写作员”。查找实际结果包括员工名称、职责、真实能力与可用状态，不读取员工私聊正文来猜适配性。

重名员工用职责等真实配置区分，最终绑定稳定员工 ID。无法可靠确定用户点名对象时先澄清，不把同名联系人静默替换成另一人。

停用、删除或配置变化导致候选失效时，展示具体事实。用户限定只能使用某员工时，不能擅自换人；用户授权按能力找人时可以重新给出有依据的选择。

### 2.4 补齐缺员

在原回复说明已有员工覆盖的职责和需要补齐的角色。例如“研究和写作已有员工可承担，还缺编辑，我会创建编辑并组织群聊”。

准备中的配置与文件不显示成正式联系人，不提供能够打开半成品员工的入口。正式提交前仍处于原组织操作的准备状态，取消沿原请求处理。

创建连接、能力和权限采用现有规则，不在这个聊天流程额外加入模型选择、技能商店、权限总开关或配置向导。

## 3. 已创建群的真实入口

只有宿主确认对象已经提交后，bobo 回复才能展示可操作入口：

| 内容 | 数据要求 | 点击行为 |
| --- | --- | --- |
| 群名称与“进入群聊” | 已提交的明确 conversationId 与实际 title | 打开这个普通群，不再创建一个群 |
| 已有员工 | 原 employeeId，来源标注“已有员工” | 打开真实员工资料，按已有入口开始私聊 |
| 新建员工 | 已提交 employeeId，来源标注“本次创建” | 与通讯录和群成员入口使用同一身份 |
| 当前处理状态 | 实际组织/消息/工作回执 | 只展示已确认事实，不由流式文字生成状态 |

回复优先用一段简洁说明，再提供群和联系人链接或已有资源样式。不要为所有内部步骤铺满卡片，不把执行日志、文件暂存路径、请求 key 或模型预算表放进常规用户流程。

对象回执必须与原组织请求绑定，不能把最近创建的群猜成当前目标。流式生成中出现“群已建好”也不能提前启用入口。

首批对象发布与 bobo 群内首条说明同事务；说明由 bobo 模型实际生成并冻结，宿主不能编造一条员工消息。实际业务工作是否开始、交付是否成立仍须分别读取工作回执。

成功后不自动跳转、不自动关闭原会话、不清空输入、不改标题。用户可以读完 bobo 回复后再打开群；如果用户已切到其他会话，迟到结果也不能抢导航。

用户关闭回复中的群入口不会解散群。重复打开复用同一个 Conversation，不重复创建群、消息或工作。

## 4. 群内目标、分工与交流

首批新群真实成员包括 bobo 和选中员工，用户以本人身份参与。群头和成员资料采用已有群聊 UI，消息使用各成员自己的姓名和头像。

bobo 在群里的第一段实际说明至少包括目标、必要约束、预计交付和建议分工。该消息在准备阶段由模型生成，固定获准来源后随群发布。若需要员工先讨论方案，明确写“先讨论”；不能同时把这段话记作每位员工都已开始执行。

群 `teamSetup` 保存可编辑背景，不充当当前请求。保存或修改背景不发起新消息，不自动制造工作；首次处理通过真实公开消息和受控的工作受理路径发生，具体事务见 [03](./03-会话成员与协作合同.md)。

| 群里发生的事 | 展示与业务含义 |
| --- | --- |
| bobo 介绍目标和建议分工 | bobo 本人的真实消息；不替其他成员声明接受 |
| 员工表示承担自己的部分 | 员工自己的消息，并以实际工作记录确认执行 |
| 员工需要用户补充 | 明确提问，保持等待；用户通过原问题关联入口在群里补充后接续原工作，普通发言不自动解除等待 |
| 员工向另一成员请求配合 | 公开交流或明确接续，沿现有成员判断和依赖规则 |
| 员工发来成果 | 署名消息与真实成果入口，保持成果版本/来源 |
| bobo 汇总进展或成果 | 引用实际工作和成果，不冒充其他员工的发言 |

群成员可以独立回应和保持安静，不要求所有消息都先交 bobo 分发。用户可以直接 @ 某员工，或点击资料进入其私聊；这些入口沿既有身份和授权，不生成同名员工副本。

bobo 在群里组织交流不获得全体员工私有资源，也不向普通成员开放核心创建工具。群里发现还缺员工时，可以返回原核心讨论提出补齐需求，不能让普通群任务自报核心权限。

## 5. 原 bobo 会话继续存在

原会话中的进展摘要只读取本次明确关联且当前仍获准的群内事实。它可以显示“研究员的资料已提交，写作员仍等待选题确认”，但不能无证据把整个群汇总为“完成”。

用户仍可在原会话讨论下一步。普通补充消息不自动变成对群里全部工作的修改，也不自动把私人讨论广播给群；希望修改目标时应形成明确群消息或受理动作。

用户明确让 bobo 把某段补充带入群后，由 bobo 以自己身份发送获准内容，并绑定来源。仅有原会话新消息不能反复使群里已执行的工具重跑。

群里的直接提问和原会话里的讨论分开定位；跳转问题和成果使用具体消息/成果身份，不跳到一个猜测的最近结果。

## 6. 处理中、失败与未知

| 状态 | 用户可见内容 | 操作边界 |
| --- | --- | --- |
| 讨论 | bobo 的建议或必要问题 | 不显示创建进度，不产生正式对象 |
| 组织准备中 | 回复附近显示简洁的实际处理状态 | 沿现有停止入口，不在输入框上方加状态条 |
| 对象已提交 | 真实群与员工入口及已公开首条说明 | 不表示成员已开始执行或工作已交付 |
| 工作待调度/失败/中断 | 群已存在、目标已公开及具体工作状态 | 只核对原启动意图和工作，不重新组群或重发目标 |
| 员工/群未提交的失败 | 明确失败与保留的请求 | 确认原回执后才能重试原操作 |
| 响应未知 | “结果尚未核对，请保留本次请求”与核对入口 | 不自动换 key，不重复发起组织 |
| 取消 | 说明正在停止或已实际退出 | 未真实退出不说清理完成；已提交对象保留 |
| 重启中断 | 显示已提交对象及未完成步骤 | 只核对，不自动调用模型、建群或重发任务 |

创建/目标消息提交的具体原子范围由 [03](./03-会话成员与协作合同.md) 锁定。首批不提供“群已创建、首条说明尚未发表”的正常中间状态；界面仍分别核对对象存在、目标公开、工作执行与交付，不能用一个“成功”覆盖全部事实。

核对接口失败不能显示“没有创建”。未知时冻结已尝试内容和请求身份，新的用户输入可以保留为草稿，但不能悄悄覆盖原请求。

必要的继续或放弃入口只服务真实中断操作，不作为正常路径的审批向导。已执行或结果不明的工具不通过“重试”盲目重放。

## 7. 生命周期入口

清空/删除原 bobo 会话沿原流程处理，关联回执保留最小去重事实；不级联删除已创建员工或群，不据此重新组织已提交对象。

解散群沿现有群操作清理群自身，保留成员身份、workspace 和其他会话。删除员工沿现有通讯录流程清理员工，群中按既有成员撤权和历史保留边界处理。

旧回复的群或员工入口失效时，显示明确对象已删除/解散，不隐式恢复、找一个同名对象或把它替换为新版本身份。入口核对失败也不能导航到另一对象。

## 8. 交互一致性与验收

- 原 bobo 分组、普通群列表、员工资料、群设置和右侧任务/产物详情全部复用已有组件和页面作用域。
- 新入口沿全局主题、按钮表面、图标、键盘焦点和可访问名称；不引入新颜色系统或整页向导。
- 长名称可省略，但打开的真实对象和无障碍名称必须准确；同名员工不能按显示文本混淆。
- 打开群和员工资料保留各会话草稿/滚动；详情只出现在其所属主页面，隐藏页面停止读取。
- 等待与失败有文字说明；停止、核对和入口支持键盘，忙碌阶段防重复提交。
- 示例名字和成果只是设计样例，不进入默认数据，也不作为实际验收证据。

具体场景和验证记录统一落在 [05](./05-实施步骤与验收清单.md)，本文件不维护第二套进度表。
