# 运行时接线与代码映射

状态：**待实施规格，尚未接入源码，未执行本组测试。** 现状核对日期：2026-10-02。
本篇说明如何沿已有运行层接线；实体、来源授权、预算和恢复的权威定义见 [03-会话成员与协作合同.md](./03-会话成员与协作合同.md)，进度只登记于 [05](./05-实施步骤与验收清单.md)。

## 1. 先固定实现目标

用户在原 bobo 会话明确要求组织事情后，bobo 分析成员需求，先找已有员工，只为缺少的能力创建新员工，再建立独立普通群。
首批群包含 bobo 与实际参与的员工；bobo 以自己的身份在群中说明目标、安排分工，成员直接交流、配合和交付。
原 bobo Conversation 保持自己的 ID、`purpose=core`、`kind=direct`、成员和历史，除用户明确清空/删除外一直保留。
群不是 bobo 会话的子页面或短暂执行容器；用户可以从会话列表、通讯录和真实结果入口直接进入它。
用户明确要求“只创建员工、不要拉群”时，走员工创建支路：交付真实员工入口，原 bobo 会话保留，不隐式建群或执行新员工任务。

三条身份不变量：

1. 员工继续使用原 `DigitalAgent.id`、配置、工作区、能力和获准记忆；不能为一次群工作克隆成另一个员工。
2. `Conversation.agentIds` 只保存 Agent 身份，用户不加入该数组；模型实例、run 和工作项不是通讯录员工。
3. 群解散只结束该群配置、记录和受管会话空间，不删除参与员工的根 workspace 或其他会话。

## 4. 组织工具的宿主授权

核心工具权限必须同时核对：

- 当前调用员工是固定 `id=bobo && systemRole=core`，且配置版本仍有效。
- 请求确实来自原 `purpose=core` 会话中用户明确要求的组织任务，来源身份没有被清理或改绑。
- 当前是获准 task/组织执行阶段；普通 chat、decision、memory、report 和自动化没有该修改能力。
- 参与员工、用户授权范围、材料/记忆来源、组织请求版本及当前运行执行权仍有效。

不能以“只有一个成员”“名字叫 bobo”“群里包含 bobo”判断核心权限。
进入协作群后，bobo 使用该群获准上下文发言和协调；普通群中的成员消息不能授予创建员工/创建群权限。
首批群内 bobo 不持有组织工具。新的组织请求回到原 core 入口受理；后续是否支持群内组织，必须另行定义授权合同。

参与判断与宿主认领前就必须明确源 core 工作的 `scope/deliverable` 是找人/创建/组织交付，完整业务目标由受理请求保留。
不能先把完整业务 `main` 认领到 core，再在工具内改写范围或搬到群；已开始完整业务的旧 core Work 首批拒绝隐式转换，要求明确新组织请求并保留旧工作状态。
这涉及 BC0 的阶段合同核对及 BC3 的判断/认领接线，不能只新增一个工具便算完成。

找人查询只返回有界的员工 ID、姓名、职责、当前可用状态及真实能力摘要，不能批量读取所有员工私聊和工作区文件。
模型负责需求判断、候选比较和分工建议；宿主负责候选分页、员工版本复核、能力事实、ID 冻结、预算与原子发布。
已有员工无效/停用/改配置或不支持当前群协作时，返回可检查原因，不按名字静默找替代者。
ACP 员工当前不支持自主群协作，首批不把它包装为可用群成员；BYOK 员工继续使用自己的已配置模型连接。

## 5. 找旧员工与补齐缺员

旧 `TeamCreation.acceptAgentPlan` 只接受整套新成员定义，`freeze` 为每项分配新 ID，再生成不含 bobo 的默认群。
因此不能通过把已有员工名字写进旧方案达到复用；那会制造新的联系人和 workspace。

新组织用例应分清两种输入：

| 输入 | 处理 |
| --- | --- |
| 已有员工引用 | 精确员工 ID + 所见配置版本；发布时复核，保留原配置和 workspace |
| 缺员定义 | 宿主校验姓名/职责/人格与真实可用模型，冻结新 ID；不凭自然语言描述自动授予技能、命令或知识 |

复用现有“短事务受理/冻结 → 文件准备 → 完整 hash 核对 → 原子发布 → 安装内存投影”顺序。
原子发布的范围和组织/群首发回执以 03 为准，不能先向 renderer 暴露部分新员工或半个群，再让 UI 补保存。
所有旧成员无需新员工初始化；其被加入新群产生的是新的会话关系，不是一次人格重建。
稳定请求重入返回原结果；未知响应只能查询原回执，不以新 key、群名或再次工具调用制造第二个群。

BC2 还包含受控 employee-only 创建操作，具体 kind/共享类型沿 03：原 core Work 只承担员工创建交付，沿原预算、稳定请求/hash、受管文件准备和员工/回执原子发布。
该支路没有 group、群消息、群业务 root 或启动意图。复用本组新员工初始化和发布能力，不调用旧 `create_team` 后再丢弃/解散它创建的群。
入口仍通过独立 typed 来源授权、严格任务阶段与副作用回执；创建成功只提供员工资料/聊天入口，不引入后台单人执行或通讯录委派。

## 6. 独立群发布后的真实开场

“群已创建”和“群内工作已受理/已交付”分别记录，不能因成员与目录创建成功就宣布工作开始或完成。
首发受理沿 03 保存原用户明确请求、本次目标、实际成员、真实 bobo 发言与调度身份的关系。
本次 bobo 执行在提交组织方案前生成群目标说明，宿主将该消息正文与身份冻结；发布事务一起保存缺员、独立群、bobo 署名的首条目标消息和回执。
不能先发布空群，再通过新的模型调用补写一条无法与原回执对应的开场消息。

当前 `GroupScheduler.prepare` 构造的是 `user_message` 事件；不能直接塞入一条 bobo 消息，让群把它当用户命令执行。
实施时增加明确的组织开场受理/事件路径，验证真实 bobo 运行和来源授权；只在已提交启动意图下通过原群调度进入成员决策。
bobo 的群开场以 `senderType=agent`、`senderId=bobo`、该群 `conversationId` 及原生成来源身份保存，沿 03 的冻结/发布合同提交；不能凭空制造尚未运行的群 run/turn。
不得伪造 user 消息、由 renderer 拼出 bobo 消息，或把“分工建议”当员工已经接单/开工的证据。

群中的后续过程沿现有机制：成员读取自己获准的上下文，独立回应或不参与；明确任务才认领工作，点名/讨论不自动生成新 Work。
若某位负责人需要分工，可沿当前同群 `delegate_work` 创建真实工作，使用实际结果依赖与定向接续；群里可以直接看见员工自己的交流和成果。
稳定 `collaborationRequest` 共享一个 `budgetId` 和原绝对期限，源 core 组织 Work 与群内唯一业务 root 保持各自会话身份，通过宿主新增预算绑定授权沿同一账本执行。
`organize_and_execute` 在发布事务内同时冻结群内业务 root 和唯一启动意图；`organize_only` 只组群并说明目标，不制造业务 root。
提交后才唯一调度；不能因跨会话重新领取默认预算，也不能把两个工作伪装成跨会话父子或迁移旧 Work。
阶段调用回执、取消范围、额度追加和安全接续统一采用 03，禁止在适配器另起第二套额度。
不能单纯复制旧 Work 到新 `conversationId`，也不能把 bobo 原会话所有历史、材料和记忆作为群初始上下文。

## 7. 为什么不需要替换成原生 subagents/A2A

`createStageAgent` 每个阶段创建新的 SDK `Agent` 实例，但 `id`、姓名、模型、persona 和上下文来自同一个持久员工。
实例销毁仅释放该次资源，不删除通讯录员工或它的长期 workspace；把模型实例当“新员工”会破坏现有身份边界。
当前 `delegate_work` 已由宿主复核当前成员/材料授权并进入 `WorkRepository`，不需要把通讯录员工直接塞进 Mastra `agents:{}` 绕开产品运行层。

用户所说 A2A 是员工彼此沟通和协作的产品行为。首批都是本应用内的长期员工，消息与任务经同一宿主管理，无需为了群内交流引入跨服务 A2A 协议。
Agent Controller 也不是本组前置依赖。它不能代替员工身份、来源授权、业务交付证据、事务预算和实际退出边界。
远程员工/外部 A2A 服务、Controller 整体替换以及隐藏后台 subagents 执行，均不属于本组首批。

## 8. 工作区、来源与清理接线

`WorkspaceService.root(agentId)` 指向员工根 workspace；`session(agentId, conversationId)` 位于该员工根目录的 `sessions/` 下。
本组继续按 employee × group 准备 `work/` 和 `runs/`，群的公共受管目录只承载明确共享对象，不替代员工自己的工作空间。
新群材料需要明确成员授权；候选选择或加入群不授予读取员工私聊/原 core 历史/全部旧材料的能力。
成果仍按真实受管原件 hash、实际发布员工和具体消息登记；bobo 汇总结果不能改写成自己完成了员工的工作。

取消/删除/清理先挡住新受理与发布，等实际模型/文件/命令执行器退出后才释放容量和处理文件。
解散群沿既有群清理；删除员工沿既有员工清理，二者入口和影响范围不可合并。
旧成员根目录不在本次组织文件清理所有权内；重启仅核对已提交回执/文件/群/消息，不自动拉人、建群或重发开场。
文件外改或来源失效显性记录，保留受影响门禁；恢复不得靠重新调用模型或重放不明副作用证明成功。

## 9. 实施前必须同步的规则与验证入口

当前 AGENTS 明确“核心会话独立，不把核心助手加入员工群”，源码 `saveConversation` 同样拒绝 bobo 入 group。
这是本组计划中的明确规则差异：实施 BC0/BC2 时，仅为获准组织入口及其已发布群建立例外，并同步 AGENTS、相关 Header/`.folder.md` 与既有测试。
文档阶段保持当前运行合同，不能把待实施例外写成已经支持，也不能一次删除所有核心工具/普通群边界。

实施顺序对应 05：BC0 核对规则/现状 → BC1 有界找人 → BC2 缺员与群原子发布 → BC3 群开场/分工/真实交付 → BC4 恢复清理 → BC5 明确已有群复用。
BC2/BC3 的“发布 + 首条目标消息 + 工作受理/启动意图 + 共享预算”是一起交付的原子合同；不能把可启动但未接完整账本/回执的半成品开放给用户。
BC5 未实施前，本组组织默认新群；不能按标题、主题相似或员工组合相同自动复用旧群。
模块验证与 Electron BDD 要覆盖真实 ID/回执/消息/文件和业务状态；模型讨论成功或 SDK run 完成不能充当群协作验收证据。
本篇仅完成源码现状核对与待实施映射；测试数量、真实交付及人工评审证据只在实施后写入 05。
