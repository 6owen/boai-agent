# 动态工作流与执行编排

日期：2026-09-27。状态：**建议基线，工作流扩展未实现**。核对 `@mastra/core 1.71.0`、`@mastra/libsql 1.23.3`，不修改现有调度器或启用新执行入口。

## 1. 先区分四件事

| 层次 | 谁决定 | 典型用途 | 当前状态 |
| --- | --- | --- | --- |
| 产品成员自决协作 | 每位员工提出 reply/pass/wait/ask/handoff，宿主管理授权和提交 | 群内讨论、自然交流、成员按职责参与 | 已有 GroupScheduler 与普通 Agent；不是 Mastra workflow |
| 代码工作流 | 开发者定义步骤图；条件和输入可在运行时变化 | 查询→整理→审核；分支、并发、循环、暂停 | 框架提供，本项目未接入 |
| JSON Dynamic Workflow | 数据描述 schema 和步骤图，经框架验证后注册 | 用户或可视化编辑器保存可复用流程，无需改源码发布 | 安装版已提供，Beta；本项目未接入 |
| 模型生成计划 | 模型提出任务拆分/组件选择，宿主验证后决定执行 | 非固定任务的受控组合 | 不是任意自然语言计划自动执行；本项目未提供通用计划执行器 |

动态 Agent 是“运行时决定员工配置/模型/指令等”，不等于步骤图。固定流程接受运行时 `inputData`、RequestContext 或模型输出，也不因此变成 JSON Dynamic Workflow。模型能写 JSON 只是计划来源之一，框架不会替产品判断计划是否得到用户授权。

当前来源：[GroupScheduler](../../../src/runtime/group-scheduler.ts)、[AppService](../../../src/runtime/service.ts)、[MastraEngine](../../../src/runtime/adapters/mastra/engine.ts)。没有 `createWorkflow()` / `addDynamicWorkflow()` 的产品集成，不应把现有员工依赖关系显示成已实现的 Mastra 流程引擎。

## 2. 安装版支持哪些 primitive

### 代码工作流

| Primitive | 作用 | 产品适配注意点 |
| --- | --- | --- |
| `createStep`、`createWorkflow`、`.commit()` | 建立具有输入/输出 schema 的步骤图 | 第一步输入、相邻步骤数据和最终输出需要兼容 |
| `.then()` | 顺序执行 | 明确哪一步产生哪个产物或外部副作用 |
| `.map()` | 转换输入/步骤结果 | 不把所有前序上下文无差别传给每位员工 |
| `.parallel()` | 多个操作处理同一输入，并以 step ID 汇总结果 | 默认一个子步骤抛错会使并发块失败；允许部分成功须用类型化结果显式表达 |
| `.branch()` | 条件选出需执行的步骤 | 当前默认引擎执行所有命中的分支，独占路由须定义互斥条件，见下文 |
| `.foreach()` | 对数组逐项执行，可配置并发 | 默认并发 1；输入条数和并发上限由产品限制 |
| `.dowhile()`、`.dountil()` | 条件循环 | 两者都至少执行一次；必须另设次数、耗时、模型和费用上限 |
| 嵌套 workflow、Agent/tool step | 复用子流程、模型和工具能力 | 原生直接调用不能绕过员工装配、审批和预算适配层 |
| `suspend()` / `resume()`、run cancel | 等待外部输入、继续或取消执行 | 配合持久快照与产品审批；不能假设所有外部副作用会自动回滚 |

运行时输入、状态和条件只能改变既定图允许的路径；图内模型步骤可以生成结构化数据交给下一步，但仍须通过 schema 和业务校验。

**条件分支的安装文档存在冲突。** `docs-workflows-control-flow.md` 的部分段落/速查表称“第一个命中、仅一个分支”。但当前安装实现 `agent-BOxKOk3n.js` 中 `.branch()` 构造 `conditional`，`executeConditional()` 并发评估全部条件、收集全部 `truthyIndexes`，再并发执行这些步骤；与 dynamic definition reference 的“全部命中都执行”一致。本方案以该安装源码为准，不依赖错误的独占路由假设。后续版本升级应重新核对并加入行为回归。

### JSON Dynamic Workflow

该版 Dynamic workflows 明确标为 **Beta，可能不经 major 升级发生破坏性变更**。主要接口：

- `mastra.addDynamicWorkflow(definition)`：验证、注册图；存储支持时同时持久化。
- `mastra.addDynamicWorkflows(definitions)`：按依赖处理一组定义，统一验证。
- `mastra.getWorkflow(id)` → `workflow.createRun()` → `run.start({ inputData })`：注册后沿用工作流运行 API。
- 定义包含 JSON Schema 和 `graph`；不是可执行 JavaScript 字符串，不支持任意闭包。

定义可以由应用、编辑器或 LLM 产生。图可引用预先注册的 agent、classifier、tool、workflow；支持 mapping、parallel、conditional、foreach、loop、sleep 和 sleepUntil。

该版本的重要格式限制：

| 项目 | 已核验限制 |
| --- | --- |
| 组件引用 | agent/workflow 使用已注册 ID；tool 使用 Mastra tools 注册键；存在性验证不等于产品授权 |
| 输入映射 | `mapping` 只能位于图顶层，不能直接塞进 parallel/conditional/foreach/loop 容器 |
| 条件与循环 | 持久定义采用 JSON predicate DSL；不能保存任意条件函数 |
| 并发/条件子项 | 每个子项必须是允许的单步骤类型；复杂组合可先构造成受控嵌套 workflow |
| 等待时间 | 存储图的 sleep duration / sleepUntil date 使用字面值；运行时计算等待使用代码工作流 |
| Agent/tool 序列化选项 | 只有文档允许的选项持久化，不能假设闭包、回调或所有 call options 会随图保存 |
| 校验 | 检查结构、引用和 schema 数据流；不能代替来源授权、内容可信度与副作用审批 |
| 持久化 | 依赖支持 `workflowDefinitions` 的 storage；无相应存储仍可内存注册，但重启丢失定义 |

安装 `@mastra/libsql` 的类型中提供 `WorkflowDefinitionsLibSQL` 与 `WorkflowsLibSQL`：前者保存定义，后者保存运行快照，不能把“定义可持久”理解为“本项目已经实现所有执行恢复”。

相同 workflow ID 的新定义会替换持久定义和活跃注册；已开始的运行继续原图，新运行使用新图。产品仍应保存不可变的版本标识和定义 hash，避免界面只展示最新图而误导旧运行的恢复或审计。

## 3. 产品分层建议

```text
自然群聊：GroupScheduler → 每位员工自主判断/公开回复
                                      ↓ 明确的 task 请求与授权
任务执行服务 → 固定模板 / 已验证的计划版本
             → Mastra workflow runtime
             → 获准的员工步骤/工具适配器
             → 现有 EngineContext、审批、预算、取消、产物发布
```

工作流处理明确的任务步骤，群聊层仍管理谁获准公开发言。不要让每个工作流步骤直接往 IM transcript 插入一条员工回复；步骤进展、工具结果、最终产物和公开消息应保留各自状态。最终发言仍需要产品层防重复提交。

第一版优先使用 `createStep` 包装受控的员工执行入口。普通 `.agent()` 或动态 agent/tool 引用可能直接调用框架能力，不能假定它自动复用本项目的 `EngineContext`、文件范围、命令审批、消息边界和 usage 回调。只有适配器覆盖这些职责后，才把组件加入动态计划白名单。

每个步骤运行时装配自己的员工、模型和当前授权；不在共享全局 Agent 上保存会串到其他员工的可变工作目录/会话状态。队友读取已发布结果，不读取其他员工私有目录或记忆。

## 4. W1：可恢复的明确步骤

目标：先用一个有实际需求的任务模板验证可靠执行，例如“整理指定资料→形成草稿→审核→发布产物”。模板不改变普通问候、讨论和自主 pass 的行为。

建议记录职责，字段属于设计，不是当前已实现接口：

| 记录 | 需要固定的信息 |
| --- | --- |
| Workflow definition version | 模板 ID、不可变版本/hash、输入/输出 schema、允许的步骤类型 |
| Product task / framework run 映射 | conversationId、turnId、发起消息、用户请求范围、框架 runId |
| Step execution | stepId、attempt、员工/配置版本、输入来源、状态、时间、usage、输出/产物引用 |
| Approval | 操作类型、具体参数/hash、批准人/时间、适用步骤和有效条件 |
| Budget | 模型调用、输出 token、耗时、循环次数、并发、文件/外部操作上限及已消耗值 |
| Side-effect ledger | 幂等键、操作意图、执行状态、外部回执/产物 ID、恢复决策 |

以上记录关联现有产品 task/run，而不是立刻改名替换全部 AgentRun。选择单个存储与提交责任，避免产品任务成功而框架失败、或框架成功而产物尚未登记时界面给出错误结论。

### 恢复、审批和副作用

Mastra 的 suspend/resume 与快照提供流程恢复基础，不等于外部副作用 exactly-once。尤其进程可能在“文件/网络操作已完成”与“结果已持久化”之间崩溃。

- 有外部幂等键的操作复用相同 key；本地产物采用受控唯一 ID、原子写入和提交记录。
- 无法判断是否完成的操作标为待核实，不自动重放支付、发送、覆盖等副作用。
- 恢复时重新检查员工是否启用、是否仍是成员、绑定资源/技能是否仍获准，以及审批参数是否改变。
- 工作区进程和子进程响应 AbortSignal；取消后不再开始新步骤或新模型调用；已发生副作用如实保留结果。
- 重试次数与 usage 必须计入同一个任务预算；不能让 workflow retry 叠加 Agent/SDK retry 形成隐藏请求。
- 计划/快照保存资源和凭据引用，恢复时通过宿主解析。不能把 API Key 或整棵私有目录复制进 JSON 定义、日志或快照。

退出条件：

1. 一个实际模板使用真实框架步骤、输入/输出校验和本地持久快照；进度与产物能从产品界面追踪。
2. 单步失败、并发部分失败、等待审批、取消、超时、重启恢复都有明确结果；不把空内容当成功。
3. 模型、步骤、重试和恢复均受预算约束；取消后的补充请求为零。
4. 在副作用完成前后分别中断进程，证明不会无条件重放；不能确定的情况有待核实状态。
5. 移除成员或撤销技能后，旧快照不能继续执行受撤销能力；输出仍留在原任务授权空间。
6. 群聊自主参与、chat 无任务工具、逐次命令审批和公开回复防重复保持现状。

## 5. W2：受控动态计划

目标：用户确需非固定步骤组合时，让模型提出可检查计划，宿主把合法计划转为受控 JSON 工作流。W1 的可靠执行、预算与恢复适配是前置条件。

### 计划与执行分开

1. 模型仅接收当前请求与获准组件清单，输出结构化计划，不输出任意代码或未登记工具名。
2. 宿主校验请求范围、员工/组件权限、输入来源、依赖、步骤数、嵌套深度、并发、循环上限、输出和总预算。
3. Mastra 再做图结构、注册引用和 schema 流校验；通过前不注册为可执行业务流程。
4. 保存具体计划版本及 hash。任务授权必须对应这一版本；需要用户批准的新增副作用按现有产品规则展示具体操作，不因模型声称“已批准”而放行。
5. 通过受控适配器执行，产物/状态回到产品任务。步骤结果是后续步骤的数据，不是扩大权限的指令。

允许模型在运行中建议改计划，但不能原地改写正在执行的图和其已获批准含义。新建议生成新版本或新的子任务，重新核对新增步骤/资源/预算；已完成结果有来源地复用，外部副作用不重做。

不把“自然群聊已有待办依赖”升级成永久自动化或定时执行。sleepUntil 表示工作流等待，不等于桌面应用退出后仍有操作系统级调度。独立的 [自动化 A1/A2](./06-自动化与定时执行.md) 已补充原生 Mastra schedules、本地生命周期、离线、睡眠、重启与漏跑策略；A1 的单员工任务只需薄包装 workflow，不以 W1 多步业务模板或 W2 动态图为前提。需要步骤级恢复时再把本篇 W1 模板作为自动化目标接入。

### 动态图必须限制的面

- 白名单注册表按当前任务可用能力生成；同一个 Mastra 实例中存在的全部工具不是可用清单。
- 图大小、foreach 输入量、parallel 并发、循环最大次数、嵌套 workflow 深度和递归引用必须有限。
- 每步进入、恢复和执行前检查当前权限；模型生成依赖不创建新成员或新资源权限。
- 工作流图和已注册代码只使用已验证的版本；升级后旧快照可否恢复需迁移或明确拒绝。
- 成本预算覆盖规划、schema 修复、分类、执行、步骤重试和记忆后台处理。达到预算时保持可解释的终态。
- 动态 API 的全局管理权限不能直接暴露给模型；注册/替换定义走产品服务，不能由模型工具任意覆盖别的任务模板。

退出条件：

1. 两类以上真实任务可用同一受控计划 schema 组合执行，并能回退到 W1 模板或明确说明不支持。
2. 非法工具/员工、跨群资源、超大 foreach、无限循环、递归图、缺失依赖和输入类型不匹配均在执行前被拒绝。
3. 计划版本可检查；旧运行继续旧版本，编辑后的新图不劫持旧批准或旧 run。
4. 模型的规划/修复不是无限重试；无预算、取消或撤权后不再请求下一步模型。
5. W1 的恢复、幂等、命令审批、产物和公开消息验收在动态图上同样成立。
