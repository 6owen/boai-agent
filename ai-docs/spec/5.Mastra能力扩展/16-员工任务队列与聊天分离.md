# 员工任务队列与聊天关联

## 1. 产品边界（以最新截图要求为准）

数字员工是一等公民，持续拥有身份、能力、工作区、记忆、主聊天和自己的任务。消息、任务及定时触发交给员工执行；普通聊天不自动变成任务。

- sidebar及定时任务页面保持计划配置、触发和记录管理。员工会话header右侧“任务”按钮打开该员工右侧任务面板，与聊天同时显示。
- 主header保留员工会话标题与原菜单；右侧任务面板使用共享详情header，提供全局shadcn看板/列表切换及创建任务按钮。
- 五个任务状态为待办、进行中、待确认、完成、已关闭；卡片和任务Dialog都能手动改状态。运行正常结束并不自动证明业务任务完成。
- 看板使用@dnd-kit/core跨列拖动修改状态，沿原修订校验保存；失败保留原列。DragOverlay挂到document.body，拖拽传感器和自动滚动由库处理。卡片和各滚动区使用全局Card/ScrollArea，留白置于内容内、滚动条贴边。任务Dialog左侧平铺属性与创建/更新时间，右侧为要求与会话；移除弹窗执行记录和时间折叠，顶部沿共享scroll-fade。
- 点击一个任务打开Dialog，展示要求、负责人、状态、创建/更新时间及完整的共享ChatView。每个任务有该员工独立的持久会话，关闭Dialog不停止执行。
- 原主聊天投影、任务消息关联和执行过程继续保留。定时记录在定时页右侧打开原执行详情，聊天图标才定位员工聊天并保留原执行过程；不在定时页挂载任务面板，自动触发不抢占页面。
- 复用agentTasks作为唯一任务记录。执行借用employee-task用途的手动投递配置；配置不冒充任务，也不进入定时计划列表。

## 2. 工作上下文与原生Session

- 打开任务只创建/读取任务会话，不运行模型。开始执行或明确发送任务消息才受理执行；同任务后续消息进入同一sessionConversationId，不同任务不共享工作上下文。
- ChatView的输入、材料、审批、问题回复、原生补充和消息回执复用原协议。受理请求冻结身份，重发/重启先核对原回执。
- Codex/Claude等依旧管理原生循环与session。BOAI按任务会话提供上下文归属；兼容原生session续接，不兼容时沿原机制换新，不能保证后端opaque session永不变化。
- 新单员工计划默认独立会话；旧员工主聊天计划的未来执行使用独立快照，并分别核对原计划与实际会话权限，不改写计划、不搬移旧记录。群计划、监控及已有明确独立上下文保持原范围。
- 旧执行记录进入任务时可复用仍有效的独立会话。原执行在主聊天的历史保持原位置，任务Dialog历史可查看原过程；打开任务不会自动重放历史。
- 主聊天继续按原事务投影指令、回复和Run；已清空消息不复活。删除单次执行日志保留持久任务及其会话。

继续复用agentTasks、AutomationDefinition、AutomationOccurrence、Work、Run和原AgentEngine，不安装第二套内核。Mastra Background Tasks是后台工具能力，Goals是线程目标机制；本改动不宣称启用两者。UI布局或session选择本身不能解决超大工具定义、摘要耗尽、浏览器超时等独立故障。

## 3. 队列与恢复合同

1. 同员工任务沿持久FIFO执行；主聊天正在执行时，新任务排队，实际执行退出后才能派发。
2. 排队认领复核版本、权限、容量；只有尚未投递的pending记录可恢复。已开始、未知回执或备份恢复后的工作不自动重放。
3. 排队取消不调用Agent；运行中停止等待真实适配器退出。失败、完成或停止后可处理下一项，不把一条失败永久卡成忙碌。
4. 任务身份与执行记录独立于session：继续同项工作沿原来源；再次运行产生新记录，不覆盖旧结果。
5. 已有计划的重复周期仍沿重叠防护，不无限堆积同计划；界面排序不改变受理顺序。
6. 任务完成、执行正常退出、成果交付和通知送达各自按真实证据记录。

## 7. 员工持久任务增量（历史阶段，状态与会话策略已由第8节替代）

用户明确确认补齐长期任务：前一轮恢复主聊天与关联入口，但没有完成独立任务生命周期，不能称为完整的员工任务管理。

### 已实现的产品行为

- 员工主聊天标题“任务”打开其右侧任务列表，包含明确创建、消息转换和定时执行产生的任务；定时任务侧栏/页面和通讯录入口保持原归属。
- 新建任务填写名称与要求，先保存待办；明确“加入执行队列”才运行。消息工具栏“设为员工任务”登记同一来源，不重复执行原消息，原聊天/原执行过程可以定位。
- 状态包括待办、进行中、等待补充、待处理、已完成。普通长期任务可标记完成、重新打开；某次执行结束不自行证明整个长期任务完成。定时实例沿原已交付事实自动完成；失败/停止及人工等待进入对应状态。
- 同一个任务可以反复补充要求并继续执行，新增执行记录挂在原taskId下，历史不被覆盖；每次输入和结果继续进入员工主聊天，同一员工仍沿原FIFO与原生session兼容规则；有仍有效的明确旧上下文时续用它，首次任务才默认员工主聊天。
- 任务详情保留每次运行的停止、取消排队、聊天定位与原执行过程。等待原问题时回到原聊天补充，不创建新运行来绕过等待。
- 任务要求独立于聊天历史保留；清空后来源显示已清理，任务仍可继续。执行记录若被明确删除，原记录不伪造恢复。

### 持久化与兼容

- 原agentTasks是唯一任务记录；新字段为description、source、sourceKind、latestOccurrenceId。原tasks.*工具仍是进度登记，单独调用它们不会启动Agent。
- AutomationOccurrence增加taskId，任务版本和归属与队列受理同事务检查；运行回执采用稳定请求身份，重复提交不创建第二次执行。无论渲染器是否在场，运行状态均由原持久记录驱动。
- 旧员工执行记录及旧手动任务只补任务关联，绝不重新执行；旧手动配置迁移保存最小标记，明确删除的任务不因配置迁移重建。
- 列表和执行历史在SQL中过滤员工/状态/taskId后分页。来源只读取匹配员工与消息的有界运行摘要，不把聊天全文或执行日志塞进任务列表。
