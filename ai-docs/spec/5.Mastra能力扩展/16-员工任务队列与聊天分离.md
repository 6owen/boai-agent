# 员工任务队列与聊天分离

## 1. 产品边界

员工仍是一等公民，拥有配置、工作区、日常聊天及任务。本次用户纠正明确禁止将定时任务改为全局任务页；任务入口属于具体员工，不把全部聊天或历史Work自动转成任务。

- 会话页用于日常沟通。普通消息仍可使用员工原有工具及本机Agent原生能力。
- sidebar和原页面保持“定时任务”，仍负责计划配置、触发和执行记录。
- 员工会话标题提供“任务”入口，面板固定属于该员工的主会话。定时执行记录、定位执行消息和通讯录任务入口，都先进入该员工主会话，再打开会话右侧任务；定时任务页和通讯录页不挂载员工任务面板。
- 面板按固定员工身份展示当前执行、队列、普通任务和历史；复用隐藏的员工主私聊，不把任务私有上下文作为会话主区，也不创建第二个主私聊。
- 普通任务使用独立purpose标记；服务端在分页前区分普通员工任务与定时计划，不混入定时计划列表和全局计划历史。
- 普通任务创建默认手动频率。先保存任务，再点击“加入执行队列”；定时计划沿原时钟受理。一次任务定义可以显式运行多次，每次有独立occurrence及上下文。
- 每次新建独立任务上下文的执行都在员工右侧任务面板阅读指令、结果、审批和补充问题；执行过程仍读取同一个Run。任务不再向员工主聊天复制指令、流式回复或执行过程。
- 任务补充只沿原问题身份、原预算和回执继续；修订成果沿原成果协议。新的独立工作从任务入口创建，任务详情不发送无归属的普通新轮次。
- 旧已公开到主聊天的记录保持可读；旧明确绑定existing-conversation的计划保持其授权和来源，过程详情兼容读取，不在后台改绑或重新授权。旧群共享聊天和监控不静默转换。

## 2. 与参考能力的对应

[Mastra Background Tasks](https://mastra.ai/docs/harness/background-tasks)解决长耗时工具在后台运行、任务状态持久化及结果回到Agent的问题；它不是员工待办列表。[Mastra Goals](https://mastra.ai/docs/harness/goals)是thread上的持久目标和候选答案复核机制，也不直接定义多项员工任务的排队方式。

[Raft任务文档](https://github.com/botiverse/raft-source/blob/main/manual/agent-knowledge/task.md)把任务作为带状态和负责人元数据的消息，并在任务面板呈现。BOAI参考其独立任务入口及讨论关联，未复制其源码。

此次继续复用BOAI的AutomationDefinition、AutomationOccurrence、Work、Run及原AgentEngine，不安装第二套运行内核，不把Codex/Claude/Pi包进Mastra目标循环。没有因本次UI/队列修改宣称已启用SDK Background Tasks或Goals。模型摘要耗尽、工具超时和供应商错误仍需各自处理，拆页面本身不能修复这些运行故障。

## 3. 队列与恢复合同

1. 繁忙或全局容量已满时，受理持久化为queued，保存原计划、授权指纹、预算、任务上下文、dispatch意图及单调队列顺序；同一请求仍幂等。
2. 同一员工只执行一个活动任务；群任务占用其参与员工。不同员工可在现有全局容量内并行。普通聊天不占用员工任务队列。
3. 排队按受理顺序认领；左栏标签/拖拽仅改变展示，不改变执行顺序。原计划已有未完成occurrence时，新周期仍沿既有重叠防护留跳过记录，不无限累积相同计划的重复执行。
4. 认领前在事务中复核任务版本、授权、当前上下文及容量；配置变化转为需核对。只有queued+pending意图可以变为admitted，开始后不会再认领。
5. 排队取消直接结束该记录，不调用员工。执行中停止保留cancelling直到原适配器实际退出；失败/完成/取消后允许下一项。等待补充/等待工作释放计算槽，继续时重新申请，不能越过同员工活动任务。
6. 普通应用重启保留未投递的queued记录并重新核对后启动；已受理但投递状态不明、已经开始或恢复自备份的记录均不自动重放。退出/备份时停止新认领。
7. 任务通知、实际执行完成和交付证据仍是不同事实。页面继续显示真实等待、失败、部分交付和需核对状态，不将“运行结束”改称已交付。
