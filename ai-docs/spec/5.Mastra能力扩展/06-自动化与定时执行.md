## 1. 结论与首期范围

**首期复用本地 Mastra 内置 scheduler，BoAI 自建自动化产品层和受控投递适配器。** 不另写一套持续运行的 cron loop，不要求 Mastra Cloud，不用 `sleep()` 循环模拟日程。

建议 A1 先完成“每天在指定时间，让一个已有 BYOK 员工处理明确任务，并把结果交付到指定单聊”。这可以基于现有 Mastra Agent 完成；不必等待新的 Memory、ACP、A2A、浏览器或动态工作流。调度所需的薄包装 workflow 是基础设施，不是要求先完成 W1 多步骤业务模板。

普通受限文件工具、Skills 说明及参考资料读取依赖 [S1 文件与技能授权适配](./03-Sandbox文件系统与Skills.md)；命令、脚本以及需要实际执行的技能依赖同篇 S2 的授权执行边界。读取脚本不等于执行脚本，文件工具无需等待 S2。A1 仍建议先交付纯文本任务，再按已完成的 S1/S2 能力开放相应任务。群聊自动化在 A2 接入既有群任务入口，不能绕过员工自决、发言授权和公开提交。

首期运行承诺是：**应用进程及本地运行时存活时调度；真正退出后不执行；重新打开或系统唤醒后只做有限补偿。** 关闭窗口、退出应用、系统睡眠、网络断开须分别显示，不能统一称为“后台”。

## 2. 现状与 Mastra 能力边界

### 2.1 本项目当前没有实际定时执行

- 定时任务页面目前只有入口、列表/详情占位；没有自动化配置存储或执行器。
- `GroupScheduler` 处理群聊事件、轮次和成员运行，不是按时钟触发的 scheduler。
- `MastraEngine` 为每次执行装配普通 Agent；当前没有产品级 `new Mastra(...)`、`createWorkflow()` 或 `mastra.schedules` 集成。
- ProductStore 使用 `@libsql/client`。已安装 `@mastra/libsql` 不代表已有 `LibSQLStore`、schedule 表或 workflow 快照。
- Electron 主进程启动 utility process，真正退出时停止它。当前 macOS 关闭最后窗口不会自动退出进程；Windows/Linux 关闭最后窗口会退出。定时能力必须据实际进程状态说明，不能按窗口是否可见推断。

源码：[AppService](../../../packages/runtime/src/service.ts)、[GroupScheduler](../../../packages/runtime/src/group-scheduler.ts)、[MastraEngine](../../../packages/runtime/src/adapters/mastra/engine.ts)、[运行时入口](../../../apps/electron/src/worker/index.ts)、[主进程](../../../apps/electron/src/main/main.ts)。

### 2.2 已核验的框架能力

| 能力 | 安装版实际提供 | BoAI 仍需实现 |
| --- | --- | --- |
| `createWorkflow({ schedule })` | 声明 cron/timezone/input；自动使用 evented engine，配支持并发更新的 storage | 固定代码任务的版本、权限、交付和状态映射 |
| `mastra.schedules` | 持久化 agent/workflow 日程的增删改查、暂停、恢复、立即触发；Beta | 用户任务配置、产品授权、幂等、执行记录和可理解的 UI |
| 本地 SchedulerWorker | 定期读取到期行、原子认领、发布事件；不负责员工实际执行 | Electron 启停集成、到期补偿、失败对账与运行健康状态 |
| `.sleep()` / `.sleepUntil()` | 工作流内相对/绝对时间等待 | 进程退出后的唤醒、持久到期投递；不能当作周期日程注册 |
| `suspend()` / `resume()` | 保存暂停快照，恢复指定步骤，可跨重启读取快照 | 审批记录、执行器重建、恢复授权检查和副作用去重 |
| Background tasks | 长工具调用脱离当前模型循环；持久记录、并发、取消、暂停等 | 与产品任务/消息/记忆的适配、跨重启执行器重建和交付 |

官方依据：[Scheduled workflows](https://mastra.ai/docs/workflows/scheduled-workflows)、[Schedules 概念](https://mastra.ai/docs/harness/schedules)、[Schedules API](https://mastra.ai/reference/schedules/overview)。这些是 SDK 运行能力，不以购买云服务为前提；本地应用仍必须保持执行进程运行。

### 2.3 必须保留的源码限制

1. 内置 scheduler 默认每 10 秒 tick，启动时立即 tick。它不是实时精确闹钟；建议产品以分钟为最小配置单位，展示预计时间和实际开始时间。
2. Electron 手工嵌入应显式管理 `mastra.startWorkers()` 与 `mastra.shutdown()`，先注册固定包装 workflow、初始化存储和产品服务。不要把服务端启动脚手架的自动生命周期假定为 Electron 已具备。
3. 当前实现先 CAS 推进 `nextFireAt`，再发布执行事件，最后记录 trigger。这三步不是一个端到端事务。进程可能在认领后、产品受理前退出，不能宣称恰好执行一次。
4. 过期日程默认触发保存的旧 `nextFireAt` 一次，再以实际当前时间计算下一次；不会自动逐次补完全部历史。暂停后恢复同样从当前时间重算下一次。
5. workflow trigger 的 `published` 只表示事件发布，后续不会自动改成业务执行成功。员工运行失败不能在自动化列表被显示成“成功”。
6. 调度目标长期未注册会被当前 scheduler 清理。固定包装 workflow 必须先就绪；某员工被删除只能阻止产品任务，不应让员工 ID 成为唯一框架调度目标。
7. 当前 evented `sleep` / `sleepUntil` 实现使用 `setTimeout`。持久化快照不会让关闭的 Electron 自行醒来，也不能据此保证计时器跨崩溃继续。
8. Background tasks 在重启后恢复 suspended 工具时，需要重新 `registerTaskContext` 登记执行器；闭包不会被存储还原。它也可能写入框架 memory，不能直接作为产品公开消息或长期记忆的新写入入口。

[Sleep](https://mastra.ai/reference/workflows/workflow-methods/sleep)、[SleepUntil](https://mastra.ai/reference/workflows/workflow-methods/sleepUntil)、[Suspend and resume](https://mastra.ai/docs/workflows/suspend-and-resume)、[Background tasks](https://mastra.ai/docs/harness/background-tasks) 描述的是不同执行机制，不能相互替代。

官方 [Workers 文档](https://mastra.ai/docs/deployment/workers) 的多 scheduler 提示与当前源码的 CAS 去重描述存在差异。本计划固定一个桌面 runtime 调度所有本地任务，不据 CAS 推导分布式恰好一次。默认内存 PubSub 也不是持久消息队列；分进程/云部署另列 A3。

## 3. 谁触发、谁执行、谁交付

```text
定时任务页面 → AutomationService → Mastra schedules（唯一时钟）
                                    ↓ 到期
                        固定 evented dispatch workflow
                                    ↓
                  产品受理/去重/权限/并发/预算检查
                         ↙                    ↘
                  单员工任务入口          群任务入口（A2）
                         ↓                    ↓
                  EmployeeExecutor      GroupScheduler
                         ↓                    ↓
                  当前 Mastra Agent / 获准 execution backend
                                    ↓
                  持久执行结果 → 产品公开提交 → 通知
```

Mastra 负责日程触发和框架运行。BoAI 负责“哪个用户配置、哪个员工/群、哪些资源、哪些动作被授权、结果送到哪里”。Renderer 只能调用白名单 IPC，不接触 Mastra、数据库、密钥或计时器。

用户在 UI 动态创建的任务建议通过 `mastra.schedules.create({ workflowId, ... })` 管理。`createWorkflow({ schedule })` 更适合开发者写死的内置日程；不能把每个用户配置写回应用源码。不得同时为同一任务保留声明式与运行时日程。

包装 workflow 使用固定、版本化 ID，例如 `boai-automation-dispatch-v1`，并显式采用安装版支持的 evented 工厂；不能假定运行时创建 schedule 会把普通 workflow 自动升级。schedule 输入仅携带 `automationId`、配置 revision 等可序列化引用，执行时从产品库重新读取配置与授权，不固化 API key 或放大权限。

**首期不直接把任意员工注册成原生 agent schedule 的 target。** 原生无 thread 时直接 `agent.generate()`，有 thread 时发送 framework signal，都不会自动经过本项目的消息、审批、资源和群聊规则。包装 workflow 的 step 必须调用受控产品入口，而不是直接 `.agent()` 绕过它。

## 4. 持久模型与配置一致性

以下是拟新增的产品模型，名称在契约阶段冻结，不是当前已存在的字段。

| 模型 | 最低信息 | 权威与约束 |
| --- | --- | --- |
| AutomationDefinition | ID、名称、任务指令、启用状态、revision、cron、IANA 时区、目标、预算、错过/并发/通知策略 | 产品配置权威；编辑采用版本冲突检查 |
| ScheduleBinding | automation/revision、Mastra schedule ID、固定 workflow ID/version、同步状态和错误 | 框架调度行是配置的执行投影；保存框架实际返回的 ID，不自行猜前缀 |
| AutomationOccurrence | occurrence ID、计划时间 UTC、实际触发时间、来源、revision、去重键、状态/原因 | 一次计划触发的事实；重试不新建另一份同槽发生记录 |
| AutomationExecution | occurrence、attempt、目标会话/turn、员工/产品 run、框架 run、backend、开始/结束、用量/产物/错误 | 区分触发、受理、运行和交付；绑定不可变配置快照 |
| DeliveryRecord | execution、目标会话、公开消息/产物 ID、提交状态、通知状态 | 消息和通知各自去重；重试通知不重跑模型 |
| EffectRecord | execution/step、动作摘要、审批、幂等键、请求/回执、未知结果标记 | A2 可靠副作用基础；不能把超时直接当作未执行 |

ProductStore 保留自动化和产品执行记录；Mastra LibSQLStore 保存 schedule、trigger、workflow 快照。建议框架状态使用独立数据库文件，由同一 runtime 管理，避免与现有通用记录表混写；具体文件名在存储契约冻结时确定。

两个数据库不能假装共用一个事务。保存配置先写产品定义及待同步操作，再由适配器幂等同步到 Mastra；同步失败显示“尚未启用/配置待同步”。启动时对账 revision、暂停状态、缺失绑定。修改后旧触发到达时先检查 revision，记录已过期，不执行旧指令。

暂停阻止未来受理，**不自动取消已经开始的运行**；取消本次执行和暂停日程是两个操作。删除建议软删除产品定义、暂停/删除框架日程，但保留 occurrence、执行与交付历史；Mastra 删除 schedule 会同时删除其 trigger history，产品审计不能只依赖该表。

备份必须包含产品表、框架存储、任务工作区引用及 schema 版本，并协调一致性快照。恢复到另一份数据目录后默认暂停全部日程，避免备份副本与原应用一起触发；本机凭据仍走 vault，不写入导出的任务 JSON。

A2 完成上述完整备份前，A1 必须给现有备份/恢复入口加兼容检查：已有自动化数据却无法完整保存或恢复时，明确阻止该操作，不能导出看似成功但遗漏框架状态的备份。没有自动化数据的原 v0.2.2 备份流程继续可用；不得用清空自动化历史来绕过检查。

## 5. 时间、错过执行与运行条件

### 5.1 时区和 DST

- UI 保存明确 IANA 时区，初次以设备时区作为可见默认值；保存后旅行或系统时区变化不暗改任务。UTC 时间只用于排序与去重，显示附本地日期、时区/偏移。
- A1 建议只开放每天/每周的时间选择，生成标准 cron，预览未来 5 次时间；高级 cron、一次性任意日期提醒可后续增加，不能借 `sleepUntil` 宣称一次性持久调度已完成。
- 建议日历时间语义：春季不存在的本地时刻跳过并可查询原因；秋季重复的本地时刻只执行一次。重复时刻用“时区＋当地日期时间＋配置 revision”去重，同时保留实际 UTC 时间。
- Mastra 当前调用 Croner 计算时间，没有本产品专用 DST 策略参数。A1 必须用安装版计算器核对跳时/重复时间行为；适配层校验输出是否符合所选本地时间，必要时记录跳过，不能另启一个调度 loop。未覆盖的复杂 cron 不开放。
- 日程调整后按新 revision 从当前时间计算下一次，不补旧版本；系统时钟回拨不让已完成的槽重跑。仅有进程内 timeout 的耗时判断不能替代持久 deadline。

### 5.2 建议首期错过策略

首期建议固定“有限补偿”：重新启动/唤醒时，保存的到期槽距离现在不超过 **10 分钟**，最多补一次；超过窗口记录“应用未运行，已跳过”，并进入下一个正常槽。这里补的是保存的到期槽，**不是补齐关机期间全部次数，也不承诺选择最近一次错过槽**。

Mastra 原生恢复会发布一个旧槽，因此包装入口在真正调用员工前检查 `scheduledFor` 和 grace window。过期 wrapper 可以被启动，但不消耗模型调用或执行工具。长时间停机产生的中间次数可用一条有起止范围的补偿记录解释，避免无限枚举。

产品适配器必须可靠取得原计划时间。当前 workflow step 输入不会自动多出 `scheduledFireAt`，它在 trigger 表及安装版 `sched_<scheduleId>_<timestamp>` run ID 中。优先关联正式 trigger 记录；若启动早于 trigger 入库，只能在封装且版本固定的适配器内校验完整 schedule ID 前缀并解析时间，再异步对账。不能散落字符串解析或拿 `Date.now()` 冒充计划时间。

| 情况 | 首期行为 |
| --- | --- |
| 应用可见/最小化，runtime 正常 | 正常 tick；最小化不暂停任务 |
| macOS 只关窗口、进程仍在 | 可以继续，但无窗口时待审批不自动通过；UI/帮助明确其与退出的差别 |
| 用户真正退出/进程被终止 | 不执行；未完成执行记为 interrupted/待核对，重启按有限策略处理 |
| 系统睡眠 | JS 暂停，不阻止睡眠、不主动唤醒；恢复后先重查条件和截止时间 |
| 无网络但本地模型/工具可用 | 按实际能力执行，不能仅凭系统 online 标志禁用本地 backend |
| 模型或所需远程服务不可达 | 记录可理解的失败/等待网络；A1 不无限自动重试，A2 只对获准安全步骤有限重试 |
| vault 锁定、授权失效、员工停用/移出群 | 阻止执行，提示需要处理；恢复后重新校验，不沿用旧权限快照 |
| runtime 意外崩溃而主窗口仍在 | 先显示调度不可用；重启 runtime 后走同一恢复流程，不能静默显示任务仍在运行 |

## 6. 幂等、并发、恢复与取消

### 6.1 触发和发布去重

自动发生记录使用 `automationId + revision + scheduledFor` 作为唯一键；DST 重复时刻另用日历槽键合并。“立即运行”使用独立用户 requestId，与 cron 槽分开；双击或 IPC 重发返回原记录。手动运行沿用相同授权检查，但不改下一次计划时间。

wrapper 第一步先持久受理 occurrence，然后才调用产品任务入口。每次受理、公开消息、产物发布、通知都必须独立幂等；不能只依赖 Mastra CAS 或内存 Map。相同 occurrence 的恢复只能继续已知阶段，不能重新制造一条触发消息。

A1 就要记录“框架已认领、产品未受理”的差异：对账 schedule 的 lastRunId、trigger、workflow 与产品 occurrence；不清楚是否执行过时标记待核对。A2 补齐持久投递/outbox、启动对账和有条件补发，覆盖认领后发布前、发布后受理前、提交后 UI 收到事件前的崩溃空窗。

### 6.2 并发和预算

- 建议同一自动化最多 1 次活跃执行；再次到点时先记录“上次仍在执行，本次跳过”，不堆积无限待办。可配置“保留最新一个待执行”留到 A2。
- 不抢占用户正在进行的群轮次。A2 群任务进入产品队列，按会话串行公开提交；任务到真正出队时再检查 deadline、成员和资源。
- 不同任务可在全局有界并发下执行；每个 execution 独立 run 目录和产物，不能因同属一员工就共享可写临时目录。
- A1 沿用现有单次预算并增加 wall-clock deadline；A2 把模型判断、实际执行、工作流重试、后台工具和记忆维护都计入总预算。预算耗尽就是有记录的终态。

### 6.3 恢复不是重新执行

没有完成证明的运行在重启后标记中断，不能直接对原 `sendMessage` 再调用一次。只读模型生成可在用户选择重试后产生新 attempt；已经公开提交的结果仅补通知/界面投影。

对外写入动作有三种结果：明确未执行、明确完成、结果未知。只有明确未执行且仍获准的动作可以自动重试；提供方支持幂等键时复用同一 effect key。结果未知显示“需要确认执行结果”，不让模型猜测后重放。

工作流暂停恢复要核对 workflow 版本、产品任务版本、当前员工/会话成员、资源范围、审批有效期及 backend capability。恢复点前后的代码可能重新进入，副作用应放在可去重步骤中，不能将持久 snapshot 当作永久授权。

记忆整理失败或中断仍只属于记忆维护，不能提供普通任务重试来重新执行原自动化。沿用 v0.2.2 的本轮/历史记录边界，不用旧失败覆盖本次成功。

### 6.4 取消链

“停止本次”依次停止产品新调度、撤销待发言/待提交、取消 framework run 和 agent/tool、终止拥有的 sandbox/browser 进程，并记录确认结果。只关闭流或 Renderer 订阅不算停止执行。

远端 backend 若只确认已发送取消请求，则显示“正在停止”；未收到确认不能谎报全部终止。已经发生的外部副作用不会回滚。退出时先停止接收新槽，再在有界窗口内取消/落盘，最后关闭 Mastra workers、storage 与工具资源。

## 7. 员工、群聊与执行后端

### 7.1 员工任务

A1 目标明确绑定 `agentId + destinationConversationId`，两者关系必须有效。执行复用现有员工工厂、模型连接、授权知识/skills、memory scope 和工具入口。一个员工在不同会话的上下文仍隔离，不因为触发源是定时任务就读取所有历史。

自动化触发是产品事件，界面标记“定时任务 · 每日摘要”，不得冒充用户刚手写的“我”。产品消息 schema 需要增加明确的来源/关联字段；若底层模型需要 user role 输入，只是 provider 消息映射，不能因此改变 UI speaker。内部包装 workflow 和 tool result 不直接写入公开 transcript。

### 7.2 群任务

A2 提供两种显式目标语义：向群发起一项自动化任务，由合法成员自主判断；或把指定员工的已授权任务结果交付到群。后者同样要检查它仍是群成员、内容来源获准公开、提交未被撤销。

每次发生记录创建自己的产品触发事件和 turn，沿用真实 sender、公开提交去重及当前轮边界。不能为了保证通知而强制所有成员回复，也不能用中央模型固定选 1–2 人冒充自主参与。群内任务不能默认带入该员工私聊记忆。

成员退出、资源解绑、权限撤销后，排队/暂停的自动化在受理、执行和公开提交三处重新校验。错误留在所属 occurrence/turn 的历史中；当前成功不会删除历史，也不会被旧错误误标成失败。

### 7.3 Sandbox 与 execution backend

员工的执行后端按 [执行后端与能力契约](../4.数字员工与协作重构/04-员工执行后端与能力契约.md) 演进。自动化面向统一产品 executor；不能在 scheduler 中写死 Mastra Agent 构造，也不能把同一员工的 ACP/A2A 实例当作新群联系人。

| 后端/能力 | 自动化接入要求 | 首期关系 |
| --- | --- | --- |
| 现有 BYOK Mastra Agent | 复用受控上下文、权限、预算、取消和结果提交 | A1 默认即可交付 |
| 受限文件工具 / Skills 读取 | 文件路径与资源授权明确；读取说明、参考文件或脚本不授予执行权限 | 依赖 S1，不要求 S2；纯文本任务可先交付 |
| Sandbox / 命令与脚本执行 | 挂载、命令、网络范围明确；后台执行仍需原审批；不静默回退宿主无限权限 shell | 命令、脚本和可执行技能依赖 S2 |
| MCP / Browser | 使用已批准连接/工具，等待登录/审批可暂停；不把人工完成登录误判为任务成功 | 任务明确需要时才依赖 C1 / BR1 |
| 本地 ACP/SDK agent | 声明无界面运行、取消、恢复、工具审批、产物和使用量能力；不支持的标记不可用于该日程 | E2 后可选，A1 不依赖 |
| 远端 A2A agent | 独立认证、任务 ID、回执/取消、数据传输授权；远端可执行不表示本地退出后自动交付 | E3 / A3 可选 |

后端或员工配置改变后，新发生记录用新版本；已开始执行保留原快照及实际版本。敏感能力新增不能自动继承旧日程授权；无交互执行不受支持时阻止并给出原因，而不是换一个更宽松后端。

## 8. 审批、通知与页面

创建/启用自动化表示允许按展示的频率发起该范围的任务，不等于给未来所有工具永久批准。命令、外部写入和新增范围仍走已有审批；无人处理时保持“等待确认”，到期后停止，不默许。

A1 最低页面包含创建/编辑、启用/暂停、立即运行、删除、下次时间和运行列表。详情显示时区、目标员工/会话、任务指令、实际可用能力、应用退出后的规则；保存前预览未来触发时间。不向用户暴露 protocol/JSON/堆栈作为主要错误文案。

每次记录至少显示计划时间、实际开始、目标、来源（定时/手动/恢复）、状态、耗时、使用量、结果入口和可操作说明。失败技术细节可折叠；默认展示当前一次，历史按时间排序并可展开。

通知由主进程调用系统通知能力，产品数据库先保存结果；点击跳到具体 occurrence/会话，不重新执行。建议默认通知完成、失败和待确认，可选择仅异常；拒绝 OS 通知时应用内仍可见，不反复弹系统授权。

通知同样持久去重，不把 token 流变成连续弹窗。系统休眠/退出时不承诺推送；恢复后展示摘要。通知本身不携带敏感原文或工具参数，详细内容在应用内查看。

## 9. 分阶段开工与依赖

| 阶段 | 可交付范围 | 必要依赖 | 完成条件 |
| --- | --- | --- | --- |
| A1 持久化与触发 | 本地 Mastra scheduler、薄 dispatch workflow、单员工 BYOK、配置/运行记录、暂停/立即运行、有限补偿、应用内结果 | 稳定产品执行入口、LibSQLStore、IPC/持久契约；受限文件/Skills 读取依赖 S1，命令/脚本依赖 S2 | 单员工端到端可用；退出不执行；重启不重复发布；调度与业务成功分开 |
| A2 可靠执行与恢复 | 持久投递对账、步骤/副作用记录、审批恢复、有限重试、取消链、群任务、系统通知与备份 | A1；群任务复用成员自决和公开提交；需要多步骤才引入 W1 | 崩溃空窗、权限撤销、重复事件、后台任务恢复与产物交付可验证 |
| A3 外部唤醒/部署（可选） | 常驻本地服务，或独立远程 Mastra worker/调度服务；必要时外部 cron/webhook | 明确运行位置、凭据/授权、持久队列、认证、防重放、设备/云交付协议 | 关闭 UI 的承诺与实际宿主一致，外部触发不能重复执行或越权 |

### A1 推荐实施顺序

1. 冻结 `AutomationDefinition / Occurrence / Execution`、产品消息来源与 executor 受理接口；为现有 v0.2.2 数据加独立版本迁移，旧任务页不伪造新能力。
2. 做最小 SDK 集成验证：本地 file LibSQLStore、固定 evented wrapper、运行时 CRUD、显式 workers 启停、存量日程启动首 tick、计划时间关联；不访问用户真实数据。
3. 建立产品配置到 Mastra schedule 的幂等同步、启动对账、受理唯一键、单任务并发/截止时间和有限补偿。先证明不误触发，再接真实员工调用。
4. 受控 wrapper 接现有单员工执行，保存结果并幂等发布；纯文本任务可独立交付。S1 完成后可接受限文件工具与 Skills 读取；只有命令/脚本执行等待 S2。错误状态必须用户可见。
5. 接定时页面和主进程状态，覆盖创建、编辑、暂停、立即运行、停止与历史。完成 A1 验收后再开放任务入口。

A2 可逐项交付群任务、W1 模板、后台长工具，不要求一次启用全部框架能力。[Memory 计划](./01-Memory与WorkingMemory.md) 保持独立；自动化不以启用框架自动记忆为前置。[工作流计划](./02-动态工作流与执行编排.md) 中 W2 动态图也不是定时执行前提。

### A3 需要另行选择宿主

常驻本地服务可在 UI 退出后继续运行，但电脑睡眠仍影响执行；操作系统开机启动、凭据解锁、应用更新、日志和取消入口都需正式支持。不能把后台任务 manager 当作操作系统服务。

远程常驻 Mastra 可以拥有自己的内置 scheduler；外部 cron 也可只负责唤醒受认证的产品入口，两者不能同时拥有同一计划槽。云端不能直接读本机 workspace/vault，未获授权的本地资源任务应等待设备上线，不能静默上传全部文件。

官方部署支持独立 workers，但这不是当前 Electron 已具备的能力；Inngest 等外部调度也有独立管理面和运行机制。A3 选择后重新核对对应版本、持久 PubSub、存储和认证，不把 Cloud/服务器能力直接写成桌面保证。

## 10. 验收清单

以下均为未来实施验收，本次没有运行这些测试。A1 只以标记为 A1 的项目作为首期门槛；A2/A3 在对应能力开放时验收，不要求 A1 提前完成群任务、强可靠恢复、完整备份或外部部署。条件性能力未接入时应明确显示不可用。

| 阶段 | 场景 | 预期 |
| --- | --- | --- |
| A1 | 创建每天 09:00 单员工任务 | 保存明确时区，显示真实未来时间；只在实际到期后通过产品入口调用员工 |
| A1 | 新建/编辑时框架存储失败 | 不显示启用成功；重启对账后不创建重复 schedule |
| A1 | 正常重启后已有到期日程 | 第一个 tick 可受理，不能因执行消费者未就绪丢失；同槽结果只发布一次 |
| A1 | 停机 5 分钟/数天 | 符合窗口的存储槽至多补一次；过期记录说明跳过，不逐次补跑全部历史 |
| A1 | DST 跳时/重复时间与时钟回拨 | 符合已冻结的日历语义，未来时间预览与实际一致，重复本地时刻不重复执行 |
| A1 | 相同 requestId/重复 fire、双击立即运行 | 返回同一发生记录/执行，公开消息不重复 |
| A1 | 已受理任务在进程退出后没有完成证明 | 标记中断或待核对，不盲目重跑；不承诺此阶段已实现所有崩溃空窗的自动补发 |
| A1 | 退出、最小化、只关 macOS 窗口、系统睡眠 | 各自符合实际生命周期；退出不执行，睡眠不靠空转维持 |
| A1 | 无网络/本地模型/凭据锁定 | 根据真实后端能力处理，错误清楚；不无限重试、不泄露凭据 |
| A1 | 上一执行未完成又到点 | 有明确跳过记录，不启动重叠执行；有限排队留到 A2 |
| A1，文件能力依赖 S1 | 员工停用、受限文件/Skills 资源撤权 | 受理、执行和公开提交前检查当前授权；普通文件与说明读取不要求 S2 |
| A1 | 停止本地单员工任务 | 取消模型调用，取消后不继续公开提交；不把关闭流当作完成取消 |
| A1 | 记忆维护中断 | 不出现重跑原自动化的普通重试入口 |
| A2 | 认领后发布前、发布后受理前、消息提交后崩溃 | 持久投递对账可区分未受理/未知/已提交，只在已知安全条件下补发，不重复公开消息 |
| A2，命令能力依赖 S2 | 自动化命令等待审批，重启后继续 | 未批准不执行；恢复重查权限，拒绝/过期得到终态；取消能终止所属工具与进程 |
| A2 | 员工退出群、群资源撤权后旧任务被唤醒 | 不执行或不公开已失去授权的内容，历史记录仍保留 |
| A2 | 群自动化与用户新消息同时进入 | 独立 turn 和真实 sender，排队/预算/发言权一致，旧轮错误不混入当前 |
| A2 | 外部动作已成功但请求超时 | 标记需要确认或按提供方幂等回执核对，不盲目重放 |
| A2 | 结果已保存但系统通知失败/重复回调 | 通知独立重试及去重，不重新调用员工；拒绝 OS 通知时应用内结果可读 |
| A2 | 备份恢复为第二份应用数据 | 日程默认暂停，历史可读，无第二调度实例重复执行 |
| A3，或提前接入 E3 时 | 停止远端执行 | 未确认的远端停止诚实显示；迟到结果不越过已撤销的公开提交权限 |
| A3 | UI 退出后的常驻执行或外部唤醒 | 与所选宿主的实际能力一致；外部请求经过认证/防重放，同一计划槽只有一个调度所有者 |
| A3 | 云任务依赖离线设备中的文件 | 等待设备或清楚失败，不静默上传本机文件或借用本机 vault；恢复连接不重复执行 |
