## 已接入的持久化基础

- `automation-repository.ts` 是定义、触发身份、状态和投递意图的 SQLite 权威。保存使用事务内版本比较；准入在同一事务读取定义、检查已有身份/容量并保存 occurrence 和 `automationDispatches`。内存 map 仅供投影，不能决定一次触发是否已经认领。
- 编辑 `revision`、执行 `executionRevision` 和日程 `scheduleGeneration` 分离。名称/通知变化只推进编辑版本；prompt/目标/授权变化推进执行版本；cron/时区变化推进日程代际。手动身份为计划 ID + requestId，周期身份为计划 ID + 日程代际 + 时区 + 本地分钟，秋季回拨的同一分钟去重。
- AppService 在宿主临界区检查许可并准备正常用户消息/turn；消息、请求、turn 与消费后的投递意图同事务提交，之后才交给现有 GroupScheduler。失败不会留下半条消息；事务已提交但尚未启动的记录在重启后需核对，不自动重发 prompt。实际工作认领仍走 WorkRepository。
- 同计划等待补充时阻止下一轮，等待记录不占两个计算槽中的一个；不同计划在同一指定聊天同时受理也会被账本拦截。新增等待工作状态释放计算槽，但仍阻止同计划重叠；取消中保留计算占用直至实际执行器退出。等待恢复时在同一事务重新认领最多两个计算槽，同时排除相同聊天的其他活跃自动化；无空位保留待接续，其他运行释放名额后重新检查。
- 产品定义先保存 pending，原生同步完成后按期望 revision 条件确认；迟到回执不能覆盖新配置。运行时配置同步提供 1/3/10 秒的有界重试，不重试业务执行。删除保留 tombstone，未知或已删除的原生日程在 worker 启动前暂停。
- Mastra `schedules.update` 只在 cron/时区真正变化时提交这两项；否则安装版 SDK 会重新计算下一时刻并丢掉原先保留的到期点。改名、通知和 prompt 保留 nextFireAt；改日程或恢复启用才重新计算。
- `NativeSchedules.history()` 按实际触发时间分页，完整读取同一毫秒跨页条目，再推进时间边界。超过单桶 25,600 条时明确报错并保持调度未启动，不默默漏掉旧记录。未知原生触发保存 native 身份和 needs_review，不套用最新执行版本，不启动员工。
- `schedule-policy.ts` 为预览和准入共用时区/日期/星期匹配；春季不存在时刻跳过，秋季重复本地分钟按持久身份去重。保留原生时钟，不新增轮询 cron。

## 跨工作归属、交付与停止

- `AutomationOrigin` 由宿主贯穿 WorkItem、WorkExecution、WorkWake、DiscussionTurn 和 AgentRun。根工作来自已持久化的原始触发消息；子工作继承父工作，接续通知继承目标工作。接续仍读取当前获准聊天上下文，但不会把最新人类消息当作新的工作来源。旧数据只按原始消息/明确 workId 回填，不按文本相似度或依赖结果推断。
- WorkRepository 的认领/委派/工具副作用/结算事务同时校验 occurrence 执行许可；普通聊天或另一 occurrence 不能改绑已有工作。显式安全重试沿用原工作/预算/来源及绝对期限，保留失败 run；停止或重启后需核对的 occurrence 不允许从旧 run 偷偷恢复。
- `automation-results.ts` 按持久身份汇总本次拥有的根工作、子工作、全部轮次和运行；独立共享依赖不纳入归属。初始 turn 结束后若仍有 child/接续待处理，不能提前结束 occurrence。
- 业务交付使用最新工作版本、该工作真实已提交的正文和当前可核查文件，复用 Work 协议的证据校验。产物必须归属对应 run，且仍为共享受管目录内的实际普通文件；缺失/路径逃逸不算证据。全部 pass、普通聊天、等待、无效证据和 requiresReview 均不能标成已交付。部分有效结果保留为 partial，执行 completed 与 deliveryStatus 分离。
- “停止本次”在与消息/发布共用的宿主临界区先保存 cancellationRequestedAt/cancelling，再取消拥有的工作树/轮次/run。后来的人工作业和独立共享依赖不受波及；适配器忽略 abort 时继续显示正在停止，不能早释放容量或备份，迟到正文/产物不能发布。适配器实际退出触发最终核对。
- 重启不恢复模型执行：已提交工作/消息/轮次均完成，只是 occurrence 汇总来不及落库时，可以纯核对恢复交付；仍需执行的工作保留中断。新记录使用统一逐请求账本，旧记录无账本时才按唯一 turn/run 保守汇总并保持 usageIncomplete=true；不反推历史精确用量。
- 页面显示运行状态和交付状态，等待补充/等待工作可停止；取消中显示正在停止。等待补充可从指定执行记录提交，明确携带 occurrenceId；新任务聊天已经接入，通知策略和持久提交回执已经接入，不能宣称 OS 送达或已读。

## 每次触发的统一预算

- 受理 occurrence 的同一 SQLite 事务创建现有 `WorkBudget`，不等待 task 认领，不为初始判断或普通聊天创建假的 Work。默认从受理起 5 分钟、24 次模型请求、8 次工作运行；已知输出上限 16,000 token。页面显示实际原始期限，等待不暂停或重置它。
- 根工作、子工作、显式安全重试共用同一 budgetId。模型入口为初始判断、执行每一步、报告修复、记忆和只读限流重试分别创建唯一请求 ID。事务预留发生在请求之前；取消或失败后不返还调用额度，缺少回执保持未知。任务认领不再重复计入已由请求入口计费的调用数，普通人工 Work 的原有计数不变。
- `budgetModelCalls` 保留阶段、run/turn/occurrence 和单次原始用量；重复 ID 只允许相同身份，重复用量回执按增量幂等合并。SDK 多步骤按明确步骤 ID 对应回执；过滤原始供应商附加字段和没有 input/output 的合成 total=0。每次请求三个 token 字段均已知后才解除它的未知标记，不把 cumulative run 用量再次相加。
- 已知输出达到上限立即停止本次；调用数/绝对期限在下一次预留前拒绝。缺失 usage 时不能精确证明输出量，上限仍由请求数和期限独立约束，界面如实展示已知部分。迟到回执只更新原预算统计，不恢复执行；聊天清理后不重建已删除账本。
- 等待中的工作恢复先在事务里重新取得全局计算槽，跨连接竞争不会挤占最后一个名额。预算和截止时间原样沿用；旧 occurrence 缺少可信逐请求账本时拒绝隐式重试，需明确发起新一轮。

## 指定运行的补充信息

- 等待记录提供“补充信息”入口。请求只包含 occurrenceId、正文和 requestId，来源与提问关联由宿主生成；普通聊天仍是普通聊天，不解除任何其他 occurrence 的等待。
- 提交时在宿主临界区检查当前获准上下文和会话空闲，再在同一 SQLite 事务检查等待版本、原预算/期限、全局容量，保存人类消息、新 turn/请求记录和对应提问的 `replyToTurnIds`。失败不留下半条消息或占用，重复 requestId 返回已提交的消息，不同正文不能复用 ID。
- 原提问轮次保留 waiting_user 历史；结果汇总只由同一次自动化的宿主补充关联解除该提问等待。再次追问形成新的明确待回答轮次，不把第一次等待永久留在活动状态。模型收到宿主确认的原始请求/提问关联，先前已交付工作保持不可重放；新的根工作仍按最初触发消息和显式共享 key 建立身份。
- 补充沿用原 budgetId、累计请求数与绝对期限，不清零。到期不能直接补充；用户明确确认固定追加额度后可继续同次安全未完成工作。人工停止、重启中断和旧无可信账本记录仍拒绝通过追加额度恢复；不能把“立即运行一次”当成保留旧工作的恢复。

## 独立编辑标签与任务聊天

- 新建入口使用稳定草稿 key，编辑使用 automationId；接入现有 DetailPanel/DetailTabSession/EditorFrame。主内容只读，选择另一计划不换掉已打开的草稿；多个编辑标签独立保存，收起/切换保留输入和滚动，关闭沿用原有继续/放弃/保存保护。创建成功关闭当前草稿并选中新计划，编辑保存停留原标签；并发版本冲突保留草稿。底部操作沿用既有固定页脚。
- 新计划默认“每次新建任务聊天”，显式选一名受控模型员工；旧计划缺少新增字段时保持指定聊天，可继续使用既有群聊。宿主验证目标互斥、员工/连接/能力，并在实际受理前再次检查授权指纹。
- 准入时生成独立聊天/工作区身份，工作区准备成功后聊天记录与 occurrence、预算和投递意图在同一 SQLite 事务提交。准备失败保存失败记录，不分配预算、不发消息；数据库提交失败整体回滚。重复触发返回原绑定，不再创建聊天。工作区目录准备不含业务执行，事务失败可能保留空目录，不将其当作已经创建了聊天。
- 自动化聊天保存 purpose/automationId/occurrenceId；普通一对一会话复用明确排除它们。新聊天不复制历史消息，使用所选员工现有获准资源/记忆规则和独立共享工作区。会话列表提供普通/定时任务来源筛选，并在预览标注来源。
- 日程增加星期多选、周一至周五工作日，兼容旧 weekday。保存 cron、触发过滤和未来五次预览共用 schedule-policy 的校验和规范化规则。预览 IPC 不创建计划、聊天、工作区或模型请求；无效时区/空星期选择显示错误并阻止提交，尚未验证的时区不进入日期格式化，防止输入过程中页面报错。运行位置与预算如实显示，新计划通知默认为重要更新，另可选择每次结果或静音；旧计划的通知偏好原样兼容。

## 完整历史与结果定位

- 新增 listAutomationHistory，默认每页 30 条、最多 100 条，由 SQLite 按 startedAt + id 降序和显式边界读取；不依赖最近 300 条摘要。时间相同的多条记录不会漏页，插入更晚记录或删除边界记录不改变较早页的语义。支持按计划过滤，保留已删除计划的历史。
- 阅读区加载更早记录，切换计划重新建立分页范围；产品事件刷新已打开的页数，重算连续边界，避免把新记录与旧分页拼成缺页的列表。错误保留可读内容并提供读取重试。
- 每条记录可展开实际保存的结果正文和证据引用，运行结束与交付待核对仍分别显示。打开结果携带精确消息 ID；聊天滚动到对应消息并获得焦点，不跳到较晚的人工消息。已清理消息显示不可用说明，不定位到猜测的替代消息。
- 当前独立详情读取复用现有 getConversation，在展示端仅选择该 occurrence 的结果 ID/来源；没有引入第二份正文存储。系统通知同样携带精确消息/执行记录身份，窗口重载后也能消费未完成的导航。

## 持久通知与提交回执

- 新计划默认 important_only；可选 all_results 或 muted。旧 notify=true/false 保持原有每次结束/静音意图；显式新策略优先，旧客户端未改布尔值时不把重要更新降成每次结果。通知偏好独立于 prompt、执行版本和日程代际。
- 在 occurrence 汇总/受理失败/未知原生触发的同一事务写 automationNotices。重要更新包括已交付/部分结果、已结束但未交付、等待补充/审批、失败、中断、需核对、权限失效和预算耗尽；一般忙碌跳过、等待独立工作、无变化不弹出。每次结果策略还包含普通运行结束或停止；静音仍保留全部应用内结果。
- 使用确定性结果/等待轮次/运行身份去重，记账回执或同一结果的重复汇总不重复入队。同一执行授权版本的重复失效只产生一条提醒；重新授权后可产生新提醒。领取前重新检查当前偏好、是否删除以及结果/等待语义，已回答的旧问题或静音后的待提交提醒转为 suppressed。
- Electron 主进程通过宿主专用通道领取记录，SQLite 原子地由 pending 变为 submitting 并生成 attemptId；渲染层不能调用领取/回执通道。系统 show 调用与数据库回执分开：submitted 只表示已调用系统提交接口，failed 表示同步失败或后续系统拒绝；迟到的 submitted 不能覆盖失败，其他 attemptId 不能改写记录。
- 主进程提交已尝试但确认回执失败时尽力写 unknown，不再次调用系统提交；如果数据库仍不可用，重启把 submitting 转为 unknown。pending 可在正常启动后继续消费；从备份恢复时原 pending 提醒转为 suppressed，不重发旧设备提醒。业务执行、模型预算和交付状态都不随通知回执改变。
- 系统提醒正文只使用固定摘要；点击时精确导航到保存的结果消息，缺少结果消息则定位相应 occurrence。导航保留到 renderer 主动读取，避免重建/重载窗口时丢事件。执行记录按需读取单条记录，允许打开不在当前分页中或计划已经删除的记录。
- 历史页面分别展示提交中、已提交、失败、未知或取消提交。已提交明确标注“不代表送达或已读”；旧 notificationDelivered 仅显示历史状态未知，不当作新回执。聊天清理删除通知中的消息/聊天引用，pending 抑制、submitting 未知，保留最小去重身份；不会重新外发。

## 迁移、清理与存储边界

首次迁移已有自动化数据时，先在数据目录保存 `automation-before-v1-<uuid>.sqlite`，再事务迁移并写 `automationSchema`；快照包含当时产品数据，应按原数据库保护。未知高版本拒绝载入。旧计划保持指定聊天和原通知意图，原地升级保留启停；恢复标志或不同安装路径使所有计划暂停。

旧 occurrence ID/nativeRunId 保持不变，手动和原生别名覆盖原身份。没有历史时区/版本快照的旧日历记录仅建立保守的防重放别名，不伪造历史版本。旧 completed 仍表示历史运行结束，`deliveryStatus=unknown`，用量缺失保持不完整。页面和系统提醒改为“运行结束”，不称业务已交付。

清空聊天时保留 occurrence/别名的最小身份，清除消息/turn/work/根工作与结果证据引用，以及 `automationDispatches` 的 prompt/来源快照和本次聊天的预算/请求回执（即使还没有 Work）；失去上下文的等待记录成为 interrupted，已清除的意图不能恢复任务。新增状态版本使清理后的旧观察结果不能回写已删除引用。

跨独立 SQLite 连接测试发现 libsql 0.5.29 在 BEGIN 争锁失败后可能保留失效语句，使后续 commit 报错。ProductStore 只在 BEGIN 前有界等待 SQLITE_BUSY，并关闭/重建尚未进入事务的闲置连接池；读写共用排队边界。事务回调与 commit 从不重试。已进入事务后的 SQLITE_BUSY 注入仍回滚且仅调用一次回调，不把数据库重试变成工具重放。

### 使用方式与数据格式

先让资料整理任务把结构化结果发布到固定聊天，例如 `metrics.json`。随后在定时任务中选择“检查数据变化”、该聊天与文件名，字段填 `/count`，按需要配置数值累计变化阈值。后续采集应继续发布同名文件的新版本；监控自身不获取外部数据。

```json
{
  "schemaVersion": 1,
  "observedAt": "2026-09-29T01:00:00Z",
  "complete": true,
  "data": { "count": 100 }
}
```

示例时间必须替换为真实采集时间，不能用发布/检查时刻伪装旧数据。此入口验证数据生产者的声明、格式、新鲜度和所选字段，不替代上游采集正确性保证；未新增直接 HTTP API、行情源、交易日历或需要语义判断的模型解释。
