本适配使用本机程序的官方非交互入口。`--bare` 配合空工具、空配置来源及明确MCP配置核验；不复用当前电脑上的Claude订阅登录。凭据由宿主明确提供，适配器不从用户目录寻找密钥。

底层“API凭据”是提供给Claude运行时的模型来源，不是BoAI额外调用Mastra父模型。真实探测采用原BoAI保存的DeepSeek连接，保留本机Claude身份与DeepSeek模型身份，不能据此声称调用了Anthropic模型。

工具阶段使用已有MCP SDK的1.30.1版本，新增直接依赖而不升级版本。只允许本阶段`mcp__boai__`工具，原生Shell、文件工具及外部发现保持关闭。CLI公开的完整工具事件与MCP请求里的`claudecode/toolUseId`对应后才进入宿主工具；该字段是当前CLI实测形状，不视为通用MCP保证。私有配置文件0600只保存随机回环令牌，不含供应商密钥；按字节核对后清理，外改保留。内部MCP桥不是用户自配外部MCP服务功能。

费用和内部重试次数没有转换为BoAI模型调用数。适配器自身不重发请求；原生CLI仍可能处理供应商层重试，尚不能宣称内部调用硬预算。用量只接收本轮完整的非负整数计数，缺项保持未知，不将会话累计费用作为本轮费用。

## 共同引擎的边界

`CodexEmployeeEngine`继续通过原app-server执行；`CodexSessions`与`observeCodexPhase`保留原调用入口和命名空间。共用员工协议不共用认证，也不把Claude只有宿主调用完成身份的事实套用到Codex原生turn回执。

Claude的判断、记忆和重新汇报是独立私有阶段。通过CLI官方`--json-schema`提供本机2.1.214实测支持的draft-07 schema，唯一工具是无业务副作用的`StructuredOutput`；只能在ephemeral且没有宿主工具/续用session时使用。聊天仍无工具，任务只提供原宿主MCP工具，三种范围不能混合。格式正确后仍需原Zod、消息来源和`workEvidenceError`验证，不把格式器回执当作工作完成。

引擎的记忆阶段只产生经来源校验的候选，最终记忆写入仍归MemoryRepository。会话续用只认实际完成且已公开的原答复；原生thread/session存在、成功模型终态和产品交付不是同一个事实。内存工作夹具的文件发布回调也不等于产品ArtifactRepository已提交。

## 单员工产品接线

- `profiles.ts`、`runtime-config.ts`：公开claude-cli配置，固定版本和程序hash，明确兼容API连接/模型。程序测试不调用模型，不读取个人订阅登录；额外参数和Codex登录来源明确拒绝。
- `employee-service.ts`、`service.ts`：公开claude-local独立员工，创建/编辑和原direct会话沿已有身份。使用ClaudeEmployeeEngine，没有API父模型；连接容量沿实际API来源，外部请求及已知/未知用量保留。
- 原`WorkRepository`与交互预算：判断、任务、汇报和记忆沿原请求身份和期限。计量共用external-turn；比较运行时具体kind/profile及持久run，不允许Codex与Claude互借回执。
- 原`ArtifactRepository`核对Claude配置并受理新根修订；实际发布仍走已有工具和事务。产品桌面首批覆盖文件发布及采用，未据此宣称修订完整流程已验证。
- 原`history.ts`清空事务删除claudeSessions；启动恢复核对claudeRuntime。备份排除.claude-private并标记新会话资格，保留已提交业务事实，不拷贝登录或自动重放。
- 原创建/编辑弹窗、本机连接设置、员工概览、composer与执行记录已接Claude及明确模型来源。Codex仍用原本机登录；无新增主页面。普通群创建及成员编辑已包含Claude；核心组织群增量见第9节，自动化新增接线见第10节。

`tests/claude-product.test.ts`通过真实AppService、SQLite和独立协议进程验证上述业务接线；`claude-employee.feature`沿原设置和新员工UI验证连续聊天、文件/原预算、采用与重启。模块、离线桌面和真实Claude分别记录于[第13组06 §52](../13.本机Agent员工运行时/06-实施步骤与自动验收.md#52-claude单员工产品接线与桌面验证2026-10-06)，不得混用来源。

## 普通群产品接线

`service.ts`在创建或编辑普通群时核对Claude程序指纹、固定版本和明确API来源；员工仍可在群内编辑自身配置。运行时继续核对这些事实，原核心组织群和自动化来源不因放开普通群而获得执行权。

每个员工使用自己的阶段运行、会话映射和目录；共享程序或API连接不共享员工身份。原`delegate_work`、`wait_for_work`及成果发布经共同MCP工具桥进入原Work事务，父子工作保持原消息来源、共享预算和绝对期限，依赖实际交付后只唤醒原负责人。无需API父模型；API同事自身的API运行与Claude自身使用的模型来源分开记账。

群创建与成员编辑复用原UI。模块新增双Claude独立交流/独立根工作、真实工具父子分工、移出和重新加入后的会话重建、程序变化拒绝加入及重启零重放。桌面新增双Claude、Claude/API两个方向的正式分工与原件/累计账本核对；当前批次成绩及未覆盖边界统一见第13组06 §54。

交互分工接续完成后，`service.ts`沿同一员工引擎整理原用户来源的增量记忆，绑定本人本轮实际delivered公开回执；等待消息不借后续交付取得维护权。API混合成员使用自己的引擎，记忆请求进入原交互账本且不续期、不认领工作执行，失败不改已交付原件。其他唤醒授权保持；实际分批结果见第13组06 §55。

## 18. 宿主意外退出与实际进程组

Claude 的输入在执行前已经写完，不能依赖 stdin 断开或者下一次 stdout 写入来发现宿主消失。旧 `process.ts` 为 CLI 创建独立进程组，正常取消可以停止整组，但宿主被 SIGKILL 后无法执行取消回调；静默 CLI 可能继续运行。真实 Electron 离线协议场景已复现这一缺口，失败原件与补救清理独立留存。

新增 `claude/supervisor.ts` 提供随 worker 编译的固定 Node 启动代码。监督进程是独立 POSIX 进程组的组长，通过宿主专用 IPC 接收一次经过核验的程序、参数与输入；实际 CLI 及其普通后代继承同一进程组。宿主 IPC 断开立即终止整组，包括监督进程自身。私有提示词和认证不加入监督进程命令行，不新增磁盘请求副本、模型调用或业务重试。

CLI 正常结束时只通过 IPC 返回实际退出码；监督进程保持存活，宿主停止并等待整组实际退出后才结束原调用。CLI 的 stdout/stderr 仍沿原有界传输接收，格式器、计量、阶段时限、策略版本和原始错误保持。实际退出码为零仍不能替代模型终态、完整计量或 Work 交付。

新增模块由真实独立宿主运行生产适配器，创建静默 CLI 和关闭了输出管道的普通后代，SIGKILL 宿主后逐 PID 核对全部退出；新增 BDD 通过原七项定时表单，在第一份真实文件写入后分别正常停止或强制结束当前运行服务，核对退出、原预算、未知用量、未发布文件以及重启不重放。测试如需补救清理，只按原 PID/启动时间身份处理并单独记载，不能算作产品退出通过。独立批次及适用范围见[第13组06 §67](../13.本机Agent员工运行时/06-实施步骤与自动验收.md#67-claude自动化停止与宿主意外退出2026-10-06)。

此保护限定当前验证的 POSIX 同进程组；不是外部程序沙箱，不能宣称隔离主动脱离进程组的任意程序。Windows 仍沿原能力门禁拒绝，其他平台及完整普通群/核心故障矩阵另行验收。

## 20. 暂不公开草稿与已声明依赖等待

真实私有汇报对照曾返回合法的 `discard`。这表示当前草稿不公开，不能撤销宿主此前受理的 `wait_for_work`。原 `WorkRepository.withhold` 无条件写入 blocked，遗失执行记录中的 pendingWait；因此子工作交付后也无法再唤醒原负责人。这是宿主状态处理缺陷，不能用降低模型思考强度代替修正。

当前暂不公开事务会沿已受理的等待保存依赖版号、nextStep、waitRevision 和已观测边界，释放原持有者，并在同一事务核对子工作结果。实际交付在前或在后都只生成一次原负责人唤醒；重新认领仍沿原 Work、来源、预算和绝对期限。未公开草稿没有结果消息或成果版号，不被计为已交付。原 Run 保存 waiting 意图与 withheld 草稿，当前 Work 可因真实依赖失败、未知操作或原无进展上限保持 blocked。

已确认副作用可以结束待核对标记，未确认副作用保留门禁；连续请求同一已观测依赖仍消耗原无进展额度。没有本轮受理等待的暂不公开保持原 blocked 行为。服务层的员工放弃公开、引擎不支持汇报和两次汇报上限共用此边界；汇报本身不获得工具或执行权限。Claude/Codex 的原生策略和模型参数未因此改变。
