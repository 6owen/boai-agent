## 1. 用户只审阅结果

以后按这条流程交付：**自动准备数据 → 自动操作真实应用 → 自动核对结果 → 生成可视报告 → 用户评价效果 → 修复后提交对照结果。**

用户打开一份报告即可看到功能实际做成什么样。数据准备、配置测试环境、发送消息、点击按钮、等待任务、制造故障、重启、核对文件与重跑都由开发代理和测试程序完成，不交给用户逐项操作。真实模型批次由开发代理按已登记连接和预算启动；“人工评审”只指阅读成果与评价体验，不指人工执行测试。

审阅入口按功能命名，例如“文件预览”“员工交付与修改”“内置浏览器”。每项直接展示实际界面和结果，技术日志在详情中备查。用户可以直接反馈：“文件预览通过”“F03 第二张图的修改入口不清楚”“这版报告缺少材料中的风险”，由开发代理关联到确切批次、场景、画面或成果版号并记录，无需用户填写 JSON 或检查数据库。

成功标准：用户不重新操作应用，仅凭报告就能回答 **入口是否好找、交互是否顺手、过程是否清楚、最终结果是否满足要求**。只有测试数量和绿色勾、没有实际界面或成果，不算完成可审阅交付。

## 2. 一份报告长什么样

首页列出全部十一项功能，每项显示本次是否执行、技术结论、效果评审结论、最近变化和直接入口。未运行项必须可见；可以筛选本次变更，但不能从总览分母中消失。

每项功能按以下顺序展示：

1. **这次要完成什么**：原用户需求、输入材料和预先固定的验收要求。
2. **实际做成什么样**：优先展示最终界面和可直接阅读的实际成果；文件可下载，Markdown/代码可预览，版本可对照。
3. **过程回看**：3–6 张关键节点原始截图；输入、流式、弹窗、切换或关闭等动态体验提供短录屏或可逐步回放的实际 trace，并明确是哪种证据。长等待允许跳过，但保留真实耗时、时间点与完整原记录。
4. **自动核对了什么**：用业务语言陈述，比如“修改后产生 v2，v1 保留；重启后仍采用 v2”；底层断言、消息身份和文件 hash 可展开核对。
5. **还存在什么问题**：失败现象、缺失证据、未支持范围、重试次数，以及修复前后的同场景对照。不能只选一次成功运行。
6. **需要用户评价什么**：每项最多三个具体问题，例如“排版是否适合阅读”“修改操作是否符合聊天习惯”“成果是否能直接使用”。默认待审阅，查看报告不会自动认可。

截图来自实际产品窗口；示意图、重画界面、预置历史和真实执行必须分别标明。报告中的聊天副本只读，带真实署名、消息顺序和来源，不能重写成更漂亮的演示对话。HTML/SVG 成果以安全源码或沙箱禁执行方式查看，不因报告预览执行其中脚本或加载远程媒体。

## 6. 自动执行与留证要求

### 6.1 两条证据链

**确定性产品流程：**复用真实 Electron + SQLite + 文件 + 本地协议服务，自动验证页面操作、授权、幂等、故障、停止和重启。明确标注“离线协议”，证明产品接线及界面，不冒充真实模型理解或内容质量。预置历史、数据库 seed 和真实发送产生的消息分别标明；要证明首次创建/实际生成的流程，必须真的执行该流程，不能只展示 seed 后的结果。

**真实模型交付：**需要语义判断的 F01/F03/F05/F06/F07/F08，以及 F09 的网页资料整理，使用真实已配置供应商、固定材料、原任务与登记预算；保留所有开始过的样本、失败和已知/未知用量。真实网站、供应商和 ACP 的兼容性结果注明具体环境，不扩大为全部支持。缺少连接或环境就标阻塞并说明缺口，仍继续其他可执行场景。

现有通用真实评估直接跑 AppService，没有产品窗口；应展示实际聊天/文件并标“后台执行证据”。需要同时证明真实模型下的界面效果时，后续补同一次执行的 Electron 捕获。禁止把另一次离线截图与真实模型正文拼成一次真实端到端成功。证据可并列参考，来源标签和 runId 必须分别保留。

旧版升级场景显式登记 `desktopMode: mixed-version`，报告显示“旧应用包至当前入口升级”。逐次实际入口、版本、构建身份和受控重启以同一场景的原启动记录为准；批次登记只说明预期迁移方向，不证明每次启动使用同版。旧包、当前源码和新包的完整性证据分别保留。该标签不证明安装器、签名或其他平台，也不把离线协议计为真实模型。开发构建、包内执行及未登记模式保留原来源说明。

### 6.2 运行顺序

1. 固定规格/场景/数据版本、待测代码与构建身份，列明本次必跑项和选取原因。真实模型执行前登记模型连接、样本数、原共享预算；失败重跑和评审调用沿既有账本管理。
2. 在隔离临时目录准备合成数据、可控网页/下载服务和协议服务。测试不动日常聊天、真实登录资料或个人工作区；供应商配置只由宿主读取，报告不包含凭据。
3. 自动操作实际产品，采集关键节点、真实消息/文件与时间；边界场景注入故障并走实际核对/重启路径。定时触发应覆盖产品已接的原生调度链，直接调用内部执行方法的结果单独标层次。
4. 执行原断言及成果检查。**在 `Desktop.dispose()` 删除临时数据前**，导出本场景必要的原件、聊天片段、检查结论和 manifest；不要只留一个会被下次运行覆盖的绝对路径。
5. 结束 trace/录屏，核对导出文件的存在、hash、来源与场景身份；失败场景同样保存。无法导出时报告“证据缺失”，不拿测试 exit 0 掩盖。
6. 生成首页和功能页，自动检查页面可打开、媒体及成果链接可读；运行日志、完整 trace 可展开，默认先给用户看产品结果。
7. 开发代理先检查自动失败、明显界面缺陷和证据完整性，能修复的修复并定向重跑，再提交给用户评价。修复前失败仍在历史中。

已有截图/trace 提取的静态画面可作为证据；不能称为连续录屏。若实现视频导出，标明原录制还是 trace 帧转换及时间压缩，并保留原 trace。首版优先复用现有可回放 trace，不以先造视频基础设施阻塞报告。

### 6.4 执行频率

- 每次修复：受影响大功能的完整代表场景 + 对应模块边界；同时跑与之相连的跨功能回归，报告明确未执行项。
