# 容量管理与上下文接续设计

更新：2026-10-24。状态：实现候选已接线；受控验证与真实业务验收分别记录在02，不能互相替代。

实施前源码与依赖说明保留为固定基线；当前实现映射见第12节，实际结果以02第5节最新记录为准。

## 1. 目标和固定边界

为 Mastra/API 员工提供持续工作能力：在当前模型输入接近容量时，保留必要信息、缩小有效上下文，或切换到新的内部上下文 Session，再继续原来的工作。

本组保持以下设计：

- employeeId、员工人格、独立 workspace、技能和来源授权不因压缩变化。
- conversationId、联系人、消息顺序、历史记录和当前页面交互不因分段变化。
- 员工长期记忆继续按现有规则跨私聊和群聊召回；上下文维护不新增默认隔离政策。
- 私聊、群中的某个成员、自动化执行可以有各自运行上下文，它们仍属于同一员工。
- 自动化继续使用现有触发、受理、Work/Run、审批、交付及原会话呈现，不改为新产品入口。
- 这次不实现经典 Agent/Bot 模式切换，不新建用户可见话题，不改造原生 Agent 后端。

群共同记忆可以作为后续独立扩展，保存群共同目标、结论和进展；它补充员工个人记忆，不承担本组的 Session 交接，也不作为本组上线依赖。

## 2. 当前源码已经有什么，缺什么

### 2.1 核对基线

- BOAI：6f2cbd631a4e3320c0ba2f129028169dc9a19527。
- 本地已安装 @mastra/core 1.71.0、@mastra/memory 1.32.1；依赖声明见 [package.json](../../../package.json)。
- 本文将代码现状和候选方案分开；实施前应重新核对当时版本与未提交变更。

### 2.2 普通 API 员工已有有界历史窗口

[message-projection.ts](../../../src/runtime/adapters/mastra/message-projection.ts) 的 contextWindow：

- 选择当前 Conversation 中已完成、有正文的消息。
- 最多 100 条，估计最多 48,000 字符，包含消息元数据的简单开销。
- 必须保留当前触发消息和最新消息，其余从新到旧选择；大条目放不下时可能跳过，并不保证得到连续历史前缀。
- 必须保留的两项自身就超过限额时直接报错。
- projectMessages 把历史背景与当前轮次区分，保留原发言人和来源含义。

这能限制部分历史规模，但不等于按模型 token 窗口管理整个请求。员工系统提示、技能、工具 schema、记忆、图片、材料和一轮内增长的工具结果还需要一起核算。旧消息离开窗口后，也没有由这个函数自动生成交接摘要。

### 2.3 Bobo 的 Memory 是另一条输入路径

[conversation-memory.ts](../../../src/runtime/adapters/mastra/conversation-memory.ts) 按 bobo:<conversationId> 使用 Mastra thread，lastMessages 为 100，working memory 为 thread 范围；prepare 重新核对源消息，删除过时投影，再交给模型。

它也调用上述 contextWindow，不应把有 Mastra Memory 本身当成已经具备完整自动压缩。新容量层必须在 Memory 装入消息之后看到实际有效输入，避免“宿主摘要一份、Memory 又补回全部旧历史”。普通员工不需要为此先改成 Bobo 的身份或会话入口。

### 2.4 多步执行已有预算与终态检查

[engine.ts](../../../src/runtime/adapters/mastra/engine.ts) 经 agent.stream 执行多步任务，prepareStep 检查上一轮流是否完整，再预留追加模型调用；[model-config.ts](../../../src/runtime/adapters/mastra/model-config.ts) 设置输出上限，目录提供时按 maxOutputTokens 收紧。

模型调用次数/工具预算、输出 token 上限、输入上下文容量是不同约束。容量维护不能重置 Work 预算，也不能绕过未知 EOF、不完整终态等现有阻断。现在的 processInputStep 主要用于模型请求观察和媒体适配，尚不是完整的上下文维护器。[agent-factory.ts](../../../src/runtime/adapters/mastra/agent-factory.ts)

### 2.5 可以复用的来源和工作区能力

- [service.ts](../../../src/runtime/service.ts) 的 contextMessages/materialMessages 已处理触发时间边界、来源快照、成员资格、材料和被遗忘消息。摘要输入必须从这些授权语义出发。
- [workspace-service.ts](../../../src/runtime/modules/workspaces/workspace-service.ts) 已有员工根工作区和按 Conversation 的工作位置、人格/记忆投影。内部上下文换代不迁移这些目录。
- [ProductStore](../../../src/runtime/adapters/storage/product-store.ts) 继续保存产品事实；摘要和分段是派生状态。
- [记忆召回](../../../src/runtime/modules/memory/memory-recall.ts) 继续提供员工长期记忆，新摘要不另造一套长期记忆所有权。

## 3. 复用 Mastra 的方式

本次按已安装包内文档与类型核对，避免将其他版本能力直接写成已接入：

- @mastra/core 的 processInputStep 可以访问每步 messages、systemMessages、tools、modelSettings，并返回调整后的消息。processLLMRequest 可检查转换后的 provider prompt。现有请求观察器需保留，与容量处理器有明确次序。
- TokenLimiterProcessor 支持估算 token、限制输入，并在 provider prompt 路径保持工具调用与结果成组处理。它主要是裁剪工具，不自动产生 BOAI 的工作交接或持久分段，不能单独作为本组完整实现。
- @mastra/memory 已导出 summarizeConversation：接受指定消息、模型、指令和 abortSignal，返回摘要与用量，不自行写入存储。可优先复用它生成压缩候选，由 BOAI 校验和提交。
- MessageHistory/WorkingMemory 继续沿当前用途。Observational Memory 是可用的另一套长期上下文机制，但本组不直接开启它来替换现有员工记忆与来源失效规则。

## 4. 四层数据关系

### 4.1 员工和产品会话保持稳定

Employee 是长期身份，Conversation 是现有用户可见消息空间，Work/Run 是业务执行记录。它们已经存在，本组不重新定义。

新增的 ContextSession 表示“当前给 Mastra 使用的工作上下文版本”。普通 API 请求未必存在服务端可恢复的 sessionId，因此这里是 BOAI 管理的内部标识，不假定供应商提供会话对象，也不把 Mastra Agent.id 从 employeeId 改成分段 id。

### 4.2 内部分段关系

~~~mermaid
flowchart TD
  E[同一数字员工与独立 workspace] --> C[现有 Conversation 与完整消息历史]
  E --> M[现有员工长期记忆 跨聊天召回]
  C --> S[Mastra ContextStream]
  S --> A[activeSessionId 当前工作上下文]
  S --> P[segments 历史上下文与来源索引]
  A --> H[已校验交接 加近期原文 加当前工作状态]
  M --> H
  H --> R[Mastra 下一步请求]
~~~

ContextStream 默认以 employeeId + 实际执行 conversationId + mastra 为身份。群中各员工的工作上下文分别管理；员工长期记忆仍贯通这些场景。普通私聊不能每次用新的 runId 建一个互不相干的 Stream。

自动化沿原来选择的内部执行 Conversation/执行身份区分上下文，最终仍在现有员工或群入口呈现。不能为容量分段新增一个用户可见会话，也不为统一内部 ID 合并现有自动化执行记录。

### 4.3 两种维护动作

- compact：当前 ContextSession 不变，生成新 checkpoint，以已校验摘要替换旧工作上下文中的一段历史，保留当前请求、必要原文和闭合工具步骤。
- rotate：创建新 ContextSession，写入 handoff 与必要近期记录，提交成功后更新 activeSessionId，旧 Session 作为 segment 保留。

选择取决于工作状态和压缩收益，不按固定消息条数强制换代。进行中的工作优先原地压缩；到达可交接点、重复压缩收益低或需要重建工作上下文时换代。即使新 Session 只包含一条交接消息，也不能漏掉当前尚未完成的用户要求。

API 主路径可以用“派生记录 + 请求装配”实现这两个动作，无须强迫每位员工新建 SDK Memory thread。Bobo 沿原有 Mastra thread 兼容 checkpoint 投影，并防止重复加载历史；若后续确需轮换其 SDK thread，必须单独完成旧数据映射与忘记语义验收，不能把产品 Conversation 一起轮换。

## 5. 容量检测

### 5.1 以真实目标模型与完整输入为依据

每次检查记录 connectionId/revision、模型实际选择、协议、窗口来源、测量时间及估算方法。模型或连接改变后重新计算，旧模型的窗口不可继续沿用。

窗口信息优先来自与当前模型匹配、可信的目录/连接能力；来源缺失时明确 unknown。不得把一个猜测的大窗口当成已确认容量。第一阶段保留现有保守字符保护并提前维护历史；对未知窗口的策略值和限制要记录在内部诊断，不能声称具备准确 token 占比。

候选计算：

- W：本模型可用上下文窗口。
- O：这次实际保留的输出容量，沿 responseOutputTokens 和当前阶段约束。
- R：协议、估算偏差及供应商规则所需预留。
- B = W − O − R：输入预算。
- I：本次最终系统指令、当前工具定义、记忆/交接、消息、工具结果、材料与媒体的输入估算总和。

必须确认该协议对输入/输出窗口的定义，不能在供应商已单列输入上限时重复扣除。缓存命中 token 仍占上下文，累计计费用量也不能代替这一次输入占用。

文本估算可以复用已安装 Mastra 的 estimator；图片/多模态依据已有协议适配能力采用可解释估算或保守预留，不能按图片 URL 的几个字符计算。未知与估算不等于实测。

### 5.2 三个检查时点

1. 本轮装配后：在已授权历史、人格、长期记忆、技能和材料准备完成后检查。
2. 每次工具循环发起下一步模型请求前：工具结果会增长，不能只检查第一步。
3. provider prompt 转换后：检查协议包装、Memory 加载及其他处理器是否又增加了输入；维护后的最终请求仍要满足预算。

初始候选可采用软线 I/B = 0.75、硬线 0.90，维护目标降至约 0.60；这些只是待 MC0 校准的内部策略，不能直接宣称适合所有模型。应有最低维护间隔和最小收益判定，避免每一步重复摘要。

### 5.3 超大单项与异常

如果仅必需指令、当前用户请求和必要输出预留就无法放入窗口，压缩旧历史无效。材料/大工具结果应沿已有文件读取、分页和来源句柄获取，保留原件与可查询位置；用户原始消息不被悄悄截断或改写。确实不可容纳时沿现有错误反馈说明原因。

供应商明确返回 context-length 拒绝时，允许在确认该请求未产生业务执行的条件下做一次有界维护与重建。超时、断流、未知 EOF 不等于容量拒绝，不能据此自动重发用户输入或工具动作。

## 6. 从检测到接续的执行状态

~~~mermaid
flowchart LR
  A[检查实际下一步输入] --> B{容量是否充足}
  B -->|充足| C[继续原 Mastra 工作]
  B -->|需维护| D[等待安全步骤边界并固定来源]
  D --> E[构建 compact 或 rotate 候选]
  E --> F[校验内容 来源 容量与取消状态]
  F --> G[原子提交checkpoint或activeSessionId]
  G --> C
  F -->|失败或版本变化| H[保留旧状态 丢弃过期候选]
~~~

维护必须满足以下条件：

- 同一 Stream 同时只有一个维护者，提交使用预期 revision/activeSessionId 校验。并发新消息仍沿原队列；交接只覆盖固定 throughSequence，其后的消息不能被当成已处理。
- 普通轮次之间是自然安全点；长任务内部可以在工具调用与结果完整配对、回执已落库且下一步尚未提交时压缩，不必等待整个任务结束。
- 有正在执行的工具、待批准请求、待用户补充或不确定外部写结果时，不通过新建 Session 规避等待状态。先沿原执行流程收敛到可接续边界。
- 先生成候选并重新验权，后持久化和切换指针。失败不能留下半份摘要成为下一轮权威输入。
- 提交后的下一次模型调用仍沿原 run/work、输入回执、取消信号与预算。若 SDK 必须结束当前 stream 再开内部调用，宿主显式记录接续关系，不创建新业务任务或再次消费原用户消息。
- 保留现有工具 call/result 的合法结构；不能移除 tool call 却留下 result，也不能把未完成调用伪装成已完成摘要。

## 7. 交接包必须保留什么

交接分为宿主结构化事实与模型生成摘要，两者不能互相覆盖。

宿主核对并提供：

- 员工、Conversation、当前 Run/Work、自动化 occurrence 等已有身份。
- 用户原始目标、当前未完成要求和最新纠正的 messageId/sequence。
- 已完成步骤的真实回执、产物 id/版本、文件位置；待执行步骤、等待依赖及明确失败。
- 本次授权资源版本、材料来源、来源快照和记忆失效版本。
- 当前业务工作目录、已有环境与产物引用；不复制或重建 workspace。
- 哪些输入已被消费、哪些消息还在队列、哪些外部效果未知且不可自动重做。
- 历史定位锚点及摘要覆盖范围。

模型摘要补充：有来源的关键事实、选择理由的简要记录、尚未解决的问题和下一步所需背景。摘要不得把猜测写成事实、把计划写成已完成，或将旧会话里的指令提升为系统权限。

必要的原文应直接保留：当前任务要求、关键数值/文件名/约束、最新用户纠正。摘要只有有限长度，不能声称无损；后续需要详细信息时应回读原记录。

摘要生成使用既有明确模型连接，不带业务写工具，不触发员工长期记忆提取。生成摘要及可能的结构化提取调用都要记入原计量；不能把附加模型请求藏在容量维护中。取消后不提交迟到摘要，不因压缩增加无限调用预算。

对超过摘要模型窗口的历史，按固定来源范围分批处理，保存每批覆盖和来源，不一次把全部历史传入摘要请求。再次压缩时保留原始锚点和覆盖关系，避免只有“摘要的摘要”而无法核对原文。

## 8. 持久化与历史定位

以下为候选领域结构，实施命名可沿仓库惯例调整；不能直接重命名现有 Conversation/Session 字段。

- ContextStream：稳定身份、activeSessionId、revision、当前 checkpoint 引用。
- ContextSession：内部 id、streamId、起止时间与消息范围、来源/模型指纹、active/sealed 状态、前序 segment、交接引用。
- ContextCheckpoint：摘要、受保护原文引用、覆盖消息/步骤、来源版本、使用模型、实际用量、生成状态、失效原因。
- ContextMaintenance：维护操作 id、预期版本、compact/rotate、准备/提交/失败状态与错误信息，用于恢复核对。

segments 可以通过 ContextSession 的链或有界索引表达，不要求把所有历史嵌在员工记录一个无限增长数组里。原始消息和执行原件继续保留在原库，分段保存关联和引用，不复制成第二份用户聊天。

历史锚点至少能表达：conversationId、messageId/sequence、runId、workId、步骤/回执 id、产物 id/版本，以及属于哪个内部 segment。回答时可用现有引用/消息定位能力；不新增 Session 页面。

历史读取优先复用 [ConversationSearchRepository](../../../src/runtime/modules/conversations/search-repository.ts)、原消息分页和授权快照。给 Mastra 装配可用的只读历史查询入口时，必须核对现有工具是否已经覆盖，缺口只补运行时桥接；不能因 UI 有搜索就宣称所有模型已能查询。

查询范围与摘要来源遵守原员工访问规则，且不能把本轮之后的新输入提前读成已处理工作。跨聊天记忆保留现状；需要原文时重新核对其来源，不把一个内部 segmentId 当成访问任意员工数据的凭据。

## 9. 恢复、失效与一致性

- 生成摘要时崩溃：active 指针保持旧值；重启只整理维护状态，不重放业务。后续获准运行可重新准备候选。
- 提交 checkpoint 或切换 Session：ProductStore 中将新记录、旧记录封存及指针 revision 一次提交，不能先改指针再补交接。
- 并发来源变化：提交前再次核对消息、记忆、材料与配置版本。过期候选不覆盖新状态。
- 仅新增队列消息：交接仍按已冻结边界有效，后续消息由原队列处理；不因新消息到达重复生成整个摘要。
- 忘记/清空聊天、撤销资料、删除来源或账号变化：相关派生 checkpoint 失效，沿原授权事实重建；已被删除的信息不能从旧 segment 摘要复活。
- 摘要失败：旧历史仍可访问；剩余容量足够则继续受控执行，容量不足则沿现有失败/继续入口停下，不无限重试或静默丢失关键要求。
- 转换成功但下一次模型失败：记录真实失败，不回滚成“从未执行”，不因换上下文重新发起已经完成的工具。

### 9.1 架构调研补充的实施约束

依据 [DS Bot 架构补充调研](../../2026-10-24-DeepSeek-Bot架构补充调研.md)，将以下机制并入本组，仍沿 BOAI 当前服务实现：

- 来源覆盖：checkpoint 保存来源身份、各自覆盖范围和版本，以及摘要/装配规则版本。不同 conversation/run 的 sequence 不可相互比较；新输入追加可作为未覆盖尾部接续，旧来源更正或撤销则沿失效机制处理。
- 一致快照：在安全步骤边界取得最终有效上下文及身份/版本，固定摘要输入，避免后续异步修改影响候选。提交前再核对 Stream revision、来源与取消状态；模型消息中的工具 call/result 必须闭合，不能用删除进行中尾部代替执行恢复。
- 权威与派生：摘要和检索投影可以重算；活动指针、输入消费状态、Work/Run 归属和业务回执不可作为缓存随意丢弃。ProductStore 保持提交权威，不引入第二份业务日志作为竞争依据。
- 跨存储准备：若使用 Mastra Memory 等外部存储承载交接内容，先准备可校验的候选，再由 ProductStore 原子提交有效引用、封存和指针；恢复时核对未引用候选，不能把数据库事务理解为已包含外部存储或模型请求。
- 输入接续：保留原 messageId、来源和顺序，区分候选准备、指针提交、输入接收及实际执行。更换请求投影时优先由原 Conversation/Work 消费原输入，不额外搬动产品消息；转交重试不能生成新的用户请求身份。
- 调用归属：摘要及提取请求复用 RunModelUsage 与原预算账本；同一回执更新不重复累计，真实新增的尝试分别计量，未知用量不能折成 0。请求重写、取消和失败仍保留原工作归属。

配置装配的按实例收敛仅作为已有 SourceService 的条件参考，不属于本组必做改造。现有事务、进程独占、员工记忆与自动化设计保持。该约束已纳入本轮候选，实际代码与验证分别见第12节和02。

## 10. 场景接入

### 普通员工私聊

按原联系人持续累积历史；只替换本轮模型工作上下文。隔天继续时，装入有效 checkpoint、近期原文、最新员工记忆和待办状态，而非只保留最后几句。

### 群中的 API 员工

按该员工在该群的运行流维护，保留发言人、群决定、自己的工作与其他成员结果的区别；群调度和 @ 规则保持。回到私聊仍通过员工记忆理解自己的群工作，不复制整个群上下文进私聊。

### 自动化

沿原自动化执行上下文维护，保留 occurrence、分工依赖、已交付内容和未完成事项。UI 仍在原员工或群会话呈现；换内部 Session 不能多产生一次触发、重复通知或成果。

### Bobo 的 Mastra 路径

在现有核心 Conversation 与 Memory 投影中接入同一容量合同。保持其 working-memory、权限和已有消息同步；只做必要兼容，不把本组扩大成 Bobo 会话重构。

### 其他一次性 API 阶段

判断、汇报、反思、自动化草稿等也需要请求容量检查；它们如果是一次性输入，不为凑统一结构强行建立持久 Stream。优先沿原输入/输出预算和已授权来源做有界装配，持久分段首先服务连续聊天与持续工作。

## 12. 本地实现映射（2026-10-24）

用户已明确开始按本文实施。候选位于分支 `feat/mastra-context-continuity`，基于文档提交 `ecc65e2c`；以下是实际接线，不代替02的验收记录。

- [context-repository.ts](../../../src/runtime/modules/contexts/context-repository.ts)：每员工×Conversation的ContextStream、内部Session、版本化checkpoint、维护记录与运行步骤checkpoint。准备阶段先登记维护者，提交时校验来源/CAS/取消；checkpoint、旧段封存和活动指针在同一ProductStore事务提交。
- [context-capacity.ts](../../../src/runtime/modules/contexts/context-capacity.ts)：有效模型目录窗口、输出预留与安全余量，以及明确标记unknown的本地输入策略。
- [context-maintenance.ts](../../../src/runtime/adapters/mastra/context-maintenance.ts)：受控摘要、历史分批、完整provider prompt的逐步检查与闭合工具组压缩、媒体快照、原消息历史定位。
- [service.ts](../../../src/runtime/service.ts)：提供宿主授权的原始全历史切面，绕过旧装配滑窗的信息丢失；每次读取/提交复核原员工、Conversation、来源、记忆和运行状态。附加用量沿RunModelUsage汇总。
- [engine.ts](../../../src/runtime/adapters/mastra/engine.ts) / [agent-factory.ts](../../../src/runtime/adapters/mastra/agent-factory.ts)：先装配有效checkpoint和未覆盖尾部，再沿原Work/Run执行；Bobo Memory同步剔除已覆盖历史，逐步容量检查发生在Memory及协议转换之后。
- 一次性行为/复核、团队规划、自动化草稿、连接测试及PPT专用审阅使用最终prompt容量守卫，不为这些调用创建持续Session。
- [history.ts](../../../src/runtime/modules/conversations/history.ts)：将五个上下文集合加入原聊天清理事务；明确遗忘清理该员工的派生上下文，删除员工同时清理其跨聊天上下文。

本地策略和边界：

- 已有有效模型目录时：使用当前精确modelId的contextWindow，减去实际输出预留和 `max(1024, ceil(window×8%))` 安全余量；软线为剩余输入预算的80%。
- 没有可信窗口时：保留 `window=undefined`、`source=unknown-policy`，采用48,000估算token的可变工作输入预算；固定系统指令与规范化工具定义另行完整计入估算，未知模式的维护线为固定装配加该工作预算。这不是供应商窗口声明，也不保证小窗口模型能接受该输入。宿主沿原目录快照提供元数据，不为此静默发起新的目录请求。
- 未知策略经过完整宿主装配的受控校准：旧24,000总量候选会误拒Bobo普通问候，其指令/Memory约7,861估算token、规范化工具定义约21,605；随后48,000总量候选仍误拒完整自动化任务的固定装配，因此最终将固定装配与48,000可变工作输入预算区分，完整输入继续统计，已知窗口仍核对全部总量。保留该原始失败，不据此声称真实供应商窗口已校准。
- 文本采用ASCII约3字符/token、非ASCII每码点1.5token的保守估算；图像部件暂按4,096估算token。工具按发送的description/JSON schema统计，二进制媒体不展开成base64正文。数值是实现策略，实际协议/模型占用仍需现场校准。
- 历史通过独立宿主端口从获准原始记录读取，不受既有100条/48,000字符装配滑窗限制；每次摘要只覆盖固定来源范围。来源引用采用增量checkpoint链，每段最多登记20,000个新增来源，读取时校验完整继承链，避免每段反复复制全部历史。兼容旧窗口时先计算实际会被其排除的来源，将摘要前缀扩展到最后一个遗漏位置；即使只有1–3条历史或未达到普通软线，也先覆盖这些来源。近期尾部不能只按条数假定可容纳；当前轮次必须完整保留，无法容纳则显式失败。单条大历史按完整序列分批处理，原始消息不改写。
- 普通轮次间首次维护compact，已有有效checkpoint且有新增待覆盖历史时在安全点rotate；运行内使用闭合工具组的临时请求投影和持久步骤摘要，继续原请求循环。
- 扩展历史在进入摘要/模型或历史工具返回前，沿原服务临界区和ProductStore事务核对原消息hash、遗忘屏障、材料版本，并追加到原RunSnapshot的召回输入与材料来源；提交成功后同步原EngineContext对象。历史工具只登记实际返回的消息，Work沿原材料来源接口继承，原失效传播和发布检查继续生效。
- 步骤摘要只在显式接续的原运行、相同员工/Conversation/Work与来源版本、原宿主确认工具已完成时作为参考恢复；核验取原Run的全部completed工具回执，包括读取工具。原completedWorkTools继续只负责其既有效果操作，不扩大效果去重集合；摘要不当作公共历史前缀，不把未知动作变成已完成。
- 摘要使用同一已选连接的无业务工具Mastra Agent，`maxRetries=0`，不配置extractor或长期记忆写入；每次实际请求取得原预算ID并记原始用量。
- ProductStore是新增持久化的唯一权威。Bobo SDK Memory仍是可重建的read-only请求投影，下一次请求前校正，未新增跨库原子事务。
- 旧嵌入式调用若既无宿主continuity端口又无已声明窗口，保留原公开chat/task合同；已声明窗口仍检查。正式AppService的Mastra/API执行统一注入端口，不因兼容旧调用而关闭产品容量维护。

真实模型的事实保留、摘要收益/延迟、图片估算和完整桌面连续工作尚待02指定验收，不能由本地HTTP模型固定回执代替。
