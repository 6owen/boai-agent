## 1. 完成标准

在保持当前页面、联系人、员工独立 workspace 和跨聊天记忆的前提下，完成并证明：

1. 下一次模型请求的上下文接近容量时能被识别，包括工具循环中途增长。
2. 能生成可核对的压缩 checkpoint，或建立新内部 Session 并更新 activeSessionId。
3. 用户目标、关键原文、已完成回执、未完成事项和历史锚点能够保留。
4. 下一步继续原员工的原工作；不重复执行已完成工具，不另建可见会话，不重置预算。
5. 取消、重启、并发消息、删除与撤权后仍符合原有事实和授权规则。

实施状态和验证结果只写在本文件第 5 节；01 维护设计，README 维护范围，不在多处分别登记“已完成”。

## 2. 实施阶段

- 验证 summarizeConversation 能使用 BOAI 原模型连接、取消信号和用量记录；核对额外 extraction 调用，不能漏计。
- 定义窗口元数据的可信来源、unknown 策略、输出预留与媒体估算；校准软/硬线，不直接复制其他项目比例。

通过条件：有代码入口及受控请求证据，能说明实际请求包含哪些内容、如何计量。未验证 helper 接入前，不先引入另一套 Memory 或独立模型 SDK。

### MC1：内部上下文状态与历史定位

- 旧数据按第一次受理当前员工工作时惰性建立初始内部 Session，不重写消息 ID、conversationId、工作区和历史 Work。
- 实现准备候选、CAS 提交、旧 segment 保留、并发单维护者和崩溃恢复。
- 落实01 §9.1的各来源覆盖/规则版本、一致快照、输入原身份和跨存储候选准备；业务权威继续由原ProductStore持有。
- 接入按原授权读取历史、回执、产物版本和消息锚点的路径。
- 在清空、遗忘、撤权、备份恢复的原链路中处理新增派生记录。

通过条件：在无真实模型的可控摘要结果下，指针/来源/失效/恢复合同成立；聊天窗口的数据身份保持原样。

### MC2：普通 API 员工的完整压缩闭环

交付内容：

- 在普通员工私聊中装配已校验 checkpoint、近期原文、当前请求和现有长期记忆。
- 在每次模型调用前计算完整预算，在工具循环边界进行维护，并检查最终 provider prompt。
- 接入受控摘要调用，保留关键原文、覆盖范围和原始定位；为大历史分批处理。
- 实现 compact 与 rotate 两种动作；轮换后继续原 Run/Work 或原消息执行链。
- 所有维护调用纳入原调用账本、取消和预算；失败有界，旧上下文保持可恢复。
- 附加调用沿原request ID核对回执，真实新增尝试分别计量；请求转换不丢工作归属，未知用量不计为0。

通过条件：长私聊、多次维护、单轮多步任务均能继续准确完成原请求；仅“请求没有超限”不足以通过。

### MC3：群、自动化与 Bobo 兼容

交付内容：

- 按同一员工在各现有执行 Conversation 的上下文分别维护，长期记忆继续跨聊天召回。
- 群中保留成员身份、共同结论、个人工作和依赖关系；不改群调度与展示。
- 自动化保留触发身份、occurrence、Work 分工、交付/通知回执和原可见聊天。
- Bobo 的 Mastra Memory 与容量处理器保持一致，避免原历史重复回灌；维持其现有 thread 和权限合同。
- 给一次性 API 阶段补必要容量检查，不强制制造持续 Session。

通过条件：同一 API 员工在私聊/群之间仍记得自己的经历；自动化容量维护前后只有原来那一次工作和应有交付。

### MC4：故障恢复与真实连续性验收

交付内容：

- 故障注入覆盖候选生成、写入、指针切换、下一请求提交及工具完成边界。
- 使用固定材料、独立答案和已批准模型配置验证长期事实、最新纠正、未完成事项与工具去重。
- 核对真实请求占用、压缩收益、维护次数、额外调用和延迟，保留失败与 unknown 结果。
- 通过现有 UI 路径确认联系人、连续记录、原工作与文件交付；不新增页面设计。

通过条件：第 3 节适用场景逐项有相同源码下的证据；未验证的模型/协议边界单独列明。技术通过不自动等于长期业务质量达标。

## 3. 固定验收场景

### 容量与压缩

- C01：同一普通 API 员工的私聊连续增长，触达软线后生成 checkpoint；早期关键事实仍可正确回答，并能回读原消息。
- C02：同一轮多步工具返回导致输入增长，下一次模型请求前触发维护；保留完整 call/result 对，已执行动作不再执行。
- C03：系统指令、技能、工具 schema、长期记忆、材料、图片和输出预留共同计入检查；不能只按聊天正文算。
- C04：模型切换为更小窗口时立即按新窗口计算；模型目录缺失时使用明确 unknown 策略，不伪造窗口数值。
- C05：单条当前输入或必需指令无法容纳时给出准确失败，原件保留；不得以成功压缩为名丢掉用户要求。
- C06：连续至少三次压缩/换段后，原始事实、时间、发言人及最新纠正仍正确，摘要引用能定位到原文。

### 身份与工作连续性

- C07：rotate 前后 employeeId、workspace、conversationId 和可见消息顺序不变；activeSessionId 改变且旧 segment 可查询。
- C08：正在进行的 Work 在安全步骤边界换上下文，下一步接续原待办与真实成果；不创建新业务任务、不补造完成状态。
- C09：私聊与群聊先后发生工作，员工回到另一场景仍可按现有长期记忆知道自己的经历；新增 checkpoint 不改变记忆归属。
- C10：同一群两名 API 员工分别维护上下文，发言人、分工和同事结果不混为自己的完成回执。
- C11：自动化在一次执行中维护上下文，occurrence/Work 身份、最终交付和通知次数正确，UI 仍归原员工/群会话。
- C12：Bobo Memory 加载后容量仍正确，已压缩历史不被重复加载，当前请求及 working memory 不丢失。

### 历史、并发与故障

- C13：交接准备期间到达新消息，候选只覆盖固定 throughSequence；新消息由原队列按一次输入处理。
- C14：同一 Stream 并发触发维护，只有一个版本提交；其他候选不能覆盖最新 activeSessionId。
- C15：摘要调用失败/超时/被取消，旧指针保持，迟到结果不提交，模型调用与取消记录准确。
- C16：分别在候选持久化前、提交前后与下一模型请求前重启；恢复得到旧完整状态或新完整状态，不存在无交接的活动 Session。
- C17：待批准、待用户补充、工具仍运行或外部效果未知时，不借换 Session 重新申请/重复执行；原等待入口继续有效。
- C18：删除消息、遗忘、清空聊天、撤销材料/来源后，旧 checkpoint、segments 和历史查询不能复活已失效信息。
- C19：明确 context-length 拒绝可按合同有界重建；普通网络断流/未知 EOF 保持原失败，不能套用容量重试。
- C20：预算、工具次数和调用账本跨维护连续；摘要/结构提取的额外调用被记录，不能以新 Session 重置额度。

### 原页面回归

- C21：沿现有员工私聊、群聊、自动化结果、历史定位与文件交付旅程检查；没有新增联系人、话题导航或 Session 操作入口。
- C22：老数据首次启用、再次重启、功能回退均保留原聊天和员工 workspace；回退可停用派生状态，但不能删除原记录或重放原工作。

### 架构补充边界

- C23：checkpoint缺失、摘要规则版本变化或来源更正/撤销时，只重建有效派生上下文；不删除业务回执，不重置活动工作，也不从旧摘要恢复失效信息。
- C24：摘要生成期间原输入对象变化、新消息追加或其他来源恰有相同sequence时，候选仍只覆盖固定来源切面；新增尾部正确接续，进行中的tool-call不被删掉伪装为完成。
- C25：同一附加模型回执重复到达只更新一次；真正新增的请求尝试分别计入原工作，失败/取消/缺失用量的事实保留，内部Session轮换不清零预算。
- C26：如果实现涉及ProductStore与Mastra Memory两处存储，分别中断于候选写入、有效引用提交及输入接收后；无交接的候选不能成为活动Session，未引用候选可识别，已消费输入不重放。若没有跨存储路径，明确记录不适用原因，不制造第二套存储。

这些是验收要求，不是本轮已通过的结果。C09 不要求新增群共同记忆库；验证现有员工记忆贯通即可。

## 4. 证据与验证方式

每次维护记录至少包含：源码/依赖版本、员工和业务身份、旧/新内部 Session、维护操作 id、来源范围、前后输入估算、窗口来源、实际模型用量、动作、提交结果和失败原因。

验证按层推进：

- 纯逻辑/存储：窗口计算、来源锚点、CAS、原子性、失效、旧数据和崩溃边界。
- SDK 受控协议：已安装 Mastra 的处理器顺序、Memory 注入、工具循环结构、摘要取消与预算登记。
- 真实 API 任务：长上下文和多次交接后的事实、工作结果与历史回读；使用已批准的配置和预算。
- 现有 UI：只验证连续聊天和原旅程未受影响；API 返回成功不能替代可见路径验收。

测试沿仓库现行开发与评估规范执行。模块通过、UI 通过、真实模型任务通过分别报告；未完成真实长对话前，不能宣称连续身份已认证。本组文档创建不触发这些产品检查。
