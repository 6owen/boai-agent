# 前端响应性能分析与优化计划

## 1. 已知问题与本轮边界

- 用户明确报告“页面切换、各种展示都感觉卡卡的”。这是已报告的体验问题；根因、触发数据规模和当前耗时仍未知。
- 用户补充：刚启动、没有Agent运行时，切页面也卡。后续优先核对空闲切页公共路径；流式输出与长时累积问题不作为当前首要假设。
- 此前仅文档阶段已被2026-10-28的实施授权替代；当前结果见第6节与05实测报告。
- 最初的仅文档阶段用于落实分析与优化合同；不把源码复杂、组件较大或依赖较多直接判为根因。后续实施状态以第6节最新记录为准。
- 覆盖应用壳、页面导航、聊天/流式展示、执行过程、列表/搜索、文件预览、设置交互。语音开发归另一session；后续性能样本只记录其启停状态，不在本专项实现语音功能。
- 用户感知发生在界面，根因可能在Renderer、Main/IPC或runtime查询。对整个交互路径计时，再分配到责任模块。
- [03现有资源合同](03-性能与内存验收合同.md)继续有效；短期内存/CPU门槛通过不能代替交互流畅。本专项也不代替长期日常使用。

## 2. P0：固定真实基线

- 先确认用户实际运行方式和构建身份，不预设每天使用`pnpm dev`；开发构建和正式构建分开。记录macOS、硬件、显示缩放、窗口尺寸、刷新率、主题、数据规模与后台任务。
- 先从实际反馈挑最明显的3条交互；再覆盖下面场景。每条保留具体起点、操作、可交互终点和复现数据，不能只留总启动时间或主观“变快”。
- 冷启动/首次打开与预热后的重复操作分开；实际个人数据先只读统计，压力复现使用隔离副本或等规模夹具，避免将个人内容放进性能报告。
- 高频交互目标采集至少3批、合计50次有效样本，报告中位数、P95及完整分布；不足50次保留单次值和样本数，不把不稳定尾部统计当精确结论。首次加载等低频场景独立报告。
- 性能采样与截图/堆快照的观测开销分开；不将强制GC开销混进自然交互耗时。正式计时批次与诊断trace批次可分开，但必须绑定相同源码和输入。

## 3. 场景与测量对象

- PF01 页面切换：聊天→通讯录→设置→聊天。测点击到首帧反馈、到目标页可交互，以及数据读取、React commit、布局/绘制所占时间。
- PF02 聊天切换：短历史与长历史、缓存命中与首次读取分别测；核对首次可读、输入框可用、消息锚点及滚动位置。既有有界窗口不预先替换为另一套虚拟列表。
- PF03 输入与流式响应：输入法连续输入、长回复分片、思考/工具事件并发；测键入到绘制、主线程长任务、每批事件的渲染次数与帧间隔。
- PF04 长内容展示：长Markdown、代码块、表格、图片及执行详情展开。定位解析、高亮、布局和图片解码，不能以隐藏正文或丢事件换速度。
- PF05 列表与搜索：会话/员工/资源列表在普通及大量数据下滚动、筛选、搜索；区分本地计算、IPC往返和数据库查询时间。
- PF06 文件面板：打开/切换/关闭PDF、Office、diff和网页预览。分别测首次初始化与再次打开；检查隐藏worker/订阅是否继续占用资源。
- PF07 设置交互：展开下拉、切换分组、编辑与自动保存；区分本地反馈和真实保存回执，不能提前报保存成功以掩盖慢请求。
- PF08 后台任务下交互：同一固定流式/工具事件负载下重复PF01/PF03；空闲与工作中分开，观察是否由事件广播或数据复制放大成本。

## 4. P1：源码检查入口与待验证假设

- 应用壳：[app-shell](../../../apps/electron/src/renderer/components/app-shell/index.tsx)。已有共享snapshot和多个页面/面板消费者；检查一次变化实际影响哪些子树。此处仅为取样入口，没有证实广泛重渲染是根因。
- 聊天：[chat-view](../../../apps/electron/src/renderer/pages/conversations/-components/chat-view.tsx)、[阅读状态](../../../apps/electron/src/renderer/pages/conversations/-components/use-conversation-reading.ts)。核对事件频率、消息窗口、切换/预取和滚动定位，保留现有消息分页、引用、草稿和阅读合同。
- 内容：[Markdown](../../../apps/electron/src/renderer/components/common/markdown.tsx)。测相同历史内容是否反复解析、长代码块是否阻塞，再决定缓存、增量解析或延迟初始化。
- 请求：[desktop-client](../../../apps/electron/src/renderer/services/request/desktop-client.ts)。把请求排队、传输、服务处理和Renderer应用结果分段；先排查重复请求和过大的snapshot，再决定是否优化协议。
- 资源：复用[desktop-resource](../../../tests/e2e/support/desktop-resource.ts)、[background-resources](../../../tests/e2e/support/background-resources.ts)和[CPU窗口](../../../tests/e2e/support/resource-cpu.ts)；保留原Main/Renderer/runtime身份和原阈值。
- 工具优先使用Chromium Performance trace、React Profiler诊断构建及Electron进程指标。React开发诊断的额外开销单列；优化收益在一致的运行模式复测。[Electron官方性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)
- 依实际证据分别采取：缩小订阅范围、降低无效更新、合并高频展示更新、复用解析结果、延迟重组件/worker初始化或减少阻塞IO。以上是候选手段，不预先批量加`memo`、定时器、缓存或换状态框架。

### 空闲切页的初步判断

- 共享渲染范围：聊天、定时任务及打开过的设置页保留在组件树中，主要以隐藏样式切换；壳层状态变化可能连带重算无关页面。需要测实际耗时和渲染次数，保留组件本身不等于性能缺陷。
- 过渡效果：[内容切换样式](../../../apps/electron/src/renderer/pages/settings/settings-transition.css)使用400毫秒位移、渐显和模糊；[设置切换逻辑](../../../apps/electron/src/renderer/pages/settings/index.tsx)有主动布局读取。可在诊断时临时关闭效果做对照；动画时长不等于主线程阻塞时长，也不意味着所有页面都使用同一过渡。
- 数据读取：返回聊天刷新会话，首次读取先获取阅读位置再取消息；定时任务页激活时读取列表。分别测IPC/查询等待与结果渲染，尚不能将读取本身判定为慢请求。
- 初步复杂度：局部动画/重复请求通常较小，组件更新隔离可能为中等；目前没有支持大规模重构的证据。后续可先给两三条空闲切页诊断设小预算，再依据热点评估修复投入，不预先承诺工期或收益。

## 5. P2/P3：修改与验收

- 每个改动绑定一个可复现问题、基线trace和因果假设。先登记预期影响与目标指标，再改代码，避免测试后挑最好看的指标。
- 门槛根据真实基线和可接受体验在改动前确定；没有采样时不凭空宣布200ms之类数值已达成，也不改现有资源合同门槛。
- 基线/候选固定同一构建模式、机器、数据、窗口和负载，交替运行控制缓存与机器波动。报告分布、样本数、冷/热差异和未解释异常；收益未超过波动时记为没有可靠改善。
- 功能必须保持：草稿、自动保存、权限/回执、完整消息/工具过程、文件版本、滚动/选区、输入法和可访问性。优先补这些交互的不变量回归，不编写只验证缓存实现细节的测试。
- 不通过禁用功能、丢流式事件、只显示最后结果、延长固定动画或伪造立即成功来“优化”。若确需改变交互，作为明确产品变更单独审阅。
- 有意视觉变化依现行[UI基准与PR门禁](../22.开发自动化与持续测试/06-UI回归基准与PR门禁.md)处理；截图通过不是性能通过。
- 验收交付包含复现步骤、基线/候选指标、原始trace位置、变化原因、功能回归及遗留项；用户体验评价与机器测量分别记录。
