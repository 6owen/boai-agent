## 8. 2026-10-08：API群顺序聊天首版

### 8.1 代码与范围

基线`804aa91a`及本次未提交修改；没有升级SDK或新增消息中间件。Mastra 1.71.0沿既有stream/用量/Trace能力增加无工具`coordination`阶段。普通新用户API群、有效收件人至少两位才解释一次；只输入获准公开对话、成员ID/姓名/角色，不输入bootstrap或私有记忆内容。

解释结果为独立参与或单轮顺序聊天。文件工作/工具任务继续走成员判断与既有Work；独立参与保持并行。无明确顺序时模型返回null，由宿主填入冻结名单；显式顺序必须恰好覆盖每位收件人一次。一次格式修复与限流重试均受原轮次计数、五分钟期限及输出上限约束。该阶段在运行中标为coordination，在模型活动中计为判断，不产生聊天气泡。

顺序状态位于`DiscussionTurn.coordination`：成员配置、来源运行、revision和每步真实Message/event/hash。其余原投递进入waiting；当前成员只运行一次无工具chat。完成Message、发言回执、进度和下一投递在现有提交事务一起保存。后续调用实际读取已完成前置正文并核验来源/hash；失败/取消不推进，用户新消息中断未开始步骤。重启只保留历史并中断未完成状态，不自动续跑。单步重试拒绝重放原顺序，要求用户明确新请求。

单聊、只点名一人、原Work/组织启动、补充/修订及本机或混合群走原路径。**本机/混合群尚未获得新顺序协议**，没有新增UI提示或改变已保存配置。任务分工仍由原Work负责，本次没有增加通用协作规划器或语义完成评审器；`completed`仅表示计划步骤结构完成。

源码落点：`group-scheduler.ts`、`service.ts`、`contracts.ts`、Mastra的`engine.ts`/`agent-factory.ts`，以及新增共享状态和纯协议`group-coordination.ts`。既有离线群模型夹具接受新增私有阶段，并明确返回独立参与，保留原业务断言。

## 9. 2026-10-08：pnpm dev 三人五轮编辑部真实验收

### 9.1 场景、来源与固定边界

用户明确“不需要安装包，直接 pnpm dev”，并要求复杂多阶段、多轮对话与多轮协作。本批使用实际开发入口启动 Vite 与 Electron，不制作安装包；隔离数据经原系统加密桥只读复用选定的 `deepseek-v4-pro` API 连接，三名新员工（选题策划、写手、编辑）保持独立身份、工作区和记忆。没有写入用户原会话，没有调用本机Agent或外部A2A。

唯一BDD入口为 `tests/e2e/features/editorial-collaboration.feature`，步骤在 `editorial-collaboration.steps.ts`。输入固定为“疲惫上班族用周末90分钟写文章”，15分钟定题、45分钟初稿、30分钟修改是合成练习安排，禁止虚构研究、采访或效果保证。每次测试为全新场景，用户通过原输入框发送五轮请求：

1. 策划→写手→编辑依次讨论立意，读取前一人的实际发言，不创建Work。
2. 用户确定立意，点名策划负责；正式委派写手交付《周末90分钟.md》，再由编辑依赖已交付初稿、实际读取原件并交付《审稿意见.md》，负责人等结果后汇总。
3. 用户从第一版卡片点“要求修改”，在同一输入框明确新开头、不含“高效”的标题、恰好三条15/45/30清单；写手发布关联原hash的第二版，原版保留，修订使用独立新根/预算。
4. 用户点名编辑负责第二轮协作，编辑和策划都实际读取第二版；编辑委派策划交付《发布文案.md》（三个标题与发布摘要），等结果后汇总，文章不再改写。
5. 完整关闭并重新 `pnpm dev` 启动同一数据，核对零新增运行/工作/成果及原件hash，再发送新聊天，写手→编辑→策划依次回顾最终版本与限制。

### 9.2 发现的实际故障与修复

第二次真实运行中，两名同事的文件和主人的最终总结都存在，但主Work仍为 `blocked/no_progress`。同次记录证实：负责人在依赖返回后的接续没有调用 `report_work`，后台采用“未提交可检查业务结果声明”的默认状态，同时发布了声称已完成的正文。不是文件丢失，也不是等待依赖未满足。
