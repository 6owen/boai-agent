# 产品范围与协作语义

2026-10-08实施说明：普通API群首版已接线，本文其余条款仍为目标范围；逐项进度以05为准。

## 1. 成功标准

用户用自然语言给出共同请求，员工能够根据请求选择独立贡献、依次接续或分工交付。用户无需编排每一次唤醒，也无需为每个群选择永久模式。

员工身份、真实发言和工具执行保持独立。宿主保证共同协议的执行顺序与状态一致，模型负责理解请求、提出方案和完成自己的内容。

## 2. 三类协作关系

| 关系 | 识别依据 | 执行约束 | 结束依据 |
| --- | --- | --- | --- |
| 独立参与 | 各自内容互不依赖，例如分别介绍或独立提意见 | 成员独立判断，按原容量并行；允许合理pass | 参与机会处理完；不自动声称解决了更大目标 |
| 依次接续 | 当前内容必须基于前一位或指定前置结果 | 一条依赖链同一时刻只有一个有效生成资格；实际提交后推进 | 约定的参与者/步骤完成，并记录可检查结果或未核验状态 |
| 任务分工 | 存在受授权执行、独立交付物和负责人 | 复用Work；独立子工作可并行，有依赖的步骤等待真实结果 | 原负责人依照交付要求核对成果，沿原结果证据结算 |

协作关系和`chat/task`是两个维度。报数、接龙可以仍是无工具chat；顺序本身不授予文件、浏览器、命令、建群或管理权限。复杂工作也不必全部串行。

## 3. 共同约定与员工自主

### 3.1 群级理解

首批候选方案是在新普通群请求上形成一次有界、只读的结构化理解，输出目标、协作关系、必要参与范围、原请求中的顺序/依赖和结束约定。宿主验证成员与来源并持久保存，员工收到同一版本。它不是新增可见员工，也不能代替其他员工编造回复。

优先复用明确的宿主接续合同；已建立的顺序接续或Work唤醒不重新从头理解。新理解的调用、格式修复和耗时都必须计入该请求原预算，不宣称这一步无成本。

### 3.2 顺序如何确定

用户指定顺序时保留精确顺序；需要轮流且未指定顺序时，首批建议固定采用本次群成员列表的保存顺序，冻结为本轮顺序。模型负责判断是否需要依次接续，代码负责按已确认名单推进，不按模型快慢争抢先后。

“大家开始报数”的候选默认解释为当前获准参与成员从1开始，每人一次。该约定来自对请求的理解，不建立全局报数关键词路由。用户明确其他起点、顺序或多轮要求时以其原文为准；涉及重要分歧且无法确定时，由一名实际参与员工提出一次澄清，不让全员各问一遍。

### 3.3 自主性与责任

宿主授予机会不等于已完成贡献。员工可指出歧义、无法完成或依赖失效；对于要求人人参与的轮次，某人pass不能自动视为报数成功。暂停/跳过必须按本轮明确约定处理，缺少约定则记录阻塞或请求澄清。

独立问候仍允许全员合法pass。模型异常不能伪装成pass，自动判断“通过”也不能冒充人工认可。

### 3.4 有限动态性

第一阶段支持本请求冻结的单链接续；不建立无限自由讨论、自治辩论主持或通用游戏引擎。若用户要求并行收集再汇总、审核后修改等工作关系，沿原Work依赖表达。任意动态对话图留作后续，不能用未经确认的新子目标延长本轮。

## 4. 用户可见行为

- 保留现有群聊天、composer及聊天/任务/文件入口，不增加模式表单、协作配置页或独立待处理页。
- 每条回复仍来自实际员工；顺序场景可以显示当前员工正在处理，但不能提前展示后续员工基于旧输入生成的答案。
- 技术ID、状态版本、投递游标等进入原活动/Trace或内部记录，不堆到普通聊天正文。
- 流程正常时无需额外主持消息；遇到阻塞，复用原消息/工作反馈，说明具体缺少什么。
- 文件工作沿原真实成果卡片、固定版本预览和明确修订；同伴说“已完成”不能替代文件证据。

## 5. 首批范围

先在Mastra/API普通群实现依赖型对话，再核对其与原Work任务分工的边界。单聊不进入群理解；bobo组织首发和Work定向唤醒沿已有真实合同，不能重复建立群根或预算。

不增加MQ/Redis，不切换Mastra Memory，不重建员工身份或消息存储，不恢复本机运行时开发/兼容测试。混合含本机成员的已有会话不能静默删员、换后端或被标作新协议已支持；首批准入和不支持时的明确反馈须在GC1落定，历史仍可读取。
