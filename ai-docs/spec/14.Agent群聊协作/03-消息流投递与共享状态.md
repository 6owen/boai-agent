# 消息流、投递与共享状态

## 1. 三层职责

| 层 | 问题 | 当前基础与新增范围 |
| --- | --- | --- |
| 消息可靠性 | 原请求和结果是否持久保存、重复或失联 | 复用ProductStore、requestId、MessageReceipt和提交事务 |
| 消息分发 | 谁可看见、哪些消息进入获准上下文 | 复用群成员/材料权限、Message和ConversationEvent引用 |
| 协作调度 | 谁现在处理、基于什么结果、怎样推进目标 | 扩展轮次协作状态和AgentDelivery语义，接原Work依赖 |

消息可见性、模型唤醒和业务执行授权分别核对。全群可读的一条结果，不等于必须让全员再调用一次判断模型。

## 2. 复用共享正文与成员投递

[sendMessage](../../../src/runtime/service.ts)已经将原消息、请求回执、轮次和成员投递记录同事务保存。正文是一份共享Message，各成员AgentDelivery引用事件；现有系统并非每成员复制整段正文。

建议继续保留这个结构，增加投递的业务原因：

| 原因（概念名称） | 对模型的影响 |
| --- | --- |
| `context_only` | 可供后续获准读取，不立即调用模型 |
| `participation` | 独立参与机会，由员工决定reply/pass等 |
| `sequence_step` | 某个已提交前置结果使本人接续步骤就绪 |
| 原`work_ready` | 原Work等待解除或委派就绪，只唤醒其负责人 |

以上名称不是新增API声明。实现时优先扩展现有事件/投递，不建立另一个泛化“收件箱服务”。这里的员工待处理事件也不是已退役的用户“待处理”页面，更不能复用用户未读游标作为Agent执行资格。

## 3. 轻量共同状态

首批已将版本化协作状态放在现有DiscussionTurn.coordination，由同一ProductStore事务维护。以下字段表保留完整设计概念；实际类型、单进程持有权与未接入条款见05及共享domain/group-coordination.ts。

| 概念 | 用途 |
| --- | --- |
| 原请求身份、协议版本、语义理解来源run | 区分本次共同约定和历史消息；旧数据不重解释 |
| 协作关系、目标、结束约定 | 区分独立回复、顺序对话和Work工作 |
| 冻结参与者与顺序、成员配置版本 | 使模型完成快慢不改变顺序；变化时重新核对资格 |
| 当前步骤、状态revision、前置结果引用 | 判断谁有资格开始，不能只靠一句“轮到你” |
| 当前持有者run与步骤代次 | 拒绝两个执行者同时提交同一位置；旧run不释放新资格 |
| 已提交贡献的员工/消息/完成事件/hash | 前置事实可复查，正文沿原消息读取 |
| 结束原因、目标检查证据或未核验标记 | 区分结构结束、目标达成和待判断 |

不复制员工私有记忆到群状态，不保存另一份消息正文或另起成果版本。正式任务仍以WorkRepository为任务权威，共同状态只引用原Work身份和结果；DiscussionTurn不另建一套工作状态机。

## 4. 可靠提交与唤醒

顺序步骤的公开消息、步骤完成事实、共同状态revision以及下一步投递意图必须原子提交。提交失败不能先推进内存或唤醒下一人。队列通知发生在事务后；通知失败保留持久待处理身份，运行期可按该身份重新投递，不能重做已经完成的模型/工具调用。

幂等至少绑定原轮次、协议版本、步骤身份及前置结果版本。重复消费先核对已有受理/提交事实。不能将普通时间戳、文本相似或employeeId单独当作业务去重键。

| 不确定窗口 | 要求 |
| --- | --- |
| 事务未提交 | 原进度不前移，无下一步资格 |
| 事务已提交、事件尚未通知 | 从原持久待处理记录核对，避免丢失进度 |
| 通知重复、消费者并发 | 比较当前步骤版本与run，只产生一次有效执行资格 |
| 已生成/已执行、提交结果未知 | 保留未知与原身份，只读核对，禁止猜测失败后重放 |
| 取消或撤权与提交竞争 | 在原临界区/事务比较当前资格，失效者不能提交迟到结果 |

这属于事务内保存后续事件的思路；队列系统本身不能替代消费者幂等。[AWS事务发件箱说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)可作原理参考，不代表本项目需要部署AWS或新增MQ。

## 5. 顺序与读取位置

必须分开记录：界面消息位置、公开完成事件、员工本次输入快照和业务步骤进度。chat气泡开始流式时已经有sequence，但当时并不构成完成结果。

只有完整提交的前置回复才能供下一步使用。下一员工的模型输入应包含原请求、共同约定、本人当前职责和固定前置结果；原文过大或源已失效时明确阻塞，不能悄悄截去必需依赖或猜最新版本。

此处的“已观察”只证明输入含哪些消息，不证明模型正确理解。目标检查仍独立进行。

## 6. 重启、清理与备份

沿现有规则：重启只核对已提交记录，中断未完成运行，不自动调用模型或重放工具。即使存在待处理投递，也不能在启动扫描时自动消费为新的业务执行。显式继续时核对原请求、步骤、前置结果、原预算、权限和未知效果后再准入。

清空/删除沿原代际与去重边界清理共同状态和待处理事件；迟到回调不能复活聊天。备份恢复保留已提交进度和中断/未知事实，不恢复活动run持有权，不把旧`completed`迁成目标达成。

## 7. IM文章的适用范围

写扩散单条消息面向N成员通常产生O(N)投递；N人各发一条时可能累计O(N²)，不能笼统称指数增长。读扩散节省写入复制，但读取、连接和网络仍有成本。微信/TG内部实现、人数限制和微博故障因果没有在本组独立核验，不作为设计前提。

对于本产品，更直接的放大风险是每次员工发言都触发其他员工模型判断。应记录真正的模型调用与无用唤醒，采用共享正文、必要投递和定向接续降低放大；不承诺“读扩散后零额外消耗”。

当前本地应用可继续使用SQLite事务与持久待处理记录。SQLite官方将桌面应用数据存储列为适用场景；只有后续确有多机运行和实测吞吐问题，才另议消息中间件。[SQLite适用范围](https://www.sqlite.org/whentouse.html)
