# 验收矩阵与效果评估

日期：2026-10-08。以下是**待实施的验收要求**，不是已经存在的测试入口或通过报告。GC-AC编号对应本组条款；实际场景文件、版本与结果由05登记。

## 1. 四个优先产品场景

### GC-AC01 五人报数

隔离建立五名真实独立员工，在普通群输入现场原样短请求“大家开始报数”。默认约定为从1开始、每人一次，参与顺序允许按本轮冻结成员顺序确定；另建明确顺序/起点的变体，不能用加强提示后的成功替代原样请求结果。

通过条件：五名不同员工各有一条本人实际生成的报数回复，按协议顺序形成1、2、3、4、5，无重复、遗漏或代报。对第2至第5位，实际模型输入包含精确前置回复及共同约定，模型调用开始晚于前置完整提交。无工具调用、不创建业务Work。最后一位结束后无无意义全员补判循环。

审核数字的解析在验收器里完成；生产不能按“报数”关键词注入正确答案。离线模型只证明调度因果，真实模型另验语义。

### GC-AC02 内容接龙

依次让每位员工在上一人的句子上新增一项内容，最后形成可检查的累积结果。测试在前一位实际完成时才产生本样本的新标记，使下一位无法从原请求提前获知它。

通过条件：每一步实际输入包含上一条新内容，输出完成本人的新增贡献并遵循已约定保留规则；不能由某个员工一次代写全组。随机标记、成员顺序和快慢配置换样本，验证通用依赖而非固定数字脚本。

### GC-AC03 写作、审核、明确修改

在原授权目标中安排写手产出V1，审核员读取该真实固定版本给出具体意见。随后由自动化测试从原文件卡片进入同一composer，以用户身份明确提交“按审核意见修改这版”的原版本修订请求，指定负责人产出V2。文件名、必要内容与审核要求在输入版本中固定；测试代理负责全部操作，用户只审阅结果。

通过条件：实际执行者身份正确；V1原件/hash与审核输入一致；V2保留版本来源，能核对修改对应意见；每个根Work内的委派/依赖共享该根预算，明确修订使用新请求/新根和预算，旧已交付根不重开；负责人只在必需结果存在后声明交付。同伴自称“已发布”不构成文件证据。本例不证明无需用户明确修订即可自动替换已发布成果。

### GC-AC04 并行介绍回归

普通群请求各介绍自己，受控慢成员与快成员同时存在。

通过条件：成员仍独立决定参与，快成员无需等待慢成员判断/生成；各自身份正确、没有文件Work或工具。确定性测试验证允许并行，不要求真实供应商每次恰好同时输出，也不以全员必须回复替代自主参与。

## 3. 验证层不能互相代替

| 层 | 可以证明 | 不能证明 |
| --- | --- | --- |
| Vitest＋受控引擎 | 并发/事务/幂等/版本、前置未提交时下一步不启动 | 自然语言理解正确、供应商实际输出可用 |
| 真实Mastra SDK＋离线HTTP/SSE | 正式适配器输入、阶段调用、流式/协议行为 | 真实供应商语义能力 |
| 隔离真实API | 真实模型是否识别关系、读取前置并正确贡献；成本 | 实际UI展示、原生关闭或发行包行为 |
| 实际Electron BDD | 原聊天入口、界面/过程/文件与重启 | 若后端是离线模型，不能声称真实语义通过 |
| 同场Electron＋真实API | 同一次实际产品交互与真实结果 | 不自动代表发行包、全部模型或用户认可 |
| 发行包 | 明确包版本下的产品行为 | 不能借源码结果填补未跑组合 |

确定性测试用屏障和提交事件建立因果，不用固定sleep猜时序。仅看到屏幕顺序1–5不足以通过GC-AC01；必须核对每个模型请求和前置提交身份。

## 4. 语义与完成口径

报数连续性、参与者唯一性、指定顺序、文件hash/版本关系等由代码检查。接龙内容连贯、审核意见是否有用、修改是否真正改善等使用预先固定的评估条件，并保留待人工评价状态。

模型自评只算一个来源；不以“我已完成”、所有delivery为completed或没有异常代替目标验收。一次失败不能被后续成功覆盖，合法pass、失败、阻塞、未知、未执行分别统计。

真实采样使用隔离员工和合成材料，不复制用户私有历史与记忆。原样短请求、明确协作变体、快慢模型组合分别报告。更换输入或模型后建立新批次，不混为同一个成功率。

## 5. 性能与调用成本

每样本记录首次实际回复、最后有效结果、调度结束和记忆结束四个时间；模型连接排队与执行耗时分开。逐阶段记录群理解、参与判断、回复/执行、纠正/检查和记忆调用，未知用量保持未知。

重点比较无贡献唤醒数、过期重判数、重复业务执行数和总调用/Token。现场20请求仅是单次观察值，不能直接充当统计基线或预先承诺降到某个数字。顺序任务允许必要等待；以正确结果和可解释开销为目标，不通过抢先生成换取低延迟。

冻结每批请求/时间/费用上限后运行，不因失败临时加额度。沿原账本计入理解、修复、记忆与子工作；停止、重启、读取历史不能新增模型请求。

按场景保留输入版本、成员配置摘要、原用户消息、共同约定及来源、每步实际模型输入/输出、完成事件/投递/状态revision、调用账本、失败与中断记录。凭据和无关私有材料不进入报告。
