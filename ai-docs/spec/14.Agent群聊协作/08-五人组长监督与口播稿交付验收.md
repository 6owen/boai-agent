# 五人组长监督与口播稿交付验收

当前范围变更（2026-10-29）：用户明确先保持轻量群聊限制，暂不通过代码强制负责人和派工链路。**本文SG-v1与已生成报告保留为历史严格实验；后续轻量验收以[05第13.8节](./05-实施步骤与进度.md#138-当前采用轻量群聊限制2026-10-29用户纠正)为准。** 独立创建Work仅作观察，不单独否定实际协作和交付。需要新测试时另登记轻量合同，不覆盖旧评分或把旧结果自动改为通过。

日期：2026-10-29。用户已授权先写方案、随后真实测试，并在发现问题后定位修改。首轮五名员工均使用已保存的 `deepseek-flash` 连接；个人员工、群聊和原始数据库保持只读。

## 1. 要回答的问题

一个组长和四个执行者，能否围绕同一目标完成“讨论选题→确定大纲→写稿→润色→交付文档”？组长是否真正使用成员结果、纠正偏离并收尾？文件操作失败时，能否保住正文、把问题交回组长处理，而不长期陷入修工具？

已有单员工续聊、历史两人委派及三人编辑部成绩只作背景。本次使用当前固定源码与全新隔离群，不能继承旧通过结论。

## 2. 五个员工与目标

| 员工 | 角色约定 |
| --- | --- |
| 组长 | 组织讨论、确定方向、分派实际工作、检查阶段成果、决定异常处理和最终交付；不替四名执行者包办 |
| 选题策划 | 提供角度和理由，参与选题讨论 |
| 大纲编辑 | 对候选角度提出具体意见，基于组长确定的方向交付大纲 |
| 文案写手 | 读取实际大纲，写成完整口播初稿 |
| 润色编辑 | 读取实际初稿，改成自然口语，保留事实和主题；负责最终文件操作时遵循组长决定 |

这是员工配置和用户要求，不通过测试代码预填成员答案、替组长决策、偷偷执行委派或强制生成成功状态。普通群沿现有产品消息/判断/Work/依赖运行。

合成题以“租房上班族下班后用45分钟整理一个小空间”为素材：5分钟选一块区域，15分钟清理明显垃圾，25分钟把留下的物品归位；不用购买收纳用品，不虚构调查/效果数据。选题角度由成员讨论决定。最终交付 `口播稿.md`，包含标题、`## 口播正文`，正文350–550个非空白字符。文件可在群里打开，组长说明使用的版本与已核对事项。

明确禁止把任务扩展为制作视频、搭建内容系统、研究导出库、安装工具或修复应用。保留素材正文和既有成果；文件路径故障可以由组长选择用户已允许的备用位置解决。

## 3. 首轮场景

| ID | 设置 | 应观察到的结果 |
| --- | --- | --- |
| SG01 `supervised-script-normal` | 五个独立员工、普通群；自然语言点名组长，没有测试专用调度器；最终首选 `self:/work/exports/口播稿.md` | 四位成员实际执行，讨论有真实前文，组长确认方向并接续；大纲/初稿/润色有原件读取链，最终文档和群根交付 |
| SG02 `supervised-script-export-conflict` | 同一任务合同、独立群；每人工作区预置普通文件 `exports`，使指定子路径真实产生ENOTDIR/EEXIST等错误 | 真实文件失败被留证；员工公开报告给组长，组长选择已获准备用位置 `self:/work/口播稿.md`；正文不因文件错误丢失，恢复交付；同一路径无新增信息地反复写入应判失败 |

正常与故障题属于同一业务簇，是诊断对照，不冒充相互独立的泛化验证。若修改生产机制，优先再跑受影响题一次，并用原 `independent-files` 题检查独立工作是否被误串行；不重新抽样直到碰巧通过。

成员过程中的求助与阶段结果检查属于本次范围。对一个始终不返回、不主动报告的长运行进行主动检测/中断，若本次没有自然触发，单列为未覆盖，不能以“最终完成”替代持续监督认证。

## 4. 判定与证据

确定性检查：

1. 五个真实员工身份、同一群和明确组长；四位执行者均有本人实际执行记录。
2. 委派确实创建子工作；组长等待真实版本后有新的执行，整体不能停留在waiting/blocked。
3. 大纲、初稿、最终稿正式发布且hash与磁盘字节一致；后续员工实际read_file读取前一产物，不以口头声称替代。
4. 最终文件存在，结构/字数/已给定数字约束可直接核对；组长最终公开回复在交付之后。
5. 故障场景核对真实错误、异常后的组长活动、备用交付，以及文件故障重复次数。冻结评分器上限为同一路径两次失败。若员工通过预检查避开错误，保留这一合理行为，但“实际失败后的组长恢复”仍算未覆盖，不能补造错误来满足评分。
6. 运行/工具/供应商错误全部保留。文件存在、run completed、根Work delivered分别记录。

2026-10-29后续评分核对：原第2项实现只核对“每名员工至少有一份组长子工作”，没有检查同一员工另外创建的独立工作；因此可能误报归属通过。本轮明确化为“本场四名执行者都有正式工作，且所有执行者Work均归同一组长根任务”，添加孤立工作/不同根任务反例。真实执行的输入与原报告保持，后续报告标明新评分器离线重评，不能把此修改冒充真实执行前已经具备的严格检查；不改变生产自然群的独立工作规则。

内容与监督质量另行阅读原件和轨迹：选题是否有依据，讨论是否使用对方意见，组长是否做出明确取舍，润色是否口语化，是否跑题/虚构事实，异常处理是否仍服务原目标。这些不凭关键词自动判通过，不代写用户评价；未获人工确认时保持待评价。

基线使用生产AppService/Mastra、SQLite、原工具和成果接口；先不启动完整桌面。服务链路结果不能证明UI展示、真实个人群、Codex/Claude/Pi混合运行或长期稳定性。需要后续桌面确认时复用既有BDD，不另造执行内核。

## 5. 执行与修改约束

- 独立worktree：`boai-group-supervision-eval`，基线 `f0ea0d87d6916a62d67efb00d66e5f744b3bd57c`。
- 模型：首轮五人使用本人已有 `deepseek-flash` API连接，凭据经原Electron只读桥在内存传递；不输出/保存密钥。
- 每题一个真实样本；每题最多120次供应商尝试，单题观察窗口15分钟。共享实验账本最多400次，包含连接探测、失败、后续一次定向复验和独立工作回归；不用剩余额度自动扩样。产品本身的默认无限执行规则不变。
- 未指定命令/浏览器任务，本组仅启用原文件与协作工具；不据此声称已验证“具备终端权限时也不会安装软件”。
- 先生成方案审阅页和冻结源码/题目/hash，再真实运行。用户已明确接受这个业务例子并授权测试，无需再次形式确认。样例的具体文字与质量标准仍可审阅，审阅标记不伪造。
- 先看失败发生在哪一步：模型分工、消息投递、依赖唤醒、来源权限、文件发布或最终汇报。每次修改只处理一个因果问题，保存原失败与新候选身份；工程回归不替代真实业务复验。
- 若确需新增组长主动监督协议等超出窄修复的产品设计，先记录缺口及具体方案，不在测试中悄悄替产品实现调度。
