## 1. 用户体验

团队创建位于「通讯录 → 加号菜单 → 创建团队」，使用弹窗填写两个必填项：「团队名称」和「团队需求」。点击生成后，名称和需求作为首条请求受理，进入系统预置核心助手的实际会话。

- 通讯录标题移除独立团队图标按钮，团队项与新建员工/群聊共用加号菜单。删除模型/用途预设、群开关、单独群名配置、方案编辑及所有团队草稿操作和状态；「团队名称」是本次请求的业务名称，不是另一个群名表单。
- 弹窗团队请求默认创建群聊，群名称使用用户提交的团队名称；AI 决定成员、职责和协作背景，不能改写用户名称。普通核心会话中直接提出团队任务且没有结构化名称时，模型可以依据请求合理命名。
- 通讯录仍展示可编辑的核心助手，移除「系统助手」分组标签。会话列表保留以其当前名称命名的独立会话分类；普通聊天与核心助手会话各自保留列表和历史。
- 会话列表标题下始终显示会话名称输入，其下以核心助手当前头像和名称显示唯一分组标题，可访问名称为「bobo 的会话分组」（跟随当前改名），无历史也始终保留，不再追加第二份文字 label。整行点击仅展开/收起，不创建会话。标题右侧更多菜单进入「助手设置」，新会话图标的可访问名称为「与 bobo 新建会话」（跟随当前改名），复用同一空白撰写动作；会话加号仅保留员工/群聊。新会话只打开未持久化的空白撰写页，不创建会话；反复点击、输入空白或放弃页面都不产生空记录。只有用户发送首条非空消息，才创建一条核心 Conversation，并将实际消息/回执一起受理。
- 分组标题整行可点击展开/收起，小箭头是同一按钮的状态指示；展开动画顺滑，沿现有语义颜色和减少动态偏好处理。标题菜单、新会话图标和分组按钮独立，不因点击标题操作误切收缩状态。
- 核心历史作为该分组子级，使用紧凑小缩进，并收紧分组与历史间距；仅显示会话标题和右侧随 hover/focus/menu 显示的更多/编辑图标，不显示头像、消息预览、时间或运行摘要。标题按钮在hover/active/focus/selected状态均透明，悬停与选中背景统一覆盖整行。核心右键/更多菜单提供编辑标题、清空和删除，不提供置顶；核心聊天标题菜单同样以编辑标题替代置顶。普通会话保留原置顶、头像、预览和时间。
- 行内编辑、右键、更多和核心聊天标题菜单共用「编辑标题」Dialog，输入label为「会话标题」，trim后长度须为1–200字符；空白不可保存，取消零提交，保存期间锁定关闭/按钮，失败保留输入。通过typed `updateConversationList` 的 `rename` 分支仅更新明确core `Conversation.title` 和 `updatedAt`，不改会话身份、成员、员工配置、记忆和消息，不调用模型；成功后列表/聊天标题同步，重启读取已提交标题。
- 分组 label 右侧的更多、编辑/compose、加号操作仅在鼠标悬停整行、键盘焦点进入该行（`focus-within`）或相应菜单正在操作时显示；静止时隐去图标视觉，但保留操作区域占位，label 和其他内容不跳动。图标继承 label 的文字颜色；键盘进入时可以发现并使用操作，菜单打开后移开鼠标仍保持显示。此规则同时适用于会话分组标题、通讯录分类及 Skills 同类标题控件；核心历史行的更多/编辑图标同样沿此规则显示，静止时隐藏并保留键盘访问。
- 核心助手可以对不明确的必要需求提问；有合理默认值时可以说明假设后执行，不要求用户选择模板。正式团队数据只有原子发布成功后才可见。
- 团队创建的最终回复须依据已提交工具回执，不能把模型文本、文件准备完成或运行结束说成员工和群已创建。新群仍使用普通员工群聊，由用户开始交流，不自动向成员发送欢迎词或游戏请求。

团队弹窗的名称/需求与空白撰写页输入只存在当前界面，不自动保存成团队草稿或空 Conversation。首发失败后先只读核对本次实际请求：已受理则进入原会话，确认无回执才允许修改输入并建立新请求，核对结果未知则保留原 key 和已尝试字段，不自动重放。团队弹窗的请求引用跨关闭/打开及前往设置保留；关闭弹窗不能把未核对的请求变成第二次受理。相同请求不重复初始消息、调度或团队。

当前控件合同：加号按钮可访问名称「新建」，菜单项「创建团队」，弹窗标题「创建团队」；团队名称使用 Input，团队需求使用 Textarea，生成忙碌时显示「正在进入会话…」，另保留取消。通讯录核心助手区域仍有供无障碍定位的语义名称，但不显示「系统助手」文字标题。折叠标题为整行按钮，小箭头常驻，宽 12px、默认 opacity 0.75/hover 1，展开约 220ms，减少动态效果偏好可缩短或取消动画。

## 2. 核心身份与模型

核心助手默认名称为 `bobo`，使用宿主预置的稳定 `DigitalAgent` 身份 `id=bobo && systemRole=core`。显示名称可在现有配置入口修改；改名不创建第二个助手，也不改变工作区、记忆归属或工具授权。普通员工叫 bobo 或提交 `systemRole=core` 都不能取得核心权限。

新库在原三个默认员工之外补齐核心助手；旧库保留原员工与配置，只补齐唯一核心身份。核心助手保持启用的 Mastra API 后端，不启用宿主命令或 ACP；员工群不能将核心助手作为成员。核心会话使用 `purpose=core` 和仅包含该固定身份的 direct 会话，不复用普通单聊或自动化任务聊天。

核心助手尚未选择连接时，第一次需要实际回复或受理团队需求会选用已配置连接中首个具有有效默认模型的 API 连接。后续明确保存的模型连接和模型选择会保留；已有选择不可用时显式报错，不静默换到另一连接。团队新成员使用本次核心助手的同一连接和有效模型，默认无命令权限、Skills 或知识绑定。

没有有效模型连接时，团队提交或普通核心首发不创建会话、团队员工、群或 Work，并提供模型设置入口。应用初始化的预置核心身份仍保留。用户可以打开空白撰写页；该页面不是已保存会话，实际发送前仍须有有效模型。

## 3. 分层记忆与 Mastra

核心助手复用 T2 员工统一记忆，SQLite `MemoryRepository` 是唯一权威，归属固定在 `employee:bobo`；不按显示名称或会话标题分配新的记忆空间。

| 层 | 保存的内容 | 生效边界 |
| --- | --- | --- |
| 当前会话上下文 | 本次获准消息、当前轮次和最近实际获知证据 | 按会话/轮次投影，不能装入全量历史或管理列表 |
| 长期 `long_term` | 用户偏好、长期事实、持续采用的决定 | 员工归属、来源、使用范围与纠正/忘记屏障 |
| 经历 `experience` | 团队设计与交流中实际获知的经过 | 按相关性有界召回，经历不是工具执行授权 |
| 临时 `temporary` | 当前事项、有限时效的约束或角色 | 明确范围、事项和有效期，到期不能继续使用 |

多次核心助手会话可以接续同一身份的相关经历；仅此聊天、明确关联事项、来源撤权、失效/到期、忘记和旧数据保守迁移继续有效。新团队成员分别拥有自己的身份和记忆，创建团队不复制核心助手私有记忆给成员。

Mastra 提供当前安装版本的 `Agent`、真实 `createTool` 和任务步骤；产品消息按授权投影进入模型，记忆按宿主统一召回注入。未额外开启 Mastra Memory 自动历史回放或并行建立一套新记忆数据库。框架能力与产品已接入能力分开描述。

## 4. 会话受理与真实团队工具

`startCoreConversation` 只接收有实际首发内容的两种严格互斥形式：

| 首发意图 | 输入 | 校验 |
| --- | --- | --- |
| 普通核心消息 | `{ requestId, content }` | content 去除首尾空白后非空，最多 100,000 字符 |
| 团队弹窗请求 | `{ requestId, team: { name, requirements } }` | name/requirements 均去除首尾空白后非空，名称最多 80 字符、需求最多 4,000 字符 |

仅 requestId、空白内容、旧 prompt 或同时提交两种形式都不能创建会话。Conversation、首条用户 Message、轮次准备记录和 `coreConversationStarts` 回执同事务保存，提交后才调度。回执绑定 messageId、可选 teamName 和输入 SHA256 fingerprint，不额外保存普通消息全文/团队需求副本。相同请求返回原会话，不重发消息或模型；不同内容占用同身份时拒绝。

`getCoreConversationStart({ requestId })` 是宿主串行边界内的只读核对接口，返回已受理的 `Conversation` 或确认没有回执的 `null`，不调度模型、不追加消息、不建立对象。接口失败不能等同于 `null`：UI 必须继续保留原 requestId 和已尝试载荷；用户主动再次提交也仍核对同一身份。普通空白页在核对期间的新输入不替换已尝试内容；找到原会话后可将较新的输入保留为该会话未发送草稿。

数据库已提交首发回执，但宿主尚未完整安装 Conversation/初始 Message 时，受理和核对接口明确提示「已受理，需要重启应用核对；保留原请求，不要重新创建」，不返回当前不可用的会话 ID，也不重新受理或调度。重启后按已提交数据库加载原会话和首条消息；核对不重发模型。

首发事务失败后，只有可靠数据库核对同时证明本次 Conversation 与入口回执均未提交，才允许对本次独占创建的空工作区使用 `rmdir`。提交状态未知、核对失败或目录已被修改时保留目录；不得递归删除，也不得把目录清理结果当作请求未受理的证明。

核心助手先按现有判断协议区分普通对话和工具任务。只有宿主授权的核心任务上下文才装配 Mastra `create_team`；判断、普通聊天、记忆维护、普通员工和自动化都不获得该工具。模型工具输入使用 `teamModelPlanSchema` 严格校验：1–12 位成员、互不重名、长度上限及工作规则总预算有效，未知权限、身份或路径字段不被接受。

宿主工具步骤执行已有 `beforeEffect/afterEffect`、原 Work 预算与可检查回执。产品请求身份固定为 `core-team:<原workId>`，一个原工作只创建一套团队：相同载荷重入返回原操作，不同方案重入拒绝；不能按工具调用次数、员工名称或文本相似度推导新团队。

`TeamCreationService.acceptAgentPlan` 接收严格模型方案，在 SQLite 事务中生成内部发布准备记录和冻结操作；宿主填充 `memberKey`、员工/群 ID、头像、颜色、版本、输入/载荷 hash、连接指纹和权威能力说明。对弹窗团队请求，宿主按原 Work 的 `sourceMessageId` 查入口回执并以 teamName 覆盖模型 `plan.name`，既不按最新聊天消息改绑，也不靠模型遵从提示来保证用户名称；后续独立任务没有该首条消息归属时，不受旧团队名约束。模型只负责团队设计，不授予权限、不写凭据，也不额外调用旧专用 planner。

原工作承担真实模型调用和执行步骤的用量；团队宿主不制造第二个 Work、独立模型调用或虚构 generation 用量。未知用量保持未知，后续整理回复和记忆仍沿现有工作/调用预算处理。

## 5. 后台日志、原子发布与恢复

旧 `teamDrafts/teamGenerations/teamCreations` 集合和兼容接口继续服务已有记录与恢复。新核心工具复用 `teamDrafts` 结构作为内部冻结准备记录，不进入全局 `TeamRepository.open` 的单未结束用户草稿限制；不同原工作可以分别保存操作。保留数据库字段不表示重新展示团队草稿产品。

核心会话清空或删除时，首发回执在同一事务中缩减为 `id/fingerprint/conversationId/cleared` 的最小 tombstone，删除首发 messageId 与 teamName 回执字段；历史 JSON 形式的 fingerprint 归一为 SHA256。这个去重身份不保留首发正文或团队名称，也不使已清理会话可恢复：后续核对或再次受理同 requestId 必须明确报「已清理」，不能新建 Conversation、重新发送首条消息或重放工具。

创建沿用以下不变量：

1. 模型方案受理和对象冻结同事务，受理写入失败不留下半条输入或发布身份。
2. 稳定操作 ID 拥有受管暂存目录、每个文件 hash 和移动日志；恢复不重新生成成员身份。
3. 完整文件准备及最终目录/连接指纹复核后，一次 SQLite 事务发布全部员工、默认群、独立同名分类、内部记录终态与成功回执。
4. 任何准备/发布失败都不暴露一半成员；数据库提交后内存批量安装失败从数据库完整重载。
5. 文件准备在宿主临界区外执行，认领和最终复核/事务发布/内存安装仍受临界区保护，因此停止不会被整段文件准备阻塞。`waitForCompletion(operationId, signal?)` 等待实际文件任务和提交后安装退出。取消先阻断未完成发布，沿已有 abandon 清理并等待真实退出；已经 committed 的团队保留。
6. 启动只核对已保存文件/事务状态，未提交操作需明确继续或放弃，不自动调用模型、重读需求或重放工具；清理仅处理 hash 匹配的受管文件，外部修改保留并报错。
7. 未结束团队操作与备份互斥。备份恢复沿原操作/成员/群身份核对，不重新创建已删除对象。

停止、失败或响应未知时，核心助手须汇报已有回执/待处理状态，不能通过新工具请求悄悄创建第二套团队。群 `teamSetup` 是可编辑背景，不是新任务，仍不启动正式游戏；T3 专用实现保持撤销。
