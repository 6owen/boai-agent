# 员工身份与连续记忆

状态：T1 保持现状；T2 待实施。**不要为了交付创建入口，顺手修改所有员工的记忆范围。**

## 1. 当前实际行为

- DigitalAgent 是持久员工身份；同一个 ID 可以被私聊和群聊引用。
- WorkspaceService 在 agents/<id>/workspace 下管理系统文件，再按 conversation 划分 session 工作空间。
- MemoryRepository 的 profile 属于员工，conversation 记忆属于“员工 × 会话”。SQLite 是权威，MEMORY.md/USER.md 是生成视图。
- 当前调用装配员工 profile 和当前会话的有效记忆；自动提取结果写入当前会话。
- Mastra 用于生成、判断与候选提取；当前 Agent 工厂没有启用原生 Memory。安装了 @mastra/memory 不代表已经使用它。

因此 T1 可以保证“同一个名字背后是同一个员工、配置和工作区”，不能承诺它已能在私聊中回忆任意群聊经历。

## 2. 三个不同问题

| 问题 | 权威来源 |
| --- | --- |
| 我是谁、如何表达、擅长什么 | 员工配置及 AGENTS.md / SOUL.md |
| 我曾经看到/记住什么 | 有来源的员工记忆和会话经历 |
| 当前场合可以读取/使用/说出什么 | 产品的会话、成员、来源和用途权限 |

独立文件夹不能代替第三项。把所有会话文本拼入一个员工 Prompt 也不能实现可信连续性。

## 3. T2 首批体验

选择四个明确场景作为目标：

1. 私聊中明确保存“以后文章开头简短”，用户选择“该员工的所有工作聊天”，以后群内写作应用该偏好。
2. 写作群中确定提纲，用户私聊该员工并明确关联该群后，可以讨论提纲与进度。
3. 私聊明确标记只在这里使用的信息，不进入群内模型上下文、群摘要或同伴记忆。
4. 员工 A 的私人经历不因同群成员 B 发问而对 B 开放。

跨会话连续的最小实现采用显式关联和选择性授权，不默认开放所有历史。私聊入口增加“关联上下文”选择；从群成员进入私聊时展示该群建议，由用户确认，不能无声绑定另一个群。

## 4. 最小记忆记录扩展

T2 在现有 MemoryEntry 上增量设计：ownerAgentId；来源会话/消息/资料；sourceScope；allowedUseContexts；可选 scenarioSessionId；事实/用户偏好/决定/推测分类；版本与删除标记。来源 ID 不因跨会话使用被改写。

“用户对某件事的描述”与“已确认事实”应区分。推测不能自动升级为事实，特别是游戏中“我怀疑 2 号是狼”。工作风格是长期偏好，每局角色身份是临时状态。

T2 初版只做显式“记为工作偏好”或选择条目跨场景使用；模型自动提取默认仍留在来源会话。不得自动把私聊候选提升到全局 profile。

## 5. 默认可见性矩阵

| 来源 | 本会话 | 同一员工的另一会话 | 其他员工 |
| --- | --- | --- | --- |
| 用户明确设为跨工作聊天的员工偏好 | 可用 | 授权范围内可用 | 不自动共享 |
| 私聊自动提取记忆 | 可用 | 默认不可用，须明确授权具体用途 | 不可用 |
| 群内公开消息/结论 | 群内按现有规则可用 | 同一员工仍有来源访问权，且本次明确关联才可用 | 只因群成员身份读取公开内容，不读取别人的私有摘要 |
| 本局角色私密状态 | 获准角色视角可用 | 只在同一局的获准通道可用 | 按游戏规则分别投影 |
| 已撤权/清除来源 | 不可用 | 不可用 | 不可用 |

必须在检索、摘要、重排和装配前过滤；不能先把秘密送给模型，再只靠提示词要求它别说。当前频道不允许使用的私聊条目直接不进入该频道上下文。游戏例外需要在 T3 按玩家视角单独定义，不能沿用全局 profile。

## 6. 上下文装配

一次回答由以下内容组合：员工身份/规则 → 当前会话有身份归属的消息 → 当前允许的 profile/会话记忆 → 用户本次明确关联且仍可访问的来源摘要 → 本局玩家投影（仅 T3）。

保留作者、来源会话、时间和来源版本，避免把另一名成员的话当成自己的经历。召回结果有长度上限，优先相关条目；不扫描其他员工目录，不用文件路径充当授权。

同一员工多个会话并行更新长期偏好时，沿用版本/epoch 保护；冲突时重新读取并显式合并，不用最后写入覆盖全部内容。

## 7. 删除、离群与迁移

来源消息清除、资料撤权、员工移出群等情况，所有派生摘要、记忆、检索索引都要按来源失效。跨会话保存不抹去原来源，使删除仍能传播。用户明确手工写入的独立偏好和从消息派生的条目应区别处理，不能借复制绕过删除。

旧 conversation 记忆保持原范围；旧 profile 不批量扩权；历史记录缺失用途字段按旧语义读取，不推断授权给新场景。迁移前备份，失败保留原数据可恢复。

T2 不与 T1 的创建账本共用记忆存储。创建方案来源只说明“为何创建”，不能当成员工已经经历过的聊天历史。

## 8. 与 Mastra Memory 的关系

框架支持 thread/resource 范围的 working memory 和 semantic recall。若未来迁移，可把稳定员工身份纳入 resource 设计、把员工在某会话的视角纳入 thread 设计；游戏局使用独立会话/资源分区及明确投影。

但 resourceId 本身不是授权检查，不能仅靠它串联所有会话。宿主仍决定来源、用途、删除和访问权。普通多人共享 thread 的示例也不能直接用作多个独立角色共享私人记忆的方案。

**本组选择：T2 优先扩展现有 MemoryRepository，不要求迁移 Mastra Memory。** 如果另行决定迁移，必须先写唯一权威、旧记录转换、缓存/索引失效、撤权删除和回滚方案；不允许两套持久记忆双写后长期漂移。官方参考见 [11](./11-决策记录与参考依据.md)。

## 9. T2 验收门槛

- [ ] 同一员工在明确关联的私聊中正确引用群决定，带准确来源。
- [ ] 未关联的其他群事实不会进入模型请求；测试检查实际请求而不只看最终答案。
- [ ] 仅限私聊的条目不进入群 Prompt、摘要、检索和其他员工记忆。
- [ ] 删除/撤权后即使条目曾跨会话使用，也不能继续召回。
- [ ] 并行更新不会丢失已确认偏好，旧 epoch 写入被拒绝。
- [ ] 重启/备份恢复后范围不扩大，旧记录不因迁移默认变全局。
- [ ] T1 已创建的员工无需更换 ID 或复制 workspace 即可接入 T2。
