# 批量创建与故障恢复

状态：T1 必须实现。不能用前端循环调用 saveAgent，最后再 createConversation 作为最终方案；现有单对象保存会逐个发布，无法满足整套可见的一致性。

## 1. 必须保持的不变量

1. 未确认方案只存在草稿中，员工/群列表看不到待创建对象。
2. 一次受理固定一套员工 ID 和可选群 ID，重试不得重新分配。
3. 全部文件准备完成后，在一次数据库事务内提交全部员工、群和成功回执。
4. 对外只能看到整套已发布对象；失败不会出现一半可聊天、一半不存在。
5. 文件系统和 SQLite 不宣称跨介质原子；使用持久操作日志核对中断。
6. 任何删除/重试只能操作当前 operation 拥有的受管路径，不能碰已有员工文件。
7. 创建不调用成员模型、不发送消息、不产生业务 Work，也不安装或执行任何外部工具。

## 2. A：原子受理

在 ProductStore.transaction 内完成：

- 先读取 requestId：相同载荷返回原操作；不同载荷拒绝。
- 校验草稿版本、planHash、状态，以及当前模型连接/有效模型引用。
- 校验所有成员字段、数量和名字，建群时校验群背景/标题；宿主生成目标 ID。
- 保存冻结的创建操作、结果 ID 映射和草稿锁定关联。
- 提交后才通知 UI/启动文件准备，不能在事务回调里再调用外层 store 方法。

一个草稿最多受理一次有效创建。两个不同 requestId 竞争同一草稿时，后者返回已有操作关联或冲突，不能另建一套。

## 3. B：准备文件，不发布对象

建议使用 dataPath/team-creation/<operationId>/ 作为暂存根；路径由宿主生成，模型和 Renderer 不能指定。为每位成员准备完整 agents/<agentId>/ 子树，包括 workspace 与 state/manifest；复用现有初始化内容和校验，不复制一套不同的系统文件格式。

现有 WorkspaceService 需要增加内部准备能力，使其能在指定的受管暂存根构建文件；最终 workspaceRef 仍是标准 agents/<id>/workspace。不要通过临时写入 EmployeeService 注册表“借用”初始化。

文件准备日志记录每个目标相对路径、归属和预期 hash。每个新操作创建独占归属标记；先核对没有符号链接、目标员工未存在，再写入。完整准备后，将每个员工子树移动到最终位置；群共享目录也按本次 ID 准备。

文件重命名不可覆盖已有非本操作路径。宿主生命周期互斥覆盖最终路径检查/移动和备份；两个操作的随机 ID 仍要实际检查冲突。若目标存在但无法证明属于当前操作，进入 needs_attention，不覆盖、不递归删除。

暂存和最终路径的每次变化均可根据日志与实际 hash 重建状态；日志落后于成功 rename 时，可以核对源/目标识别已完成步骤。SQLite 尚未发布这些 ID，因此普通员工列表/聊天/API 不可访问它们。

## 4. C：原子发布与内存安装

发布前重新核对取消门禁、操作持有者、冻结配置、所有目标文件及当前连接配置。文件和准备步骤不能在数据库事务内运行；最终数据库事务只做读/检查/写。

同一事务写入全部 DigitalAgent、可选 Conversation、creationSource 和 teamSetup，以及 committed 状态/回执。对象已存在但不属于这次操作时拒绝；已 committed 时直接返回原回执。

事务提交后才把对象安装到 EmployeeService/会话内存映射，且批量安装完成再发一次整体变更通知。安装失败则标记本服务需要重载并从数据库恢复整个集合，不能继续用半套内存状态对外应答，也不能回滚已经提交的数据库对象。

2026-09-30 用户追加要求：每次成功创建团队都建立一个独立的通讯录分类，以方案中的团队名称命名，将本次全部员工归入其中；只创建员工时也建立分类。分类与员工/可选群/回执同一事务写入，身份沿用创建操作 ID。名称沿用 40 字符限制，同名或保留名称“未分类”自动加序号；不合并已有分类、不移动原员工、不改已有手动顺序。沿用最多 100 个分类限制，满额时整套发布失败并保留明确继续入口，不能只发布员工。已成功操作重读/重复提交/重启不重建用户后来删除的分类，也不改回手动调整的归属。不预建单聊，不创建聊天消息。群背景来自 teamSetup 的显式投影，不把一个虚假的用户消息插进聊天。

## 5. 取消与提交的竞争

取消先提交门禁并定向终止准备任务，等待其实际退出后清理；旧准备任务不能继续提交。发布事务和取消事务比较同一操作状态/版本：

- 取消先赢：发布被拒绝，清理未发布文件。
- 发布先赢：操作已完成，返回真实结果；不把取消解释为删除成员。

关闭标签只是关闭视图；只有明确放弃才请求取消。清理失败保留 CLEANUP_REQUIRED 和路径摘要，不能把它标为 cancelled 后遗忘残留。

## 6. 断点矩阵

| 中断位置 | 启动/重读时如何判定 | 用户可执行动作 |
| --- | --- | --- |
| 方案生成期间 | generation interrupted；无创建操作和成员 | 重新生成 |
| 受理已提交，尚未写文件 | 同一操作与 ID 映射仍在 | 继续创建 / 放弃 |
| 某成员暂存文件写到一半 | 对照日志，尚未发布 | 继续核对并补齐本操作文件 / 放弃清理 |
| 部分子树已移动到最终目录 | 目标存在且归属/hash 匹配可识别为已准备 | 继续剩余准备，不分配新 ID |
| 所有文件到位，发布前 | ready_to_commit 或 interrupted，无可见员工 | 明确继续后重新校验并提交 |
| 数据库事务失败 | 事务回滚，无可见员工；文件仍受日志管理 | 继续同一操作 / 放弃 |
| 数据库已提交，IPC 响应丢失 | committed 与全部对象同事务存在 | 返回已有结果，不创建第二套 |
| 提交后进程退出、内存未安装 | 启动从数据库加载已提交对象 | 直接显示结果 |
| 路径被外部修改/替换 | 归属或 hash 不一致 | needs_attention，保留文件供核对 |
| 取消后清理失败 | 日志仍列未清理项，无对象发布 | 再次清理；不能声称干净结束 |

启动仅执行状态和文件核对，不自动续写未完成创建。普通重读也不触发模型、准备文件或新建实体。用户明确“继续创建”只续行文件初始化/提交，不重新生成方案。

## 7. 安全的继续和清理

继续前以事务领取当前操作，建立新的执行 attempt；旧 attempt 完成/报错不能更新新 attempt。对于不完整但明确属于本操作的暂存文件可重新生成；最终路径存在完整匹配内容则跳过该步骤。已执行的 rename 不盲目再次覆盖。

只有未发布且实际执行器退出的操作可清理。删除前核对 operation 归属、受管根、路径无链接和未被 committed 对象引用。外部修改后的文件保留并要求人工处理；不得用 force 删除掩盖冲突。

清理完成后提交 cancelled 墓碑，删除需求正文、方案和临时内容，保留 requestId/payloadHash/结果 ID 预留的最小防重信息。以后可新建草稿，但旧 requestId 不能复活已放弃操作。

## 8. 已提交结果的生命周期

创建成功后员工和群走正常编辑/清理流程。回执显示成员当前名字；对象不存在时标记“已移除”，不根据原冻结方案补造。删除群不连带删除成员；清空聊天也不删除员工身份。

备份与创建文件交换互斥；未完成文件操作先处理后备份。正常备份包含 committed 回执、来源及实际文件；恢复后仅核对，不补发欢迎词、不开始业务任务。

## 9. 实施检查

- [ ] 受理、取消、发布均使用数据库条件读写，不依赖内存先查后写。
- [ ] 不在事务回调中等待模型、操作文件或重新调用外层存储队列。
- [ ] 文件日志在真实中断测试中可用，不只模拟函数抛错。
- [ ] committed 操作永远不会进入自动重建/清理分支。
- [ ] 清理失败、提交结果不明和内存安装失败都能重新核对。
- [ ] 不改变普通单员工创建与群编辑的既有行为。
