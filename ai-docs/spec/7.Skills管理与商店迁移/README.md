# Skills 管理与商店迁移

更新：2026-09-28。状态：**迁移规格已整理，功能尚未实施**。本次只研究本地源码和编写文档，没有复制业务代码、安装技能或修改旧项目数据。

## 迁移结论

建议将 `boai-app` 的 Skills 列表、收藏分组、详情、多来源安装和三家商店能力，接入当前项目的“资料库”。保留本项目的 `Resource.id`、受管文件副本、员工 `skillIds`、运行时授权和 Mastra 渐进加载；不把旧应用的全局 Skills CLI 管理方式直接作为新应用的安装方式。

落地后的主链路是：**发现技能 → 查看内容与来源 → 安装到本应用 → 用户绑定员工 → task 按权限加载**。收藏是用户整理方式；安装是文件管理；绑定才赋予员工使用资格。三者分别保存和展示。

当前项目已经实现本地 Skill 目录导入、公共/员工专属资源、员工绑定、版本化读取和删除撤权。需要新增的是管理界面、来源信息、收藏分组、商店检索、批量扫描与安装、可检查的更新和便携迁移能力，不必重建一套运行引擎。

## 本方案采用的假设

1. 用户这次需要可供后续开发的规格，不要求立即实现或迁移真实技能文件。
2. 技能最终供 BoAI 数字员工使用；默认安装到应用数据目录，不修改 `~/.agents/skills`、Codex/Claude 的目录或用户项目。
3. 已有资料库的知识资料与员工视图继续保留；先在资料库内增加技能管理，不新增重复的一级入口。
4. 使用当前 Soft UI、Base UI 和本地图标入口，参考旧交互而不复制 Craft 的整套界面依赖。
5. 本地资源管理与商店可先独立交付；脚本执行环境的准备继续属于第 5 组 S2，不因商店接入而提前宣称已就绪。

若后续明确需要“统一管理本机所有 Agent 的 Skills”，应新增独立的外部目录管理阶段，列明写入目标和卸载边界；该能力不隐含在本方案的“安装”按钮中。

## 范围与交付顺序

使用 **K1–K5** 表示本组阶段，避免与既有 B/S/G 阶段混淆。

| 阶段 | 交付范围 | 状态 |
| --- | --- | --- |
| K1 | 已安装/我的、收藏分组、技能正文与文件详情、本地批量扫描导入、员工绑定入口 | 待实施 |
| K2 | skills.sh / ClawHub / SkillHub 的只读列表、搜索、分页、详情和缓存 | 待实施；可在 K1 合同确定后开发 |
| K3 | 商店及远程来源安装、来源记录、检查更新/单项更新、受管卸载 | 待实施；依赖 K1，商店入口依赖 K2 |
| K4 | 旧应用导出库导入、当前技能库导出、可携带来源与收藏关系 | 待实施；离线恢复可先于远程更新完成 |
| K5 | 本应用技能使用统计、更多来源及外部 Agent 适配 | 可选后续，不阻塞主闭环 |

核心验收是：用户从商店安装一项技能，在资料库看到来源和内容，显式绑定一位员工后由该员工的 task 读取；未绑定员工不可读取，更新/移除不破坏授权和旧数据。K1–K3 完成后可称主闭环交付；K4 完成后才可称旧技能库迁移交付。

## 与现有规格的关系

- [工作区与资源隔离](../4.数字员工与协作重构/02-工作区与资源隔离.md)：沿用物理路径、所有者和资源撤权，不改变群知识交集规则。

- [员工执行后端与能力契约](../4.数字员工与协作重构/04-员工执行后端与能力契约.md)：当前 ACP 员工不能直接绑定 BoAI Skills；本组不得用商店安装绕过这个限制。
- [Cumora 协作重构](../6.Cumora协作重构/README.md)：安装管理不是员工工作项；不新增模型判断、任务预算或自动重试机制，重启后不重放业务工具。

本组以本地代码快照为依据，未运行旧应用或联网探测商店。旧适配器中存在某个接口，不表示该外部接口现在可用；K2/K3 实施时需单独核对并记录结果。
