# 数字员工与会话模型

> 归档说明（2026-09-27）：下文保留原制定时的设计与时间语境；“当前/下一版/尚未开发”不代表最新状态。实际交付请读 [当前功能与代码现状](../2.已实现功能与代码现状/README.md)。

版本：v0.1（草案）  
日期：2026-09-26

> v0.2 更新：本文的 @ / 协调者模式及未来自由讨论安排已由 [09 独立员工与自然群聊](./09-独立员工与自然群聊.md) 替代。下一版每位员工持有自己的工作区、记忆和会话状态，按群事件自主判断参与；本文其余身份、消息来源和隔离原则仍作为背景参考。

本文定义第一版产品中的数字员工、单聊、群聊与运行上下文之间的关系。
文中的对象是产品领域模型，不代表已经选定的数据库表结构或 Mastra API。

## 1. 决策状态与范围

### 已确认的方向

- 从零创建独立 Electron 产品，外层结构参考 `boai-app`。
- 使用 Mastra 构建在用户电脑上运行的 Agent 内核。
- 用户可以配置数字员工，每位员工具有自己的模型、skills、知识库、工具和权限。
- 支持用户与单个员工单聊，也支持将多个员工组成群聊。
- 同一个员工在不同会话中保留同一身份，但具有独立的会话上下文。

### 本文建议的第一版默认值

- 群聊先支持明确 `@` 路由与协调者模式。
- 群内一次处理一个讨论轮次，允许该轮次内部的独立任务并行。
- 群成员的后台推理、工具轨迹与群消息分别记录。
- 私聊与其他群中的长期记忆，默认不进入当前群的上下文。
- 具体轮次预算、模型配置界面与成员管理交互，在原型阶段确定。

这些默认值是实现建议，不等同于用户已经批准全部产品细节。
当前范围不包含多人实时 IM、跨设备同步、企业组织治理或可视化流程设计器。

## 2. 必须保持的关系

```text
AgentDefinition 数字员工定义
  └─ Participant 加入某个 Conversation
      └─ AgentSession 该员工在该会话中的上下文
          └─ Run 一次具体执行

Conversation 会话
  ├─ Participant 参与者
  ├─ Message 对用户可见的消息
  └─ Workspace 引用
```

一个数字员工可以加入多个会话；一个会话可以包含多个数字员工。
联系人存在不意味着其进程始终运行，只有任务触发时才需要创建或恢复执行。
Workspace 的目录、隔离与生命周期见 [04 本地工作区与资源执行](./04-本地工作区与资源执行.md)，本文只保存引用。

## 3. AgentDefinition：数字员工身份与配置

数字员工定义回答“这个员工是谁、可以做什么”，不保存某个群的聊天记录。

| 属性 | 含义 |
| --- | --- |
| `agentId` | 稳定身份，改名或更换模型不改变身份 |
| `name`、`avatar`、`description` | 联系人展示信息 |
| `instructions` | 职责、工作方式与角色指令 |
| `modelRef` | 模型及连接配置引用，不包含明文密钥 |
| `skillRefs` | 可使用的 skills 及版本或内容标识 |
| `knowledgeRefs` | 可访问的知识库引用 |
| `toolRefs` | 启用的工具引用 |
| `permissionProfileRef` | 文件、命令、连接器等权限配置引用 |
| `configVersion` | 配置版本，用于解释历史执行采用的配置 |

建议每次 Run 固定本次配置快照；用户修改员工配置后，下一次 Run 使用新配置。
在途执行不因配置编辑而悄悄切换模型、工具或职责；权限撤销应立即参与执行检查。
删除员工的具体交互待定，但历史消息必须保留其发送者标识和展示快照。

## 4. Conversation：单聊与群聊

Conversation 是用户看到的持久聊天空间，与 Mastra 内部线程标识分别管理。

| 属性 | 含义 |
| --- | --- |
| `conversationId` | 产品会话标识 |
| `kind` | `direct` 或 `group` |
| `title` | 会话名称 |
| `routingMode` | 群聊采用明确 @ 或协调者模式 |
| `coordinatorParticipantId` | 协调者身份；明确 @ 模式可以为空 |
| `workspaceRef` | 会话工作环境引用 |
| `createdAt`、`updatedAt` | 会话生命周期与排序信息 |

单聊默认包含本地用户和一名数字员工；群聊包含本地用户与多名数字员工。
协调者可以是群内某个员工，也可以是产品调度组件；两者的展示方式需要明确。
隐藏调度组件的摘要不可冒充某个成员的原话，必须采用明确的系统或协调者身份。

Participant 保存成员在本会话中的身份、角色、加入状态及配置覆盖引用。
建议用稳定的 `participantId` 关联消息，使用 `agentId` 关联数字员工定义。
成员退群后保留历史署名；退群后的新任务不可继续将其作为有效接收者。
新加入成员可读取多少群历史，属于待确定的产品规则。

第一版建议：移除成员时停止对它的新调度，取消未开始的任务，并向在途 Run 和工具传播取消。每次组装上下文、调用工具及发布结果前重新检查成员状态和权限版本；已移除成员的迟到结果保留在运行记录中，不继续自动发到群里。

资源撤权后，后续模型输入和检索排除该资源，并废弃或重建仍引用它的摘要与上下文缓存。若在途请求已经包含被撤回资料，停止相关后续调度并尽可能取消请求；已发送给模型的内容和已发生的外部操作无法由本地撤权自动撤回，状态应如实记录。

## 5. Message：产品消息与实际发送者

产品消息记录是会话历史的权威事实，界面展示和群历史查询以它为准。
消息进入持久存储后，再向界面广播已提交事件，避免出现只存在于界面的完成消息。

| 属性 | 含义 |
| --- | --- |
| `messageId`、`conversationId` | 消息与所属会话 |
| `speakerType`、`speakerId` | 实际发送者：用户、数字员工或系统 |
| `senderSnapshot` | 发送时的名称、头像等展示快照 |
| `contentParts` | 正文、附件、文件产物等结构化内容 |
| `replyToMessageId`、`mentionIds` | 回复关系与明确提及的成员 |
| `turnId`、`runId` | 关联讨论轮次与产生消息的执行 |
| `status` | 流式生成中、已完成、失败、已取消或已中断 |
| `sequence` | 会话内稳定顺序，避免仅凭时间戳排序 |

`speakerType` 是产品身份；模型接口中的 `user`、`assistant`、`tool` 是输入协议角色。
两者不可一一硬编码映射：研究员的消息对写手而言可能是带署名的共享背景资料。
不得把所有员工发言都写成当前模型的 `assistant` 历史，让模型误以为是自己说过的。
上下文适配器负责保留署名、来源和回复关系，并按模型协议生成合法输入。
工具调用与工具返回必须保持配对，不能从界面消息中随意截取并拼成运行历史。

工具进度、内部委派和重试主要属于 Run 事件；仅在需要时形成明确的公开群消息。
流式内容使用同一条消息更新，取消后保留可见的部分结果及取消状态。

## 6. AgentSession：每个成员各自的执行上下文

第一版建议用 `(conversationId, participantId)` 定位一份 AgentSession。
Session 保存框架线程引用、上下文版本、摘要引用和最后处理的消息位置。
不要以单个 `agentId` 共用所有会话的框架线程。

产品保存的消息、显式共享资料与持久 Run 事件共同提供可审计的来源记录。
Mastra Memory 用于执行历史、上下文压缩或检索等运行需要；群消息事实不依赖其私有结构。
可重新生成的摘要和上下文视图应允许重建，并记录覆盖的消息范围与来源版本。
暂停工具调用所需的状态若不能从产品事件重建，必须另外持久保存，不可假定 UI 消息足够恢复。

第一版上下文入口建议采用以下单一路径：由产品上下文适配器从获准消息及本会话运行材料显式构建每轮输入，不同时启用框架对同一公开消息历史的自动回填。Mastra 的执行状态持久化可以保留，但应与公开历史注入分别配置；是否支持这项组合，以选定版本的原型验证为准。

适配器记录本轮输入所覆盖的 messageId、sequence 范围与摘要版本，并按标识去重，不能按正文去重，因为用户可能有意重复发送相同内容。最后处理位置用于审计与调度，不代表此前历史从下一轮上下文消失。若以后改为由 Memory 增量加载历史，应作为明确的策略迁移，不能混用两种入口。

每次执行为该成员构建上下文时，建议包含：

1. 当前员工的职责和本次有效配置。
2. 获准使用的会话消息、摘要与显式任务输入。
3. 本会话允许访问的知识库、共享资料与工作产物引用。
4. 本成员在该会话中的必要执行状态。

群聊默认不读取该员工的其他私聊、其他群消息或跨会话私人记忆。
用户明确要求共享的内容，应作为有来源的消息或资料加入群，再供成员使用。
协调者委派时仅转发获准公开的信息，不能直接附上自己的全部运行上下文。
摘要与检索也遵守相同范围，不能借助长期记忆绕过会话边界。

## 7. Run：一次执行及其结果

Run 回答“这一次谁执行了什么、执行到哪里、是否完成”。
建议记录 `runId`、`turnId`、触发消息、执行成员、配置版本、输入范围与 Workspace 引用。
同时记录父子 Run 关系、工具事件、使用量、错误、取消原因和产物引用。

建议状态流转：`queued → running → completed / failed / cancelled / interrupted`。
等待用户操作时进入 `waiting_input` 或 `waiting_approval`，满足继续条件后再回到 `running`，不算已完成。
`interrupted` 用于进程退出或异常中断后无法确认继续运行的执行。

应用重启后，不把未完成 Run 自动显示成成功，也不盲目重新执行全部工具。
对发邮件、写外部系统等副作用，应记录工具操作标识、执行结果及可用的幂等键。
若外部系统不支持幂等且结果不明，恢复时需要先核对结果或等待用户选择。
可安全重算的任务可以重新运行；恢复策略与重复操作风险应在执行层分别判断。

### 重启后的状态协调（建议）

- 先核对原运行进程是否仍存活；窗口重连不等于执行中断。
- 确认执行进程已退出后，未完成的在途 Run 标为 interrupted，其仍在生成的 Message 同时结束为已中断，保留最近持久化的部分正文和已有产物。
- 所属轮次尚未开始的子任务不自动启动，保留待恢复状态与依赖关系。
- waiting_input / waiting_approval 保留原问题和已记录回答；恢复前重验成员状态、权限和资源。不能把上次等待授权视为已获得授权。
- 用户选择继续后，根据检查点恢复或创建关联的新 Run；不能把整个轮次从头重放当作通用恢复机制。
- 状态协调和事件接收需要幂等：重复重连不生成新消息，已终止执行的迟到事件不能把它改回 running 或成功。

框架 subagent 调用默认只是一次委派，它不会自动创建产品联系人或群成员。
需要以某位群成员身份执行时，调度层必须显式绑定该 Participant 与 AgentSession。
成员实际发言使用其真实发送者身份；协调者转述的内容以协调者署名并标明来源。

## 8. 群聊路由与终止规则

### 明确 @ 模式

- 用户 `@研究员` 时，仅研究员收到本轮任务。
- 用户提及多位成员时，调度层依据明确依赖串行执行；独立任务可以并行。
- 未提及成员时，建议提示选择对象；是否设置默认接收者留待交互验证。
- 员工普通回复不自动触发其他成员，避免相互响应形成循环。

### 协调者模式

- 用户提出目标，协调者产生执行计划，选择成员并分配各自可见的任务输入。
- 接续任务通过显式调度事件触发，协调者依据完成或失败事件决定下一步。
- 成员结果可以公开到群；工具轨迹和内部草稿是否公开由产品规则决定。
- 对外展示具体执行者，汇总与成员原始结果保持可追踪的关联。

### 并发、去重和停止

- 建议同一群内一次只有一个活动讨论轮次，新消息排队或显式打断。
- 同一个 AgentSession 同时只执行一个 Run，避免历史写入和上下文游标冲突。
- 使用持久触发标识与唯一约束去重，重复传输或重连不能生成重复 Run。
- 并行任务使用独立产物路径；合并共享文件由明确的后续步骤负责。
- 一轮必须具有最大调度次数、工具执行限制、时间及费用或 token 预算。
- 达到目标、达到限制、用户取消、关键失败或需要输入时，均有明确停止结果。
- 取消需向子 Run 和工具传播；取消请求不等于能够撤销已发生的外部操作。

预算数值是待验证参数，不能把无限重试或无限讨论作为默认行为。

## 9. 具体示例：研究员、写手与审核员

用户创建三位联系人：研究员查找资料，写手整理文章，审核员核对事实与表述。
三位员工各有模型、skills、知识库及权限，在“产品研究群”中协作。

1. 用户单聊研究员询问私人项目资料；这些消息保留在该单聊。
2. 用户在群里 `@研究员` 要求研究某个公开主题，只有研究员开始执行。
3. 研究员将资料来源和结论发到群里，消息的发送者是研究员。
4. 用户 `@写手` 引用上述结论，写手获得获准公开的资料并生成文稿。
5. 用户 `@审核员` 引用文稿，审核员给出审查意见，以自己的身份发言。
6. 改用协调者模式后，研究、写作、审核可以按依赖自动接续。

研究员在群里不会自动带入步骤 1 的私人资料；需要用户明确把相关内容共享到群。
审核员是产品群成员；研究员临时调用的一个检索 subagent 只是后台执行角色。

## 10. 第一版验收场景

| 场景 | 预期结果 |
| --- | --- |
| 同一员工加入两个群 | 身份一致；输入消息、摘要和运行线程相互隔离 |
| 私聊后进入群聊 | 私聊内容不自动进入群成员的输入或检索范围 |
| 明确 @ 一位员工 | 只生成该成员的任务，其他员工不被动跟随回复 |
| 协调者完成三步任务 | 各步骤的执行者、输入来源和公开结果可追踪 |
| 多员工并行生成文件 | 分别写入独立产物路径，不覆盖彼此文件 |
| 界面重连重复提交事件 | 同一触发只生成一次有效执行与最终消息 |
| 重开历史、重试或重连后再次提问 | 模型输入中的每条公开消息只出现一次，保留正确署名 |
| 成员退出或资源撤权时仍有任务 | 排队任务及在途任务按规则停止，后续输入不读取撤权资源或其旧摘要 |
| 更改员工模型后继续会话 | 新 Run 使用新配置，历史 Run 的配置仍可解释 |
| 用户中途取消 | 停止继续调度，界面保留部分输出并显示取消状态 |
| 执行过程中退出并重启 | 未确认完成的 Run 标记为中断，不重放未知结果的外部操作 |
| 流式消息生成时进程退出 | 关联消息结束为已中断，保留已保存部分，不永久显示正在输入 |
| 等待用户操作时退出并重启 | 保留等待信息，恢复前重新校验，不自动批准或执行 |
| 重建会话摘要 | 产品消息不改变，新的上下文视图保留来源范围 |

通过上述场景后，再决定是否增加自由讨论、自动发言和更复杂的任务调度。
