# 当前实现与差距

本文保留 `87010ab` 的实施前基线；后续已接入的容量、工作控制和并行发布见[实施记录](../2.已实现功能与代码现状/20-Electron-BDD与协作重构.md)，不要把下述基线缺口全部视为当前仍缺失。

日期：2026-09-27。状态：**实施前源码的静态盘点；当时未重新运行行为测试，后续验证见 07/08。**

## 1. 当前执行链

```text
用户消息 → 创建 turn/event/deliveries → 每位员工独立 decision
  → 校验动作、引用、依赖与上下文序号 → 候选获得 grant
  → chat/task 执行 → 最终消息及协作记录提交
  → 新事件触发有界接续 → 本轮结算与记忆维护
```

主要入口为 [GroupScheduler](../../../packages/runtime/src/group-scheduler.ts) 的 `prepare/evaluate/respond/queue` 和 [AppService](../../../packages/runtime/src/service.ts) 的 `executeDecision/executeResponse`。公开消息与私有参与决定已经分开；不需要重建一套中央主持 agent。

## 2. 已经具备，必须复用

| 能力 | 当前依据 | 后续约束 |
| --- | --- | --- |
| 自主参与 | `decisionSchema` 和 `MastraEngine.decide` | 保留五种动作，失败不伪装 pass |
| 公平与有限并发 | 首轮 pending 优先、三个并行判断 | 首个可用候选不等最慢成员，全员机会不被抹掉 |
| 明确收件人 | 用户 mention 与 handoff 接收人校验 | 非收件人不抢答，handoff 接收方仍可拒绝 |
| 上下文版本 | `observedThroughSequence` 由宿主提供；过时结果重判 | 模型不能生成或覆盖权威序号 |
| 发言许可 | 单 `active.speaker` 与 `Grant` | 取消、撤权与旧运行不能绕过许可 |
| 依赖和失败 | `Contribution`、环检测、一次依赖补判 | 上游失败可见，不能永远等待 |
| 发布记录 | 最终 message/run 与协作记录通过 publish 回调批量写入 | 已有流式消息和产物登记也会提前持久化，不能把全过程描述成单次事务 |
| 重启边界 | 未结束运行、投递和轮次标为中断 | 不自动重放工具或外部副作用 |

模型装配见 [agent-factory.ts](../../../packages/runtime/src/adapters/mastra/agent-factory.ts)，上下文投影及协议校验见 [engine.ts](../../../packages/runtime/src/adapters/mastra/engine.ts)，数据类型见 [shared/domain](../../../packages/shared/src/domain/index.ts)。

## 3. 当前预算口径

| 项目 | 当前值/含义 |
| --- | --- |
| 判断并发 | 每会话最多 3 个 |
| 公开响应 | 同一会话单个 `active.speaker`，覆盖整个执行阶段 |
| 判断调用 | `max(12, 成员数 × 4)`，包括已批准的协议修复 |
| 总阶段调用 | `max(24, 成员数 × 8)` |
| 输出用量 | 累计已报告 outputTokens 达到 16,000 时停止；缺失用量保持未知 |
| 本轮时间 | 5 分钟 |
| 单员工发言 | 本轮最多 2 次主动公开发言 |
| 自动接续 | generation 上限 3；成员首次贡献不按群消息总数逐条增代 |

`modelCalls` 不是精确 HTTP 请求总数，task 内部多步调用另受 SDK 限制。结构重构保留这些口径；调整预算需要单独记录依据和回归结果。

## 4. 需要改善的边界

### 4.1 参与判断与执行使用同一员工模型

`createStageAgent('decision', ...)` 仍使用员工的模型配置，并装配员工规则、记忆和对话背景。可评估压缩判断输入、单独配置判断模型，但不能假设小模型必然保持判断质量，也不应在现有 decision 前无条件多加一次 triage。

### 4.2 一名员工的长任务占用整个响应时段

`active.speaker = respond(...)` 等待 `hooks.speak(...)`；后者进入 `executeResponse` 并等待引擎工具执行完成。因此当前“判断可并行”并不表示“同群实际任务可并行”。长调研会推迟另一位员工的短答复。

G2a 先建立最小工作记录和 run 执行权，G2b 再处理执行容量和发布顺序两个资源。只把 `speaker` 改成数组会破坏当前上下文、流式消息与序号假设，不能作为独立小修复提交。

### 4.3 发言前重判不能单独支撑并行草稿

当前在开始响应前检查版本；串行响应限制了竞争范围。若未来多个执行并行，执行结束时仍需检查草稿是否过时。`executeResponse` 当前提前创建 streaming 消息、分配序号并向 UI 发送正文；等正文全部展示后再拒绝发布已经太晚。

建议 task 执行期展示活动，最终正文在发布前保留为草稿；短 chat 初期继续单路流式输出。消息序号、最终排序和用户插话规则须随 G2 一起设计。

### 4.4 工作项标识不能防止不同员工重复执行

当前 `Contribution` 标识为 `turnId:agentId:main`，支持本轮员工依赖，但两个员工可分别登记同一目的。它不提供面向同一共享交付物的原子认领，也不支持跨轮次长期任务。

参考 Paperclip 后，将最小工作 ID、负责人和 run 执行认领前移到 G2a，作为 G2b 并行执行的前置条件。相似的自然语言目的不直接视为同一任务；多人独立评审也不应被错误去重。

### 4.5 轮次结束与工作完成仍需分开

现有代码在响应发布时可将关联 Contribution 标为 completed。这适合当前轻量贡献模型，却不足以表达“已给进度但文件尚未完成”“交付后待审核”等长期工作状态。

G2a 即定义最低工作交付依据，G3 再扩展多阶段验收和业务 disposition；不能静默重解释历史 completed 记录。固定两次发言或三代接续是安全上限，不是业务完成证明。

### 4.6 持久记录不等于可恢复等待

当前启动会把未完成状态标为中断；队列与 Promise 不恢复执行。已有[自动化服务](../../../packages/runtime/src/modules/automations/automation-service.ts)也保留重启不重放原任务的语义。等待依赖跨越重启，需要 G4 单独设计，不能仅添加一个定时器。

### 4.7 当前协作事件仍主要属于聊天轮次

ConversationEvent 当前包含 user_message、agent_message、handoff、dependency_resolved 和 stopped，投递身份关联 turn/event/agent。它没有独立长期工作、父子任务关系或按等待周期去重的工作唤醒记录。

G3 增加类型化工作接续，不改成所有消息广播执行。父子关系表达拆解，依赖边表达等待；依赖失败/取消不能视为解除阻塞。来源 run 自己的进度评论与已经结束任务的致谢不产生新的工作执行。

### 4.8 当前预算以单轮为主

总调用和输出用量主要记在 DiscussionTurn。未来如果任务通过新轮次、重试或子任务继续，仅保留单轮上限无法约束整个用户请求的成本。

G2a 在工作层记录跨 run 预算归属；G3 将子任务计入根工作。并发准入需要原子预留，运行故障重试、无进展继续和发布补判分别计数但共享根额度。未知用量不按零处理。

以上是对[原方案的 Paperclip 修订](./05-Paperclip机制与方案修订.md)，不代表已经新增这些运行时记录。

## 5. 存储与已有验证入口

[ProductStore](../../../packages/runtime/src/adapters/storage/product-store.ts) 提供串行批量写入；它目前没有对外提供“读取、条件检查、写入”同一事务的通用接口。任务认领不能采用无保护的 `load → 判断 → write`，也不能把 write 自身的串行性当作原子认领证明。

后续优先扩展这些已有验证入口：

- [service.test.ts](../../../tests/service.test.ts)：首轮机会、三判断并发、用户插话、依赖、取消、失败恢复、历史轮次和重启。
- [mastra-engine.test.ts](../../../tests/mastra-engine.test.ts)：私有判断协议、chat/task 边界、用量与上下文投影。
- [extensions.test.ts](../../../tests/extensions.test.ts)：外部执行后端、自动化与运行边界。
- [Electron 用例](../../../tests/e2e/)：实际消息顺序、活动、停止与历史展示。

本组列出的差距是后续能力边界，不代表当前保持行为的 B3 任务应一次全部解决。
