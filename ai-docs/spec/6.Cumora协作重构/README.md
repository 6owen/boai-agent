# Cumora 协作重构（结合 Paperclip 任务机制）

2026-10-08新增设计见[第14组Agent群聊协作](../14.Agent群聊协作/README.md)：普通群共同约定、顺序接续与定向唤醒。该组02第6节明确独立参与并行与顺序请求逐位接续的区别；普通API群首版已接线，旧历史验收保持，实际证据和未完成范围归该组05。

更新：2026-09-28。状态：**G0–G3 已实现；此前预登记验收记录为 197 项回归、15 个 Electron BDD 场景及真实模型语义 44/45。后续用户反馈暴露群聊问候的串行补判与提前超时，已修复并新增回归；真实五人问候延迟及格式稳定性仍需改善，G4 未启用。** 历史证据见[实施记录](../2.已实现功能与代码现状/20-Electron-BDD与协作重构.md)，本次按成员并行修复、五人流式/独立工作区回归及真实模型限制见 [10](./10-群聊问候并发与超时修复.md)。

目标：让多名数字员工能依据自己的身份、职责和授权上下文，自主决定是否接话、做事、等待或交接；同时由宿主保障顺序、任务所有权、预算和可停止性。

保留 Electron 本地架构、Mastra 执行适配和员工独立身份。Cumora 主要提供自主群聊参考，Paperclip 补充工作责任、run 执行权和有依据的任务接续；不整体迁入它们的服务端、数据库、组织层级或运行框架。目录路径保持不变，避免已有引用失效。

真实模型评估按[预先登记的协议](./06-真实模型评估协议.md)执行，使用隔离合成场景并保留所有结果；[逐项验收证据](./07-验收矩阵与证据.md)区分已覆盖的程序不变量、真实采样结果与语义质量/成本限制。

## 与既有计划的关系

- [第 4 组 B3](../4.数字员工与协作重构/03-群组协作与运行生命周期.md) 继续负责保持行为的模块拆分；不能借搬目录调整自动接话次数、执行并发或重启策略。
- 本组使用 **G0–G4** 标记协作行为演进。G0 建立评估基线；G1 优化参与判断与事件合并；**G2a 先建立最小工作项、run 执行认领与任务预算，G2b 再分离执行与发布并开放有限并行**；G3 增加父子委派、显式依赖及业务终止；G4 按需启用跨重启自动恢复与到期唤醒。
- G0 可先进行。G1–G3 开工前需有清楚的 collaboration/runs 责任边界，可复用 B3 成果；不要求先完成所有 Mastra 新能力。
- [第 5 组 Workflow](../5.Mastra能力扩展/02-动态工作流与执行编排.md) 可承载确定的任务步骤，但不接管每位员工的群聊发言判断。
- G4 与[自动化](../5.Mastra能力扩展/06-自动化与定时执行.md)共用现有调度和运行入口，不再创建第二套 cron 时钟；应用外执行仍属于原 A3 范围。

文中的概念字段与模块职责不等同当前 API；当前合同以源码为准，已验证范围以 07/08 为准。后续启用 G4 前仍需独立设计与验收。

## 必须保持的产品约束

1. 每位员工独立判断自己的参与行为，不引入中央 LLM 选择唯一发言人。
2. 用户发消息意味着应获得参与判断机会，不意味着强制全员回复；全员合法 `pass` 仍允许发生。
3. 已完成消息、私有判断、工具进度和最终交付物语义分开；模型失败不能伪装成自主沉默。
4. 用户新指令、停止、移除成员和撤权保持优先；失效运行不能启动新操作或发布迟到结果，已发生副作用保留核对信息。
5. 外部项目的并发数、时间间隔和轮数不直接成为本项目默认值。
6. 轮次完成、一次运行完成、工作项完成分别判定；结束聊天不等于已经完成用户工作。
7. 当前重启中断、不自动重放工具的行为继续有效，直到有明确迁移与副作用恢复方案。
8. 任务负责人、当前运行和发言许可分开；父子任务关系不自动构成执行依赖，依赖失败/取消不算成功。
9. 原始工作预算跨重试、运行和子任务累计；自己的评论、重复完成通知和已结束任务的致谢不自动开启新工作。
