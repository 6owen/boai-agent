# 多 Agent 测试体系与评估集方案

2026-10-03 补充：[自动化功能验收与结果审阅](../02-自动化功能验收与结果审阅.md)定义按大功能展示实际聊天、界面、成果与失败的交付形式，用户只评价结果。现有执行器、版本化样本、评分、人工标签和共享预算继续复用；可视汇总/统一留证尚待接入，不能据此将下列人工待评审或未执行项改为通过。

日期：2026-09-28。状态：**已实现首版执行器、38题、离线评分/报告、冻结合同和离线 CI 配置；已跑真实模型开发抽检。** 人工标签校准、正式留出验收与单人/多人对照尚未执行。下文保留设计依据，第11节记录实现及实测，不能把覆盖目录当作全部场景通过。

目标：证明多名数字员工能正确分工、交换可靠结果、交付用户目标，并在插话、失败、停止和预算耗尽时保持可控；同时回答“多人协作是否比单人更有价值”。默认业务范围为研究、计算、写作、审核与文件交付。

建议采用：**项目自己的业务评估集作为主线，Cumora 场景补充协作规则，Mastra 提供评分能力，公开研究补充复杂任务与失败分类。** 评估单位是一条用户目标及其完整工作树，不能把若干单 Agent 回复的平均分当作整组协作质量。

## 1. 制定方案时的基础与缺口（历史快照）

| 层面 | 已有能力 | 下一步缺口 |
| --- | --- | --- |
| 程序规则 | `tests/service.test.ts`、`work-repository.test.ts`、`work-dependencies.test.ts`、`model-capacity.test.ts`、`task-admission.test.ts` 等 | 将 04 的协议条款与断言持续关联，补故障组合，避免只统计测试数量 |
| 桌面流程 | `tests/e2e/features/` 的中文 BDD；协作场景覆盖委派、等待、停止与重启 | 增加产物核验、明确失败/阻塞展示、用户插话和撤权的代表性流程 |
| 真实模型 | `tests/evaluation/cases.ts` 的 9 个固定场景；`harness.ts` 从真实 AppService + MastraEngine 运行整组协作 | 当前只有初始输入和可选历史 seed，没有通用中途事件、任意成员配置、完整自动评分及留出集 |
| 结果留证 | 隔离数据库/工作区、消息、工作状态、产物文本、请求与用量、待复核字段 | 增加可重评分的事件时间线、工具效果记录、完整产物 hash、版本化评分标准与汇总报告 |
| 历史验收 | 08 记录的 197 项回归、15 个 BDD、真实模型 44/45 | 这些是该次版本的结果，不是本方案新增覆盖或当前最新测试总数 |

现有 9 类为：6 人介绍、12 人介绍、旧群问候、正式 @、自然点名、仅要计划、委派汇总、独立文件交付、合法沉默。每类 5 次是 **9 个任务 × 5 次采样**，不等于 45 种任务。

这些样本已用于多轮调试，适合保留为回归集，不能再充当未见任务上的泛化证明。上轮基线与最终候选均为 44/45；这证明候选达到当轮门槛，不能证明总体质量提升。最终 token 增加约 31.5%，因此新体系必须同时记录收益与开销。依据见 [08](./08-真实模型评估结果.md)。

制定方案时执行器还有几项实施约束：每场景样本编号最多到 5；请求上限默认 600、允许最大 1,000；产物正文只保存前 48,000 字符；退出码和 `complete` 不能直接代表语义通过。新增能力应在这些位置扩展，避免另造平行执行器。

首期优先内部业务集与 Cumora 的两类相反约束。外部任务要登记来源、版本、许可和改写内容；不整体迁入外部调度框架，否则测到的是另一套系统。

## 3. 四层测试及各自回答的问题

| 层 | 要回答的问题 | 运行方式 | 主要证据 |
| --- | --- | --- | --- |
| L1 确定性协议回归 | 抢锁、取消、预算、依赖、重启等规则是否正确？ | Vitest；真实 SQLite + 可控引擎/本地协议服务 | 原子状态变化、事件、实际效果和回滚 |
| L2 桌面 BDD | 用户能否发起、查看、停止、重新打开协作结果？ | playwright-bdd；真实 Electron + 本地协议服务 | 界面断言、产物、状态、截图和 trace |
| L3 真实协作评估 | 模型是否自主正确分工并完成目标？ | 隔离 AppService + 真实 MastraEngine + 固定业务数据 | 完整工作树、消息、产物、依赖和评分 |
| L4 对照与长期回归 | 改代码/提示词/模型后，质量、耗时和成本怎样变化？ | 同一数据版本的基线/候选实验 | 按任务类别比较的成功率、用量、延迟和失败明细 |

L1/L2 不能证明真实模型会合作；L3 不能替代数据库竞争与取消边界测试。大部分真实评估从服务层运行，少量 L2 场景验证 UI 与服务连通，不把全部模型采样放进昂贵且易受界面变化影响的桌面流程。

```mermaid
flowchart LR
  C[版本化任务与素材] --> H[现有评估执行器]
  H --> S[真实 AppService]
  S --> A[员工独立判断与 Mastra 执行]
  A --> W[工作树、消息、产物与效果记录]
  W --> R[确定性规则评分]
  W --> J[事实与质量评审]
  R --> V[逐场景结论与版本对比]
  J --> V
```

### 一道完整业务题的样子（B04）

给四名员工两份本地资料：订单 CSV 与指标定义。CSV 包含 O1（120、退款 0）、O2（80、退款 20）、O3（50、退款 0）、一条完全重复的 O2，以及已取消的 O4（999、退款 0），币种均为人民币。定义规定：按订单 ID 去重、取消订单排除、净额等于金额减退款、每单净额保留两位小数。

用户目标：研究员清理数据，分析师计算，写手产出 `report.md`，审核员核验后由负责人交付。基准答案由普通代码计算：有效订单 3，金额合计 250，退款合计 20，净额 230，平均每单净额 76.67。

验收同时核对：实际产物存在；数字和计算口径正确；报告说明去重与取消规则；审核引用真实资料；最终报告版本与审核版本一致；不存在额外的趋势、盈利或异常判断。记录真实工作和结果依赖，不能只看聊天中是否出现“已审核”。

轨迹按**必要先后关系**评分：清理结果先于计算、计算和草稿先于最终审核、审核结果先于正式交付。独立阅读可以并行；不要求固定的逐条工具调用顺序。现有用户可见消息和产物支持哪种草稿/正式发布区分，需在实现本题时明确，不能凭文件名猜测。

## 5. 评估集的数据合同

保留 `tests/evaluation/` 作为唯一入口。每个场景分为“给员工看的输入”和“只给执行器/评分器看的验收信息”，避免把答案或成功轨迹泄漏给被测系统。

| 字段组 | 必需内容 |
| --- | --- |
| 身份与版本 | caseId、datasetVersion、来源、业务类别、回归/开发/留出标记 |
| 输入 | 用户消息、初始资料、群成员职责、工具/文件权限、历史上下文 |
| 事件脚本 | 用户补充、停止、撤权、结果延迟/失败；按可观察事件触发，而非随意等几秒 |
| 预期目标 | 允许的交付/澄清/阻塞结果，必需产物及事实、允许误差 |
| 协作约束 | 必需参与角色、显式依赖、必要先后关系、禁止的效果和发布 |
| 预算 | 产品原预算、评估请求上限、场景超时、评分费用上限 |
| 评分 | 适用的硬断言、语义评分项、评分版本、失败严重度 |

例如 B02 的答案 `{sum: 60, average: 20}` 与“子结果交付早于父报告”保留在评分侧；模型收到的仍是原始用户任务。模型可以知道用户要求的质量标准，但不能看到内部标准答案、隐藏错误注入位置或留出题评审标签。

数据分三组管理：

1. **回归集**：原 9 类完整保留，新增真实失败最小复现，如等待声明冲突、截断判断、无依据扩写。
2. **开发集**：32 项矩阵中适合语义评估的业务实例，用于改提示词和评分器。程序故障实例仍放 L1，不凑真实模型题数。
3. **留出集**：第二阶段新增至少 16 个独立业务实例，覆盖串行/并行/合并、冲突证据、澄清和审核。题材、来源资料与任务结构按簇分离；只换姓名或数字不算未见任务。冻结后不用于调参，失败样本公开调试后转入回归集，并补入新留出题。

先用可离线核对的合成资料建立评分可靠性，再加入经过明确授权、去标识的真实业务任务。需要实时网页的任务单列“外部环境”集，保留资料快照与访问时间，不与离线可复现题混算稳定性。

## 6. 怎样评分：规则、结果、语义分别判

### 6.1 硬规则由代码检查

原子认领、权限、停止、根预算、依赖版本、结果归属、发布一致性、重复效果全部来自运行事件和持久状态。需要实际效果时检查文件内容/hash 或本地工具效果账本，不能只用模型文字证明。

检查“重复副作用”按同一逻辑操作及其效果身份判断，不能粗暴规定“一个文件只能写一次”；用户授权的修订可以产生合法后续写入。重新汇报阶段则必须没有新增工具效果。故障注入须记录自己确实命中预定阶段，否则是无效测试，不能算通过。

任何适用的关键硬规则失败，该样本不得通过，不能用漂亮的文案或高平均分抵消。缺少必要证据、评分器错误或无法评分须单列，不能被平均值自动忽略。

### 6.2 业务目标优先用确定性答案

数字用明确公式和精度；文件用真实存在、内容和归属；引用用资料 ID 与事实对应；多步骤任务用必需里程碑与最终交付检查。工作状态 `delivered`、模型退出成功、工具调用成功只说明各自状态，不直接等于业务成功。

预期结果可以是正确澄清或明确阻塞。停止测试的成功是及时停止，不能因为没有继续产出文件而判错；正常业务任务则不能以“准备开始”冒充交付。

### 6.3 开放内容用语义评审

每题只选择适用项：事实有据、需求覆盖、交接正确、审核有效、表达可用。各项用 0/1/2 的可解释等级，并要求输出消息/产物位置作为依据。关键事实与必需交接必须满分；风格分仅作诊断，不冲抵事实错误。

评审器读取题目、固定来源、最终产物及必要轨迹，不读取被测模型的私有推理。不允许使用被测群中的“审核员说通过”作为外部评审结论。工作流内的审核员本身也是被测对象。

建议使用独立配置的 judge 做初评；不同模型可减少部分自评偏差，但不能保证独立正确。先准备至少 20 份人工标注的正反样本校准，展示混淆矩阵及漏判；首期目标为总体一致率至少 90%、校准集中关键违规漏判为 0。没有人工复核时如实标“模型辅助评审”，不标“人工通过”。

发布候选人工复核全部失败、所有 judge/规则分歧，并随机抽取通过样本：数量为通过数的 10% 向上取整且至少 10 份，通过数不足 10 份时全部复核。需要改变评分标准时升级 scorerVersion，对基线和候选同批重评分；保留旧结果。

### 6.4 结果状态与指标

每个样本分别保留 `executionStatus`、`hardChecks`、`goalVerdict`、`judgeStatus`、`runtimeErrors`，最终汇总区分 passed / failed / incomplete / review-needed。业务交付成功后出现一次额外判断错误，可如实记录“目标通过、运行有错误”，不可把错误抹掉，也不可不看影响就丢弃成果。

| 指标 | 口径/用途 |
| --- | --- |
| 完整目标成功率 | 满足全部必需业务目标且硬规则通过的样本 / 已启动待测输入的样本 |
| 各场景成功率 | 单独报告分子/分母，防止大量问候掩盖委派失败 |
| 关键违规次数 | 越权、重复效果、停止后新执行、虚假交付；逐项显示，不平均 |
| 错误拦截率 | 注入错误被发现且更正/明确阻塞的比例；单列注入集 |
| 无依据结论率 | 对所有需事实验证的实质结论核对来源；不能只检查数字 |
| 首次有效成果、最终交付耗时 | 以确认有效的消息/产物事件为锚点；与首次字符时间分开 |
| 有效交付用量 | 全部已启动样本消耗（含失败）/ 成功目标数；成功数为 0 时不输出有限数值 |
| 运行健康度 | 判断/工具错误、无进展续跑、补判次数、预算退出、必要等待和阻塞 |
| 多人协作增益 | 在可公平比较的业务题上，与单人同预算成功率及耗时/用量比较 |

用量缺失保持 unknown，同时报告覆盖率。产品执行、seed/连接检查、judge 三项分账，再给全部实验总开销。供应商错误导致已启动任务未完成时计入端到端失败率，同时单列原因；任务开始前的环境失败不算业务失败，但使实验完整性不足。不得删除超时、取消、失败后只统计成功样本。

## 8. 对照、采样、预算与运行频率

### 8.1 三种对照分别回答不同问题

| 对照 | 固定项 | 可以得出的结论 |
| --- | --- | --- |
| 当前基线 vs 候选代码 | 数据、模型、角色、权限、预算、评分器版本 | 本次代码/提示词整体改动是否改善 |
| 单员工 vs 多员工 | 同一业务目标、资料、工具权限和总预算 | 多人协作是否有业务价值；单人获得完成任务所需的资料与工具并注明配置差异 |
| 串行 vs 有限并行 | 相同团队、任务和总预算 | 并行是否降低交付时间、增加冲突或开销 |

“必须由写手计算再交给研究员”的协议题不纳入单人增益对照，否则单人必败而结果没有意义。增益对照用目标等价、不强制团队拓扑的业务题。所有对照保持原有授权和副作用保护，不通过关掉安全规则获得速度优势。

每次尽量只改变一个因素。保持相同 fixture/样本计划，交错安排基线与候选的运行顺序，减少供应商时段差异；无法固定 seed 时明确记录。保留源码快照或完整 diff、锁文件、全部相关源码/提示词/资料/评分器 hash，避免只保存 HEAD 或四个文件就遗漏未提交变更。

### 8.2 频率与门槛（新体系建议，执行前登记）

| 时机 | 范围 | 判定 |
| --- | --- | --- |
| 每次提交/PR | 类型、UI 检查、L1、受影响 L2；合并前完整相关桌面回归 | 确定性断言全部通过，不调用付费模型 |
| 调提示词或模型 | 对应开发场景 1 次探路，再固定样本跑比较 | 探路结果保留但不算正式门槛，不因失败单独补跑 |
| 发布候选 | 固定回归真实子集每类 5 次，冻结的业务留出集首轮每题 1 次 | 硬违规 0；真实回归每类至少 4/5 且不低于同批基线；16 题留出至少 15/16，且无高严重度失败 |
| 有需求时的周期趋势 | 固定小集与新增历史失败；模型变更时跑完整候选流程 | 不以随机一次失败直接判断代码坏了；保存完整批次、分类趋势 |

这些是首版建议门槛，不追改 06 的历史标准，也不声称已被现有结果验证。留出单次用于初筛，不能证明稳定；对高风险/波动业务另预登记完整复测批次。5 次采样要报告原始 5 个值与区间，不用小样本 P95 宣称稳定 SLA；相近结果标“证据不足”，不强行排名。统计区间和对比按任务/模板簇计算，不能把同题重复当作大量独立任务。

性能先沿用简单社交中位延迟不超过基线 1.25 倍、判断输入不超过 1.10 倍作为回归参考。新增业务题先建立基线，之后再登记可接受的交付时限和成本；不得用本轮 +31.5% 结果倒推一个宽松标准。只有目标质量合格才比较速度和成本。

扩展后不一次跑满“所有题 × 所有模型 × 所有拓扑”。先按每类试运行测请求分布，再在执行前锁定批次与总预算；每个现有 runner 进程不超过 1,000 请求，父级实验预算必须覆盖所有批次、连接检查、失败和 judge，不能拆标签绕过总上限。预算不足保留 incomplete，不自动追加。产品根预算与评估总预算相互独立，不扩大产品预算来迁就长题。

本方案不创建定时任务。周期执行是后续测试流程选项，需真正实施调度后才称为已启用。
