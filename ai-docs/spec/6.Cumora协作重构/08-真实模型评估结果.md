## 第一版候选：任务验收失败

`candidate-formal-1790531080188` 的连接检查收到 HTTP 200，但输出超过 64 token 检查上限，未启动场景。随后在总预算内重试连接并开始 `candidate-formal-retry1-1790531156949`，完整保存了 19 个样本（截至最后完整样本累计 346 次请求）。

正式 @、自然点名、介绍、计划与沉默的已查看样本符合要求，普通解释不再创建工作。但两轮委派和独立文件均未完整交付（各 0/2），已经不可能达到 4/5 门槛，因此提前停止该版，保留全部已完成样本。中断中的 `introduce-12-3` 留有数据库状态，但当时中断处理尚未输出完整样本 JSON，不纳入完整样本统计；不能用 346 宣称包含中断后的全部请求。

失败原因：

1. 两个独立交付物都被模型赋予 `main`，宿主按正确的排他认领规则拒绝第二人执行。此前指令同时要求新的 work key 和旧 contribution 的固定 main，容易混淆。
2. 负责人通过聊天式 `request_handoff` 转交计算，没有建立自己负责的持久父工作与显式等待。
3. `report_work` 的答复摘录与后来正文不一致，事务严格拒绝交付；已有文件虽保留，报告不能发布。没有放宽证据检查来掩盖失败。

## 修复后的复测与正式采样

- 判断指令区分交付物标识与旧 contribution 字段。独立部分以交付物命名；负有整体责任的员工认领父工作，在执行阶段使用委派/等待工具。
- 执行上下文提供当前有效内置同事的 ID、名称和职责，不包含同事私有配置；随机 ID 的 SDK 回归先复现缺失，再验证修复。
- 发布前共用证据预检，失败进入已有无工具报告流程，最多两次并计入根预算；事务内仍严格复核。实际写入不重放，无法修复则保留草稿并阻塞。新增成功修复与达到上限两种回归。
- 评估中断处理改为取消当前会话、保存当前样本再退出，避免后续再丢失中断样本 JSON。
- 公开汇报使用业务结果和产物名称，不主动暴露内部工作 ID、版本或协议字段。

`candidate-repair-pilot` 的两个真实任务场景复测均通过，共 39 次请求（含连接检查）。委派有父子/显式依赖和定向恢复，独立文件有两个不同工作标识；证据修正期间没有重复文件操作。该试运行不计入正式 5 次样本。

`candidate-repaired-formal` 按同样 9 场景 × 5 次执行，最多再请求 961 次，与复测合计不超过 1,000。最终收集 45 个完整样本、844 次请求，与复测合计 883 次。语义通过 42/45；委派仅 2/5，未达到 4/5 门槛。其他 8 类均为 5/5。完整逐条复核见该目录的 semantic-review.json，汇总见 `.local/collaboration-evaluation/candidate-repaired-summary.json`。

- 45 个完整样本的请求（含场景 seed、不含连接检查与行政截断）：基线 **824**，最终 **885**。仅待测输入之后：**759 → 820**。不能宣称整体更便宜。

- 判断运行 **441 → 435**，判断 HTTP 请求 **446 → 442**。最终的 7 次额外判断请求属于有界格式/截断修复，无供应商限流重试。
- 最终有 **18 次无工具报告刷新**、0 个未发布草稿。它们计入上述请求和原工作预算；没有重复文件副作用。委派首个实际成果的中位延迟 **10.03 → 22.96 秒**，独立文件 **3.85 → 4.98 秒**。新增持久委派/证据汇报存在实际开销，不称作任务延迟优化。
- 最终 25 次任务运行均有可检查的交付/等待声明；排除错误扩写那次后，语义有效为 **24/25**。基线没有 disposition 字段，不据缺失字段计算 0% 有效率。
- 根预算合计保存了全部子工作/重新汇报的调用、用量及未知标记，完整值见 `final-comparison.json.current.budgetUsage`。无进展结算为 0；10 个定向唤醒均对应 5 次子工作启动及 5 次依赖就绪，没有自身评论或重复就绪导致的新工作。
