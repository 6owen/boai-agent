# 目标协作协议

日期：2026-09-27。状态：**目标协议；G1–G3 已实现并完成本轮预登记验收；具体失败、成本和模型质量限制见 08。下文概念不等同当前接口声明。** 实施以[阶段计划](./04-实施阶段与验收.md)限定范围。

已结合 [Paperclip 研究](./05-Paperclip机制与方案修订.md)修订：最小工作项和执行认领前移到 G2a，G2b 才开放有限并行；G3 增加父子任务、显式依赖及任务级终止。

## 1. 责任分配

| 责任 | 所有者 |
| --- | --- |
| 谁有权看到消息、使用资源和执行工具 | 宿主授权与运行快照 |
| 是否回复、做事、等待、澄清或请求接续 | 当前员工自己的模型 |
| 投递、容量、版本检查、发布顺序和停止 | collaboration / runs 中的确定性逻辑 |
| 同一共享工作由谁执行 | 产品持久状态中的认领结果 |
| 工作长期由谁负责、下一步等什么 | 工作项、负责人和显式依赖/等待记录 |
| 模型流、工具调用、步骤控制 | Mastra / 已验证能力的 AgentEngine 适配器 |
| 消息、工作进度与阻塞展示 | 产品查询投影与 renderer |

继续复用 scheduler hooks、AgentEngine、ProductStore 与当前授权服务。下文描述逻辑职责，不要求为每一项新建一个类、服务或公共接口。

### 1.1 四种记录各自回答一个问题

| 概念 | 回答的问题 | 生命周期 |
| --- | --- | --- |
| DiscussionTurn | 当前用户请求引起的讨论到哪里了 | 保留现有轮次与用户插话语义 |
| WorkItem（拟新增） | 哪项工作、谁负责、什么算完成、下一步等什么 | 可关联多个轮次与运行，不因换 run 丢失责任 |
| AgentRun | 某次模型/工具执行是否成功结束 | 继续复用现有运行状态；不等同业务完成 |
| 定向接续记录（G3） | 因哪个事件、叫谁继续哪项工作、是否已处理 | 关联来源事件与运行；G4 才启用跨重启自动恢复 |

普通 chat 不必须创建 WorkItem。用户明确请求执行且存在可交付目标时，员工可提出工作意图，由宿主校验并保存稳定 ID；重复请求沿用来源幂等关系，不用 purpose 文本猜测任务相等。

逻辑关系为 `WorkItem → 多个 AgentRun`、`WorkItem → 可选父工作/显式依赖`，而不是把所有业务进度塞回一个 DiscussionTurn。子任务范围不得超出原始用户请求；负责人不是全群发言的中央裁判。

## 2. 投递与参与判断

1. 先保存用户消息与触发事件，赋予稳定 ID；权限过滤后投递。
2. 对同一员工、会话和兼容上下文的连续 agent 事件合并调度，保留所有来源引用及最新未处理边界。
3. 员工根据本轮请求、实际新消息、自己的既有回复和相关工作状态，选择现有五种参与动作。
4. 宿主校验 schema、成员、引用和依赖。输入失效则重新装配，不使用模型输出修正权威版本。
5. 新用户轮次、撤权、停止和不兼容配置版本不能被旧事件合并吞掉。
6. G3 的工作接续按事件类型和明确关系定向投递，不将每条进度评论都广播成新的 task；记录可信的 sourceRunId/sourceAgentId，不能让正文自报来源。

首期保留“每条用户请求创建独立 turn”的语义；输入合并主要作用于同轮 agent 事件。不要直接把 Cumora 的全收件箱合并方式用于压缩多个用户指令。

人工输入应有判断机会，但模型合法 `pass` 不自动转为回复。自然语言点名由员工识别；只有明确 mention ID 才由宿主硬限制收件人。不得用中央分类模型给所有员工决定发言资格。

工作评论默认不唤醒其来源运行自身；已完成/取消工作收到致谢不重新开启执行。用户明确追加需求可创建新工作或显式重新开启并增加版本。工作完成事件不会自动替代对话里的用户消息，也不能使用户输入被当作已处理。

## 3. 判断成本与故障

轻量判断仍属于当前员工，使用其获准身份和最小必要上下文。优先精简输入，再比较判断模型；若引入单独模型配置，需说明默认继承、凭据归属、版本与失败回退策略。

| 结果 | 建议处理 |
| --- | --- |
| 合法 pass | 记录已处理，保持公开沉默 |
| 格式错误 | 按现有有限修复预算处理，耗尽后明确失败 |
| 供应商限流 | 有界退避，保留待处理输入，不立即升级到更昂贵调用 |
| 纯 agent 过滤不可用 | 可延后接续并记录原因，不标成业务 pass 或完成 |
| 人类请求判断失败 | 展示失败/可重试状态；不可静默确认已处理 |

模型连接维度的容量覆盖 decision、execution、memory；不同会话共享连接时也受约束。队列等待和实际模型执行的超时分别记录，取消能移除尚未启动的请求。

## 4. 有限并行工作与公开发布

G2a 先交付第 5 节的最小工作项、run 执行认领和任务预算，G2b 才允许互不冲突的 task 有限并行，chat 按员工独立并行流式（2026-09-28 根据聊天产品目标修订）。并发数由评估和连接容量决定，不在本文预设为所有用户的固定值。任务 ID 不同不代表文件/外部资源互不冲突，冲突操作继续串行。

```text
投递 → 员工自主决定 → 校验与执行准入
  ├─ pass / wait → 沉默或等待明确依赖
  ├─ chat → 员工独立并行流式回复
  └─ task → 有限并行执行 → 私有结果草稿
                              ↓
                   发布检查 → 有序提交 → 接续事件
                      ↓
              有新信息：更新汇报或放弃公开回复
```

执行期可展示工具状态和工作进度，但未经发布检查的最终草稿不能先作为已完成聊天正文出现。task 的最终序号和产物关联与发布顺序一致；chat 保持开始流式时的位置，完成通知使用独立事件 ID，不能把消息起始序号当成完成版本；活动占位不能被另一名员工当作已经完成的答案。

发布检查至少验证：运行/授权仍有效、员工仍是成员、当前输入未撤回、观察版本有效、发布幂等键未消费，以及工作负责人、当前 run 执行权和工作版本仍有效（G2a）。

新消息出现时，将实际新增内容交给员工，允许更新汇报、确认仍相关或沉默。无工作、收件人或依赖的首次 chat 回复意图，不因同伴先回复而作废；生成正文时读取当前获准消息。后续判断仍验证完成事件版本，任务发布按已观察的完成消息集合检查，避免漏掉先开始、后完成的流式回复。未声明依赖的独立根工作结果不使当前草稿过期，用户/聊天/同根及显式依赖结果仍检查。补判次数有界；禁止通过“强制发送”绕过未读状态。BoAI 首期不引入通用 `send-anyway` 开关。

**重新汇报不能重新执行已经发生的操作。** 文件已写入、命令已执行或外部调用已完成时，只重组结果说明；需要新操作必须走新的授权执行。副作用结果不明确则显示待核对状态，不能猜测失败后自动重试。

发布检查及提交必须在宿主同一串行临界区内与用户新消息、停止和撤权协调；如使用数据库条件更新，需同时保证检查与写入不可被竞争者插入。仅在模型调用前检查一次，或只依赖 `ProductStore.write` 排队均不足够。持久提交失败不能提前确认成功或消费投递。

用户插话的默认边界保持：新输入先保存，当前 chat 按既有规则结束后让位。并行 task 不再启动旧轮新工作；迟到结果先检查是否仍适合汇报。显式停止继续取消当前与排队工作，不因并行而弱化。

## 5. 共享工作认领与完成证据

G2a 最小工作项概念包含：稳定 ID、原始用户请求、会话、任务范围、目标交付物、负责人、工作状态、当前执行 run、版本、预算归属与结果证据。G3 再扩展父工作、显式依赖和等待条件。具体字段在实施时沿用现有领域命名，不直接把本文当数据库 schema。

负责人是长期 agent 身份；执行权绑定具体 run 与工作版本。BoAI 首期可以使用一个 activeRunId 表达执行占用，不要求照搬 Paperclip 两种 run 锁字段，但必须分别校验长期负责人和当前执行者。

认领针对明确的共同工作 ID。两个相似的 purpose 字符串不等于相同工作；同一任务也不能仅因换了员工就生成另一份可重复执行的工作。

- 未认领的工作：原子核对负责人、预期状态/版本、依赖与剩余预算，取得 run 执行权后才能产生副作用；重复认领同一 run 可幂等成功。
- 已被他人认领：等待结果、贡献独立部分或交接，不反复争抢。
- 有依赖的工作：等待真实结果或失败事件；不得把“开始做了”的进度当作完成。
- 工作完成：记录可检查结果，如已登记产物、数据结果或明确答复；验证要求由任务类型决定。
- 用户取消或授权撤回：停止执行；历史结果保留并准确标明状态。

持有者失联或租约到期只表示需要核对，不证明副作用未发生。首版不自动夺取正在执行的工作；人工/用户授权的重试也应先核对既有结果。

执行结束释放占用时必须比较当前持有者仍是该 run；旧 run 的 finally、取消回调或迟到提交不能清空后继运行的执行权。释放占用不删除工作负责人，也不自动将工作标记完成。外部效果与本地提交之间仍可能有不确定窗口，使用操作幂等键或人工核对处理，不能宣称锁保证所有外部操作 exactly-once。

现有 Contribution 继续解释为历史轮次贡献。新增长期工作记录时采用明确版本和关联，不将旧 completed 全部迁成“业务验收通过”。

### 5.1 父子工作、依赖与定向唤醒（G3）

- `parentWorkId` 表达任务拆解/目标归属；`dependsOnWorkIds` 才表示执行必须等待的条件。两者均需校验范围和环。
- 父任务不自动等待所有子任务；父任务所有孩子到终态也不自动等于父任务完成。任务自身验收条件独立存在。
- 依赖仅在成功交付且所需结果可用时解除。失败/取消只产生阻塞通知，由负责人决定替换依赖、缩小范围或请求用户处理。
- 等待时释放模型运行与当前执行权，保留负责人、依赖/等待版本与下一步。后续读取持久结果，不靠持续轮询同伴或扫描聊天措辞。
- 工作状态变化与待通知记录在同一事务提交，之后再投递；重复回调与恢复扫描使用相同幂等规则。入队、送达和业务处理完成不是同一个状态。
- 依赖就绪按 `workId + waitRevision + 所需结果版本` 去重；同一等待不重复执行，新等待周期不被历史完成回执误拦。

G3 只在当前应用运行期处理定向接续。工作记录和未消费输入可持久保存，但重启仍按现有规则中断并待明确恢复；G4 才允许核对后的自动恢复。

## 6. 接续与停止

业务进展、无进展接续和硬预算分别记录。有效进展来自可核对状态变化，例如依赖完成、产物更新或任务进入明确阻塞；“我会继续”“收到”不构成完成证据。

停止依据分为：任务完成、员工合法 pass、需要用户补充、依赖失败、用户停止、授权失效、无进展接续达到限制，以及调用/用量/时间硬上限。各原因应可在活动或详情中查看，不制造虚假的员工消息。

G1/G2 保留当前发言次数和 generation 上限。G2a 起工作预算贯穿重试与换 run；G3 若需要跨轮次或超过原两次发言限制，仍受原始工作及其子任务合计预算、无进展边界和取消范围限制，不先取消现有保护再依赖提示词收尾。

运行终态与业务 disposition 分开：引擎成功可以对应已交付、取得进展、等待输入、明确阻塞或没有进展。需要审核的任务先等待审核结果；普通任务不增加一律人工审批的门槛。用户只要计划时计划可交付，用户要执行时只有意向说明不算完成。

三种继续执行分别计数：运行故障恢复、业务无进展补跑、草稿过期重新汇报。均需有界，不能更换 runId 后重置。真实进展须有消息/产物/状态变化证据；循环创建子任务、改状态或追加相同文案不能重置无进展计数。

根工作预算在接纳并发执行前原子预留最小运行额度，结束后按已知用量结算；子任务额度来自根工作剩余额度，不能各自领取全新预算。未返回 token 的调用仍占调用/时间预算，用量标未知；既有 modelCalls 不能冒充精确 SDK 请求数。停止根工作需覆盖其新建子任务及排队接续，跨工作共享依赖不得连带取消。

提示词只保留可复用原则：依据已发生事实；只处理自己的职责；有新贡献才补充；遇到明确依赖可等待；完成目标后停止。模型看到同伴内容不意味着获得新增权限。

## 7. 持久等待与可观察性

G3 已定义当前宿主内的工作事件接续；G4 才启用跨重启自动恢复、外部事件订阅和到期唤醒。等待应保存依赖、权限版本与已消费事件标识，释放模型运行；事件到达后走现有产品运行入口。闲置聊天本身不是唤醒理由。

恢复只处理明确未消费输入，不重放状态不明的工具执行；权限变化、手动暂停、关闭任务及备份恢复都应使旧唤醒失效或等待重新启用。时间触发复用现有自动化与 Mastra schedules，进程退出时不承诺继续执行。

唤醒入队时与实际开始执行前均重新检查任务状态、依赖、授权版本、暂停和预算。重建上下文时读取当前工作与产物，不把旧 Mastra/ACP session 中的陈旧授权当作有效依据。待核对的外部效果未解决前不接纳重试。

可观察数据记录来源事件、观察序号、运行 ID、工作 ID、合并次数、发布受阻原因、等待时间及已报告用量。保留短事实原因，不保存或展示模型私有推理；未知 token 不记为实际零成本。
