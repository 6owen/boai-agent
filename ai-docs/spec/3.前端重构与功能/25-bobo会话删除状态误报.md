# bobo会话删除状态误报

2026-10-22，状态：**修复已接线，受控竞态回归及隔离桌面删除路径通过**。用户最初要求先记录、后统一修改，随后授权开始执行五项目标；本轮已修改产品与回归测试源码，没有操作实际用户会话。

## 1. 现象与已知边界

用户删除“bobo agent”的会话时，偶发同时出现以下两条错误提示，随后会话仍成功删除：

> 组织结果暂不可核对：此会话清理尚未完成，请重试清空聊天记录

> 此会话清理尚未完成，请重试清空聊天记录

用户说明“有时候出现，有时候没有”，本次刚遇到一次。对用户而言，删除最终成功却先提示失败和重试，会造成操作是否完成的歧义；删除成功应有明确、正确的成功反馈。

证据边界：对话中的用户截图可确认两条提示同时可见；最终删除成功及偶发频率来自用户描述。截图未另行复制到仓库。本轮没有独立复现、读取用户聊天/数据库或核对当时运行进程；具体会话ID、触发时刻、单条/批量入口、删除时是否正选中该会话及请求顺序尚未确定。

这里记录的是删除会话，不是删除bobo员工。后续沿用原会话删除、清空聊天记录和员工删除的区别，不扩大数据清理范围。

## 3. 预期状态反馈

| 原删除流程确认完成 | 从会话列表移除并按原规则离开已删除会话，统一通过Sonner提示一次“会话已删除”；不再出现该操作遗留的清理中错误 |

### 6.2 2026-11-04删除会话性能修复

用户报告删除 DS 会话长时间停留在“正在清理…”，随后授权修复。此次处理的是删除耗时；§6.1 的读取守卫、真实失败、恢复与单次成功语义保持。旧“删除提交后同步整理并单独反馈整理失败”的行为由本节替代。

**已确认原因：** `ConversationHistory.clear` 原先对每个集合执行 `tx.list(...).filter(...)`。其中 Trace 会先读取全部 JSON、按 rowid 排序并在 JavaScript 中反序列化，之后才判断是否属于目标会话。`AppService.clearConversationRecords` 在清理已经提交、完成事件已经发出后，仍等待整库 `VACUUM` 和 WAL 整理；前端要等整个请求返回才关闭弹窗。

**实现：**

- `ProductStore.RecordTransaction.relatedIds` 只接受固定会话、轮次、运行、工作及快照身份，在原事务内筛选并仅返回记录 ID。不同引用以 `UNION` 合并，运行/轮次 ID 数组驱动 `CROSS JOIN` 索引查找，避免组合 OR 或 IN 子查询误选集合扫描；重复关联只删除一次，空范围不匹配任何记录，大批身份使用 JSON 数组参数。
- Trace 增加会话、运行和轮次三个局部索引，沿现有 `init` 的 `CREATE INDEX IF NOT EXISTS` 接入旧库；首次加载建立索引，后续增删改由 SQLite 维护。只读取证连接不执行该迁移。
- 会话历史与单次执行历史复用上述 ID 查询；运行目录准备改用既有按会话读取。删除仍逐条经过原 `tx.remove`，保留搜索/FTS/时钟失效钩子，以及共享预算、材料/成果 hash 校验、来源记忆失效、去重回执和重启恢复。
- 会话清理提交并完成必要失效后返回，不再逐会话调用 `compact`。释放页面供 SQLite 后续写入复用，数据库文件不保证立即缩小；既有独立 `compact` 和备份路径保持。没有新增后台整理定时器或并发清理服务。

**验证记录：**

1. 先在基线 `4b21b0f7` 运行新增回归：大 Trace 正文零反序列化、删除/清空不依赖整库重写，共 3 项预期失败；旧代码确实反序列化了全部 28 条测试 Trace，并触发同步整理。
2. 修复前后从同一份只读 SQLite 备份生成独立临时副本，使用真实 `ProductStore`、`ConversationHistory`、材料/成果/阅读仓库清理已无记录的 DS。该快照约 275.26 MiB，包含 3067 条 Trace、正文约 242.00 MiB。未对个人数据执行删除，未调用模型。

| 其中 Trace 查询 | 1529.36 ms / 返回 3067 条正文 | 0.05 ms / 返回 0 个匹配 ID |
