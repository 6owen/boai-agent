# 浏览器能力迁移

更新：2026-10-02。状态：**原版窗口/宿主桥/员工任务源码已迁入，模块验证通过，真实桌面/发行目录与模型正在验收。** 本次实施记录见 [R2 验收](../../2026-10-02-R2浏览器迁移验收.md)，最终详细进度以 05 为准。

实施顺序：本组位于 [01 后续功能路线图](../01-后续功能实施路线图.md)的 R2，在 R1 本地检索升级完成后启动；旧浏览器复用方案和 BRM0–BRM4 合同继续有效。

## 已确定的实现方向

**以旧 `boai-app` 为源，直接迁入浏览器窗口、工具栏、视觉控制和 CDP 操作，再适配当前员工任务。** 尽量保留原类名、函数、交互和命令，避免重新写一套浏览器。

- 保留独立 `BrowserWindow` 与 toolbar/page/overlay 三个 `BrowserView` 的组合；首批不改成 IM 内嵌网页或另一种视图架构。
- 保留 `BrowserCDP`、AX snapshot/ref、页面动作实现，以及 `BrowserPaneFns`、命令 parser 和单一 `browser_tool({ command })` 入口。
- 保留地址栏、返回/前进、刷新/停止加载、隐藏/关闭、可见自动操作、截图与人工登录的交互基础。
- 适配旧包别名、日志/主题/导航、IPC、构建和 Pi 工具注册；Mastra 只在获准 task 中挂工具。
- 修正共享 Cookie 分区、全工具自动放权、在途动作取消和未知回执；这些改动是当前多员工执行所必需。

这一选择取代上一轮分析中“优先将模型入口拆成多个独立工具”的建议：**保留原统一入口，但确定性解析后进行逐动作授权，首批拒绝模型批命令。** 不把整套 browser_tool 当成只读，也不在运行时执行被禁用的子命令。

登录方案也采用原版持久体验，替代前期分析“先临时资料”的候选建议；分区按员工×会话隔离，并有明确清除和备份排除。

首批不安装 `@mastra/agent-browser`，不搬 Pi/远程 WS/MCP 运行框架。当前链路是 **Mastra task → 原版浏览器命令适配 → 宿主桥 → Electron/CDP**。将来需要标准 `Agent.browser` 属性时，可另封装自有 provider；它不是本批前置条件。Computer、MCP 插件和结构化搜索服务后续单独设计。

## 首批成功是什么样

用户在员工详情启用浏览器，给该员工一项明确网页任务。员工使用专用窗口打开页面，用户看得到操作、能够人工登录和接管。读取结果包含可核对来源；需要下载时保存受管原件并明确发布成果。任务停止后没有继续操作或迟到发布；其他员工的页面与登录不受影响。应用重启保留已提交事实和选定的登录资料，旧任务动作不自动重放。

新员工权限默认关闭；启用能力不启动窗口、不触发消息、不创造 Work。普通聊天、判断与记忆维护不挂浏览器工具。团队创建仍保持名称/需求两字段；ACP 员工仍使用外部自有工具，本组不把本机能力自动注入 ACP。

同一员工在不同聊天的浏览器登录分区首批独立；同一分区可沿旧体验保留登录，但不共享到其他员工或群聊。没有旧共享 Cookie 导入步骤，不扫描用户日常 Chrome profile。账号复用的额外产品规则留给后续明确需求。

3. 本地底层代码以复制和局部适配为先；每项行为改变说明原因与验证，不能以“兼容”为由继承共享登录、跳过授权或重放副作用。
4. 当前首批只做本地 Browser。不能借迁移引入默认 Computer、云服务凭据、插件市场、用户桌面控制或第二套记忆/Work 系统。
5. 每批完成后同步源码 Header/目录地图、本组 05 及实际实现记录。未测试、失败、未知用量和待人工评审分别记录，不能计为通过。
