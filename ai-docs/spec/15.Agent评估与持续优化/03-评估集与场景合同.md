# 评估集与场景合同

日期：2026-10-09。本文给出候选题目合同；下表是覆盖方向，不表示这些场景已经全部实现或通过。

## 1. 题目、采样与任务簇

- **题目（case）：** 固定用户目标、材料、初始状态、事件和成功条件。
- **采样（trial）：** 某个代码/模型配置对同一题目的一次独立执行。失败后重跑是新采样，原失败保留。
- **任务簇（cluster）：** 共享任务结构或素材来源的相关题目，用于分集和统计。
- **实验（experiment）：** 事先登记的题目、配置、重复次数、总预算和比较目标。

五道题各跑三次是五道题、十五个样本，不是十五种业务覆盖。更换姓名、数字或角色顺序的变形题，应保留与原题同簇的关系，不能据此宣称新领域泛化。

## 2. 数据集用途与生命周期

| 用途 | 允许怎样使用 | 维护要求 |
| --- | --- | --- |
| 回归集 | 保护已经承诺的行为，所有候选都可重复运行 | 保留真实失败最小复现、常见成功与不应触发的负例 |
| 开发集 | 分析完整失败轨迹，提出和调试改动 | 可见题目和答案，但不能将特定答案写进产品提示词 |
| 验证集 | 按预登记频率比较候选、判断泛化趋势 | 优化者只获得约定汇总；它参与选优，不称为最终未见测试 |
| 最终留出集 | 对选定候选做最终验收 | 题目/参考答案与优化工作区隔离，不参与每轮选补丁 |

现有`EvaluationCase.split`只有`regression/development/holdout`。验证集、访问治理和新生命周期属于待实施设计；不得只改文档名称就宣称当前支持四分集。实际扩展应升级合同，兼容旧记录。

现有`holdout-manifest.json`保持原样。本轮不查看或扩写其答案；后续先核对既有题目曾被谁、用于什么目的访问，再决定能支持哪种结论。不能仅凭hash未变就声明未泄漏。任何已向优化者公开用于修复的留出题，转入开发/回归用途并补充新版本题目，旧成绩保留。

不同分集按任务簇和素材来源分开。最终题目使用独立受控位置与最小访问权限，日志和报告也不能间接泄漏参考答案；具体存储机制在实施时确定，不以路径命名代替隔离。

## 3. 一道题应具备的合同

以下为逻辑字段，不是本轮新增的TypeScript接口。

| 字段组 | 必需内容 |
| --- | --- |
| 身份与版本 | caseId、caseVersion、所属功能/条款、cluster、分集、来源和输入hash |
| 用户可见输入 | 原请求、必要业务规则、材料及版本；不能在评分侧临时增加隐藏要求 |
| 初始环境 | 员工/角色/模型、会话状态、工具和权限、隔离数据、允许继承的历史 |
| 中途事件 | 明确修订、纠正、取消、成员变化或重启；触发条件、消息内容与执行身份 |
| 硬规则 | 权限、预算、因果、版本、幂等和副作用约束；回链正式产品合同 |
| 结果标准 | 必需成果、数值/格式/范围、内容评审断言和允许的合法解法 |
| 评分侧材料 | 参考解、公式、评分条件、已知正反样本；与被测员工输入分离 |
| 限额与观测 | 产品原预算、评估总预算、最大时长、必需证据和结束条件 |

业务内容要求必须在任务或获准材料中可获得。权限、未知不重放等系统规则来自既有产品合同，不需要在每道用户消息中重复，但必须可以追溯，不能凭评分者偏好临时添加。

不规定唯一文案，除非精确文本本身就是任务要求。不用“必须调用三次工具”代替“必须读取指定成果版本”。故障注入题显式标注注入方式，不能冒充自然真实供应商成功。

## 4. 跨功能覆盖方向

| 功能 | 正常业务题 | 困难或不应触发的题 | 关键证据 |
| --- | --- | --- | --- |
| 多Agent聊天 | 独立介绍、顺序接龙、共同事实更新 | 慢成员、明确无需回复、旧消息不重复响应 | 前置消息原文/hash、输入、启动与提交顺序 |
| 多Agent工作 | 串行审核、并行研究后汇总 | 缺依赖、矛盾证据、失败分支、步骤耗尽 | 完整工作树、实际读取、文件与公开交付 |
| 连续IM | 追加需求、引用前文、明确纠正 | 取消旧限字、普通进度不重新开工 | 每轮实际输入、约束来源及公开输出 |
| 材料与文件 | 材料到报告、固定版本修订 | 缺材料、错误版本、只讨论不修改 | 来源资格、V1/V2原件、修订请求及hash |
| 记忆与检索 | 相关历史在当前任务中有效使用 | 无关记忆、来源失效、撤权、当前纠正优先 | 实际检索/上下文、来源及无泄漏检查 |
| Skills与工具 | 需要时选对能力并完成任务 | 无需使用、未绑定/不可用、工具报错 | 获准能力、真实调用、实际效果与解释 |
| bobo组织 | 复用员工或只补缺员、建群回执 | 只讨论、只创建员工、未知回执核读 | 身份、真实群与原请求、零重复创建 |
| 自动化 | 正常触发、明确补充、结果通知 | 重复触发、额度耗尽、回执未知及重启 | occurrence、账本、状态、实际副作用 |
| 浏览器 | 在隔离环境查找资料或完成获准操作 | 页面失败、取消、需要授权但未获授权 | 页面/环境终态、调用来源和实际退出 |

各功能从自己的专题选择适用题，不要求首期一次覆盖全部矩阵。普通群关系和有工具工作分别统计；不把报数成绩外推为任意协作能力。

## 5. 首批完整任务示例

首批优先衔接第14组`GC-S15`五轮编辑部，以其已固定输入和原断言为准。下表是结构说明，不替换现有feature正文。

| 阶段 | 输入与动作 | 要检查的结果 |
| --- | --- | --- |
| 讨论 | 三名独立员工按当前约定讨论立意 | 各自真实贡献、事实正确、当前发言长度约束 |
| 写稿与审核 | 用户明确安排初稿与依赖审核 | V1存在；审核者实际读取V1；意见对应原件 |
| 明确修订 | 通过原文件卡片在同一composer提交修订 | 新请求/新根Work、V2与V1来源对应、V1保持 |
| 复核与发布文案 | 按新一轮明确分工产出结果 | 审核新版本、指定摘要片段长度达标、负责人公开交付 |
| 重启续聊 | 同场重启，再发送明确新消息 | 重启零重放；历史可读；新回复遵循当前要求 |

完整成功必须满足全部必需阶段。摘要达标但未公开交付、只完成前三轮、缺原件或第五轮未运行，都不能计为整题通过。阶段性成绩保留用于诊断。

这道题已经用于调试，应进入开发/回归用途。未来另建不同素材和业务结构的独立题检验推广效果，不能把换一组姓名的编辑部题作为未见任务证明。

## 6. 样本来源与维护

优先使用已有授权的隔离测试材料、真实失败记录和产品需求；对真实用户记录先确认可用范围，再最小化和脱敏。生成题应锚定可核对业务事实，给出可行参考解，不能批量生成无人核读的题目来充数。

每次新增题检查：人能否完成、规则是否明确、合法解法是否可能被误判、为什么有业务价值，以及是否与其他分集同源。题目不可解或评分条件错误时登记题目缺陷；不得悄悄改输入后覆盖原失败。

首批题量和重复数在试运行后登记，由预算与可测量变化决定，不预设“全功能×全模型×全拓扑”的大矩阵。旧场景ID及历史证据保留，新输入建立新版本。
