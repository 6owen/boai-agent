## 1. 要回答的问题

- 当前功能在什么任务上可靠，在哪些条件下失败？
- 一次提示词、模型、工具说明或运行代码改动，改善了什么，又损害了什么？
- 多名员工相对单名员工，是否带来可测量的业务收益？
- 一次技术通过是否具备完整证据，内容质量是否经过适当评审？
- 在既有权限和预算内，能否稳定完成用户目标？

评估单位是一条完整用户任务及其相关会话、工作树和成果。无Work的顺序聊天按完整对话轮次评估；文件任务不能只看最后一条回复或某个子Work的状态。

## 4. 范围与边界

首批复用`tests/evaluation/`、既有脚本和`playwright-bdd`；不预建通用平台、新数据库或产品评估页面。确定性规则使用代码，开放内容使用有证据的模型评审，并由人工校准。

真实桌面验证沿用户已明确的`pnpm dev`方式，无需安装包。真实模型实验按批次登记配置和预算，不自动开启周期任务。当前本机合同以第13组10/11及专项补充[14](../13.本机Agent员工运行时/14-本机Agent输入交付与原生信息修复合同.md)为准，实际状态归06；本组12 §8固定输入交付/元信息待修验收，当前仅文档准备归07 §12，A2A继续延期。

同日通信入口定位下复核见07 §13：员工入口转交原文/材料、绑定配置/session、原生Agent自主执行；普通已结束的提问和真实阻塞输入分开验收，产品材料权限不扩大为原生门禁，可选信息缺失保持未知。12 §8是后续实施的验收依据，尚未运行这些新增场景。
