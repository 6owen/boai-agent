# 本机Agent任务稳定性评估方案

日期：2026-10-12。用户确认重点为**稳定完成真实任务**。评价一条完整用户任务及全部轮次、真实文件和依赖链；Codex与Claude分别测量，不因能发现程序、生成回复或某次运行结束就算成功。复用第15组11的独立评分/校准/隔离候选规则，不另建评估平台。

2026-10-12后续澄清：本机Agent自己提供原生能力，先评估BOAI传递指令并回传结果是否影响同一任务。现已接§7的native-parity小批真实对照，实际成绩/失败唯一归第13组06 §140。下列八题/48样本仍是先前扩展提案，未执行；API `eval:build/hillclimb`没有因此支持所有本机题。所需产品/旧评估入口缺口见[第13组review](../13.本机Agent员工运行时/13-本机Agent接入Review与评估准备.md)。

## 1. 三层入口

| 层级 | 要回答的问题 | 执行与判定 | 自动触发 |
| --- | --- | --- | --- |
| 工程合同 | 接受消息、事务、来源和实际退出是否正确 | Vitest + 原生协议夹具 + 真实OS子进程；不调用真实模型 | 现有离线CI |
| 产品流程 | 用户是否能完成回答、审批、修订和重启 | 既有Electron BDD，以`pnpm dev`启动隔离数据；流程夹具明确标offline | 离线CI/开发回归 |
| 任务质量 | 在原预算内是否稳定交付符合目标的成果 | 同一产品路径接真实本机CLI；确定性检查 + 独立judge两次 + 人工校准 | 显式登记后手动启动 |

不以单元测试分数代替真实业务质量；不恢复旧五阶段限制、不关闭原生工具来使测试容易通过。材料、模型和普通消息仍走当前产品入口。

## 3. 六项必须同时覆盖的边界合同

| ID | 触发与检查 | 所需证据 |
| --- | --- | --- |
| N-G1 | 原生等待追问时，普通回答同时附TXT/图片；继续同turn，材料来源获准，无重复新轮执行 | 原输入请求、消息/材料回执、对应答案、session/turn；首先复现R1 |
| N-G2 | 同一明确原生请求分别批准/拒绝；回应后与重启后仍可看实际决策，秘密答案不展示 | action身份、参数、所选范围、终态、只读历史；首先复现R2 |
| N-G3 | 实际原生命令及另建进程组子进程写入后停止；确认PID身份对应、后代退出且无最终副作用 | 停止前PID/创建身份、台账、退出事实、文件hash、重启零重放 |
| N-G4 | 外部执行受理后传输故障或应用重启；保存unknown/interrupted，不能自动重发已受理副作用 | 受理/故障边界、原request/session、工作区标记、重启前后调用差异 |
| N-G5 | 员工A/B或两个聊天读取不同标记材料；移除成员/来源失效后再明确发消息 | 权威成员/来源版本、不同session、未授权材料未进入新增输入；历史不重解释 |
| N-G6 | 执行中模型/profile换绑被拒绝；真实退出后显式换绑保留员工和聊天，原未知不重放 | 前后配置版本、资源退出、旧历史、新session/model身份 |

G1/G2可先用协议夹具确定性覆盖双后端；G3用真实OS及CLI验证实际退出。G4–G6的故障必须命中预登记边界，未触发列incomplete，不能以任务自然结束代替。每项首版每后端1次，12个边界样本独立于内容48个样本，不混算一个成功率。

## 4. 采样、配置和预算

1. 先修review发现的接线和评估问题，离线确认失败也有记录、重复身份不冲突、strict可信、输入/规则hash固定。建立未知/缺件/失败的评分器负例，不能只测成功归档。
2. 探路选D1–D4，每后端一次，共8个真实任务。只采集输出、失败与成本，最多16次独立judge调用；不开启自动优化。用开销/波动决定正式计划，不能在启动后续改原计划。
3. 正式基线为八题×Codex/Claude两个后端×每题3次，**48个内容任务**；D/V分开、后端分开显示。三次是测量下限，不能据此认证全业务可靠性。六项边界另12个样本；合计60个任务/边界尝试，不合并结构与语义成绩。
4. 程序路径/hash/实际版本、profile配置hash、原生认证来源、实际模型/effort、权限、系统环境、题库/评分器/judge版本和源码hash均预登记。BOAI不复制本机登录token。
5. 文档/代码每任务最多3个外部turn，材料最多2个，原生协作参考现有8个外部运行上限；核心产品Work输出额度与绝对期限保持原值。正式内容基线的上限计算为`(3+3+2+8)×2组×2后端×3次=192`个外部运行，不是192个供应商内部请求。边界另行登记，失败也消耗额度；不扩大生产额度以换成功。
6. 正式语义评审每份完整样本2次，最多96次judge API请求，与被测外部运行分账。运行中途失败原样记分，不为了取得judge满分重跑BOAI。用量只记录实际报告，原生内部请求数未知保持null，未知不能作零或用外部turn推算金额。
7. 真实路径与judge模型使用已明确选择的配置；尚未启动的本计划没有消费或新增预算授权。不得借准备文档自动启动这60个样本、自动化周期或Codex优化。

以上上限是建议预登记值，执行前按探路成本固定。停止条件为预算/原期限耗尽、未知调用、输入/规则变化、原件hash不符、评分不一致/未校准；保存停止和未执行列表，不重试直到成功。

## 5. 判定与报告

硬检查负责真实文件/数值/版本、依赖原件读取、权限与退出、重启增量、冻结测试和限定文件变化。原生工具证据来自完整执行事件，`runs.toolEvents`仅是BOAI桥，不能用于断言没有发生原生操作。只读检查包含工作区文件hash，不能仅看没有新增artifact。

内容标准每条0/1/2，独立judge连续评价同一输出两次；引用限定真实消息/run/artifact证据。条款或逐项分数不一致、截断、非法引用、原件不完整均保留pending/invalid。人工校准沿原合同：至少20个不同正负样本、固定judge版本、至少90%一致且零关键漏判；不由开发代理代填human标签。历史原生评分只作未校准模型建议。

每个attempt有以下三个独立维度：`technical`（运行/硬检查）、`evidence`（同场身份/hash/完整性）、`quality`（内容判定）。任何一项failed则整任务failed；缺证据incomplete；内容未校准review-needed。不能用已交付状态、模型自称完成或用户打开报告替代质量通过。

报告必须显示登记数、已启动数、passed/failed/incomplete/review-needed/not-run全分母。内容失败没有最后阶段快照也生成记录；生命周期场景单列。不计算“完整记录中全通过”来代表原完整批次。未全部判定前显示通过数及pending，若展示`passed/登记数`须标为固定题集完成下界，不伪称最终可靠性估计。

记录first reply/完整任务耗时、BOAI外部运行、原生报告tokens及覆盖率、API同事真实调用、judge成本和优化者Codex用量；未知值不填0。少量重复只报告每题/后端的分布、失败类型和配对差异，沿第15组11保留区间假设及小样本限制。

## 6. 最小实现落点与验收顺序

| 顺序 | 复用位置与必要改动 | 验收结果 |

| 2 | `checks.ts`、`rescore.ts`、`score-collaboration.mjs`：native投影进既有评分/报告，严格状态和比较；样本身份绑定任务与评分合同 | 失败退出1，待评/缺证据退出2；不支持baseline时明确拒绝；改合同旧评审失效 |
| 3 | 现有`native-execution.feature/steps`及shared Desktop生命周期：输入参数化、题目/材料fixture、冻结代码测试和故障命中；保持业务断言 | 离线流程完整通过，能够用真实CLI运行同一产品路径；新轮与重启无重放 |
| 4 | `cases.ts`或其原生业务子模块：登记八题/六边界与开发验证簇；由`eval:build`生成实际输入/规则/rubric审阅页 | build零模型调用；本机题明确走native desktop executor，拒绝API runner误执行 |
| 5 | `judge.ts`、`calibration.ts`、`report.ts`：原件两次评分、真实人工标签及后端/分组报告 | 8项探路原件供审阅，评分校准门禁保持，失败/未知未被挑除 |

本轮准备止于设计。先交付可检查基线与失败分类，再接自动优化；不承诺尚不存在的`eval:native`命令。现有离线native导入用`eval:score --source native`，待评分仍须显式走后续rescore/judge，且review列出的缺陷修复前不用于strict门禁或成功率比较。

功能修复和真实本机任务成绩继续写第13组06；第15组07只登记评估基础设施和实验机制。最终未见题、其他平台与所有模型组合的认证另立隔离任务，不挪用此处48个样本作该结论。

## 7. 当前收窄目标与可执行对照入口

目标是同一指令/材料直接交给本机CLI与经BOAI交给原生会话时，真实任务效果是否一致，并核对公开回复/Agent信息是否完整。两类任务（材料计算与代码修复）覆盖文件读取、实际命令、修订和重启只读续聊；不为每种原生工具设计新的产品适配，也不宣称覆盖全部工具。

```sh
node scripts/evaluate-native-parity.mjs --root .local/NEW_PARITY_RUN \
  --codex /ABS/SELECTED_CODEX_PROGRAM --claude /ABS/SELECTED_CLAUDE_PROGRAM --prepare-only
node scripts/evaluate-native-parity.mjs --root .local/NEW_PARITY_RUN \
  --codex /ABS/SELECTED_CODEX_PROGRAM --claude /ABS/SELECTED_CLAUDE_PROGRAM --run-prepared
```

首条冻结源码、实际输入/规则和程序身份，生成design-review.html/plan.json，零模型调用；次条先零模型开窗，再沿既有BDD执行。固定四组对照、八条路径各两轮、最多16个外部运行、一次样本、零重试。原生内部供应商请求仍未知，不能将16外部运行称16内部请求；开放语义/人工标签不由硬规则伪造。

`--reuse-direct-root PRIOR --budget-file ORIGINAL_LEDGER`只复用原程序/题目相同且完整留证的CLI结果，准备时固定原件hash；按原账本继续，不重新跑业务，也不将跨批两入口拼成同一场成功。中断/缺失基线明确拒绝，未执行和失败进入报告。产品任务、准备失败、元信息可比性和生命周期问题分口径展示。

## 8. 输入交付与原生信息修复的验收登记

## 9. 输入修复的v2真实探路接线（2026-10-12）
