# 报告留证与工程接入

日期：2026-10-09。复用[全局自动验收与结果审阅](../02-自动化功能验收与结果审阅.md)，由开发代理准备数据、运行场景和留证，用户审阅实际效果。

## 1. 两种报告，共用原始证据

| 报告 | 主要读者问题 | 复用入口 |
| --- | --- | --- |
| 功能审阅 | 用户在界面上经历了什么，成果是否可用？ | `scripts/generate-feature-review.mjs`与同场截图/原件 |
| 实验比较 | 哪个版本更可靠，改进是否超过噪声，代价是多少？ | `tests/evaluation/report.ts`及版本化评分 |

功能报告按spec大功能组织，实验报告按固定配置和题库版本组织，通过experiment/trial/case和原证据hash关联。入口不同不复制成两套事实数据库；同一失败在两份报告里仍指向同一次运行。

## 2. 每次运行的证据清单

| 分类 | 应保存的事实 | 缺失时的处理 |
| --- | --- | --- |
| 实验登记 | 目标、预定样本、基线/候选、上限、接受标准 | 不宣称已完成受控比较 |
| 版本 | 源码/未提交diff、构建输入、锁文件、题目、提示词、评分与judge版本 | 列出不可比项，不只使用HEAD冒充全部输入 |
| 用户与团队 | 原消息、材料、隔离成员/角色、模型配置摘要、权限 | 无法确认输入或身份则不完整 |
| 过程 | 实际可观察输入输出、事件、工作树、依赖、工具调用与副作用 | 不用自然语言完成声明补造过程 |
| 成果 | 原件、字节数/hash、版本、来源、发布与读取证据 | 截断正文不冒充完整原件 |
| 预算与耗时 | 每阶段调用、已知token、覆盖率、排队/执行与结束时间 | unknown与0区分，原账本与活动计量分开 |
| 桌面证据 | 关键画面、实际尺寸、Trace/适用录屏、重启前后状态 | 最终截图不冒充完整操作过程 |
| 评分 | 各硬检查、语义证据、判定、根因和评审身份 | 评审缺失或无效保持待评/不完整 |

不要求保存供应商不可提供的内部推理。凭据、密钥、无关私有历史和浏览器登录资料不进入报告。使用真实材料时先确认可用于评估和报告的范围；脱敏产生的派生件记录版本与关系，不伪称与原件同hash。

## 3. 留证时机与失败保留

沿`BOAI_REVIEW_RUN_DIR`在隔离场景清理前导出，结束后校验文件bytes/hash及引用关系，再从最终结果生成新报告目录。保留场景失败、启动前失败、取消、超时、未运行计划与导出错误。

场内重启使用本场目录；采样之间使用不同目录。旧run迟到、退出未确认或文件保存未知时，记录真实状态，不让评估脚本自动重发业务获取“更完整的结果”。

一次场景的截图、模型输入、原件与状态必须属于同一个trial。多个局部成功不能拼成一次完整五轮通过。聚合报告可以并列展示多次运行，但不能替换它们的原始身份。

## 4. 报告阅读顺序

首屏展示被测版本与范围、登记/启动/完成数、passed/failed/incomplete/review-needed、关键违规、已知成本及计量覆盖。随后按功能、任务簇、入口和模型来源展开。

逐样本页面应提供：输入 → 阶段里程碑 → 实际成果/版本 → 检查和评审证据 → 失败原因 → 调用与预算。原件和Trace可以直接打开；只有概要统计不能支撑“协作正确”的结论。

版本比较展示固定项、允许的差异、配对样本、分组变化和统计限制。明显不可比的两批仍可并列浏览，但不给出“提升百分比”的误导结论。

技术结果、证据完整性、语义评审和人工效果评价分别显示。点击查看报告、脚本采用成果、模型说满意，都不等于用户认可。

## 5. 离线重评分

保留原始样本不可变；新评分写入新目录并引用原样本hash。评分错误修复后，适用基线和候选使用相同新版评分器处理，旧成绩保留。

重评分必须无业务模型调用、无工具执行、无产品状态写入。若需要新增模型judge评审，这是另一个有预算的评审批次，先保存评审结果，再由离线重评分消费，不能冒充零成本重评分。

损坏JSON、丢失文件、hash不匹配和旧合同缺字段均显式登记，不能从报告过滤掉。旧记录确实没有新证据时保持缺失；必要重跑属于新的trial，而不是补齐旧历史。

## 6. 工程频率与现有命令

| 时机 | 执行范围 | 规则 |
| --- | --- | --- |
| 日常修改/PR | 受影响模块、离线SDK、评分器与冻结检查、适用BDD | 不自动调用付费模型；重要工程规则必须确定性通过 |
| 明确启动真实实验 | 对应开发题及固定重复 | 使用已登记配置、隔离数据、总预算和原产品限制 |
| 候选验收 | 相邻功能回归、验证集及适用最终留出 | 按预登记规则执行，未运行范围保留 |
| 周期趋势 | 后续按需求确定 | 当前不创建定时任务、不宣称已有自动监测 |

现有入口继续使用，不在本组预造未实现的CLI：

| 命令/位置 | 当前职责 | 本组拟衔接 |
| --- | --- | --- |
| `pnpm eval:dataset` | 清单与冻结合同校验 | 版本索引；留出详情的访问需要按03治理 |
| `pnpm eval:score` | 已保存证据的离线评分/比较 | 扩展实验关联、统计和评审显示 |
| `pnpm eval:collaboration` | 服务层真实模型评估 | 固定配置下的业务基线和对照 |
| `pnpm test:collaboration` | 第14组离线/真实API开发窗口BDD | 保留原UI场景，适配同场评分记录 |
| `.github/workflows/tests.yml` | 离线工程检查与Electron BDD | 必要时增加离线合同检查，真实实验继续手动启动 |

现有`eval:score --strict`的0/1/2分别表示全部通过、失败、证据不足/待评审；默认生成报告不表示质量通过。运行命令成功退出、生成HTML或有Mastra数值分，都不能代替业务判定。

## 7. 接入验收

- 成功、失败、缺证据和待评审四种样本均能从报告追溯到同场原始记录。
- 重评分不会调用供应商或改变业务；不同评分版本可并列查看。
- 新报告不改写第6/14组历史分数和原件，功能进度继续由原专题维护。
- 离线CI没有真实凭据也能执行；真实实验的选择、上限和未执行项可审计。
- 首批通过本地HTML/JSON交付，不以建设产品内评估中心为前置。
