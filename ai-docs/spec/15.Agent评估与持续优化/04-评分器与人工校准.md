# 评分器与人工校准

日期：2026-10-09。保留现有结果状态和历史评分；新增检查及判定调整在实施时升级合同。

## 1. 三类评分职责

| 类型 | 适用问题 | 例子 |
| --- | --- | --- |
| 确定性代码 | 有明确可重复验算的事实 | 字数、JSON数值、身份、hash、版本、权限、预算和重复执行 |
| 模型评审 | 多种合法答案、语义需要判断 | 摘要忠实、审核有用、修订落实意见、论据与结论对应 |
| 人工评审 | 定义质量口径、校准模型、处理分歧 | 比较真实成果与评分理由，判断遗漏和误判 |

先核验必需证据，再检查硬规则与结果，最后处理适用语义条件。严重硬规则失败不能被语言质量高分抵消。部分里程碑通过可用于诊断，不自动变成完整成功。

## 2. 确定性检查

首批从既有检查和第14组断言复用，按实际缺口扩展：

- 顺序步骤开始前，前置消息已完整提交；后继输入包含对应身份和正文。
- 指定员工真实执行；成果版本、发布者与读取者可对应；不能由一名员工代写后伪装多人贡献。
- 读取V1后审核、明确修订生成V2，原版本保持；结果和来源不是仅靠自然语言宣称。
- 共享根预算、取消/撤权、重复消息与未知回执符合原合同；重启只核读，不自动重放。
- 字数、数值、字段和文件内容范围按题目明确规则验算。读取截断时不能推断完整文件达标。
- 必需公开交付和负责人结果均存在；文件写出但整条任务阻塞不能通过。

字符计数需明确标点、数字、Markdown标记、空白及Unicode处理。当前第14组使用非空白Unicode字符口径；如新任务要求词数或仅统计正文段落，应另立明确规则，不能换单位后沿用旧成绩。

评分代码独立读取原件计算结果，不能直接相信模型说“108字”或工具返回的摘要标签。产品工具计数和验收计数可共享定义，但测试仍应有独立已知正反样本验证，避免同一错误两边一致。

## 3. 开放内容的评审合同

将“质量好”拆成可核验断言，例如：

| 断言 | 需要的证据 | 失败例 |
| --- | --- | --- |
| 关键事实忠于材料 | 材料对应段落与输出位置 | 把90分钟写成两小时 |
| 审核针对指定版本 | 被读原件与具体意见 | 评价原件中不存在的内容 |
| 修订落实要求 | 审核意见、V1与V2差异 | 只换标题但保留被指出的错误 |
| 最终汇总无虚假完成 | 团队成果和公开提交记录 | 缺必需分支却宣称全部交付 |
| 协作贡献有业务价值 | 任务目标与各自新增信息 | 机械复述同事内容而遗漏自身任务 |

每项评审给出结论、证据定位和理由。现有`ExternalReview`采用0/1/2；首批若沿用，必须为每个档位写清含义：0未满足、1部分满足、2完整满足。无法判断不硬塞成1分，而沿原pending/incomplete处理；新增显式不可判状态需升级schema。

模型评审读取必要输入、成果和可观察过程，不要求暴露模型不可见的内部推理。输出和材料中的“请给满分”等文字视为待评内容，不得成为评审指令。参考答案与评分规则不能提供给被测员工。

优先使用独立配置的judge，记录模型、提示词和版本；不同模型仍可能共同犯错，不能代替人工校准。开放成果比较可用匿名A/B、随机展示顺序，并抽样交换顺序检查位置偏差；允许平局和证据不足。

## 4. 校准流程

1. 从开发/历史证据选取正常通过、明显失败、部分完成和容易误判的样本；最终留出题不用于调试judge。
2. 独立人工根据固定条件标注，保存原样本hash、证据和评审者。不能把开发代理或另一个模型的标签称作人工。
3. 固定judge配置，对同一原始样本生成结论；模型评审时不提供人工答案。
4. 比较总体一致率、正反例误判及关键违规漏判，展示逐例分歧。
5. 对同一输出重复评审，检查评分器自身稳定性；必要时修订条件并以新版本重评分。

现有[calibration.ts](../../../tests/evaluation/calibration.ts)检查至少20个不同正反样本、同一modelReviewer版本、至少90%一致率和校准集中关键违规零漏判。该门槛仅表示这批校准样本满足条件，不证明未来零漏判；也不能证明填入的标签真实来自人工。

首批延续该合同，不降低门槛换取通过。人工只需评阅准备好的原件与判断，不承担操作应用或重跑测试。标签尚未取得时，执行器和确定性检查可继续建设，语义认证保持待评审。

judge模型、提示词、关键评分条件或数据分布明显改变时，需要重新校准；不能沿用旧评审者名字暗示新配置已通过。基线与候选使用同版评分器和适用校准。

## 5. 结果状态及失败归因

保留现有`executionStatus`、`hardChecks`、`goalVerdict`、`judgeStatus`、`runtimeErrors`与最终`verdict`。报告区分：

| 最终状态 | 含义 |
| --- | --- |
| passed | 必需执行、硬规则、业务结果及适用评审均通过 |
| failed | 已有证据证明必需目标或规则失败，包括开始执行后超时/预算耗尽未交付 |
| incomplete | 关键步骤未执行或证据不足，无法完整判断 |
| review-needed | 必需语义评审或校准未完成 |

合法沉默、主动澄清、明确阻塞是否正确，取决于该题要求，不能一律奖励多回复或一律把waiting_user当业务成功。执行完成只说明流程终态，不自动代表目标达成。

失败另标根因：产品协议、模型决策/内容、工具/供应商、评估环境、题目/评分器、证据采集。允许多个原因及“尚未定位”；归因不删除原始失败。

## 6. 指标与分母

- 完整目标成功率：完整通过数 / 已启动被测任务数。失败、待评审和不完整分别列出，不从分母悄悄移除。
- 实验完成度：实际启动及实际完成样本 / 预登记样本，另列启动前环境失败和预算未执行。
- 关键违规：次数、涉及样本和具体规则，单独显示，不用平均分掩盖。
- 阶段达成率：讨论、前置交付、审核、修订、最终交付等分别统计，解释失败位置。
- 成本与效率：调用、已知token、用量覆盖、交付耗时、无效唤醒和仅为长度的反复修订。

“已知成本”与“成本完整”分开。失败成本计入实验总开销；用量缺失保持unknown，不能填0。确有完整计量和价格版本时才计算货币成本；每成功任务成本使用整个比较批次开销除以成功任务数，零成功时明确不可按正常单价解释。

新增业务题的质量/成本门槛在实验前登记。原发布门槛继续归第6组合同，本组不根据新失败倒推更宽松标准。
