# 员工主私聊与群聊领域设计

最新确认及实施授权日期：2026-10-14。用户确认同一员工共用身份与执行配置，BOAI 主聊天与所有渠道聊天分别保留上下文；主列表每员工一个入口，右上角进入该员工的渠道页面。§1–5/§9为现行合同，§6–8保留历史。领域词汇见CONTEXT，实际结果唯一归02 §7.16。

## 1. 会话与入口

| 入口 | 展示位置 | 上下文/发送目标 |
| --- | --- | --- |
| BOAI本人私聊员工 | 主会话列表，每名普通员工一个item | BOAI主私聊，普通消息只本地保存 |
| BOAI多员工群 | 主会话列表，各BOAI群独立 | 原多员工协作与Work规则 |
| 本人或其他授权用户私聊机器人 | 员工渠道页面的私聊列表 | 各平台私聊分别保留历史，平台触发回复回原私聊 |
| 外部群提及员工机器人 | 员工渠道页面的群列表 | 员工×平台×租户×群隔离，平台触发回复回原群/回复链 |

渠道页面复用现有左侧会话列表、右侧聊天/任务/文件与详情面板，提供返回员工BOAI主聊天入口。主列表不展示渠道房间，员工的渠道新回复通过真实完成/可见阅读事实提示；处理中/待授权/失败沿原真实活动显示，不把未读或错误正文伪造进主聊天预览。点击渠道提示进入该员工页面和对应会话。核心助手历史与自动化专用聊天保持现行边界，不改为普通员工主私聊。

## 2. 身份与权限

渠道绑定属于员工，一个机器人可服务私聊及多个外部群。首版新增每员工一个绑定，旧多绑定可停止、编辑或解除。本人用户ID仅用于显示本人归属，仍须在授权名单中；不再触发历史归一、主私聊路由或迁移，也不取得桌面审批/管理/预算权限。其他授权用户与各群继续按真实平台身份核对。

员工的模型、技能、运行方式和执行配置共用；每个会话的聊天上下文、Work来源、原生session与回复目标独立。BOAI群成员管理不改变渠道参与者，不拉取/冒充全群成员，不自动创建外部人员联系人。

## 3. 同步与回发

这里的同步表示机器人实际收到的消息及其回复在BOAI渠道页面显示，不表示完整平台聊天同步。每次回发严格使用触发消息及原Work的bindingId、平台会话和回复链；本地普通消息不借最近目标发送。

BOAI主聊天保持只本地保存。渠道页面可保留现有对员工的本地输入，明确标注本地交流，其消息及普通回复同样不自动投递平台。主动以机器人身份发布到平台仍为单独能力，不在此次会话分离中隐式新增，不能冒充平台人类用户。

群名仅显示元数据，沿已有异步缓存/失败回退，不参与房间或幂等身份。渠道列表可按私聊/群筛选；外部群只读来源和接入员工，不提供BOAI群添加成员、改远端群名或解散功能。删除本地会话沿清空/隐藏语义，成功受理的新平台消息恢复原渠道条目及所属员工入口；重复、未授权或失败受理不恢复。

## 4. 切换与历史

此次生效后的所有平台新消息进入独立渠道会话，包括已明确关联本人的私聊。旧未归一渠道房间尽量原位续用；已经归一的BOAI主房间和归档别名原样保留，既有消息/run/Work/材料/成果/文件hash、原生session和发送回执不拆分、不改写、不重放。若旧渠道键指向主房间或归档别名，新消息建立新的渠道房间，后续继续沿用该新房间。

保存本人ID不再迁移记录，因此不要求无关BOAI主聊天停止执行。原有忙时换绑、实际退出、清理未知/幂等回执门禁仍按各自合同。旧多员工渠道房间只读历史，新事件仍进各员工独立渠道；原忙中工作允许按旧来源收尾，不重新派发。

## 5. 验收

通过既有AppService/真实SDK协议、原生stdio与隔离pnpm dev Electron BDD验证：两种创建顺序、本人/其他用户/群隔离、旧已归一房间/归档键新路由和旧重复回执、原生session分别续用、原文件预览/备份/清理、入口/返回/筛选/真实阅读提示、搜索/任务定位自动进入正确渠道页面与草稿保留、隐藏恢复及停止授权。默认并行完整回归与性能门槛保持；渠道页面循环、监听器/GC/RSS/空闲CPU保留短期观察和长期未认证范围。实际结果唯一归02 §7.16。

## 6. 外部群边界简化建议（2026-10-14，历史候选，已由§8替代）

用户指出：飞书群消息进入BOAI后，外部人员是否展示、能否在本地追加机器人，会把外部群与BOAI群混成两套成员管理。此次先梳理产品边界。本节为建议，不覆盖上方现行合同或宣称运行代码已收窄。

建议保留一种通用会话，用来源区分三个入口，不新增平台成员同步、群桥接或另一套聊天执行器：

| 入口 | 谁决定参与者 | BOAI中的操作 |
| --- | --- | --- |
| 员工主私聊 | 本人与一名员工 | BOAI与明确关联本人平台私聊共用历史，沿当前来源回复合同 |
| BOAI群 | BOAI | 选择数字员工、讨论及协作，管理本地群 |
| 外部群会话 | 飞书/Telegram等所属平台 | 查看机器人实际收到的消息、回复、任务与文件，管理已接入员工的执行与渠道 |

外部群会话表示同一个真实外部群在BOAI中的本地视图。保存本地消息与工作记录是必要的，但不能把该视图变成有自己独立成员名单的BOAI群。群名/群ID、聊天上下文和回复目标继续沿原外部群身份；未送达机器人的其他平台群消息和完整群成员列表，不冒充已同步。

外部人员只按实际发言来源出现在消息中：姓名/可用头像/稳定平台身份，本人关联保留当前展示归属与原权限。无需自动建立BOAI联系人、数字员工或拉取全群成员。标题右侧员工头像应标明「接入员工」，不能标作全部群成员。

外部群会话不提供本地「添加员工」来改变群参与者。另一员工通过其绑定的平台机器人加入实际外部群、配置原授权后，才可成为该会话的接入员工；平台提及仍决定本轮接收范围。同群多个已接入机器人共用一个会话条目。BOAI内部群仍可直接添加员工。API或本机Agent只决定员工的执行方式，不再增加一种群。

界面建议：外部群保留标题、聊天/任务/文件、接入员工与执行入口；群成员、改群名/解散等管理归外部平台，不复用可编辑的BOAI群表单。删除本地条目仍沿列表隐藏/新消息恢复合同，不能解释为解散远端群。

首版建议把外部群窗口作为查看群交流与办理员工执行的入口，群聊天在所属平台发起；BOAI内部讨论在员工主私聊或BOAI群进行。这样不在外部群里产生一条只有本地可见的第二条聊天流。此建议会收窄当前BOAI外部群内本地发言能力，待用户决定；以后如需要从BOAI发到真实外部群，应明确采用机器人发言身份和平台发送入口，作为单独能力设计，不借本地人员身份或最近目标隐式发送。

代码差异：当前 `Conversation.kind=group` 的统一标题/成员配置入口及 `saveConversation` 仍允许编辑外部群的本地员工集合；普通本地发言仅保存在BOAI。这是需要收窄的实际行为，不能把本节建议当作已完成修复。此次不迁移历史、不变更原会话ID/员工执行配置，也未运行新的模型或平台测试。实际进度见02 §7.12。

## 7. 员工身份与渠道会话的候选方向（2026-10-14，历史讨论，结论见§8）

用户在查看mock后重新明确：平台机器人就是绑定数字员工的外部收发身份，渠道消息交给该员工执行；BOAI群只表达多个数字员工的协作。随后提出本人机器人私聊与员工主私聊镜像、外部群提及单列渠道会话，并要求参考GitHub OpenClaw。本节记录最新讨论，不把§6或原型升格为已认可设计，也不替代现行生产合同。

| 入口 | 交流空间 | 员工身份 |
| --- | --- | --- |
| BOAI本人私聊 / 明确关联本人的机器人私聊 | 同一个员工主私聊，共享历史 | 同一数字员工 |
| 飞书群A或群B提及该员工机器人 | 各自独立的该员工渠道会话，单列在「渠道会话」 | 仍是该数字员工，不建新的员工或BOAI协作群 |
| 其他获准用户私聊机器人 | 独立渠道私聊，不能混入本人主私聊 | 同一数字员工，外部发送者单独核对 |
| BOAI多员工群 | 当前BOAI协作群，按原群成员与工作规则执行 | 原有多个独立数字员工 |

机器人绑定回答「交给哪个员工」，会话来源回答「使用哪段交流上下文、回到哪里」。员工加入BOAI群，不自动把所有渠道消息广播到这些群。一个机器人同时服务私聊和多个外部群，仍只有一份机器人配置。

首版可以把员工配置入口限制为0或1个机器人绑定，但这是BOAI的可选产品简化规则，不是OpenClaw限制，也不是会话隔离的必要条件；当前BOAI代码仍允许同员工多绑定。若选择此方向，渠道会话按员工及外部来源区分，只允许该员工处理，不能复用BOAI群成员编辑器来额外拉其他员工；同一个外部群联系两名员工可形成各自的渠道会话，不视为自动创建一个多员工BOAI群。该点与§6同外部群多个接入员工共用条目的建议不同，须以最终讨论结论收口。

「私聊镜像」需独立明确交付范围。共用主私聊历史已经是现行能力；BOAI主动发起的消息当前不会自动发到平台。若镜像包含BOAI消息及员工回复也向本人机器人私聊投递，必须作为新的明确发送规则设计：只投递到该绑定明确关联本人的私聊，保留独立发送回执/未知不盲目重发，不借最近一次群目标回退。机器人发言和本人人类账号发言身份不能混为一谈。

OpenClaw固定第一方研究见[04](./04-OpenClaw渠道与会话路由参考.md)。采用其Agent、绑定、会话来源分离与默认群隔离的思路，不直接迁入全部多Agent路由、主会话跨会话观察或多用户默认DM合并。此轮仅研究/候选设计，不修改运行代码、真实数据或原型。

## 8. 较早用户确认后的合同（2026-10-14，已由§9替代）

用户明确「跟OpenClaw一致，不要把BOAI消息再发到飞书，可以开始修改」。采用§7的独立渠道会话方向，放弃§6的同外部群多员工共用条目和强制只读聊天建议。

1. 本人关联平台私聊与员工主私聊共用历史。其他获准用户的私聊及每名员工的外部群交流，单列于「渠道会话」；BOAI普通会话和多员工群保持原入口。渠道会话显示群名、平台与接入员工，不拉取全群成员，不自动建立外部联系人。
2. 渠道信息仅展示来源及绑定员工，不允许通过BOAI群编辑器添加员工、修改远端群名或解散远端群。员工配置、任务、文件和执行入口保留。BOAI本地输入可用于该员工的本地交流，但不投递平台；平台触发的回复只回原来源，不采用最近目标回退。
3. 新员工渠道配置采用0或1个机器人绑定；同一个机器人可服务私聊和多个外部群。已有多绑定配置保留并允许停止、编辑和解除，不自动删除凭据或历史。该限制是BOAI的界面简化，并非OpenClaw限制。
4. 旧单员工外部群尽量原位沿用房间ID、历史及原生session；旧多员工外部群保留历史，不自动拆分消息/成果或改写归属，新事件进入员工各自的渠道会话。旧多员工房间只读，不继续受理本地协作。重复或未知旧回执不能变为新请求。
5. 新消息恢复隐藏条目、明确本人权限、Work/原生生命周期、凭据隔离及未知不重放沿原合同。验证使用既有公开AppService/平台协议、原生stdio和隔离Electron BDD入口；执行默认并行回归和性能门槛，短期内存观察不等于长期无泄漏认证。


## 9. BOAI与渠道分离（2026-10-14，用户已确认并授权修改）

用户最新选择「BOAI的是BOAI的，渠道的是渠道的」，同员工一个主列表入口，右上角进入员工渠道页面，私聊/群分别列出。此合同替代§8的本人平台私聊归一及主列表渠道分组。同步仅指平台交流在渠道页面的本地呈现；不恢复BOAI主聊天自动发送平台，不隐式新增主动机器人发送能力。代码实施和实际成绩归02 §7.16。
