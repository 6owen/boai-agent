# 重构与能力扩展总计划

2026-09-30 阅读说明：当前优先执行 [第 9 组团队创建助手](./9.团队创建助手/README.md)的 T1，随后分期推进连续记忆和游戏场景。[第 8 组](./8.Agent-IM产品完善/README.md)保留基础完善清单，不作为 T1 的全部前置。本计划保留既有技术阶段、依赖与历史状态；实际交付核对源码和第 2 组最新记录，不按早期“尚待实施”重复开发。

日期：2026-09-27。状态：**首批 B1、B2、S1、F1 已实施**。运行基线 v0.2.2，未改发布版本号；[本次实现与验证记录](./2.已实现功能与代码现状/15-B1-B2-S1-F1首批重构实现.md)。S2、B3、执行后端、自动化和主题阶段仍待实施。

## 目标与分工

1. 第 1 组保存产品与架构依据，第 2 组说明已经实现的行为。
2. 第 3 组重构前端，按既有两份方案开发外观与主题。
3. 第 4 组拆分员工配置、Agent 工厂、工作区和员工组协作模块，并扩展 BYOK、ACP、本地 SDK Agent 等执行后端。
4. 第 5 组优先完善 Sandbox / 文件系统 / Skills，接入浏览器、连接和 Mastra 自动化；Memory、Working Memory 与动态 Workflow 保留为独立阶段。
5. 第 6 组[结合 Cumora/Paperclip 改进自主协作](./6.Cumora协作重构/README.md)，分 G0–G4 建立行为基线、优化参与判断，先建立工作与 run 认领/预算，再开放有限并行，随后增加父子委派、依赖和按需持久恢复；当前仅文档规划。

`renderer` 是前端。`runtime` 是本地后端和 Mastra 适配层。保持 Electron 本地进程架构，不因使用 Mastra 而新增必须运行的 HTTP 服务。

## 阶段顺序

## 依赖和所有权

- 前端拥有 renderer 目录；外观宿主服务放 main/appearance，外观 DTO 放 shared 的纯模块。模型运行不负责外观。
- 后端保持 worker 组合入口和 AppService 兼容 facade；工厂只装配 SDK 实例，员工用例负责注册与配置。
- 分开三类配置：模型连接（BYOK / 本地模型 API）、员工执行后端（Mastra / ACP / SDK / A2A）和能力连接（如 MCP）。本地模型不等于本地 Agent，连接协议不等于员工身份。
- Workspace 是工作环境组合，Filesystem 管文件，Sandbox 管执行，Skills 提供可发现的工作指引。原有员工持久主目录继续存在；单次 Sandbox / Browser / 外部 Agent session 都是运行资源。
- 外部 Agent 通常拥有自己的工具和权限循环；不能默认继承 BoAI 的 Workspace、记忆、Skills 或审批。必须通过能力契约显式适配，无法适配时准确限制可用阶段。
- 产品数据库继续拥有用户可见会话、消息和运行。引入 Mastra Memory 前必须选定每类记忆的唯一写入者，避免产品库与框架库各自维护不同答案。
- 共享契约改动先写清输入、输出、事件、版本与兼容范围；并行开发者不得各自修改同一字段语义。前端调用从一个 transport adapter 进入。
- 群协调属于 collaboration 模块；Workflow 作为被明确委托的任务执行方式接入，不能自动取代群成员自主发言机制。
- 自动化模块拥有任务定义、目标、执行授权和结果投递，Mastra schedules 提供持久调度。触发必须经过产品运行入口，不能绕过群发言许可、文件审批与配置版本检查。
- 每个阶段先合入最小可运行闭环，过渡 re-export 注明删除阶段；有实际职责才创建文件，不预建空仓储、插件或容器框架。

## 结构重构与新行为分开

B1–B3 首先保持 v0.2.2 的 IPC、存储格式、数据路径、调度语义与授权边界。S/E/C/BR/A 与 M/W 是单独的新行为阶段；执行后端字段、连接配置、自动化记录、框架存储等均需显式版本迁移，不能夹进纯目录调整。

G 阶段同样属于独立行为演进：工作与运行分离、执行认领、并发发布、定向唤醒、根任务预算和终止条件逐项验证；涉及新持久记录时单独设计兼容迁移。Cumora/Paperclip 的实现和参数仅作参考，不直接成为当前运行规则，也不引入强制管理层级或新的 agent 框架。

当前工作区隔离为应用级隔离，已批准的 shell 命令仍有宿主权限。不能在重构后仅凭文件换了目录就把它描述成强沙箱。

安装版 LocalSandbox 默认 `isolation: 'none'`；macOS 内置 seatbelt 策略也允许全盘读取。S2 必须区分可信本地运行与经过验证的强隔离环境，不能仅设置一个选项就宣称跨员工文件保密。首版不强制用户安装 Docker；容器/VM 或自定义原生策略在需要强隔离时另行验证。

“Dynamic Workflow”需区分框架的动态图注册能力、固定工作流的运行时分支，以及模型自主规划。第 5 组会记录安装版 API 能力与 Beta 限制，不能把一个自然语言计划直接当可执行任意代码。

## 验收与回退

每个阶段记录改动范围、仍兼容的合同、数据有无变化、测试证据和已知限制。按改动运行类型检查、相关测试、生产构建以及关键 Electron 流程；涉及宿主/打包/资源协议时必须验证真实应用包。

v0.2.2 的 **102 项测试、3 项打包桌面流程**是此前已通过的基线，不是未来重构的通过证明。规划轮次仅整理文档；首批源码重构已重新验证，证据以本次实现记录为准。

涉及数据写法变化的能力阶段，先在隔离数据副本上验证迁移、失败回退与撤权；保留已有员工、会话、运行、工作区和记忆来源。中断后不自动重放命令或已提交的外部操作。自动化恢复按 occurrence/run 的持久状态对账，不依靠重新调用模型猜测任务是否已完成。
