# 员工目录授权与执行权限设计

日期：2026-10-18。状态：**已按用户最新说明修订，仅文档，等待后续goal；产品未实施。**

目标：给员工预先授权常用业务目录，例如`/Projects/coding`，使其日常可以在这里读取、编辑和生成文件。员工需要访问其他位置时可申请授权；员工设置为完全权限时，其他目录的访问自动授权。群聊中仍由各员工执行，本机Agent也使用所属员工的授权规则。

本篇替代此前“指定目录是不可越过的硬边界”“完全访问也不能访问目录外”“首版仅一个不可扩展根”的草案。目录授权不要求所有工具、进程和应用状态都在这个目录运行，也不建立一套独立于员工权限的永久禁入模式。实施及唯一进度见[06](./06-工作范围实施计划与验收.md)。

## 1. 四个概念与实际行为

| 概念 | 决定什么 | 示例 |
| --- | --- | --- |
| 员工目录授权 | 员工已获准访问哪些业务目录，以及只读/读写范围 | coding目录及子目录已经读写授权 |
| 本次工作位置 | 当前文件目标、命令cwd或原生任务项目位置 | 在coding子项目执行构建，或授权后读取Documents中的文件 |
| 执行权限 | 是否可修改，以及新目录或其他操作是否需要本人批准 | 请求审批、只读、完全访问 |
| BOAI受管工作区 | 员工系统文件、会话临时内容、状态、材料和交付副本 | 原WorkspaceService及员工×会话空间 |

预先授权目录通常是员工处理文件的主要位置，但不是所有执行的唯一cwd。用户明确的文件/项目路径优先用于确定目标，再核对授权；未指定目标时可使用唯一预授权业务目录作为默认文件位置。存在多个目录且目标不明时依据当前任务项目定位，仍不明确就澄清，不把文件写入随机目录。普通问答、浏览器、远端MCP和内部状态继续使用原运行位置。

### 1.1 权限组合

| 员工执行权限 | 已授权业务目录 | 未授权目录或超出已有读写许可 |
| --- | --- | --- |
| 只读 | 可读取获准内容，不能编辑/删除 | 可申请读取；写入要求先明确修改员工执行权限，目录批准不能越过只读上限 |
| 请求审批 | 在已授予的读/写范围内直接进行相应文件操作，不反复询问目录权限 | 在实际访问前请求本人批准，获准后执行；拒绝/取消则不访问 |
| 完全访问 | 直接读写 | 自动授权读取、编辑和生成等文件操作，不弹目录权限申请；仍受OS实际权限约束 |

完整例子：给员工A授予coding目录读写权限，并选择请求审批。A可直接在coding内写代码；读取`/Documents/specs`时申请该目录只读权限，编辑该目录内容时需取得读写权限。若直接批准该目录读写，此后授权有效期内的读写均可执行。将A改为完全访问后，上述额外目录访问自动获准。原生工具、Mastra工具和群内执行遵守同一规则。

目录批准只处理文件访问；命令执行、网页提交、远端写入等仍按各自原有操作权限办理。同一动作同时需要命令和目录批准时，沿同一待决操作展示范围，避免相同授权连续询问。完全访问沿原规则自动处理这些员工侧审批，不获得管理员提权或第三方账号的新权限。

### 1.2 员工、群聊与执行引擎

目录授权归员工。私聊、群聊、渠道、定时任务、分工和文件修订在调用时读取**当前执行员工**的授权与执行权限。群是消息/协作上下文，不建立一个覆盖成员授权的群目录或群沙盒。

- A授权coding，B授权reports：同群分工时A处理coding，B处理reports。A需要访问reports时按A自己的权限申请；B或负责人已获准不代表A也获准。
- 同一员工加入不同群，沿用自己的持久目录授权；聊天、原生session和私有执行记录仍按既有员工×会话身份保存。
- API员工沿现有Mastra Workspace、filesystem与执行适配；本机员工沿自己的Codex/Claude或插件运行环境。二者只是实现路径不同，不要求本机Agent再运行于Mastra循环，也不因本机模式另建一套用户目录配置。
- 群内交付仍通过原成果发布和获准材料共享。文件目录访问与“将文件公开给群成员”是两件事；`shared:/`等产品投影不成为所有员工自由操作的宿主目录。

## 2. 配置与授权交互

### 2.1 员工配置

在现有“独立工作区”Card展示**授权目录**列表，每项包含真实路径、只读/读写许可和移除操作；新增目录使用系统目录选择器。允许保存多个目录，以承载初始授权及后续明确长期允许的目录。执行权限继续使用原入口；完全访问时说明“其他目录自动授权”，已保存目录可保留为常用业务位置。

沿原员工草稿和保存按钮，选择目录不自动保存，不扫描目录内容、不启动模型或脚本。工作区页面另外展示原员工系统目录/会话空间；不把BOAI数据目录移动到coding，也不显示旧的“默认工作区／指定目录／全局”互斥范围选择器。

新员工保持现有默认执行权限；没有外部目录授权时继续使用当前获准受管工作文件。bobo的广泛文件能力来自其实际执行权限，不按显示姓名额外扩权，也不自动把旧bobo或普通员工改成完全访问。

### 2.2 执行中申请新目录

复用原审批卡片、待决输入、配置版本与请求回执机制，增加明确的目录访问申请，展示员工、真实目标目录、只读/读写许可、触发操作及原因。模型可以提出需要，授权决定由本人或已保存的完全访问策略作出。

| 选择 | 效果 |
| --- | --- |
| 允许本次运行 | 仅当前员工、当前运行在所示目录和读写范围内可用；终态/取消/重启后失效，不传给群成员或其他运行 |
| 始终允许此目录 | 保存为该员工持久授权，后续私聊/群聊等均可使用；员工配置可查看与移除 |
| 拒绝或取消 | 不执行被阻止的访问；沿原待决回执返回，可继续不依赖该文件的工作 |

只读申请默认请求只读，编辑/生成请求读写；批准前清楚展示实际范围。读取单个文件不自动申请整个home；选择最小明确目标目录，用户可在批准前收窄范围。不把一次批准默认为永久授权。

完全访问由宿主在同一门禁自动返回授权结果并记录实际策略来源，无需打开审批UI；不为每次自动授权写入一条永久目录配置。OS拒绝、路径不存在等仍是实际错误，不伪报已获系统访问。

群/渠道触发的申请仍由原可信本人审批入口处理，外部渠道请求者、其他员工或网页文本不能代本人批准。审批成功只接续原等待操作，不重新执行此前已完成或回执未知的命令。

### 2.3 保存、变更与生效

- 配置保存沿原CAS、草稿守卫、忙时关闭锁和未知回执核对；目录、读写许可及回执由宿主核验，迟到结果不能串员工。
- 当前运行等待目录审批时，允许该批准补充本运行的授权快照。持久批准同时版本化保存；它不能被普通“活动中配置不可变”误拦，也不能顺带改模型、引擎或其他配置。未被批准的并发运行不自动接续旧待决动作。
- 移除/缩小授权或退出完全访问时，先阻止受影响的新操作，沿原停止/真实退出和版本门禁处理旧运行。持有旧授权的原生session不继续使用；新消息按新规则运行。
- 授权失联先核对同一请求身份；重启不自动批准、重放业务或恢复运行级临时授权。持久授权按已提交事实恢复。

### 3.2 一份授权，按后端执行

宿主生成当前员工的有效授权：原受管材料许可＋持久业务目录授权＋本运行临时授权＋执行权限。API侧交给已有Mastra Workspace及文件/命令工具；本机侧交给其原生cwd、目录配置和批准接口。插件沿现有公共能力接口承接，不能读取群负责人的权限代替调用员工。

请求审批模式必须确保未授权访问先等待批准；只是设置cwd或提示词不足以完成这条行为。Mastra命令/脚本和原生工具均需验证“先拦住、批准后继续”。完全访问则使用允许宿主业务目录访问的原生/执行策略，不能还被coding白名单锁死，再要求用户重复批准。

保留原生自主循环、已选模型/连接、连续会话和工具能力；不为统一权限而把本机执行改造成Mastra文件工具代理。若某个后端不能正确接目录批准，应记录实际缺口并补适配，不把它解释为“群聊或本机与员工授权矛盾”。

## 4. 文件与资源边界

- 目录及读写许可按真实路径核验，不能只做字符串前缀判断。相对路径、链接或目录替换指向未授权位置时，在请求审批模式触发对应实际目标的申请；完全访问按自动授权处理。删除链接不跟随它误删目标。
- 写前hash/版本冲突、同目录多员工/多运行占用与原取消生命周期保持。目录许可不等于允许静默覆盖已被修改的文件；授权父目录删除/搬迁须在具体操作中明确，不从普通子文件授权推导。
- [知识资料](./07-员工知识资料设计与实施计划.md)、附件、技能说明等沿获准只读输入提供；读一份材料不自动授予其原文件夹。需要直接编辑原目录中的文件时，按上述目录申请或完全访问策略处理。
- [Web Search](../19.应用插件架构/09-WebSearch工具接入设计与实施计划.md)的远程MCP和现有BOAI浏览器无需把进程放到授权目录。local源、本地MCP、插件文件操作及浏览器上传/下载，在实际本机文件访问时核对当前员工授权；需要新目录时正常申请，完全访问自动授权。
- 远端账号、渠道消息与产品资料仍按原来源授权。目录访问不会自动获得所有员工聊天/知识的产品API权限；完全访问的宿主权限也不能宣传为员工间OS级文件隔离。
- 用户业务目录和BOAI系统存储保持各自归属。删除员工、清空聊天、清理记录、移除授权不会删除或回滚业务目录；受管副本只按原所有权/hash清理。

## 5. 领域、旧配置与恢复

沿员工定义与原审批仓库增加目录授权数据，概念上包含目录、读写许可和授权来源；本次运行授权绑定原run/request，永久授权绑定员工。最终字段在WS0/WS1依据已有合同确定，不另建员工、消息或权限数据库。

旧员工缺少新字段时保留既有行为并明确兼容状态，不能将缺字段解释成“用户拒绝了全部目录”，也不能升级时自动授予完全访问。编辑姓名等无关字段不触发权限迁移；用户设置目录后进入新规则。原“完全访问”按用户本轮明确含义保持目录外自动授权。

备份保存持久目录配置和原受管文件，不递归打包用户业务目录；不保存待批准请求为已授权，也不恢复本运行临时批准。恢复后只核对路径及已提交事实，不修改外部原件或自动执行任务。旧批准/过期快照不能恢复已撤销权限。

## 6. 范围与交接

当前macOS首轮目标为API/Mastra、Codex、Claude的目录内访问、目录外申请/批准/拒绝，以及完全访问自动授权。Pi/OpenCode等沿公共插件准入记录实际能力，完整插件认证和其他平台单列。工程重点是现有员工运行链上的目录授权与批准接续，不扩大成新沙箱平台、群文件系统或网络策略工程。

知识资料与Web Search可独立实现；本功能完成时在WS-A10联合验证它们的本机文件入口。当前只有文档修订，未创建goal、运行模型、改产品或修改个人员工配置；实际进度唯一归[06第5节](./06-工作范围实施计划与验收.md#5-唯一进度与实际记录)。
