# 群组协作与运行生命周期

日期：2026-09-27  
任务：B3  
状态：**待实施结构重构；保留 v0.2.2 调度算法和公开行为。**

依据：[自然群聊基线](../1.产品与架构基线/09-独立员工与自然群聊.md)、[v0.2.2 历史轮次修复](../2.已实现功能与代码现状/14-v0.2.2历史群聊与本轮边界.md)。每位员工使用自己的模型、身份、规则和获准记忆，自主选择参与动作；宿主做有界调度与协议校验，不用中央 LLM 决定谁值得发言。

## 1. 当前分工与建议归属

| 当前位置 | 已有职责 | 建议归属 |
| --- | --- | --- |

| GroupScheduler | turn/event/delivery/decision/contribution/grant、参与队列、发言权、依赖与预算 | collaboration |

| executeDecision / executeResponse / updateMemories | 创建阶段 run、引擎调用、增量写入、终态、维护与异常 | runs |
| requestApproval / cancelWhere 等 | 持久审批、Promise 响应、取消信号和迟到事件阻断 | runs，保持 facade 可及时调用 |

## 2. 保持的数据语义

| 记录 | 意义 | 重构约束 |
| --- | --- | --- |
| Conversation / Message | 持久会话和用户可见聊天 | 消息权威仍在产品层，不交给框架自动回放 |
| DiscussionTurn | 一条原始用户请求触发的一轮讨论 | 权威 turnId 独立于原始消息，重试旧请求也创建新轮 |
| ConversationEvent / AgentDelivery | 公开事件及面向各成员的投递/观察版本 | 同一事件不得重复投递；保留首轮独立机会 |
| DecisionRecord | 员工对获准输入作出的私有参与决定 | 不是公开回复，也不能直接展示为已完成任务 |
| Contribution | 员工本轮 main 工作项、依赖、结果消息与产物 | 不借重构扩成任意工作流/DAG 产品 |
| Grant | 某个有效决定获得的短期发言权 | 取消/上下文失效后不可发布 |
| AgentRun | decision/execution/memory 等具体阶段 | 一轮可有多个阶段，多次私有判断不算多条公开发言 |
| RunSnapshot / BootstrapSnapshot | 该次阶段的配置与授权依据 | 版本可追溯，不从最新员工定义反推旧运行 |

这些记录已持久化，但当前不是通用事件溯源系统，也没有跨设备消息总线。B3 不新增重放调度器或 durable workflow；重启保持“未完成即中断，不自动重放”的约定。

## 3. 保持的执行链

```text
sendMessage → 校验/去重 → 原子保存用户消息、request 与初始 turn/event/deliveries
  → collaboration 排队
  → 每成员独立 decision（最多 3 个并行）
  → 宿主校验决定、观察序号、成员和依赖
  → 首个合法且可执行的候选获得唯一公开发言权
  → runs 装配 chat/task 上下文并执行
  → 最终消息和协作结果原子发布
  → 新公开事件触发有界接续判断
  → 本轮结算 → 获准的记忆增量维护
```

同一会话的用户轮次排队，不同会话可并发。单聊也先由该员工决定 chat/task，不因只有一人就绕过运行、权限、取消或记忆边界。

### 成员自决与接续

- 动作继续为 reply/pass/wait/ask/request_handoff；responseKind 为 chat/task。宿主验证格式和引用，不把普通文本自动猜成 reply。
- 全员 pass 是合法结果，不虚构公开回复。模型故障必须记录失败，不能伪装成自主 pass。
- 一位员工先回复不会替换尚未判断成员的原始用户投递。过时候选在获得发言权前重判，但不反复预取必将过时的决定。
- 首轮 pending 优先，首个合法候选不等最慢成员。已判断成员的重判不挤掉其他成员首次机会。
- @ 使用明确有效收件人；非收件人可以保留自主判断但不抢答。handoff 接收者仍可 pass 或 ask，不被中央编排强制执行。
- 工作项依赖保留当前 main 键和环检测；上游失败/拒绝时给依赖方一次重新判断机会，不无限等待。
- “自动接续代数”与“已有多少成员首次回复”分开。6/12 人都可在预算内首次贡献，不能误变成全群最多 3 条消息。

### 用户插话

新用户消息先持久化，当前公开发言按既有边界结束后优先处理新轮，不继续无关自动接话。显式 stopPrevious / 停止继续中止当前与排队轮次。慢记忆维护让位新用户消息，不能阻塞新轮。

这套语义不是中央 plan 选成员。旧 `AgentEngine.plan?` 只作为迁移遗留类型识别；确认所有引用后可移除内部死接口，但不要改旧持久记录或重新暴露 coordinator 模式。

## 4. context 与 runs 的边界

context 装配按阶段执行，顺序保持：检查成员/启用状态 → reconcile 系统文件版本 → 取得显式连接与凭据 → 筛选获准资源、历史和记忆 → 准备 session/run 路径 → 固化快照 → 调用 adapter。

必须保留以下约束：

1. 当前 turnId 由宿主传入，不从旧 triggerMessage.turnId 猜测重试轮次。
2. 当前轮与旧轮背景明确分离。旧问候、自我介绍和失败不能成为“本轮已回复”的证据。
3. hasRespondedInTurn 依据本轮该员工真正完成的公开消息；私有 decision、工具活动、记忆整理和旧轮回复都不算。
4. 排除未来排队的用户消息、未完成消息、失效快照、已移除成员和撤权资料派生的上下文。
5. 记忆组合仍是员工 profile＋当前会话记忆；来源和 epoch 保持准确，其他会话学习事实不隐式混入。
6. 运行中配置变更、授权撤销或停止使旧上下文失效；模型忽略 abort 时，宿主仍阻止迟到公开消息、工具更新和产物登记。

runs 负责阶段状态和副作用，不决定群内谁更适合发言。collaboration 负责发言资格和调度，不直接取得 API Key、打开文件或创建 Mastra Agent。

## 5. 原子发布和失败语义

提取模块时要保留现有 publish 回调形成的写入边界：最终 message/run、event、grant、delivery、turn、contribution 的消息/产物关联，以及本次已登记 artifacts，应在同一个 ProductStore 写事务中提交。不能改成“先发成功事件，再分别更新几个模块”。

流式正文仍增量持久化并归属具体 run；取消后保留已收到内容并标记终态。task 的步骤说明保留在活动里，只把最终 SDK 步骤的正文作为公开答复；私有判断 JSON、推理和记忆候选不得流入聊天消息。

失败恢复继续使用宿主权威判定：

- 同员工后来的有效决定可以恢复更早的 decision 失败，早于失败的成功不能覆盖它。
- execution 失败需要后来的完成公开回复来恢复，单次 pass 不能把实际任务失败抹掉。
- 历史失败记录保留；未恢复失败投递集合供 UI 展示，前端不复制另一套聚合算法。
- 记忆维护失败不把已经成功的公开回复伪装成失败；memory run 禁止使用普通 retryRun，避免重新执行原用户任务。
- 普通 retryRun 保持 requestId 幂等，沿用原始用户请求但生成新讨论轮；不新增一条假用户消息，也不重跑全群旧请求。

## 6. 预算、取消与恢复

以下为 v0.2.2 当前参数和含义，B3 只集中命名与查询位置，不悄悄调参：

| 项目 | 当前限制 |
| --- | --- |
| 群成员 | 最多 12 人 |
| 并行参与判断 | 每会话最多 3 个；单公开发言者 |
| 判断调用 | `max(12, 4 × 成员数)`，含额外判断协议修复 |
| 总 modelCalls | `max(24, 8 × 成员数)`，包括各 decision、公开执行、memory 阶段及宿主批准的额外修复 |
| 输出用量 | 累计已报告 outputTokens 达到 16,000 时停止后续工作；缺失字段保持未知 |
| 自动接续 | 代数上限 3；每员工本轮主动公开发言上限 2；首次贡献不按全群消息数增代 |
| 轮次时间 | 5 分钟 |
| 阶段限制 | 判断宿主等待 15 秒；记忆维护 30 秒；chat 1 个 SDK step，task 最多 12 个 |

`modelCalls` 目前是产品阶段及显式修复计数，**不是精确 HTTP 请求总数**：task 内多步模型/工具循环另受 SDK maxSteps、输出用量、时间约束。B3 不借统一工厂把这一统计悄悄换成另一种口径；将来若要按每个实际 SDK 请求计费，需要单独设计和回归。

首调用由宿主预留；额外协议修复必须先请求追加预算，前后检查 abort。usage 回调为当前阶段累计值，宿主按新旧差额加入轮次，不能重复累计两次修复的完整总量。未知 token 不记为“实际使用 0”。

取消层次保持为会话/轮次控制器与单 run 控制器的组合。审批记录持久化，等待 Promise 在批准、拒绝、停止与退出时都能结束；慢连接测试不能持有业务串行入口，阻塞批准或取消。

重启把未结束 run/message/turn/delivery/grant/工作项恢复为中断或失效，清除过期审批，不自动重发模型或执行命令。旧 v0.1 jobs 仍只标中断，不进入新调度。队列、内存 Promise 和 SDK 实例不作为可恢复执行凭据。

## 7. B3 渐进拆分步骤

1. 先搬移 collaboration，实现保持不变，旧 `group-scheduler.ts` 过渡重导出；继续使用现有 hooks。
2. 提取 runs 的阶段执行与审批/取消；facade 保留对用例变更的串行控制，不另造一个全局队列包住耗时模型请求。
3. 提取上下文装配，与 B1 员工快照、B2 工作区计划接线；保留其串行 reconciliation 及权限检查。
4. 提取 conversations 的发送/幂等与 snapshot/detail 投影；列表摘要、活动状态、最后真实消息时间继续一次查询返回。
5. 把预算、依赖、候选排序、失败恢复等适合纯函数的规则逐项移出大循环。每项先复用既有测试，不把全部状态机一次改写。

不要求建立新的公共 `ContextService`、EventBus、WorkflowEngine、Supervisor 或 AgentPool。模块可以使用少量组合函数和现有类；为各实体都建一套抽象接口会增加跨模块事务协调负担。

## 8. B3 验收

| 场景 | 保留结果 |
| --- | --- |
| 6/12 人收到同一用户消息 | 每人有首次独立判断机会；预算内可分别发言，不强制全员回复 |
| 慢判断与快候选 | 快候选可先发；始终单公开发言，慢结果不会覆盖新上下文 |
| all-pass / 部分失败 | 正常沉默无假消息；真实错误可见，不全轮假成功 |
| 旧群再问候 / 重试旧请求 | 旧历史保留为背景；当前 turnId 正确，无“以前答过所以本轮已答”的状态混淆 |
| @ / handoff / 依赖 | 有效成员校验、不抢答、接收方自主选择、环和上游失败可结束 |
| 新消息 / 停止 / 撤权 | 用户消息优先，当前/排队工作可停，迟到事件和审批不能复活执行 |
| 协议修复 / 工具多步 | 额外修复有预算，usage 累计不重复，工具说明不拼接成公开长回复 |
| 失败后恢复 | 只后续合法结果恢复对应失败；execution 失败不被 pass 掩盖 |
| 记忆失败/中断 | 公开回复保持完成，普通重试被拒绝，无新轮、消息或模型请求 |
| 重启 / 备份恢复 | 排序按明确时间/序号，历史完整，未结束任务中断且无重放 |
