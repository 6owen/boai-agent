## 1. 验证的问题

每次比较回答三个问题：任务是否得到可检查且符合要求的成果；用户需要补充和返工多少次；多人协作相对单人获得的质量收益是否值得额外耗时和用量。

不以运行完成、全员发言、回复长度或调用数量证明成果质量。成功与失败样本都计入端到端统计。

## 2. 复用已有体系

[第 6 组评估方案](../6.Cumora协作重构/09-多Agent测试体系与评估集方案.md)已包含版本化回归/开发/冻结留出、共享预算、完整产物证据、离线评分与报告。实施前核对最新数据，不重复建设评估执行器或第二份账本。

当前审阅发现的验收余项包括人工独立标签、评分器校准、正式留出及单员工/多员工比较。它们是待补证据，不能写成执行能力不存在；后续状态以该专题最新记录为准。

历史四角色任务停在草稿并耗尽预算，属于回归候选。先在当前版本和登记预算下复核，再定位判断、执行、修复、记忆或汇报的消耗；通过减少无效工作改进，不靠隐式追加/重置预算让失败变成成功。

## 3. 分开验证四个层次

| 层次 | 使用证据 | 证明什么 |
| --- | --- | --- |
| 模块/事务 | SQLite、真实文件与确定性断言 | 归属、版本、幂等、清理、预算及停止等不变量 |
| Electron 流程 | 隔离数据、实际 UI、重启及准确导航 | 用户能完成上传、预览、修订、采用与找回 |
| 真实模型 | 固定资料/任务/配置/预算与完整产物 | 真实语义、事实引用与端到端交付质量 |
| 人工评审/采用 | 明确版本、原材料及评审结论 | 成果符合实际需求，评分与用户认可可区分 |

某一层通过不能替代其他层；人工待评审也不能由模型自评自动转成通过。

## 4. 本组首个真实场景

输入两份文本资料，要求产出一份带来源的 Markdown 报告；事先固定事实核对项、格式要求、期望修改和预算。

1. 留存原材料及内容身份，核对员工实际获准读取的内容。
2. 保存报告实际字节、来源引用、发布身份和必要审核证据。
3. 用户对明确 V1 提出修改，检查 V2 变化是否符合要求，旧版是否保留。
4. 用户采用 V2，核对采用记录与所见内容一致。
5. 保留整个工作树、事件、调用账本、失败/中断与已知/未知用量。

没有报告、来源错误、审核与发布内容不同或预算耗尽停在草稿，均不得计完整交付通过。纯文本结果满足任务时无需强迫生成文件；本场景因明确要求报告文件，以实际文件作为验收条件。

## 5. 单人/多人对照

使用相同数据版本、原始任务、可用工具、材料、总预算和评审口径。分别固定单员工配置与团队配置，保留模型/提示词/代码版本。

探路使用开发集并保留失败；正式比较执行前登记样本、重复次数、预算、指标和门槛。冻结留出遵循原专题版本规则，不因本组功能失败改题或降低通过门槛。

| 指标 | 统计口径 |
| --- | --- |
| 合格交付率 | 全部已开始业务样本中达到预登记标准的数量；按场景分别报告 |
| 首次可用成果耗时 | 从受理到可检查合格成果，不以首 token 时间替代 |
| 补充/返工 | 明确区分必要用户输入、错误纠正与偏好修改 |
| 已知 token 与缺失覆盖 | 复用唯一调用回执；未知保持 unknown，不作零 |
| 有效交付用量 | 已开始样本全部消耗/合格目标数，保留失败消耗 |
| 人工判断 | 对确定版本评价事实、完整性、引用与实际可用性 |

未配置可信历史价格时不显示推算人民币成本。产品执行、连接检查/seed 与评审调用分账，再给实验总开销。

## 6. 人工校准与失败分析

沿用原专题要求补独立人工标签和同版评分器校准；重点审查模型/规则分歧、无依据扩写、来源错配、旧版审核继承和草稿冒充成品。

失败分类服务于修复：环境/供应商失败、材料解析或授权失败、协作无进展、预算消耗过高、产物/来源不合格、预览或采用版本错配。保留原始失败，不只统计成功结果。

修改评分标准时升级评分版本，对基线与候选用同版重新离线评分；不重新调用业务工具来填补缺失证据。

## 7. 产品中的用量呈现

首批复用任务详情展示目标/工作树已有预算的请求数、已知 token、缺失用量和历时，明确范围与完整性。统计读取不发模型请求，不创建 Work，不改变业务交付或采用状态。

工作、员工、自动化 occurrence 的聚合不得重复计费；清理与备份恢复遵循已有观测边界。用户采用率等新指标先有真实事件，再展示统计，不填示例数字冒充结果。
