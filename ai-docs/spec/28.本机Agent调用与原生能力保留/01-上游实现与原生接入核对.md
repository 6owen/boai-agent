## 2. Lody：通过ACP适配器调用实际Agent

- 桌面应用默认启动随包本地CLI，由CLI运行Agent适配器。ACP协商所支持的能力；图片、恢复、MCP、子Agent等能力按具体适配器和Agent区分。[官方快速开始](https://lody.ai/docs/quickstart/)、[能力矩阵](https://lody.ai/docs/acp-feature-support/)
- Codex入口要求`CODEX_PATH`并加载`acp-extension-codex`；Claude入口要求`CLAUDE_CODE_EXECUTABLE`，经Claude SDK与`acp-extension-claude`接到ACP。实际执行仍由对应Agent程序承担。[Codex入口](https://github.com/LodyAI/Lody/blob/05a60e018f79ec85d0a57523ada280b1cffe9c80/apps/cli/src/codex-acp-entry.ts)、[Claude入口](https://github.com/LodyAI/Lody/blob/05a60e018f79ec85d0a57523ada280b1cffe9c80/apps/cli/src/claude-acp-entry.ts)
- `acp-runner.ts`负责启动进程、传入工作目录和环境变量、协议初始化及取消；桌面执行宿主用租约处理执行端点归属。[运行器](https://github.com/LodyAI/Lody/blob/05a60e018f79ec85d0a57523ada280b1cffe9c80/apps/cli/src/agent/acp-runner.ts)、[桌面执行宿主](https://github.com/LodyAI/Lody/blob/05a60e018f79ec85d0a57523ada280b1cffe9c80/apps/electron/src/main/services/desktop-execution-host.ts)
- 对BOAI的参考：通过明确的协议适配层调用本机Agent，再将其交互和结果呈现到产品里。是否保留某项原生能力要逐项核对，不能仅凭“使用ACP”判定全部无损。

## 3. Raft：不同Agent使用各自的driver

- Codex driver启动实际`app-server`，处理`thread/start`、`thread/resume`、`turn/start`与运行中的`turn/steer`，并传入工作目录及产品附加能力。[Codex driver](https://github.com/botiverse/raft-source/blob/db5e399f017d584e49597e3a28757645d6807893/packages/daemon/src/drivers/codex.ts)
- Claude driver启动实际CLI，通过stream-json交互，传入补充指令及产品MCP；继续会话使用原生session，由Claude恢复历史。[Claude driver](https://github.com/botiverse/raft-source/blob/db5e399f017d584e49597e3a28757645d6807893/packages/daemon/src/drivers/claude.ts)
- `ChildProcessRuntimeSession`区分逐轮进程与持续流，处理初始输入、忙时追加、轮次完成和进程退出。输入已写入、Agent本轮完成、进程退出分别有含义。[RuntimeSession](https://github.com/botiverse/raft-source/blob/db5e399f017d584e49597e3a28757645d6807893/packages/daemon/src/drivers/runtimeSession.ts)
- 对BOAI的参考：保持原生执行循环，适配各Agent真实支持的交互。BOAI与Raft这一层都需要理解会话和事件协议，但无须自行实现Agent的推理、工具选择和执行循环。

## 4. Cindy：Codex走app-server，Claude走Agent SDK

- Codex适配器使用自己的`AppServerHost`管理实际`codex app-server`子进程及JSON-RPC传输；通过原生thread/turn进行启动、恢复和中断，并把通知与批准请求转成产品事件。渲染层消费统一事件，原生会话由适配层关联。[Codex适配器](https://github.com/makecindy/cindy/blob/fa14df2e2eb0f0c1bbd64c3fe6191c03be93dcd3/packages/maker-core/src/agents/codex/index.ts)
- Claude使用`@anthropic-ai/claude-agent-sdk`的`query`，本机分支明确传`pathToClaudeCodeExecutable`、cwd、输入队列、原生resume/sessionId、补充系统指令及工具批准回调。它调用实际Claude程序，并非把Claude能力重新实现一遍。[Claude适配器](https://github.com/makecindy/cindy/blob/fa14df2e2eb0f0c1bbd64c3fe6191c03be93dcd3/packages/maker-core/src/agents/claude-code/index.ts#L4407-L4566)
- 同一Claude适配器也存在产品模式差异：普通本机分支读取user/project/local设置；部分模式使用空`settingSources`、严格MCP配置或工具过滤。说明“可以调通Agent”与“任意模式完整保留个人原生配置”需要分开核实；本轮不把Cindy全部默认参数当作BOAI目标。
- 对BOAI的参考：统一的是产品交互和事件呈现，底层保留各Agent的协议；对模型、会话恢复、批准、子Agent等可选能力明确区分支持状态，按用户实际用例补接。

## 5. BOAI当前原生接入静态核对

### 5.1 Codex

- 生产`CodexEmployeeEngine`进入`runCodexConversation`，后者以`native: true`启动`CodexClient`。本机路径的启动参数是app-server及系统代理设置，不应用旧`codexStartupArgs`的禁用工具列表。[生产引擎](../../../packages/runtime/src/adapters/codex/engine.ts)、[会话驱动](../../../packages/runtime/src/adapters/codex/conversation.ts)、[客户端](../../../packages/runtime/src/adapters/codex/client.ts)
- 因此，搜索到旧policy中`computer_use=false`、关闭Skills/MCP等文本，不足以认定当前员工聊天被禁用。旧阶段/探测策略与生产路径必须按实际调用链区分。
- 复用登录时保留明确`codexHome`/本机配置来源；使用`thread/start`或`thread/resume`以及`turn/start`，产品工具以增量动态工具提供。原生文件/命令执行未在此路径被统一替换为BOAI工具。
- 本轮同时发现应纳入对照的宿主行为：程序字节变化要求重新测试；运行采用明确cwd；BOAI添加员工/协作指令；会话指纹变化可失去续用资格；未识别的交互请求显式报错。这些行为确实存在，但本次尚无证据表明它们导致用户所用能力损失。

### 5.2 Claude Code

- 生产路径使用实际CLI的双向stream-json，`--resume`/`--session-id`、追加指令文件及BOAI产品MCP；未使用旧policy的`--disable-slash-commands`/`--strict-mcp-config`组合。[生产会话](../../../packages/runtime/src/adapters/claude/conversation.ts)
- 原生进程模式不执行旧普通路径的8MiB累计输出限制；仍有单事件传输限制、初始化/收尾检查及明确取消。它们不等于BOAI重写了Claude执行循环。[进程传输](../../../packages/runtime/src/adapters/claude/process.ts)
- 需实测的差异包括：所选cwd及配置源、MCP合并、本机Skills/hooks/插件发现、子Agent活动、原生询问回传和最终结果呈现。收到能力目录或没有传禁用参数，都不等于每项已成功使用。

### 5.3 两条路径共享的边界

- [LaunchProfile](../../../packages/shared/src/domain/backends.ts)已有程序、来源、协议、版本/摘要、revision等身份；[原生会话](../../../packages/runtime/src/adapters/native-sessions.ts)保存员工与聊天到thread/session的映射。
- [权限派生](../../../packages/shared/src/domain/execution.ts)支持`useNativePermissions`返回本机权限配置；其余模式按员工明确选择派生。对照时必须核对实际选择，不能一边原生完全访问、一边BOAI只读，然后将差异归因于引擎。
- BOAI的“传声筒”意味着保留执行自主性，仍需传输、会话映射和可见事件解析。Lody/Raft同样维护这些接缝。原生执行能力与终端TUI交互分别登记：协议可用但BOAI缺少入口的，仍应记录为接入缺口；只由TUI提供的能力应明确其边界。
- 暂不能称“原生能力100%对等”，也未发现足以启动全面适配器重构的证据。待核对清单和分母见02，现有[原生对照runner](../../../scripts/evaluate-native-parity.mjs)继续复用。


## 6. 当前判断

- 三款上游都通过适配层驱动实际Agent。Lody主要经ACP，Raft使用各Agent的driver，Cindy分别使用app-server和Claude Agent SDK；这不是三种需要照搬的新产品概念。
- BOAI已经具有同类本机Agent接入，不需要因本次目标再造一套“管理电脑”架构。下一步应明确已有入口能控制哪些原生交互，以及哪些能力可能在适配或展示时损失。
- “兼容性”在此具体指程序启动参数、配置发现、协议消息和会话语义的衔接；不能直接推导为BOAI严重依赖某版本或必须大改。源码发现、原生功能差异和已复现缺陷分别记录。
- 当前仅静态核对；没有运行上游应用，也没有完成BOAI与原生CLI的全量对照。后续沿[02验收计划](02-本机Agent控制与验收计划.md)取证，再决定是否修改。
