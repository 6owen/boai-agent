## 实际用户流程

用户直接找员工、直接在群里交流、与 bobo 讨论后组织群，三条路径并存。需求讨论本身不创建工作、员工或群。明确要求执行组织动作时，bobo 检索真实通讯录候选，复用合适员工，仅补齐缺员，并根据授权范围执行：

| 范围 | 实际行为 |
| --- | --- |
| 只创建员工 | 发布独立员工；不拉群、不启动业务 |
| 只组织群 | 发布独立新群及 bobo 真实目标/分工公告；不启动业务 |
| 组织并处理事情 | 发布上述群及公告；提交后一次启动群内工作，成员交流、配合、交付 |

原 bobo Conversation 保持原身份、标题、消息和输入状态；创建群不转化、关闭或跳转原讨论。原聊天中显示实际组织结果与明确的进入群入口。结果未知保留原操作身份，先只读核对；已发布群尚未开始工作时，可显式开始原群工作。

员工始终是独立通讯录联系人，各有自己的身份、工作区和记忆，能继续私聊或加入其他群。群只组织成员；解散群保留员工及其他聊天。bobo 在受控创建群中以自己的身份参与；普通手动建群仍沿既有成员限制，不因此开放员工创建通讯录对象的权限。

## 代码与授权边界

- `src/runtime/modules/bobo-collaboration/` 管理有界真实候选、冻结配置版本、准备文件、原子发布、稳定回执、只读核对和实际退出后的清理。候选不含私人记忆或其他会话正文。
- `src/runtime/adapters/mastra/bobo-tools.ts` 仅向宿主授权的核心组织任务提供 `find_employees` 和 `organize_collaboration`。组织阶段没有浏览器、命令、文件发布或隐藏员工调用能力；原结构化团队入口保留 `create_team`。
- 原消息身份固定组织请求；同请求不同载荷拒绝，不按文字相似度去重。所有缺员、群、公告、来源证明、启动意图与回执一次事务公开；失败不发布半个团队。
- 公告是 bobo 的实际 Agent 消息，具有原组织 Run/模型调用/工具调用来源。它不是伪造用户消息，也不携带整个核心聊天或私人材料。材料不支持从核心组织请求隐式转交，新成员不自动获得材料授权。
- 核心组织工作与群内业务根分别保存，无跨会话父子关系，共用原累计预算与绝对期限。群中成员使用实际工作记录分工、结果版本依赖和定向接续；所有模型判断、执行步骤、修复、记忆及子工作按唯一调用回执计账，未知用量不计零。
- 启动意图仅消费一次，发布提交后才启动群。重启只核对既存对象和结果，不自动重放模型、文件或业务工具。恢复同一组织操作先核对来源、原工作、版本、文件归属/hash、记忆限制和原预算，再认领新执行权，保留原公告来源；不制造恢复成功聊天或重复员工。
- 原核心记录清理会结束其私有来源；已发布群和员工按各自生命周期保留，共享累计预算和最小去重事实不被重置。外部修改的受管文件不被覆盖或删除。

群里说“已安排”“已发布”仅是聊天文本。实际文件交付必须有真实原件、hash、注册 Artifact 身份与所属工作证据；普通聊天不能凭 Markdown 正文冒充文件创建、读取或发布。
