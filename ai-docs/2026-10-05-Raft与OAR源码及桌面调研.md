**2. 最值得借鉴：同一会话的聊天 / 任务 / 文件**

Raft 在频道和私聊中复用 `ChatPanel`：聊天看交流，任务看这段交流中形成的任务，文件看已经发送的附件。标签切换保留当前会话身份，并独立管理标签、线程和消息定位参数。子线程本身只提供聊天。

这适合 boai 的 IM 定位：进入员工私聊或群聊后，顶部并列三个视图。

| 视图 | 应回答的问题 | boai 可复用的事实 |
| --- | --- | --- |
| 聊天 | 员工说了什么，现在需要我回应什么？ | 原消息、附件、审批卡、问题卡、成果卡 |
| 任务 | 这段交流形成了哪些工作，谁在做，卡在哪里？ | 本会话 Work、负责人、父子关系、依赖、交付证据 |
| 文件 | 我给过什么材料，员工交付了什么，当前看的是哪一版？ | Material、Artifact、明确消息与版号/hash |

**三个视图要读同一组业务事实。** 从任务/文件回聊天时，定位原消息；选中文件继续在右侧预览；审批、采用和修改仍在员工原消息完成。切换标签不应丢失聊天草稿、阅读位置或文件选择。

Raft 的真实实现：[三视图挂载](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/message/ChatPanel.tsx#L1534)、[消息与任务关联](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/message/ChatPanel.tsx#L898)。

boai 当前：主区域始终挂 `ChatView`；标题栏/菜单和 `/files` 打开右侧“任务与产物”。右侧已显示真实 Work 与发布成果，**不是空壳，但也不是完整三视图**。输入材料散落在消息中，没有进入统一文件清单；单聊的直接入口还弱于群聊。

**3. 全局任务值得做，但应是原工作记录的跨会话总览**

Raft 用同一个 `TasksPanel` 服务会话内与全局任务页，复用看板/列表、任务卡、创建者/负责人筛选；全局额外按频道筛选。完成和关闭的列默认折叠。会话内可新建任务，全局页没有脱离聊天来源的新建按钮。点卡片用会话和消息 ID 打开原任务讨论。

本机全局页面实际显示“0 个频道任务”，有待办、进行中、待确认、完成、已关闭五组，以及看板/列表切换。这是亲自查看到的页面；未创建虚假任务来填满看板。

源码依据：[组件与范围](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/task/TasksPanel.tsx#L503)、[点任务回原消息](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/task/TasksPanel.tsx#L853)、[会话内创建入口](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/task/TasksPanel.tsx#L1033)。

**不能照搬的两点：**

- Raft 后端全局查询只纳入 `channel`、`joint` 且未归档的会话，私聊与线程不在其中；前端实时补丁还包含 `private`，与完整查询口径存在差异。boai 个人工作台更适合汇总本人当前获准的私聊、群聊与自动化工作，清楚标明来源。[后端查询](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/services/taskService.ts#L762)、[前端实时范围](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/store/taskStore.ts#L128)。
- Raft 的“待确认”不是强制人工验收关卡。普通状态机可从进行中直接到完成，具备频道写权限的 Agent 也能更新；一般完成操作不核验成果文件/hash，仅特定资源任务另核验资源回执。看板拖成完成不能被 boai 当作真实交付或本人采用。[状态与资源回执](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/services/taskService.ts#L2028)。

boai 已有 `WorkItem`，包含原会话/消息、员工、父子与依赖、预算、结果消息、成果 ID 和版本。建议默认按根工作聚合，展开真实子工作；每次模型调用或工具步骤不单列成用户任务。可以显示“等待开始、进行中、等待输入/依赖、已交付、异常/停止”等分组，具体文案应从现有状态映射，不新增一个随意拖动就覆盖执行事实的状态字段。

全局任务和当前“定时任务”各自有明确用途：前者看已经形成的工作，后者管理何时触发的计划及触发历史。一次自动化形成的真实 Work 可以出现在全局任务里，并回链对应计划和发生次数。

技术缺口：目前只有按会话的 `WorkRepository.view()`，内部还会读取集合再过滤。需要宿主提供有界、可筛选、可分页的 Work 查询；不能让前端依次拉所有会话完整详情来拼看板。成果证据失效、清理和权限变化，也要在全局查询/点击时一致处理。

依据：[Work 字段](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/shared/domain/work.ts:78)、[当前查询](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/runtime/modules/collaboration/work-repository.ts:118)、[元信息即时核验](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/runtime/service.ts:765)、[现有定时任务页](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/renderer/pages/schedules/index.tsx:54)。

原规约禁止把审批/补充/采用迁到独立待处理中心。**用于浏览与导航的全局任务总览可以兼容这个边界**；若看板直接办理上述动作，则会和当前 IM 合同冲突。这是本次建议，尚未实施。

**4. 文件页应补“汇总、筛选、回原消息”，现有预览可以继续复用**

Raft 的聊天文件聚合已发送附件，包含子线程附件，保存上传者、时间、消息/频道/线程身份，以 50 项分页。预览、下载、回原消息是不同操作。Agent 工作区另有文件树，未把私有工作文件等同于发到聊天的成果。[附件查询](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/routes/channels.ts#L2166)、[预览与回源](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/message/ChannelFilesPanel.tsx#L310)、[员工工作区](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/agent/AgentWorkspace.tsx#L46)。

boai 的文件页建议将“发送的材料”和“员工交付”纳入同一可筛选视图，同时保留各自身份。每行清楚展示文件名、发送/交付员工、时间、类型、版号与采用标记。逻辑成果可折叠版本，默认版本规则要明确；同名独立文件不能被误当修订链。

点击文件复用现有 Markdown / Shiki 右侧预览；来源按钮回到明确消息。外部执行目录里尚未发布的文件、员工系统文件与记忆文件继续在各自管理入口。Raft 的 HTML 渲染预览不应带入 boai；boai 已确定 HTML/SVG 只看源码。

**5. Agent 配置：让通讯录先呈现一个员工，再展开执行配置**

Raft 的资料页把身份、职责、所在电脑、运行时、模型/推理强度、Skills 等放在员工名下；活动、聊天、提醒、工作区、Apps、MCP 是不同维度。本机的运行配置表单确实有运行时、模型扫描、推理强度和快速模式，查看后已取消，没有保存。

boai 通讯录其实已有资料与编辑分离，以及“配置 / 系统文件 / 工作区 / 记忆”四标签；能力可用性也有真实核验，并不是全未实现。问题是“这个员工能做什么、现在在做什么、有哪些能力实际可用”分散在多个页面。

建议先整理员工首页：头像/姓名/职责、当前工作、实际可用能力、发消息入口；编辑模型、系统文件和诊断作为后续入口。员工任务摘要复用全局 Work 查询按员工筛选，不另建一份员工任务库。无需照搬远程电脑、多服务器和全部七个标签；没有接入的 MCP 等也不先放空面板。

依据：[Raft 员工标签与权限](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/web/src/components/agent/AgentDetailPanel.tsx#L218)、[boai 资料与编辑](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/renderer/pages/contacts/index.tsx:57)、[现有四标签与能力状态](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/renderer/components/employee/index.tsx:49)、[真实版本化保存](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/renderer/components/employee/editors.tsx:67)。

**6. 还有哪些细节值得学**

- 精确回源：任务卡、文件行、消息使用稳定身份互相定位，减少“看到结果却不知道员工在哪儿交付”的割裂。
- 局部与全局共用组件：会话任务是限定范围，全局任务是扩大范围，排序、状态解释与文件入口保持一致。
- 任务意图可显式表达：本机发送框有“作为任务”，普通消息也能显式转换；boai 可以研究提供用户明确指定工作意图的入口，复用原稳定请求身份。它应保持可选，不能让所有普通聊天都强迫用户判断任务类型。
- 任务讨论保留原消息：Raft 线程能把一个话题的往返集中起来。boai 可先补准确回源与上下文，不必立即增加第二个聊天输入框或完整 Slack 式线程体系。
- 资料页把发现与可用分开：知道某个 Skill/MCP 配置存在、确认运行时能读取、真正可以调用，是不同事实。

Raft 任务现已独立存入 `tasks` 表并关联原消息，消息上的旧 task 字段是废弃快照。新任务和主持消息在事务内创建，显式转换普通消息时也保持消息内容。这再次说明可借鉴的是“同一事实、多视图、消息锚点”，不是从界面标签推断它没有独立任务模型。[任务表](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/db/schema.ts#L3412)、[创建事务](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/services/taskService.ts#L1593)、[消息转换](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/server/src/services/taskService.ts#L2184)。

**7. OAR 的价值与接入边界**

OAR 统一的是外部 Agent 运行时，不是员工、群聊或业务任务管理。其独立查询接口能报告安装状态、模型、额度、Skills、MCP 与工具；记录流保留 request / response / native frame，派生界面事件。

| 借鉴点 | boai 可得到的改善 | 必须保留的界限 |
| --- | --- | --- |
| 能力查询的明确结果 | 配置页区分可用、需要登录、不支持、暂时读不到 | 发现配置不能冒充执行验证，未知额度不显示 0 |
| 原始记录与界面事件分层 | ACP 外部任务更好地展示实时文本、工具活动与失败原因 | 脱敏、有界保留；Work 仍是业务权威 |
| accepted / rejected / unknown | 解释任务是否受理、控制操作是否被接受 | accepted 不等于执行成功，turn 结束不等于文件交付 |
| 状态由已发生事件推导 | 能区分等待输入、工具执行、没有新活动 | “疑似停滞”只是观察结论，不把它当作已失败事实 |

依据：[记录合同](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/records.ts#L23)、[受理语义](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/records.ts#L244)、[运行时查询](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/runtime.ts#L20)、[能力清单范围](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/inventory.ts#L19)、[状态观察](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/observe/agent-status.ts#L5)。

不能直接换入的原因是实际合同不一致：OAR 默认自动批准；Codex 默认 `danger-full-access` 和 `approvalPolicy: never`，ACP 优先 allow_always。boai 现有原聊天审批不能靠一个表面 Adapter 自然保留下来。[Session 合同](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/session.ts#L88)、[Codex 启动策略](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/runtimes/codex/open.ts#L34)、[ACP 自动批准](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/shared/acp/client-app.ts#L35)。

OAR 的 resume 恢复 native 会话，不代表恢复 boai 原工作/预算；序号会重开。上游自己的崩溃恢复记录显示，某些 Codex 队列会在恢复后自动开始下一轮，必须与 boai 重启只核对的约束逐项适配。它的 Task 指后台 shell/子 Agent/tool 活动，不是带成果与采用身份的业务 Work。[恢复实测](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/docs/runtimes/crash-resume.md#L39)、[Task 合同](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/packages/oar/src/contracts/tasks.ts#L1)。

Raft 当前生产接入 OAR 主要用于账户用量，主执行仍有自身 drivers。boai 可先学习 OAR 的合同并改善现有 ACP 适配器，后续再单独评估是否引入依赖；不应为三个会话标签顺手替换整个执行框架。OAR 当前要求 Node ≥24，也需要核对本项目桌面运行环境。[Raft 用量读取](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/daemon/src/runtimeAccountUsage/collector.ts#L14)、[自有执行 Session](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/packages/daemon/src/drivers/runtimeSession.ts#L13)、[boai ACP](/Users/wangwenbo/Desktop/demo/boai/boai-agent/src/runtime/adapters/acp/client.ts:16)。

**8. 建议优先级与验收方向（未实施）**

| 顺序 | 建议范围 | 应交付的可审阅效果 |
| --- | --- | --- |
| 1 | 会话“聊天 / 任务 / 文件”三视图；补材料与成果统一列表 | 发材料→形成工作→文件交付→主视图找到文件→右侧预览→回原消息修改/采用；切换不丢草稿与位置 |
| 2 | 全局任务总览；同一 Work 卡片与有界查询 | 跨私聊/群聊查看真实工作，按员工/来源/状态筛选，展开子工作并精确回源；失效成果不能继续显示可靠交付 |
| 3 | 通讯录员工首页与配置整理 | 一眼看懂职责、当前工作、真实能力状态；编辑仍走现有版本核对 |
| 4 | 外部运行时能力与活动表达 | ACP 实时过程、明确受理/失败/未知、实际退出；保留原审批与预算边界 |
| 单独评估 | 多运行时/OAR 原生恢复 | 按后端验证权限、记录、额度、崩溃与重复执行；不绑在 UI 调整里 |

不建议现在照搬的还有：完整多人服务器/远程电脑管理架构、任意拖动完成、把原生运行日志直接当业务持久化、展示尚不可用的配置选项。Raft 的员工详情单文件很大，也不适合直接作为组件拆分模板。

**9. 源码复用范围**

Raft 使用 FSL-1.1-ALv2，许可文本包含竞争性商业用途限制，未来转 Apache 有对应等待条件；不能当作当前 MIT/Apache 项目直接搬代码。OAR 当前为 Apache-2.0。这里据原文记录许可差异，建议先借鉴产品行为并独立实现，实际代码复用范围另行核对。[Raft LICENSE](https://github.com/botiverse/raft-source/blob/05f7d8fd77d2535f993d5d90b85118438bc18216/LICENSE)、[OAR LICENSE](https://github.com/botiverse/oar/blob/9c1bd92330e18af2da3a6cca8cdb913ba6fc477f/LICENSE)。

**本轮结论：boai 下一步最有价值的是把现有工作与文件能力变成用户能自然找到、理解、回到聊天处理的主视图。源码和桌面都支持这个方向，但 Raft 的任务完成语义与 OAR 的默认执行权限不能直接继承。**
