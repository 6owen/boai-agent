# 团队创建后的功能调研

调研日期：2026-10-01。问题：一句话创建成员和群聊之后，什么功能最能让团队持续产生价值？

同日 BYOK 补充：用户明确强调模型与工具由用户自行配置。本文的“网页研究”是能力目标，不表示 BoAI 代付搜索服务或把联网包含在模型 Key 中。按可扩展的数字员工产品方向，建议把下一步接入功能收敛为 **MCP 客户端与员工工具绑定**，以一个用户自配的搜索/读取 MCP 服务验证完整链路；直接接搜索 API 仍是合法的 BYOK 实现方式，MCP 不是联网的技术必要条件。配置分层、其他 BYOK 产品和具体首批范围见[BYOK 与 MCP 工具接入调研](./2026-10-01-BYOK与MCP工具接入调研.md)。

## 1. 推荐方向

建议下一步先做**真实网页研究能力，以及按员工授权的工具连接**：新团队的研究成员可以搜索/读取网页，把实际取得的材料与引用交付给同伴。首批围绕只读 search/read 和来源证据落地，不以工具目录规模为目标。

其次补充**长期目标与主成果工作台**：现有群内任务与产物已有目标、负责人和成果，需要增加的是一个群当前明确事项、获准资料与本人采用版本的关联聚合。再做**保存工作方式**：把一次已完成且检查过的工作保存为可复用流程，下次替换输入继续做。这个排序是结合 BoAI 本地缺口和产品取舍的推论，GitHub 功能声明只提供参考，不是 GitHub 榜单、市场唯一性或商业成功的证明。

示例：创建“科技写作组”以后，用户设定本期目标，提供资料，团队研究、起草、审核，用户选择采用版本；下周打开同一工作台换一批资料，用保存的工作方式再完成一次。

## 2. 调研方法与证据边界

- 只使用官方 GitHub 仓库、官方文档和公开源码；未安装或运行这些产品，未调用付费模型。
- README 说明项目宣称的功能；官方操作指南增加交互和配置依据；源码说明仓库存在相关实现路径，不能据此声称生产稳定性或本机可用性。
- 官方站点文档可能比某个发布包或自部署版本更新；需要登录、第三方授权、云服务、实验开关的能力另行标注。
- 对路线图条目不计为已交付能力；不根据 Star 数给功能优先级。
- 下列源码链接固定到本次公开 GitHub 默认分支的提交，便于以后复查；产品文档链接仍会随官方更新。

## 3. 五个相近项目

### 3.1 Paperclip：把工作、项目、成果和使用规则联系起来

官方仓库将工作关联到项目与目标，并把讨论、文件和运行记录附在任务上。参考价值是让用户能够沿成果追到原目标和工作，而不只看聊天记录。[官方 README](https://github.com/paperclipai/paperclip#features)

它的成果指南描述了对具体文字片段发表评论、回复、解决和重新打开讨论；文档变化后，评论锚点可能标记过期或成为孤立讨论。[成果与评论指南](https://docs.paperclip.ing/guides/day-to-day/artifacts/#commenting-on-documents)。本次抽查了包含评论线程、评论和锚点快照的[注释服务源码](https://github.com/paperclipai/paperclip/blob/467125fafb47a8520856504fecc48d6e32055db1/server/src/services/document-annotations.ts)，没有运行它的测试。

Team Catalog 的团队包含成员、项目、任务和技能，支持先查看安装内容，再选择安装；部分可选团队要取得外部技能。它说明团队复用可以携带工作配置。[Team Catalog 指南](https://docs.paperclip.ing/guides/org/team-catalog/)

连接器指南区分凭证、人员归属、可使用的 Agent 和具体动作权限；也说明目录列出某服务不保证登录方式在当前实例可用。[连接器指南](https://docs.paperclip.ing/connectors/)

**可借鉴的轻量下一步**：群内目标与成果总览、针对固定版本的片段反馈、保存角色分工和步骤。公司组织架构、多用户治理和云沙箱属于更大产品方向，当前不作为必要前置。

### 3.2 LobeHub：Agent 群与共享内容空间

官方 README 描述 Agent Groups、共同创作的 Pages、Project 和 Workspace；同时列出可编辑结构化记忆与工具/MCP 插件。[协作功能说明](https://github.com/lobehub/lobehub#collaborate-scale-new-forms-of-collaboration-networks)

源码的项目详情会读取成员、工作、任务、知识库和完成审核信息，存在添加/移除项目知识库的操作。[项目服务路由](https://github.com/lobehub/lobehub/blob/14dfc07b14eee1984e52c195df9319636d6b167b/apps/server/src/routers/lambda/project.ts#L81)。仓库还包含 Page 内容编辑的 BDD 场景。[Page 编辑场景](https://github.com/lobehub/lobehub/blob/14dfc07b14eee1984e52c195df9319636d6b167b/e2e/src/features/page/editor-content.feature)

**可借鉴的轻量下一步**：群详情展示一个明确的当前目标、关联资料和当前成果，成员围绕它继续工作。README 宣称的持续学习不等于已证明能够提高任务质量；本次没有验证所有部署形态的 Pages、Project 或 Workspace 可用程度。

### 3.3 Eigent：从团队聊天延伸到桌面实际工作

官方 README 描述单 Agent 与多 Agent Workforce，列出 MCP、技能、浏览器和终端工具；同时明确区分快速云连接启动和独立本地部署。[官方能力与启动方式](https://github.com/eigent-ai/eigent#-key-features---open-source-cowork)

仓库存在[浏览器工具实现](https://github.com/eigent-ai/eigent/blob/f723da6b187053f0bdcfcce0bfe56ba1ee72cab7/backend/app/agent/toolkit/hybrid_browser_toolkit.py)和[使用已配置 MCP 的 Agent 工厂](https://github.com/eigent-ai/eigent/blob/f723da6b187053f0bdcfcce0bfe56ba1ee72cab7/backend/app/agent/factory/mcp.py#L32)，说明有实际接入路径；不代表任意网站、任意 MCP 或本地模型都能顺利工作。

**可借鉴的轻量下一步**：先围绕写作/研究提供网页读取、证据保存，再选一个用户实际需要的数据服务。需要特别注意，它的 README 仍把固定工作流和 Workforce 多轮对话支持放在 Roadmap；本次不把这些路线图条目作为成熟产品证据。[当前路线图](https://github.com/eigent-ai/eigent#️-roadmap---open-source-cowork)

### 3.4 Sim：聊天、文件、表格和流程共享资源

官方仓库和文档把聊天、流程、表格、知识库、文件与运行日志放在同一工作空间。[仓库能力说明](https://github.com/simstudioai/sim#capabilities)、[工作空间结构](https://docs.sim.ai/introduction#the-anatomy-of-a-workspace)

表格文档说明可以通过聊天创建表格、查询/更新行和导出 CSV，再供流程使用。[Tables 文档](https://docs.sim.ai/chat/tables)。本次读取了实际带 workspace 上下文的[更新行工具](https://github.com/simstudioai/sim/blob/2a7f85d7d5fc2b16f395c4d4af3609d1f4e83977/apps/sim/tools/table/update_row.ts#L8)。文件指南描述工作空间文件编辑；上传附件在聊天可用与正式保存到工作空间 Files 是不同位置。[文件与文档指南](https://docs.sim.ai/chat/files)

MCP 指南包括连接测试、工具发现、工具选择和变更后的受影响流程提示，并明确当前接入使用 streamable-http。[MCP 工具指南](https://docs.sim.ai/agents/mcp)。日志指南记录每次流程的触发来源、执行身份、步骤输入输出和错误；这些记录帮助定位失败，不能当用户已经采用成果。[运行日志指南](https://docs.sim.ai/logs-debugging)

**可借鉴的轻量下一步**：团队共用一张内容日历或对比表；在聊天旁打开相关成果；展示一项具体工作实际读了哪些资料。全功能流程画布、API 部署与多种资源系统应分开评估。

**可用性限制**：当前 README 明确自部署的 Chat 是 Sim 管理服务，需要 Chat API key；不能将“代码开源/自部署”解读为所有 Chat 能力完全离线。[Chat API Keys 说明](https://github.com/simstudioai/sim#chat-api-keys)

### 3.5 CrewAI：角色自主协作与确定步骤分离

CrewAI 是 Python 框架。官方仓库区分角色协作的 Crews 和有状态、路由与条件分支的 Flows，适合作为设计参考，不能当成 BoAI 的现成用户界面。[Crews 与 Flows 说明](https://github.com/crewAIInc/crewAI#understanding-flows-and-crews)

任务文档定义输入占位符、预期输出、明确上下文依赖、结构化结果和人工输入，并提供函数及模型判断的结果检查。[Tasks 文档](https://docs.crewai.com/en/concepts/tasks)。源码也保留 expected_output、context、human_input 和 guardrail 字段。[Task 实现](https://github.com/crewAIInc/crewAI/blob/fbcf2de39d3f8252500b74a0751b92c5774c751b/lib/crewai/src/crewai/task.py#L153)

**可借鉴的轻量下一步**：保存“收集材料→写稿→审核→用户采用”的工作方式，固定必要输入、成员职责、完成条件和结果格式，把执行控制交给程序。不能直接照搬框架的自动重试来重放 BoAI 已经执行过或结果未知的工具。

**质量限制**：结果格式验证或模型评分通过，不证明事实正确、工具动作安全或用户认为质量合格；应保留实际证据和人工意见。

## 4. 候选功能如何落到 BoAI

本地核对确认：群详情已存在真实任务与全部成果展示，材料、成果版号/采用和全局待处理也已有实现；新建成员没有自动取得命令、技能和知识授权，一等任务工具尚无网页 search/read、MCP 或浏览器。因此首选解决“团队有角色但拿不到新资料”的问题；工作台和工作方式是后续聚合与复用增量。

### 4.1 团队工作台的范围

初期一个群可以有一个当前明确事项：例如“10 月第一期科技文章”，包含目标、获准资料、关联工作及主要成果。它补的是长期目标与主成果关系，已有 Work 目标、负责人、依赖、停止树和成果列表继续复用。将来存在多事项需求，再评估项目实体与独立排期。

- 关联现有工作与成果，保留原身份和来源，不复制一份“看起来完成”的状态。
- 资料授权仍以实际成员和来源为准；放入工作台不自动授权给所有现有/新成员。
- 群背景解释这个群做什么；当前目标是本次明确事项；二者有不同用途。
- 选择已有群/员工承接事情，保留独立身份和 workspace；工作台不是把所有员工目录合并。
- 关联普通对话不凭空建立 Work；真正任务继续沿现有受理、预算、取消和交付协议。
- 打开工作台、选定关注目标或主要成果只保存关联，不调用模型、自动恢复工作或替用户采用；需要处理的事项仍导航至原问题、审批、工作或固定成果版。

可演示的验收：用户创建写作团队，开始一期文章，添加资料并获得成果；再次打开群时，能定位当前事项与本人采用版本，不必翻完整聊天记录。

### 4.2 保存工作方式的范围

第一版从已有成功任务保存，而不是提供复杂流程画布。用户能查看、修改和命名输入要求、角色分工、阶段结果和最终检查条件。

- 保存步骤与要求，不保存可重放的旧工具调用。
- 新运行有新工作身份，重新核对材料、权限、模型与工具可用性，并建立本次预算。
- 默认引用现有团队身份；复制团队是另一个明确操作，不能每次运行都创建员工。
- 模型负责起草工作方式和开放判断；程序负责受理、次序、条件、回执与状态。
- “已保存模板”与“模板实际跑成功”分别记录；保存不等于执行可用。

可演示的验收：用户把一期科技文章保存为“每周科技稿”，下次换一批资料后运行；系统留下本次成果和检查记录，不重复上次的命令、通知或外部发布动作。

### 4.3 外部资料连接的范围

第一优先从科技写作/研究的只读网页获取开始：search 找候选来源，read 读取具体页面，保存可检查来源和实际摘要；失败、不可读取和空结果如实返回。开发团队的 GitHub Issue、资料研究的 Notion 页面作为后续具体连接需求。不要先以“接入 100 个工具”为验收目标。

首批可以直接接一组搜索/读取服务，MCP 和交互浏览器不是必要前置。保留 URL、获取时间、实际读取片段及内容身份；可变化的 URL 不能代替当时使用的证据。网页来源保存与引用需要明确的新合同，不能把当前仅支持 TXT/MD 的本地材料入口写成已支持网页。实施沿[第 8 组工具接通](./spec/8.Agent-IM产品完善/04-工具接通与能力检查.md)与现有材料/成果来源规则补齐，先核对该专题历史文案和当前实现，不恢复旧团队草稿界面。

- 已安装技能、已配置模型、已保存连接分别核对；这些状态不能互相替代。
- 先完成一次受控的实际读取，展示来源、时间和结果；连接测试或发现工具列表不计作工作成功。
- 外部写入/发布分开定义权限和未知回执处理；结果未知时先核对，不能自动重放。
- 外部内容进入记忆和成果后仍保留来源与授权链；读取网页不赋予任意浏览器会话控制。

可演示的验收：研究员读取用户指定来源，输出含可检查引用的摘要，写作者使用摘要完成文章；失去授权后后续调用不能继续读取旧快照。

首个完整亮点演示：一句话创建写作团队 → 用户请求调研一个近期主题 → 研究员实际搜索并读取来源 → 按需要委派写作/核对 → 发布带引用的文章 → 用户预览、针对固定版本修订并采用。明确区分真实资料获取、来源正确、成果质量与用户采用，不以多名员工轮流发言作为完成标准。

## 5. 当前不应直接推导的结论

- 多个项目都有群协作、资料或流程，并不证明这些功能在所有环境稳定运行。
- Project/Workspace 在不同产品里可能是组织权限、运行目录或内容容器，不能只因为同名就复制数据结构。
- 外部工具数量和自动运行时间并不证明业务交付质量；必须观察实际结果和人类判断。
- 员工记忆已经接入不代表应再建设一套自动学习系统；更直接的增量是让用户能把具体反馈沉淀到获准工作方式。
- BoAI 当前已经撤销专用狼人杀规则实现；本调研不把游戏主持、游戏状态机或游戏面板作为下一阶段要求。
